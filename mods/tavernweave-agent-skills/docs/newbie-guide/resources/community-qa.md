# TavernWeave 社群常見問題 Q&A

這份問答收的是 TW 討論帖裡大家反覆問的問題，意思相近的合成了一題。答案按當前 **TavernWeaveX無限月讀 2.3.0 正式版**和 23 個 Skill 的實際分工整理；完整發行包與校驗檔案見 [v2.3.0 正式釋出頁](https://github.com/LiarMTTT/TavernWeave/releases/tag/v2.3.0)。上一版 [v2.2.0 釋出頁](https://github.com/LiarMTTT/TavernWeave/releases/tag/v2.2.0)也是 23 個 Skill；更早的 [v1.9.1 釋出頁](https://github.com/LiarMTTT/TavernWeave/releases/tag/v1.9.1)保留歷史包，含 22 個 Skill。使用哪個版本，就按那個版本的清單核對。

不同客戶端、酒館版本和模型服務，表現可能不一樣。凡是“裝上後到底能不能用”“導進酒館能不能跑”這類問題，最後都要在你自己的環境裡實際試一次。

## 怎麼讀這份問答

問題按四個階段分組：新人／萌新、入門、熟練、老手。分組只是告訴你這題大概什麼時候會碰到，不是給人定級，跳著看也沒關係。

先把幾個常見詞對一下：

| 原詞 | 大白話 |
| --- | --- |
| TW | TavernWeave，就是本倉庫這套 Skill |
| ST／酒館 | SillyTavern，玩角色卡用的軟體 |
| Agent | 能讀你的檔案、跑命令、幫你幹活的 AI 助手 |
| 客戶端（宿主） | Agent 工作的軟體，比如 Codex、Claude Code |
| Skill | 給 Agent 看的分工說明書，碰到對應任務時讀取 |
| Host Front Door | 客戶端每次開任務時讀取的 TW 入口規則，可選，推薦裝 |
| Library | TW 隨包帶的資料庫，裡面有開發指南、設計和動效參考，按需查 |
| 世界書 | 滿足關鍵詞或條件時，自動塞進提示詞的設定條目 |
| 變數／MVU | 變數是會隨劇情變的資料，比如好感、日期、地點；MVU 是一套常用的變數更新方案，讓模型在回覆裡順帶改變數 |
| Zod／schema | 規定變數有哪些欄位、每個欄位是什麼型別的“格式表” |
| EJS | 一種提示詞模板寫法，能按變數決定哪段內容發給模型 |
| 正則 | 按規則找文字並替換，常用來改顯示效果，或把介面掛到訊息裡 |
| 酒館助手 | Tavern Helper（JS-Slash-Runner），讓卡能跑指令碼、顯示網頁介面的 ST 擴充套件 |
| 樓層 | 聊天記錄裡的一條訊息 |
| iframe | 嵌在訊息裡的小網頁框，狀態列常裝在裡面 |
| 原始碼／成品 | 原始碼是拆開、方便修改的專案檔案；成品是打包出來、能直接匯入酒館的 JSON 或 PNG |
| 實機測試 | 把成品導進真正的酒館，照著玩一遍 |
| 續接記錄 | 寫著目標、進度和下一步的交接筆記，比如 `NEXT.md`，換會話時靠它接著做 |
| token | 模型計算文字量的單位，用得越多越貴，也越占上下文 |

## 一、新人／萌新：先弄明白、裝好、跑通第一件事

### Q01. TW 是軟體、外掛，還是一張角色卡？

**A：** 都不是。TW 是一套裝進 Agent 客戶端的 Skill，也就是給 AI 助手看的工作說明書。它不裝進酒館，也不能當角色卡匯入。

裝好以後，Agent 會照著它的方法幫你規劃、製作、檢查角色卡、網頁和小工具。做出來的東西，再放到酒館或對應的軟體裡用。

### Q02. ChatGPT、Codex、Claude Code、Agent 和 TW 是什麼關係？不會寫程式碼能用嗎？

**A：** 可以這樣理解：Agent 是幹活的 AI 助手；Codex、Claude Code 是它幹活的地方；TW 是交給它的分工說明和參考資料。普通 ChatGPT 聊天視窗預設沒裝 TW，一般也讀寫不了你電腦上的專案檔案，所以不能和這種工作環境混為一談。

不會寫程式碼也能開始。你要講清楚四件事：想做什麼、手上有什麼材料、哪些東西不能動、做到什麼程度算完成。其餘的交給 Agent，同時要求它把關鍵選擇講給你聽，最後交一個你能親手試的版本。

### Q03. 我到底要下載或安裝哪些東西？STDB、AFV 要另裝嗎？

**A：** 只用 TW 自帶的資料的話，不用另裝。你要準備的是：

1. **TW 的完整 Skill 清單**：當前 2.3.0 正式版有 23 個；歷史 1.9.1 原包有 22 個。按實際選用版本安裝，不把兩份清單混用。
2. **Host Front Door**：可選，推薦裝。
3. **酒館（ST）本體**，以及你的作品自己需要的擴充套件或依賴，按作品需要單獨準備。

STDB 的正式指南和篩選過的 AFV 設計、動效參考，已經打包進 TW 自帶的 Library，按需讀取，不用再另裝完整的 STDB 或 AFV 倉庫。

### Q04. 安裝時給 Agent 什麼指令？工作目錄選哪裡？

**A：** 安裝指令直接用 [README 的安裝指令](https://github.com/LiarMTTT/TavernWeave/blob/main/README.md#%E5%AE%89%E8%A3%85%E4%B8%8E%E6%9B%B4%E6%96%B0)，要求 Agent 按所選版本 `skills/` 的完整清單安裝。當前 2.3.0 正式版應核對 `23/23`；歷史 1.9.1 原包應核對 `22/22`。

這裡有兩個容易混的資料夾：

- **安裝位置**：客戶端實際會去找 Skill 的那個 `skills` 目錄。TW 的原始碼資料夾不算，拿原始碼資料夾來核對“裝好了沒有”，等於查錯了地方。
- **工作目錄**：做角色卡時，選這張卡的專案根目錄。開工前先讓 Agent 讀專案說明、原始檔和續接記錄。

### Q05. 可以在手機、網頁端或 DeepSeek Harness 上直接用 TW 嗎？

**A：** 要看那個環境能不能做到三件事：找到並讀取 Skill、讀寫需要的檔案、呼叫工具。

倉庫正式支援的是 Codex 和 Claude Code。DeepSeek Harness 從 2.1.0 起提供獨立的 **TavernWeave X DSH** 外掛包：在 DSH 外掛頁安裝 bundle、啟用並在新任務裡選擇 `TavernWeave X DSH` preset 後，包內 23 個 Skill 與 Host Front Door 才生效。能否使用仍取決於你的 DSH 版本（當前實測 `0.2.1-rc.2`）和外掛頁安裝結果；手機或網頁能開啟一個 AI 對話，不代表它已經載入了 TW。先確認上面三項能力，再實際叫它用一次 Skill 試試。

### Q06. 從哪裡開始學？必須先學完所有術語和指南嗎？

**A：** 不用先學完。從 [新人教程](https://liarmttt.github.io/TavernWeave/) 和一個很小的目標開始就行，比如做一張純文字卡，或者修一個明確的顯示問題。

先想清楚三件事：想得到什麼、手裡有什麼、做好了怎麼試。Agent 會按問題去讀需要的資料。碰到看不懂的詞，直接問它：“用大白話說說，這個詞在這次任務裡是幹嘛的？”

### Q07. 顯示安裝成功了，客戶端就一定會用嗎？

**A：** 不一定，要分兩步確認。

1. **檔案齊不齊**：對實際安裝目錄執行倉庫自帶的核驗器。若使用 2.3.0 正式版，預期是 `INSTALLATION VERIFIED: 23/23`；若使用歷史 1.9.1 原包，預期是 `INSTALLATION VERIFIED: 22/22`。這隻說明對應版本的 Skill 檔案齊全。
2. **客戶端用不用**：新建一個任務或重啟客戶端，讓 Agent 實際呼叫一個 Skill，並說出它讀了哪個入口、做了什麼。

做到第二步，才算客戶端真的找到並用上了。全域性規則檔案存在，也只算第一步。

### Q08. 第一次向 TW 提需求，怎樣說最省事？

**A：** 一句目標，再加三樣資訊：手上有什麼材料、哪些不能改、第一版做到什麼程度就算成。比如：

> 我想做一張現代懸疑純文字卡；只有這份人物設定；保留主角關係；先做一個能匯入 ST 並聊三輪的版本。

哪一項還沒想好，就直接寫“你推薦”。Agent 要說出推薦的理由，創作方向還是由你來定。

### Q09. 模型、API 和費用由 TW 提供嗎？新手選什麼？

**A：** 不提供。TW 不送模型額度，也不帶 API Key。

選模型和服務時，先確認你的客戶端配上它以後，能讀檔案、能呼叫工具、能撐住比較長的任務；然後拿一個小任務試，比比花費、速度和效果。價格和能力經常變，以服務方當時的頁面和你自己試出來的結果為準。

API Key 不要貼進聊天，也不要寫進角色卡檔案。

### Q10. TW 能解除模型拒答、平臺限制或自動處理所有成人內容嗎？

**A：** 不能。TW 管的是創作和製作流程，改不了模型提供方和平臺的規則。

內容被拒時，可以把允許處理的部分單獨拿出來說，比如角色設定、卡的結構、介面或技術問題。別把“裝了 TW”當成繞過限制的辦法。

### Q11. “新人、入門、熟練、老手”會改變功能或作品質量嗎？Soul 又是什麼？

**A：** 不會。四個擋位隻影響講得有多細、一次走多大一步，功能和質量要求完全一樣。擋位由你自己選，Agent 不能看你表現如何就自作主張換擋。

Soul 是當前任務裡可以開啟的一種教學或審查語氣。它不會讓 Agent 多出改檔案、釋出之類的許可權，也不能代替事實核對。退出 Soul 以後，大白話和你選好的擋位照常有效。

## 二、入門：把第一個作品做出來

### Q12. 做第一張角色卡，合理順序是什麼？

**A：** 大致五步：

1. 定下這張卡怎麼玩、有哪些人物，第一版做到哪裡就算能玩；
2. 選能做到這些的最簡單結構；
3. 寫開場和必要的設定，準備好要用的依賴；
4. 匯出一張試用卡，導進你要用的酒館裡真聊幾輪；
5. 每輪根據看到的問題，修一兩處明確的地方。

狀態列、資料庫和複雜指令碼，不用一開始就全裝上。

### Q13. 我只有模糊想法，或只想改一個小地方，Agent 會不會把專案做大？

**A：** 有這個風險，所以一開始就把範圍說清楚。

- **新專案，只有模糊想法**：先讓 Agent 把總設計和第一版能玩的範圍收住，再動手。
- **已有作品，只改一點**：先讓它讀現狀和續接記錄，只改跟這次目標有關的地方。

可以直接這樣說：“這輪只改開場，其他都別動；改完告訴我，匯入後要看哪幾處。”如果它想擴大範圍，要先說明這跟你的目標有什麼關係。

### Q14. 接手別人做的卡，只有 PNG 或 JSON，能直接續更嗎？

**A：** 能接手，但先別急著改。先讓 Agent 查清這張卡里實際裝了什麼，講清它是怎麼運作的，再決定是“沿著原作繼續維護”，還是“拿它做二創”。

PNG／JSON 是打包好的成品，裡面不一定有方便維護的原始碼。沒有原始碼，就要記下哪些部分只能從成品裡拆出來還原。另外還要確認三件事：

- 哪些人設必須保留；
- 舊聊天和存檔還能不能接著用；
- 第一次先改的最小一處是什麼。

### Q15. 小說、圖片和網頁資料很多，怎麼給 Agent 才不亂編？

**A：** 先分清三類內容：原作寫的、二創設定的、你自己拍板的，並標明是哪個版本或哪幾章。

TW 的作品資料庫能把文字資料整理成可以編輯的 Markdown 和索引，之後能按來源、改編版本和劇透階段（劇情進行到哪一步才揭曉）回頭查。圖片和網頁參考，也要記清出處和用在哪裡。

Agent 沒讀到的內容，要標成“待核實”，不能拿模型的印象當原作事實。

### Q16. Skill 會自動全開嗎？我需要逐個點名嗎？

**A：** 不會全開，也不用逐個點名。直接說要做什麼，Agent 應該自己挑最相關的 Skill，再從 Library 裡讀需要的指南；只有工作確實跨了好幾個領域，才會幾個 Skill 一起用。

你也可以點名要某個 Skill。但要留意：倉庫裡有這個 Skill，不代表這次任務真的讀了、用了它。

### Q17. 純文字、MVU Zod、hybrid 三類角色卡怎麼選？

**A：** TW 的主型別固定為這三類，按作品實際需要選擇：

- **純文字（text）**：用開場白和世界書承載主要內容。可以沒有前端，也可以使用簡單文字狀態列或正則狀態列。
- **MVU Zod（mvu_zod）**：玩法需要持續更新結構化狀態，使用 MVU 配合 Zod 結構約束，通常搭配前端。按實際專案核對初始化、更新規則和執行依賴。
- **hybrid**：確有混合執行機制時保留的型別，需要說明各機制負責的內容和寫入邊界；同時出現文字與前端，不足以把卡歸成 hybrid。

舊卡的獨立 MVU 路線保留相容識別，不因改了分類就自動加裝 Zod 或遷移存檔。資料庫式設計是一種按需採用的資料組織方式，不另算第四類卡。型別與舊卡處理詳見[卡型與執行依賴](https://github.com/LiarMTTT/TavernWeave/blob/main/skills/tavern-card-builder/references/card-types-and-runtime-dependencies.md)。

### Q18. 世界書、角色設定、開場和 NPC 資訊分別放哪兒？

**A：**

- **世界書**：承載主要人物設定、世界觀和演繹規則，按需要配置常駐或條件觸發。設計前先向作者解釋小型、中型、大型的區別及後續影響，複用已有選擇。結構化呈現優先。
- **開場白**：給出能開始遊玩的具體起點。完整角色卡必須同時有可用開場白和實質世界書，空白佔位不算完成。
- **人物與 NPC**：常駐內容和按條件需要的細節都放進世界書規劃。單核心角色的人物條目用藍燈；多核心角色保留藍燈概覽，人物細節用綠燈。人物事實不等於玩家代演許可。

新卡通常不再重複填寫角色描述、性格、場景、示例對話及卡級提示詞等傳統欄位。酒館仍支援這些欄位；接手舊卡時先檢查其作用，保留有效內容，不自動清空。掃描深度為 2，全部條目關閉雙向遞迴；機率、黏性和冷卻通常不使用，作者提出或確有需求時再推薦。整卡配置見[世界書配置](https://github.com/LiarMTTT/TavernWeave/blob/main/skills/tavern-card-builder/references/lorebook-and-prompts.md)；獨立規劃、審閱或精修世界書可走[世界書規劃與寫作](https://github.com/LiarMTTT/TavernWeave/blob/main/skills/worldbook-design-and-writing/SKILL.md)。

寫完用實際聊天查兩件事：該出現的內容有沒有觸發；同樣的內容有沒有重複塞進提示詞、白佔篇幅。

### Q19. 我想要開場頁面、狀態列或控制中心，該從哪一種做起？

**A：** 先看它們各管什麼：

- **開場頁面**：開局時讓玩家做一次設定，然後發出真正的第一條玩家訊息。
- **狀態列**：放經常要看的當前狀態。
- **控制中心**：處理比較複雜的設定和管理。

動手前先寫清楚：資料從哪來、什麼時候更新、玩家能改什麼，再挑能滿足需求的最小介面。只有幾個開場選項，一般用不著做成完整應用；複雜的管理操作，也別全塞進狀態列。

### Q20. 做完後交付什麼：原始碼、JSON、PNG，還是截圖？

**A：** 看用途：

- **以後還要改**：要有原始碼。
- **匯入酒館**：一般是專案打包出來的 JSON，或者帶卡資料的 PNG。
- **截圖**：只用來展示介面長什麼樣，證明不了卡能匯入。

打包時要檢查需要的世界書、正則、指令碼和圖片是不是真的進了成品，並寫明版本、說清測過哪些。

### Q21. 為什麼“自動測試透過”了，還要進真實酒館試？

**A：** 因為有很多問題只有在酒館裡才會暴露。自動檢查能找出檔案、結構和一部分規則的錯；離線網頁預覽能看佈局。但匯入、訊息顯示、擴充套件注入的內容、變數更新、重新載入和資料儲存，都要看真實的酒館和你裝的擴充套件。

至少把試用卡導進你要用的那個版本，把這次改動相關的操作走一遍，比如開場、對話、編輯訊息或切換聊天。

### Q22. 任務太長中斷了、Skill 更新了，怎樣接著做？

**A：** 靠續接記錄，不靠聊天記憶。結束前留好這些：專案目標、已經確認的決定、當前原始碼和成品的版本、做過哪些檢查、哪些還沒驗證、下一步做什麼。

開新任務時，先讓 Agent 讀倉庫裡的 `AGENTS.md`、`NEXT.md` 或同類續接記錄，再看實際檔案。更新 Skill 以後，先核對安裝目錄，再開新任務，讓客戶端重新找到它們。舊聊天裡的結論，不能拿來證明新環境已經用上了新版本。

## 三、熟練：變數、渲染、介面和流程故障

### Q23. 世界書條目的觸發、順序、深度和提示詞佔用怎麼調？

**A：** 沒有通用數值，要對著你的酒館版本調。獨立規劃或精修世界書時可參考[世界書規劃與寫作 Skill](https://github.com/LiarMTTT/TavernWeave/blob/main/skills/worldbook-design-and-writing/SKILL.md)；它不會替你驗證實際酒館載入結果。

1. 先確認你用的 ST 版本里，每個設定到底是什麼意思；
2. 把每個條目的觸發條件、插進提示詞的位置、誰優先、佔多少篇幅記下來；
3. 準備“應該觸發”和“不該觸發”兩組聊天樣例去試。

劇情變亂時，先查三樣：同一內容是不是重複插入了、誰把誰覆蓋了、有沒有條目太長。查完再動引數。

### Q24. MVU 變數第一次沒有值，或者更新停了，先查哪裡？

**A：** 按這條鏈一段一段查：

**欄位定義 → 初始值 → 更新規則 → 模型能看到的內容 → 執行時讀取 → 介面顯示**

每一段都要在幾種情況下試：新開聊天、換不同開場、編輯或重新生成、切換聊天、重新載入頁面。有些開場方式，要等玩家真正發出一條訊息，變數才會進入正常的更新流程。

兩個常見誤區：

- 狀態列顯示舊值，不能直接斷定模型沒更新，也可能是中間某一段斷了；
- 不要用指令碼假裝觸發了初始化，把中間缺的一環蓋過去。

### Q25. 變數、EJS、世界書、指令碼、正則到底各管什麼？

**A：**

| 部分 | 管什麼 |
| --- | --- |
| 變數 | 存會隨劇情變化的資料 |
| 世界書 | 滿足條件時提供知識或規則 |
| EJS 等提示詞模板 | 決定怎樣把資訊送給模型 |
| 指令碼 | 必須算準、每次結果都一樣的讀寫和互動 |
| 正則 | 找到特定文字並改寫 |

分好工以後，給每項資料定一個唯一的來源，寫清誰寫、誰讀、什麼時候重新整理。別讓五個地方各自維護同一個狀態。

### Q26. 劇情寫著過了一天，狀態列的時間卻沒變，怎麼定位？

**A：** 先搞清“時間”是從哪來的：模型寫在正文裡、存在 MVU 變數裡，還是指令碼算出來的。

再找兩處：哪一步負責把劇情裡的時間變化寫回變數；狀態列在等哪個更新事件。

然後拿同一段聊天，對照三樣東西：訊息原文、變數當時的值、介面上顯示的值。這樣才能分清是模型沒寫、寫入失敗，還是介面沒重新整理。

### Q27. 正則改了卻沒生效，或者誤傷了開場／正文，怎麼查？

**A：** 逐項核對：

- 有沒有啟用；
- 作用在哪類訊息上；
- 改的是顯示給你看的內容，還是發給模型的提示詞；
- 深度和替換順序。

然後用最短的樣例文字分別試“應該匹配的”和“必須原樣保留的”。

如果這條正則還負責把介面掛到訊息裡，還要確認替換後的網頁結構（DOM）和指令碼載入路徑對不對。離線樣例透過以後，仍要在真實酒館裡，看訊息從生成、顯示到編輯的整個過程。

### Q28. 電腦上正常，手機或窄屏就錯位，先查什麼？

**A：** 先量真正裝著介面的那個框有多寬，通常是訊息區域或 iframe，而不是整個瀏覽器視窗。

然後查：寫死的寬度、內容溢位、縮放、按鈕夠不夠大、長文字會不會撐破。用窄框預覽試完，還要在目標裝置上的酒館裡再試一次。離線截圖看著沒問題，說明不了手機酒館裡的載入、滾動和點選都正常。

### Q29. SVG、圖片、音訊、影片或 Live2D 放進卡里，怎樣避免失效？

**A：** 先定資源放哪：直接塞進成品、跟著專案一起發，還是從網上載入。然後記下來源、授權、檔案大小、要不要提前載入，以及載入失敗時顯示什麼。

檢查最終的 JSON／PNG 裡真的帶著這些資源，或者外部地址在你的環境裡打得開。會動的媒體，比如音影片和 Live2D，還要在真實酒館裡看啟動、切換、關掉時的表現，以及在手機上的樣子。

### Q30. Agent 說“會用工具”，卻沒呼叫 MCP 或 Skill，該怎麼辦？

**A：** MCP 是讓 Agent 連線外部工具的介面。遇到這種情況，讓 Agent 拿出實際記錄：這輪讀了哪個 Skill 入口、用了什麼工具、輸入了什麼、得到了什麼能檢查的結果。拿不出記錄，就按“還沒呼叫”處理。

如果是工具本身用不了，先查三樣：客戶端有沒有識別到這個工具、許可權夠不夠、工作目錄對不對。再把問題縮小到一個能重現的動作。Agent 寫出來的計劃只是打算，不能當作已經做過的證明。

### Q31. 打包後匯入是空卡、缺世界書、圖片只有殼，怎麼排查？

**A：** 從頭往後追：

**維護原始碼和構建設定 → 最終 JSON → PNG 裡嵌的卡資料是否和 JSON 一樣**

逐項看名字、開場、世界書、正則、指令碼和要用的資源在不在。然後用一張全新匯入的測試卡驗證，免得舊卡的快取或舊聊天把問題擋住。

還有一點：如果專案自己沒有構建工具，不能因為 TW 有某個 Skill，就以為已經有現成的打包命令。

### Q32. 多 Agent 分工、換模型、控制 token，什麼時候值得做？

**A：**

- **多 Agent 分工**：資料整理、某個模組、某項檢查這類能各自獨立完成的工作，才適合幾個 Agent 並行。共用同一份狀態、同一個瀏覽器、同一份打包輸出的工作，要統一安排，不能各幹各的。
- **換模型**：先定好共同目標、每個檔案歸誰管、怎樣算合格，再拿實際任務比表現和花費。
- **省 token**：先刪重複資料、把任務範圍說清楚、留好續接記錄。別為了省錢隨手刪掉必要的規則。

### Q33. 更新了 TW、ST 或擴充套件，舊任務的結論還能用嗎？

**A：** 一部分能用。創作目標和你確認過的決定可以照用；安裝目錄、API 的表現、擴充套件事件和實際執行結果，要按新版本重新查。

- **更新 TW 後**：按所用版本核對 Skill 清單（當前 2.3.0 正式版為 `23/23`；歷史 1.9.1 原包為 `22/22`）和全域性規則狀態，再開新任務實際呼叫一次 Skill。
- **更新 ST 或擴充套件後**：把受影響的操作在真實酒館裡重新跑一遍。

記錄時寫明是“舊版本測過”還是“當前版本測過”。

## 四、老手：複雜架構、效能、維護與釋出

### Q34. 複雜計算和資料庫邏輯，交給模型、提示詞還是指令碼？

**A：** 各做各擅長的：

- **指令碼**：要算準、每次結果都一樣的公式和資料升級。
- **模型**：寫劇情、提出可選方案、做開放式判斷。
- **提示詞**：告訴模型規則是什麼、輸出不能越過哪些邊界。
- **資料庫結構**：定欄位、每條記錄的唯一編號（主鍵）、存在哪裡、版本號。

每個關鍵數值都寫清楚：從哪來、誰寫、誰讀、出錯了怎麼辦。別讓模型既當資料庫又當計算器。

### Q35. 資料庫卡能在同一樓層完成所有更新嗎？

**A：** 目前還不能這麼承諾。TW 的資料庫卡方案，支援的是正常的多輪對話：狀態跟著一條條訊息（樓層）儲存。在同一條訊息裡完成全部更新，也就是同樓層方案，還沒有驗證過。

設計時要把“資料存在哪”寫進約定，也別讓備用方案偷偷把資料換個地方存。要說某個具體做法支援同樓層，得先在你的酒館裡實測過：新建聊天、編輯、重新生成、切換聊天、資料儲存都沒問題才行。

### Q36. 大卡變慢，怎樣知道是提示詞、世界書、正則、指令碼還是媒體拖的？

**A：** 分兩步：

1. **先數清楚**：拿同一版成品，分別統計檔案大小、提示詞長度、世界書條目數、正則數、指令碼數和內嵌媒體，作為基準。
2. **再實測**：在一個寫明版本的真實環境裡，測首次開啟、重新生成、切換聊天、開啟控制中心這些場景。

按耗時或體積找出是哪一部分拖慢了，先做最小、隨時能撤回的最佳化，再用同樣的統計方法和基準比。用 Node 在電腦上跑出來的靜態計時，說明不了真實酒館裡流不流暢。

### Q37. 舊卡只改一個元件，還需要整卡重做和重新驗收嗎？

**A：** 不用整卡重做，但該測的還得測。

先圈出這次改的是哪個元件、它依賴什麼、會影響哪些地方，只改維護原始碼裡對應的那部分，再用專案自己的工具重新打包。

回頭檢查要覆蓋受影響的鏈路，以及原來重要的功能，也就是改完再試原來能用的地方；跟執行有關的，照樣要在真實酒館裡試。別因為“只是小改”就跳過成品內容的檢查，也不用把不相關的設計全部推翻重來。

### Q38. 獨立前端、嵌入式介面和普通狀態列怎麼取捨？

**A：** 看四樣：互動有多複雜、資料歸誰管、在哪執行、維護起來多費勁。

- 經常看、很少改的狀態：輕量狀態列；
- 開局時選一次：開場頁；
- 大量設定和管理操作：才考慮控制中心。

如果獨立前端或同樓層方案在酒館裡沒有可靠的支援，Agent 應該直說不推薦，先給更輕的辦法。就算只是做個原型試試，也要留著“真實酒館裡測過才算數”這一關。

### Q39. 從設計到釋出，哪些檢查可以合併，哪些不能互相代替？

**A：** 同一個改動的自動檢查可以一起跑，但結果要分開記，因為它們說明的是不同的事：原始碼檢查、自動測試、離線成品檢查、瀏覽器預覽、真實酒館測試、人工驗收、Git 提交、釋出許可。

劇情和畫面你滿不滿意，只能你自己說了算，自動檢查替不了；真實酒館裡跑通了，也不等於同意公開發布。每一關都記下對應的版本，以及還沒測的部分。

### Q40. 怎樣給角色卡做一次“健康檢查”或全量架構審查？

**A：**

1. 先定好查哪些內容、查哪一版成品；
2. 讀維護原始碼、打包過程和執行依賴；
3. 分塊看：提示詞與世界書、變數鏈路、正則與指令碼、介面、安全、效能、交付。

報告裡要列清楚：哪些查完了、哪些只查了一部分、哪些沒讀、哪些有意排除。每個問題都附上依據、影響和修法。只讀審查只能說明“發現了什麼”，不能當作“已經修好”，也不能當作“已經在酒館裡測過”。

### Q41. 不同客戶端或擴充套件版本的 API 表現不一樣，TW 給的例子還能照抄嗎？

**A：** 別直接照抄。先查清你用的 ST、酒館助手（Tavern Helper／JS-Slash-Runner）等的實際版本和官方介面，再把例子改成適合這個環境的寫法。

宏、事件、變數介面、正則在哪個階段執行、iframe 什麼時候載入和銷燬，都可能讓結果不同。先用最小的例子把呼叫試通，再接進整張卡。TW 提供的是核對方法，不保證任何一段程式碼換了版本還能直接用。

### Q42. 能不能把 TW 的 DeepSeek Harness 適配說成“正式相容”？

**A：** 不能直接說成“正式相容”。2.1.0 起可以說明“提供 TavernWeave X DSH 外掛包，已在指定 DSH 版本上完成部分執行驗收”；DSH 自身仍是 Developer Preview，正式相容、跨平臺與模型效果必須以 `host-adapters/dsh/dsh-plugin-contract.json` 的 `runtimeAccepted` 和實測版本為準。

對外介紹時要寫清驗證到哪一步：外掛安裝、preset 選擇、Skill 載入、真實酒館與模型效果是不同證據。等目標環境裡安裝、選擇 preset、找到 Skill、呼叫工具和做出實際作品都跑通了，再更新說法。

### Q43. 髮卡、打包或公開作品前，最後要核對什麼？

**A：** 按這張清單過一遍：

- 固定原始碼和準備釋出的版本；
- 依賴、國內／海外載入地址的選擇、世界書和內嵌資源都齊全；
- JSON 和 PNG 裡的卡資料一致；
- 在目標酒館裡把關鍵操作走一遍；
- 列出哪些做過自動檢查、哪些實機跑過、哪些經過人工確認、哪些還沒驗證；
- 素材來源和使用授權單獨核對。

提交原始碼、交付成品檔案、公開發布是三件事，各自按專案約定和授權來。

### Q44. Skill、Soul、Library 或設計參考“已經存在”，就表示它被採用或驗收了嗎？

**A：** 不表示。從“有”到“驗過”，中間還隔著好幾步：

**存在 → 這輪讀過 → 專案選用 → 寫進原始碼 → 在客戶端或酒館裡真的跑起來 → 你認可**

Library 挑選頁裡的候選項，只說明“可以考慮”；Soul 只改說話風格，不改變該做的檢查和該拿的授權。每個“已完成”的說法，都應該能對上實際的執行記錄或對應的成品。
