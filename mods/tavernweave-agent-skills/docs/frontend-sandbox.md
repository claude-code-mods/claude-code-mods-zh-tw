# 前端沙盒：讓 Agent 按你的作品搭建

前端沙盒適合在封裝前反覆調介面、試互動、檢查多個前端能否正確配合。**TW 提供搭建規範和工作方法；你可以讓 Agent 根據作品的真實原始碼，在專案自己的測試目錄裡搭建沙盒。** 頁面佈局、除錯控制元件和預覽方式按作品需要安排，沿用已有技術棧。

這一步是可選的。你可以直接跳過，繼續原有製作、封裝與真實酒館測試；跳過不算失敗。

> 作者在實際制卡中，透過封裝前的沙盒打磨，減少了後續實機驗收中的反覆調整和 Bug；具體效果取決於專案與使用方式。

## 直接這樣告訴 Agent

```text
採用封裝前沙盒打磨，按我的作品搭建。
先讀真實原始碼和續接記錄，列出本次全部前端模組、入口與宿主依賴，推薦單模組或聯合模擬。
在專案測試目錄裡直接載入這些原始碼，保留必要的 iframe／blob 層級和介面位置；沿用專案的預覽方式，除錯控制元件貼合我的前端。
測試資料先展示來源、目標聊天／樓層、前後差異及預計事件，等我明確確認後注入。目標或狀態改變時，重新預覽；已確認的場景序列不用每步再問。
讓我用滑條和精確數值調 UI，支援基線對照、復位、預設和引數匯出。手調預覽尺寸時不要替我改視口。
最後把選中的改動回落到真實原始碼，移除臨時覆蓋複測，留下狀態對照、復現記錄和實機還需檢查的專案。
```

本次不用時，直接說：“跳過沙盒，按已有製作與封裝流程繼續。”已經作出的採用／跳過決定可沿用。

## 選哪種模擬

| 方式 | 適合什麼情況 | 搭建時要保留什麼 |
| --- | --- | --- |
| 單模組 | 集中調狀態列、手機、開局頁或控制中心 | 該模組的真實原始碼、依賴、視窗層級與互動邏輯 |
| 多前端聯合 | 檢查共享狀態、事件同步、遮擋與皮膚干擾 | 本次範圍內的全部模組、正確的狀態與事件連線、各模組的樣式和儲存邊界 |

“全量”按本次確認範圍計算。讓 Agent 分別列出已裝載、未接入、暫不支援和本次未測試的專案；頁面開啟不代表所有功能都測過。

## 實際操作順序

1. **對準原始碼。** 核對正在跑的檔案、版本和依賴；有測試副本時記錄它和維護原始碼的關係。不能用仿製介面代表你的元件。
2. **看資料再注入。** 初始預設、後續修改、恢復和重置都先說明目標與差異。確認繫結這一批資料和當前狀態；切聊天或狀態變化後舊確認失效。取消不寫入，寫入失敗如實記錄。
3. **對照各處顯示。** 把注入前、待注入、實際提交後和各模組看到的值放在一起，檢查該更新的地方是否更新、事件有沒有重複。
4. **親手調 UI。** 在已採用範圍內，滑條和數值輸入即時預覽，業務資料仍走確認。保留當前值與基線，可單項／整組復位、切預設、匯出和重新載入。需要面板時讓它能移動、收起和隱藏；並排對照使用同一原始碼的兩個隔離例項。
5. **把結果帶回原始碼。** 臨時樣式只算候選。選定後寫回維護原始碼，移除除錯覆蓋，再重放同一場景；儲存 JSON／Markdown 記錄、引數與尚未覆蓋的宿主行為。

搭建的詳細要求見[工作流程](../skills/sillytavern-embedded-ui/references/sandbox-workflow.md)、[專案適配合同](../skills/sillytavern-embedded-ui/references/adapter-contract.md)和[場景參考](../skills/sillytavern-embedded-ui/references/sandbox-recipes.md)。這些資料是給 Agent 的實施依據；具體專案仍需要實際搭建和驗證。私有原始碼、原聊天與玩家資料留在專案測試目錄。

## 沙盒之後還要檢查什麼

報告分別寫清自動檢查、瀏覽器操作、真實酒館表現和你親自試用的結果。沙盒的宿主適配有範圍，真實 SillyTavern 的訊息樓層、擴充套件、模型和裝置行為仍需用新構建複驗；駕駛員驗收由你的明確確認給出。

本頁對應[奶人教程第四章的可選小節](newbie-guide/index.html#frontend-sandbox)。第四章的 **Mock Receiver** 是接收真實酒館執行記錄的本機工具，名字裡的 Mock 不表示模擬酒館。
