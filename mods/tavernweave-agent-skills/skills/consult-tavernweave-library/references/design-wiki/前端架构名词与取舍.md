# 前端架構名詞與取捨

前端架構先回答三件事：頁面怎麼切、HTML 在哪生成、狀態放哪。名詞本身沒有對錯；對錯在規模、團隊和互動密度對不上。本頁按行業合同蒸餾，不按「角色卡能不能用」刪方案。對照表見 [[comparisons/行業架構方案何時用]]。動效庫見 [[concepts/動畫庫與動效管線]]。視覺 / token 見 [[concepts/視覺CSS與設計token]]。連結賬本見 [[queries/前端視覺與靈感站點蒸餾目標]]。

本倉庫兩條產品線的**對映**放最後一節，不當過濾器。

## 頁面形態

| 名詞 | 何時用 | 優點 | 缺點 |
|---|---|---|---|
| MPA | 內容站、文件、SEO、跨頁狀態弱 | 首屏快、可少 JS、CDN 簡單 | 跨頁狀態丟、難做應用感 |
| SPA | 後臺、編輯器、郵箱類 | 互動連續、狀態可留記憶體 | 首包重、TTI 差、不適合內容站 |
| MPA + Islands | 內容為主、區域性要互動 | 預設零 JS、按可見性注水 | 島間共享狀態要另接；堆多了變偽 SPA |
| HTMX / HDA | 伺服器已能出 HTML，互動是增強 | 少前端狀態機 | 複雜客戶端編排弱 |

另有 [HTMX 超媒體驅動](https://htmx.org/essays/hypermedia-driven-applications/)：伺服器繼續出 HTML，瀏覽器只做增強。適合互動是「增強表單/片段」而不是重寫整個客戶端。複雜手勢和離線編輯仍會回到 SPA。

來源：Astro [why](https://docs.astro.build/en/concepts/why-astro/)、[islands](https://docs.astro.build/en/concepts/islands/)。

## 渲染與啟動

| 名詞 | 何時用 | 優點 | 缺點 |
|---|---|---|---|
| CSR | 殼先出、資料客戶端拉；SEO 不重要 | 可部署成靜態檔案 | 首屏空、爬蟲弱 |
| SSR | 首屏/SEO，內容隨請求變 | FCP 好、爬蟲可見 | TTFB 綁伺服器；全量注水仍晚可點 |
| SSG | 文件、營銷、不隨使用者變的目錄 | CDN 友好、無執行時渲染稅 | 內容變要重建；個性化弱 |
| ISR | 大量內容頁、可短暫滯後 | 不必全站重建 | 有陳舊視窗；靜態匯出不支援 |
| Hydration | SSR/SSG 之後還要互動 | 先看見再可點 | 注水前點選無效；全頁注水傷 TTI |
| Resumability | 要互動但不想啟動即跑全應用 | 無強制啟動注水、按互動懶載入 | 與現有框架心智不相容，生態窄 |
| RSC | React 樹預設在服務端算 | 少把資料序列化給客戶端 | 只在 React 棧；要學序列化邊界 |

來源：[web.dev rendering](https://web.dev/articles/rendering-on-the-web)、[Next ISR](https://nextjs.org/docs/app/guides/incremental-static-regeneration)、[Qwik resumable](https://qwik.dev/docs/concepts/resumable/)。效能合同先讀 [Web Vitals](https://web.dev/articles/vitals)（LCP / INP / CLS）。React 前後端分層見 [Server Components](https://react.dev/reference/rsc/server-components) 與 [Server and Client](https://nextjs.org/docs/app/getting-started/server-and-client-components)。RSC 是 React 樹的預設服務端計算，不是「又一種 SSG」。

## 微前端、聯邦、BFF

| 名詞 | 何時用 | 優點 | 缺點 |
|---|---|---|---|
| 微前端 | 多團隊、獨立釋出、前端單體已堵交付 | 團隊自治、可分期上線 | 一致性、共享依賴、非原子釋出；小團隊常虧 |
| Module Federation | 已決定微前端，要執行時拼裝 | 獨立部署、少重複打包 | 版本錯配、除錯難、執行時失敗面大 |
| Web Components 微前端 | 技術棧無關嵌入，主要隔離樣式 | 瀏覽器原生、容器薄 | 不是源隔離；無障礙/SSR 要另做 |
| BFF | Web / 移動 / 嵌入要的資料形狀差很多 | 少 round-trip、契約跟 UI 走 | BFF 增殖；代管會重新變瓶頸 |

來源：[Fowler micro-frontends](https://martinfowler.com/articles/micro-frontends.html)、[Module Federation](https://webpack.js.org/concepts/module-federation/)、[Sam Newman BFF](https://samnewman.io/patterns/architectural/bff/)。Fowler 沒有獨立 BFF bliki，BFF 用 Newman 原文。

聯邦是執行時、可獨立部署的拼裝。單體倉是構建時共享原始碼與工具鏈。只要更快構建、不要獨立釋出，用單體倉。只有釋出節奏必須錯開才上聯邦。來源：[Nx micro-frontend](https://nx.dev/docs/technologies/module-federation/concepts/micro-frontend-architecture)。

BFF 與 API Gateway 不是同一種門，見 [[concepts/後端架構名詞與工坊對照]]。

## 狀態分層

| 名詞 | 放什麼 | 不要放什麼 |
|---|---|---|
| 本地 UI state | 開關、輸入草稿、當前 tab、拖拽 | 別人會改、重新整理必須還在的資料 |
| 服務端狀態 / Query | 列表、詳情、許可權、MVU 快照 | modal 開合、純 UI 開關 |
| 全域性 store | 跨應用共享且更新邏輯複雜的客戶端真相 | 每一個輸入框的值 |

來源：[Redux organizing state](https://redux.js.org/faq/organizing-state)、[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview)。

URL 也可以當狀態（篩選、頁碼、深鏈）。該進 URL 的不要只放記憶體。

## 樣式架構

| 名詞 | 何時用 | 優點 | 缺點 |
|---|---|---|---|
| 元件驅動 | 同一控制元件多處、多主題 | 可單獨測、設計與實現同契約 | 沒有 token 會變成元件墳場 |
| 工具類 CSS | 應用 UI、要快、有元件封裝重複組合 | 無全域性級聯戰爭 | 標記噪；嵌入宿主容易漏進主文件 |
| 語義 CSS / BEM | 嵌入宿主、選擇器必須可審計 | 可讀、特異性低 | 要命名紀律；易長出巨型 CSS |
| Design tokens | 站點 / HUD / 管理臺要同一套決策 | 主題可替換，元件不寫死魔法數 | 只貼 token 檔案、元件仍寫死色值，系統是空的 |

來源：[NN/g design systems](https://www.nngroup.com/articles/design-systems-101/)、[W3C Design Tokens CG-FINAL 2025-10-28](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/)、[BEM](https://bem.info/en/methodology/)、[Tailwind utilities](https://tailwindcss.com/docs/styling-with-utility-classes)。DTCG 是社群組報告，不是 W3C Recommendation。

嵌入別人的文件時，utility 容易漏進宿主；BEM 或 `data-*` 更好審計。獨立站點可以 utility + token 並行。細則見 [[concepts/視覺CSS與設計token]]。

## 嵌入邊界（摘要）

三路徑對照見 [[comparisons/嵌入三路徑對照]]。一句話：

- **iframe**：獨立瀏覽上下文。不信任第三方、要源隔離時用。`allow-scripts` + `allow-same-origin` 會自我解除沙箱。來源：[sandboxed iframes](https://web.dev/articles/sandboxed-iframes)。
- **同文檔掛載**：共享事件迴圈和焦點，能摸輸入框和主題變數。無源隔離，樣式會互撞。
- **Shadow DOM**：封裝 DOM/CSS。和宿主同 JS 堆、同卡頓。來源：[Using shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)。

跨文件 iframe 的 `backdrop-filter` 糊不到父頁。iframe 裡 `1vh` = iframe 高。細則見 [[concepts/視覺CSS與設計token]]、[[comparisons/嵌入三路徑對照]]。

## 即時

| 名詞 | 何時用 | 優點 | 缺點 |
|---|---|---|---|
| 輪詢 | 更新稀、可晚幾秒 | 無狀態、好快取、斷了下次自己好 | 高頻浪費；延遲 = 間隔 |
| SSE | 進度、通知、直播列表（只聽） | 比 WebSocket 簡單，走 HTTP | 單向；HTTP/1.1 每域連線數很少 |
| WebSocket | 協作編輯、對戰、在場、高頻雙向 | 全雙工，不必為回覆再拉 | 心跳、鑑權續期、代理都要自己管 |
| 樂觀更新 | 低衝突、可逆的寫 | 手感不受 RTT 綁死 | 錢、許可權、庫存不要先樂觀 |

來源：[SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)、[useOptimistic](https://react.dev/reference/react/useOptimistic)。

協作編輯、對戰、在場這類產品該上 WebSocket；目錄頁和偶發稽核不必。

## 例子

- 正例：文件站 SSG + 搜尋島；後臺用 SPA；多客戶端形狀差很多時加 BFF。
- 正例：按鈕用 CSS transition，長滾動敘事用 GSAP，見 [[concepts/動畫庫與動效管線]]。
- 反例：內容站一上來整站 SPA + 微前端 + 自建 WS 推靜態目錄。
- 反例：把「卡用不上」當成行業方案不存在。

## 邊界與易混概念

- 本頁不是設計系統採納清單，也不是工坊/HUD 禁令表。
- Islands 堆多了就是偽 SPA；有島不等於已經做對效能。
- RSC ≠ SSG；CSR ≠ SPA（SPA 是應用形態，CSR 是渲染位置）。
- BFF ≠ API Gateway。

## 對映到本倉庫

角色卡 HUD：入口掛宿主 document；整頁尾本走 TH iframe；開合/拖拽 = 本地 UI state；MVU = 服務端狀態心智。詳見 [[concepts/酒館宿主與iframe分層]]、[[concepts/MVU變數閉環]]。
獨立工坊站：當前落點是 SSG/ISR + islands + 小 Gateway，見 [[comparisons/工坊架構該上與不該上]]。
這兩條對映不刪除上表裡的 SPA、聯邦、WebSocket、GraphQL。
