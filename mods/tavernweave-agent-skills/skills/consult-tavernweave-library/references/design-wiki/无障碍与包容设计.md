# 無障礙與包容設計

行業層：人怎麼感知、操作、理解介面；規範、模式、認知與遊戲三條軸怎麼疊。本頁是機制蒸餾，不是某倉庫的皮膚或合規宣告。對比度與動效底線見 [[concepts/視覺CSS與設計token]]，本頁不重複那一節。

## 一句話定義

無障礙是可測的內容合同（現行樞紐是 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)）；包容設計是從排除出發的方法；通用設計是「儘量一份設計服務所有人」。三者相關，不是同義詞。

## 為什麼重要

HUD、表單、空面板和命令面板都會把人擋在門外：焦點出不去、欄位錯只閃一下、空白區看不出是空還是還在載入、快捷命令沒有鍵盤模型。規範回答「能不能聲稱符合」；模式回答「這個控制元件怎麼鍵鼠」；認知與遊戲指南迴答「規範沒蓋住的使用需求」。混用會把 Note 當成 Rec，或把遊戲清單當成法律清單。

## 如何運作

### 規範層：WCAG 是 Rec，APG 不是

[WCAG 2.2](https://www.w3.org/TR/WCAG22/) 是 W3C Recommendation（現行公佈頁日期 2024-12-12；首發 2023-10-05）。四條原則：可感知、可操作、可理解、健壯。符合性看可測成功標準（A / AA / AAA），不是看「有沒有跟一篇模式文」。2.0 / 2.1 / 2.2 都仍是現行 Rec；後一版加條、不改舊條（2.2 把 4.1.1 Parsing 標過時）。[WCAG 總覽](https://www.w3.org/WAI/standards-guidelines/wcag/) 寫明：WCAG 是給要技術標準的人用的，不是入門課。WCAG 3 仍是早期草案。

[ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/) 教怎麼把 ARIA 語義和鍵盤行為落到常見控制元件。它是模式指南，合成若干規範的用法，**不是** W3C Recommendation。跟了 APG 示例 ≠ 自動符合 WCAG。APG 自己寫：角色是承諾，錯誤 ARIA 比不用更糟；示例按 ARIA 1.2 說明正確用法，不負責給瀏覽器/讀屏缺口打補丁。採集日讀屏基線記 [NVDA](https://www.nvaccess.org/) 2026.1.1；WAI Easy Checks 遷址後新頁當時是空殼，不當活清單。

### 方法層：包容 ≠ 無障礙 ≠ 通用

[Microsoft Inclusive Design](https://inclusive.microsoft.design/) 把包容設計寫成方法：承認排除、向多樣性學、為一人解再擴到多人。工具包（如 Inclusive 101）許可是 **CC BY-NC-ND**，可引用不可當商用改作素材。無障礙通常指對照 WCAG 等標準去掉障礙。通用設計（Ron Mace 傳統）追求一份設計儘量不用適配就服務所有人。包容設計承認情境錯配，不承諾「一個控制元件打天下」。

### 認知層：COGA Note 不構成符合性

[WAI Cognitive](https://www.w3.org/WAI/cognitive/) 寫明：WCAG 已覆蓋一部分認知需求（夠時間、可讀、可預期、輸入幫助等），仍有需求不在現行標準裡。[Making Content Usable（COGA）](https://www.w3.org/TR/coga-usable/) 是 2021-04-29 Working Group Note，摘要寫：遵循它**不是** WCAG 符合性要求。補充目標/模式同樣「超出 WCAG 2 才要求的部分」。

三套語言合同不可互換：[Digital.gov Plain Language](https://digital.gov/guides/plain-language) 是美國聯邦「寫給特定讀者、清楚簡潔」；`plainlanguage.gov` 已重定向到 Digital.gov。[Easy Read / Easy-to-Read](https://www.inclusion-europe.eu/easy-to-read/) 是短句 + 配圖、面向智力障礙等讀者的版式。COGA 是認知無障礙目標與模式。把其中一套當成另外兩套的符合性證明，會漏人。

### 遊戲層：GAG / XAG / APX 三軸

[Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/) 自 2012 起按基本 / 中等 / 複雜分檔，是行業參考清單。[Xbox Accessibility Guidelines](https://learn.microsoft.com/en-us/gaming/accessibility/guidelines) 現行 **v3.2**（2023-06-08）；文件寫明給設計/開發/測試當護欄，**不是**任何法律或合規清單。[Accessible Player Experiences (APX)](https://accessible.games/accessible-player-experiences/) 是 AbleGamers 的 22 條設計模式，分 Access（進得去）與 Challenge（玩得下去），用來找障礙和討論方案，不是終檢表。三套目的、粒度和作者不同，不能互相替換。

### 表單、空態、命令面板

表單先用原生控制元件兌現承諾，再補 ARIA。[APG Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)：輸入框 + 彈出層（listbox / grid / tree / dialog），預設收起；可編輯與僅選擇是兩套行為。[`:user-invalid`](https://developer.mozilla.org/en-US/docs/Web/CSS/:user-invalid)（Baseline，約 2023-11 起跨引擎）只在使用者互動或提交之後標無效，避免空必填一進頁就全紅。欄位錯要貼在欄位旁並保持到改對；這是輸入幫助，不是系統廣播。

空態：[NN/g](https://www.nngroup.com/articles/empty-state-interface-design/) 要空容器說明系統狀態、給學習線索、給關鍵任務入口；空白或「還在載入卻寫沒有記錄」會毀信任。通知：[NN/g 的 Indicators / Validations / Notifications](https://www.nngroup.com/articles/indicators-validations-notifications/) 主張 Toast 適合被動通知，**不適合**校驗或欄位錯（會在使用者改錯前消失）。[Carbon Notification](https://carbondesignsystem.com/components/notification/usage/) 把 Toast 寫成可超時的短訊息，預設可常駐，也可編成約 5 秒後消失，並要求超時後別處還能再讀；帶操作的 Toast 應等到使用者關掉。兩邊都留，不要併成一條家規。

命令面板：APG **沒有** Command Palette 專模。行業實現疊 [Dialog (Modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)（焦點困在層內，Escape 關，關閉後焦點回喚起處）+ [Listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/)（選項、鍵盤與 type-ahead）。[cmdk](https://github.com/pacocoursey/cmdk) 是 React 組合庫，不是 W3C 模式。

## 例子

- 正例：必填郵箱用原生 `type="email"` + 可見標籤；用 `:user-invalid` 在使用者改過或提交後再標紅；錯誤文字寫在欄位旁並用 `aria-describedby` 掛上。
- 正例：空收藏夾寫「還沒有收藏」+「去加一條」按鈕，不留白，也不在請求未完成時寫「沒有記錄」。
- 正例：快捷命令開啟模態對話方塊，選項走 listbox，Escape 關閉並把焦點還給喚起控制元件。
- 反例：用 `role="button"` 的 `div` 卻不提供鍵盤啟用（APG：角色是承諾）。
- 反例：把 COGA Note 或 XAG 勾完，寫成「已符合 WCAG」或「已滿足無障礙法規」。
- 反例：欄位校驗只彈 Toast；或把 cmdk 的外觀當成 APG 專模。

## 邊界與易混概念

- 本頁不是角色卡皮膚、不是「已採用」的元件庫，也不搬 WCAG / APG / COGA 全文。
- 視覺對比度、減少動效見 [[concepts/視覺CSS與設計token]] 的「無障礙底線」；本頁管合同分層與控制元件模式。
- APG ≠ WAI-ARIA 規範 ≠ WCAG。ARIA 給語義，APG 給用法，WCAG 給符合性。
- 包容設計方法 ≠ 通用設計「一份適配所有人」≠ WCAG 符合性宣告。
- Plain Language ≠ Easy Read ≠ COGA 目標/模式。
- GAG 分檔 ≠ XAG 護欄 ≠ APX 模式語言；XAG 自己否認法律清單身份。
- Toast ≠ 欄位校驗；Inline / Callout / Modal 各管不同打斷級別（Carbon 四分法）。
- 命令面板 ≠ Combobox 專模；無 APG 專條時是 Dialog+Listbox 的疊用。
- Easy Checks 遷址空殼、未核過的讀屏版本，不當現行驗收真源。
- 不寫攻擊或繞過輔助技術；不搬卡 JSON；不做成品皮膚。

## 必須保留的衝突

下列衝突不得靜默合併。檢索日 2026-08-14，賬本見 [[queries/第二批蒸餾目標]]、[[queries/第三批蒸餾目標]]。

1. **APG 是模式指南，不是規範；WCAG 2.2 才是 Rec。** 跟 APG 示例不能當成符合性證明。
2. **包容設計 ≠ 無障礙 ≠ 通用設計。** 方法、可測標準和「一份設計服務所有人」是三層。
3. **COGA Note 不構成 WCAG 符合性。** Content Usable 與補充模式是超出現行成功標準的指導。
4. **Plain Language ≠ Easy Read ≠ COGA。** 聯邦簡明語言、配圖易讀版、認知任務組目標不可互換。
5. **GAG / XAG / APX 三軸不可互換；XAG 不是法律合規清單。** XAG v3.2 正文自己這樣寫。
6. **NN/g 主張欄位錯勿用 Toast，Carbon 允許 Toast 超時。** 兩邊都留：欄位錯貼欄位；系統短訊息可否超時，按產品合同選，不要假裝行業已統一。
7. **命令面板：APG 無專模，疊 Dialog+Listbox。** cmdk 等庫是實現，不是缺失的那條 APG 模式。

## 對映到本倉庫

先按行業合同看三塊介面，不按「卡能不能用」刪方案。

**HUD / 覆蓋層。** 懸浮球、抽屜、浮窗是入口外殼，內容仍在控制中心或狀態列。覆蓋層要按 Dialog 管焦點：開啟時焦點進層，Tab 不漏到背後，關掉後還回去。跨文件 iframe 是獨立瀏覽上下文，框內焦點與讀屏樹到不了父頁；認窗見 [[concepts/酒館宿主與iframe分層]]。半透明玻璃和細字的對比度、大位移動效可關，只鏈 [[concepts/視覺CSS與設計token]]，不在本頁重寫。

**表單。** 設定項、篩選、嚮導都是表單：可見標籤、`:user-invalid`、欄位旁持久錯誤。Combobox 不要做成「看起來像搜尋、讀屏卻是一堆無角色的 div」。欄位錯走欄位，不走會消失的角標。

**空態。** 無收藏、無日誌、無篩選結果，要寫清「空 / 還在載入 / 出錯」，並給下一步。不要用載入中的「沒有記錄」騙走使用者。

角色卡只在這裡點名、不當過濾器：開局嚮導和授予者表是表單；控制中心設定是表單；狀態列空分頁是空態；若做命令面板，按 Dialog+Listbox 疊，不發明 APG 專模。細則見 [[concepts/開局頁路徑]]、[[concepts/控制中心與狀態列]]、[[concepts/入口外殼與HUD宿主]]。
