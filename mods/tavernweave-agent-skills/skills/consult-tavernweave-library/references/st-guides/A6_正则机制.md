## 1. 機制總覽

SillyTavern regex extension 是執行在客戶端 JS 層的文字變換管線。每條正則指令碼（regex script）是一個 JSON 物件，儲存於角色卡 `data.extensions.regex_scripts`（scoped）或 `settings.json`（global）。執行時，`getRegexedString()` 將所有匹配當前 placement + 上下文條件的指令碼**順序鏈式應用**，上一條的輸出是下一條的輸入。

**三類指令碼儲存位置：**

| 型別 | 儲存位置 | 生效範圍 |
|---|---|---|
| GLOBAL | `settings.json` | 對所有角色生效 |
| SCOPED | 角色卡 `data.extensions.regex_scripts` | 僅當前角色，需 `allowScopedScripts()` 顯式允許 |
| PRESET | API 預設 | 僅繫結該預設時生效 |

**執行順序：** Global → Scoped → Preset（順序鏈式，不併行）

> 原始碼訂正（草稿原寫 Global→Preset→Scoped，已更正）：`SCRIPT_TYPES = { GLOBAL: 0, PRESET: 2, SCOPED: 1 }`，`getRegexScripts()` 以 `Object.values(SCRIPT_TYPES).flatMap(...)` 遍歷——JS 對整數鍵按升序排列，實際順序為 GLOBAL(0) → SCOPED(1) → PRESET(2)。

來源：`[執行時原始碼]` engine.js `SCRIPT_TYPES` 列舉 + `getRegexScripts()` 實現 | 適用版本：v1.14.0 | **high** `[執行時原始碼]`

## 2. 欄位完整參考表

### 2.1 執行時欄位

| 欄位名 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `id` | string | 建議 | UUID 識別符號；缺失時自動生成 |
| `scriptName` | string | 是 | 顯示名稱；為空則無法儲存 |
| `findRegex` | string | 是 | 正則表示式字串，含旗標，格式 `/pattern/flags`；為空則不執行 |
| `replaceString` | string | 否 | 替換字串；支援 `$1`/`$2`... 捕獲組引用、`$<name>` 命名捕獲組引用、`{{match}}` 宏（內部轉為 `$0`）；**不支援** `$&`/`$$`/`` $` ``/`$'` 標準 JS 替換特殊模式（原始碼使用函式形式 replacer，這些符號不被 JS 特殊處理，當作字面量傳入 `substituteParams`） |
| `placement` | number[] | 是 | 作用域陣列（見第 3 章 placement 列舉）；至少一項否則不啟用 |
| `disabled` | boolean | 否 | true = 遮蔽自動執行（slash command 仍可手動觸發） |
| `markdownOnly` | boolean | 否 | true = 只在渲染顯示時執行（UI 對應 "Alter Chat Display"） |
| `promptOnly` | boolean | 否 | true = 只在發給模型的 prompt 時執行（UI 對應 "Alter Outgoing Prompt"） |
| `runOnEdit` | boolean | 否 | true = 使用者編輯訊息時也執行 |
| `substituteRegex` | number | 否 | 宏替換模式：0=不替換，1=原始替換，2=轉義替換（見第 6 章） |
| `minDepth` | number\|null | 否 | 最小樓層深度（0=最新一樓，null/-1=不限）；`depth < minDepth` 則跳過 |
| `maxDepth` | number\|null | 否 | 最大樓層深度；`depth > maxDepth` 則跳過；須 > minDepth 才生效 |
| `trimStrings` | string[] | 否 | 從**捕獲組匹配值**（$1/$2/... 的實際值）中逐一 replaceAll 刪除的字串列表；作用於每條捕獲組求值階段，而非整條 replaceString 完成後——**medium·單源孤證** `[執行時原始碼]`（僅 engine.js 可見，實際效果待真機驗證） |

來源：`[執行時原始碼]` engine.js | 適用版本：v1.14.0 | **high** `[執行時原始碼]`

### 2.2 元件庫構建元資料欄位（非執行時）

以下欄位僅存在於本工作區模組化元件庫的 `regex_object.json` 構建模板中，**不會進入 ST 執行時**，打包工具負責剝離：

| 欄位名 | 用途 |
|---|---|
| `field` | 標記 replaceString 由外部 HTML 檔案提供（如 `"field": "replaceString"`） |
| `replaceStringSource` | 指向提供 replaceString 內容的原始檔路徑 |

| `afterScriptName` | 排序提示：本指令碼須排在指定名稱的指令碼之後 |

示例（來自 `模組化元件/regex_suite/status_placeholder/regex_object.json`）：

```json
"field": "replaceString",
"replaceStringSource": "update_variable_omni_done_regex.html"
```

來源：`[本地實戰]` 模組化元件庫 | 適用版本：工作區內部 | **high** `[本地實戰]`

## 3. placement 列舉（作用域）

| 數值 | 名稱 | 觸發時機 |
|---|---|---|
| `0` | MD_DISPLAY | **已廢棄**，勿用 |
| `1` | USER_INPUT | 使用者傳送訊息後 |
| `2` | AI_OUTPUT | AI 回覆生成後 |
| `3` | SLASH_COMMAND | STscript slash command 返回值 |
| `5` | WORLD_INFO | 世界書條目注入；**必須同時設 `promptOnly: true`**，否則不啟用（world-info.js 硬編碼傳入 `{ isMarkdown: false, isPrompt: true }`，預設兩者均 false 的指令碼在此路徑不滿足啟用條件） |
| `6` | REASONING | AI 推理塊（Gemini / Deepseek 等推理 API） |

來源：`[執行時原始碼]` engine.js `export const regex_placement` | 適用版本：v1.14.0 | **high** `[執行時原始碼]`

> 避坑：`placement: []`（空陣列）= 指令碼永遠不自動觸發，只能透過 slash command 手動呼叫。本地實戰卡均用 `[2]`（AI 輸出）。
>
> `MD_DISPLAY (0)` 標記為 deprecated，原始碼未完全移除，舊卡含此值時的實際行為不確定——**low** `[推斷]`，新卡停用。

## 4. markdownOnly / promptOnly / Ephemerality 三態邏輯

這是本機制最易混淆的核心。

**UI 欄位對應關係（關鍵）：**

- UI 中的 "Alter Chat Display" = `markdownOnly: true`
- UI 中的 "Alter Outgoing Prompt" = `promptOnly: true`

來源：`[執行時原始碼]` engine.js 啟用條件邏輯 | **high** `[執行時原始碼]`

**原始碼啟用條件：**

```javascript
(script.markdownOnly && isMarkdown) ||
(script.promptOnly && isPrompt) ||
(!script.markdownOnly && !script.promptOnly && !isMarkdown && !isPrompt)
```

**四種組合語義：**

| `markdownOnly` | `promptOnly` | 含義 | 寫回 JSONL |
|---|---|---|---|
| false | false | **預設**：永久寫入聊天記錄；顯示和 prompt 均改變 | 是 |
| true | false | **只改顯示**（Alter Chat Display）：僅影響 markdown 渲染 | 否 |
| false | true | **只改 prompt**（Alter Outgoing Prompt）：僅影響發給模型的內容 | 否 |
| true | true | **完全臨時**：顯示和 prompt 均改變，但不寫檔案——**medium·推導未驗證** `[推斷]`（見下方注） | 否（中等置信） |

> 注：`markdownOnly: true, promptOnly: true` 雙 true 的"完全臨時"行為，其 JSONL 不寫回的確切觸發邏輯（isSend/saveMessage 呼叫層）在 engine.js 中未直接體現，可能在 chat.js 上層處理。實際行為待真機驗證。——**medium** `[文件·多源] + [推斷]`

**實戰含義：**

- 卡A / 卡B所有美化正則（狀態列、氣泡、OMNI-NEXUS wrap）均設 `markdownOnly: true, promptOnly: false`：隻影響顯示，不汙染模型上下文。
- 卡B的 prompt 清理正則（`promptOnly: true`）：從歷史樓層裁剪變數塊，隻影響發給模型的內容，使用者介面不變。

來源：`[本地實戰]` 卡A 3.0.2 + 卡B v2.0.9 | **high** `[本地實戰]`

## 5. 深度過濾（minDepth / maxDepth）

深度值 = 訊息在歷史中的位置，**0 = 最新一樓，數值越大越舊**。

**原始碼邏輯（引自 engine.js）：**

```javascript
if (typeof depth === 'number') {
    if (!isNaN(script.minDepth) && script.minDepth !== null &&
        script.minDepth >= -1 && depth < script.minDepth) {
        return; // 跳過
    }
    if (!isNaN(script.maxDepth) && script.maxDepth !== null &&
        script.maxDepth >= 0 && depth > script.maxDepth) {
        return; // 跳過
    }
}
```

**常用值語義：**

| 值 | 含義 |
|---|---|
| `minDepth: null` 或 `-1` | 無下限，對所有樓層生效（含 Continue 追加的訊息） |
| `minDepth: 0` | 從最新樓開始，實際等效於對所有樓層生效 |
| `minDepth: 6` | 只對第 6 樓以深（較舊）的訊息生效 |
| `maxDepth: null` | 無上限，對所有歷史樓層生效 |
| `maxDepth: 3` | 只對最新 4 樓（深度 0-3）生效 |

**實戰用例：** 卡B清理正則設 `minDepth: 6`，只清理發給模型的 prompt 中第 6 樓以深的舊變數塊，減少 token 消耗，同時不影響介面顯示。

來源：`[執行時原始碼]` engine.js + `[本地實戰]` 卡B v2.0.9 | 適用版本：v1.14.0 | **high** `[執行時原始碼]`

> 懸案：`minDepth: -1` 對 Continue 追加內容的深度計算方式待驗證——**medium** `[推斷]`，見第 10 章。

## 6. substituteRegex 宏替換模式

控制 `findRegex` 欄位中宏（如 `{{user}}`）的處理方式：

| 值 | 名稱 | 行為 |
|---|---|---|
| `0` | NONE | 宏當作字面量，不替換（**絕大多數場景用此值**） |
| `1` | RAW | 直接插入宏值（宏值含正則特殊字元會破壞 pattern，危險） |
| `2` | ESCAPED | 先 escape 宏值中的正則元字元再插入（安全） |

來源：`[執行時原始碼]` engine.js `substitute_find_regex` enum | 適用版本：v1.14.0 | **high** `[執行時原始碼]`

> 避坑：若要在 `findRegex` 中動態嵌入 `{{user}}` 等宏值，用 `2`（escaped），不要用 `1`（raw）——角色名可能含正則元字元（如括號、點號）導致 pattern 語法錯誤。

## 7. 生產正規化程式碼

以下所有正規化均來自本地成熟卡，經實際執行驗證。

### 7.1 正規化 A：AI 輸出美化——XML 標籤替換為 HTML 渲染塊

將 AI 輸出中的 `<analysis>...</analysis>` 替換為前端元件掛載點，僅影響顯示。

```json
{
  "id": "xingyue-analysis-done-omni-nexus",
  "scriptName": "[美化]變數預分析-OMNI-NEXUS v3.0.2",
  "findRegex": "/<analysis>\\s*((?:(?!<\\/?analysis>[\\s\\S])*?)\\s*<\\/analysis>/gi",
  "replaceString": "<div class=\"xy-omni-mount\" data-xy-omni=\"analysis\"><div class=\"xy-omni-raw\" data-xy-omni-raw style=\"...\">$1</div></div>\n",
  "placement": [2],
  "disabled": false,
  "trimStrings": [],
  "markdownOnly": true,
  "promptOnly": false,
  "runOnEdit": false,
  "substituteRegex": 0,
  "minDepth": 0,
  "maxDepth": null
}
```

來源：`[本地實戰]` 示例學園 MVU 3.0.2.json | **high** `[本地實戰]`

### 7.2 正規化 B：流式進行中（無閉合標籤）美化

流式輸出時 AI 尚未生成閉合標籤，用負向前瞻匹配**未閉合**的開放標籤，提供流式進度展示。

```json
{
  "id": "xingyue-sync-progress-omni-nexus",
  "scriptName": "[美化]變數同步中-OMNI-NEXUS",
  "findRegex": "/<UpdateVariable(?:variable)?>(?![\\s\\S]*<\\/UpdateVariable(?:variable)?>)\\s*([\\s\\S]*)$/gi",
  "replaceString": "<div class=\"xy-omni-mount\" data-xy-omni=\"progress\">...$1...</div>\n",
  "placement": [2],
  "markdownOnly": true,
  "promptOnly": false,
  "runOnEdit": false,
  "substituteRegex": 0,
  "minDepth": 0,
  "maxDepth": null
}
```

關鍵技巧：`(?![\s\S]*<\/UpdateVariable>)` 負向前瞻確保只匹配**未閉合**的標籤（流式中間狀態）。

> 配套說明：正規化 B（流式中）與正規化 A 的閉合版本須並存。閉合版的貪婪匹配用 `[\s\S]*?`（惰性），避免跨塊吞掉其他內容。兩條指令碼缺一會導致流式過程中或完成後顯示異常。

來源：`[本地實戰]` 卡A 3.0.2 + 卡B v2.0.9 | **high** `[本地實戰]`

### 7.4 正規化 D：佔位符插入——多步正則聯動

狀態列渲染需要兩步：先在變數塊旁插入佔位符，再將佔位符替換為真實 HTML 元件。ST 按陣列順序序列執行，順序必須正確。

步驟 1（插入佔位，須排在步驟 2 之前）：

```json
{
  "scriptName": "[顯示]變數更新狀態列佔位",
  "findRegex": "/(?:<StatusPlaceHolderImpl\\s*\\/>\\s*)*(<UpdateVariable(?:variable)?>\\s*[\\s\\S]*?\\s*<\\/UpdateVariable(?:variable)?>)(?:\\s*<StatusPlaceHolderImpl\\s*\\/>)*/gi",
  "replaceString": "<StatusPlaceHolderImpl/>\n$1\n",
  "placement": [2],
  "markdownOnly": true,
  "promptOnly": false,
  "minDepth": 0,
  "maxDepth": null
}
```

步驟 2（替換佔位為真實元件，須排在步驟 1 之後）：

```json
{
  "scriptName": "狀態列美化 HUD",
  "findRegex": "/<StatusPlaceHolderImpl\\s*\\/>/g",
  "replaceString": "```html\n<!doctype html>...\n```\n",
  "placement": [2],
  "markdownOnly": true,
  "promptOnly": false
}
```

> 排序注意：元件庫構建元資料欄位 `beforeScriptName` / `afterScriptName` 是打包工具的排序提示，非執行時欄位。打包後腳本陣列順序即為執行順序，需人工或工具確認正確性。

來源：`[本地實戰]` 模組化元件庫 `regex_suite/status_placeholder/regex_object.json` + 打包卡 | **high** `[本地實戰]`

## 8. 執行管線時序

```
使用者傳送 / AI 回覆生成
        ↓
getRegexedString(rawString, placement, { characterOverride, isMarkdown, isPrompt, isEdit, depth })
        ↓
getRegexScripts({ allowedOnly: true })
  →  Object.values(SCRIPT_TYPES) 順序：GLOBAL(0) → SCOPED(1) → PRESET(2)
  →  flatMap 展開為指令碼合集
        ↓
per script: 過濾檢查（但注意：placement 檢查在最後）
  1. (markdownOnly && isMarkdown) ||
     (promptOnly && isPrompt) ||
     (兩者均 false && isMarkdown=false && isPrompt=false)?
     （不滿足任一 → 直接跳過，不再檢查後續條件）
  2. runOnEdit=false && isEdit=true → 跳過
  3. depth 在 [minDepth, maxDepth] 內?
  4. script.placement.includes(placement)?
     （最後檢查 placement，而非最先）
        ↓ 四道全透過
runRegexScript(script, currentString)
  1. substituteRegex 處理 findRegex 中的宏
  2. regexFromString(regexString) 將字串編譯為 RegExp
     （注：v1.14.0 engine.js 中無 RegexProvider/LRU cache，
      草稿原描述有誤；每次直接呼叫 regexFromString）
  3. String.replace(regex, replacerFn)
     - replaceString 中的 {{match}} → $0（字面替換為 $0 字串，再由 JS replace 解析）
     - $1/$2/... 及 $<name> 命名捕獲組替換
     - 每條捕獲組值在求值時經 filterString(match, trimStrings) 過濾
       （trimStrings 作用於各捕獲組的匹配值，非整體 replaceString 結果）
  4. substituteParams(replaceWithGroups) 處理宏替換
  5. 返回變換後字串
        ↓
下一條指令碼的輸入 = 上一條輸出
        ↓
最終字串
```

> 訂正說明：①執行順序為 Global→Scoped→Preset（非原寫 Global→Preset→Scoped）；②無 RegexProvider/LRU cache，為草稿虛構內容，已刪除；③trimStrings 作用於捕獲組值，非整體結果；④placement 檢查位於四道關最後，不是第一道。

來源：`[執行時原始碼]` engine.js `getRegexedString` + `runRegexScript` 逐行閱讀 | 適用版本：v1.14.0 | **high** `[執行時原始碼]`

## 9. 高頻避坑

1. **`placement` 必須至少一個值**——空陣列 = 指令碼永遠不自動觸發（只能 slash command 手動調）。實戰卡均用 `[2]`（AI 輸出）。
   來源：`[執行時原始碼]` | **high**

2. **`markdownOnly: true` 的替換結果不會寫回 JSONL**——在做介面美化時安全；若要讓模型在下一輪看到替換結果，必須改用預設（兩者均 false），或用 `promptOnly: true`。
   來源：`[執行時原始碼]` script.js 呼叫架構（isMarkdown=true 僅在渲染路徑呼叫，寫回 JSONL 發生在獨立的儲存流程，不受 getRegexedString 結果影響）+ `[本地實戰]` 卡A/卡B生產驗證 | **high** `[執行時原始碼] + [本地實戰]`

3. **多指令碼順序依賴**——佔位符先插再替換的兩步正規化，必須保證陣列順序，ST 按索引順序序列執行。構建工具的 `beforeScriptName`/`afterScriptName` 排序提示在打包時生效，需校驗最終陣列順序。
   來源：`[本地實戰]` + `[執行時原始碼]` | **high**

4. **流式中間狀態的正則必須成對**——`progress` 正則（無閉合標籤）和 `done` 正則（有閉合標籤）須並存；`done` 正則的貪婪匹配要用 `[\s\S]*?`（惰性），避免跨塊吞掉其他內容。
   來源：`[本地實戰]` | **high**

5. **`minDepth: null` vs `minDepth: 0` 的區別**——`null` 無限制對所有樓層生效（含 Continue 追加）；`0` 從最新樓開始，實際上也對所有樓層生效。要限制只對舊樓生效，用較大的 `minDepth`（如 6）。
   來源：`[執行時原始碼]` | **high**

6. **`substituteRegex` 推薦用 `0` 或 `2`，停用 `1`**——絕大多數場景用 `0`（不替換宏）；需動態嵌入 `{{user}}` 等宏值時用 `2`（escaped），不要用 `1`（raw），因角色名可能含正則元字元。
   來源：`[執行時原始碼]` | **high**

7. **`MD_DISPLAY` (placement=0) 已廢棄**——現存舊卡可能含此值，新卡不要用，廢棄後的實際行為不確定。
   來源：`[執行時原始碼]` 標註 | **medium** `[執行時原始碼]`（實際副作用為 **low** `[推斷]`）

8. **`runOnEdit: true` + `promptOnly: true` 聯合使用**——如卡B清理正則，確保使用者編輯歷史訊息時 prompt 也被清理。`markdownOnly: true` 的指令碼通常不需要 `runOnEdit: true`，因編輯後重新渲染會自動觸發 markdown 路徑。
   來源：`[本地實戰]` 卡B v2.0.9 | **high** `[本地實戰]`

9. **`trimStrings` 是捕獲組值內過濾**——作用於每個 `$1`/`$2`/... 捕獲組的**實際匹配值**（在 `filterString()` 中 replaceAll），而非作用於整條 `replaceString` 完成後的最終結果。若 replaceString 中無捕獲組引用（$1/$2），trimStrings 實際無效。本地實戰卡均為空陣列 `[]`（不需要）。
   來源：`[執行時原始碼]` engine.js `runRegexScript` 實現 | **medium·單源孤證** `[執行時原始碼]`（描述已訂正；原 high 降級：草稿原描述有誤，且實際邊界行為未真機驗證）

10. **Scoped regex 在群聊中無法透過 UI 編輯**——index.js 原始碼顯示，在 `selected_group` 為真時，UI 層對"新增/編輯/批次操作 Scoped 指令碼"均彈出 toastr.error 並阻止。但**執行層**（engine.js `getScriptsByType(SCOPED)` + `allowedOnly` 檢查）完全依賴 `character_allowed_regex` 的 avatar 列表，與是否群聊無關——若 avatar 已在白名單且存在 scoped 指令碼，群聊中也會執行。"群聊預設停用"的說法**不準確**，應改為"群聊中 UI 禁止編輯 Scoped 指令碼（執行准入仍由 avatar 白名單控制，不由群聊狀態決定）"。
    來源：`[執行時原始碼]` index.js `selected_group` 檢查 + engine.js `getScriptsByType` 實現 | **medium·推導未驗證** `[執行時原始碼]`（執行路徑從原始碼推導；群聊中 Scoped 指令碼是否實際執行待真機驗證）
