## 1. 定義與主鏈

### 1.1 一句話定義

**資料庫二創前端**是在正常多樓層角色卡中，以 SP·資料庫儲存的表格為狀態後端，把人物、揹包、任務、關係、地圖或經營資料呈現為作品專屬狀態列、控制中心或訊息內面板的前端。

它在體驗上近似“資料庫版的 MVU 狀態列/控制中心”，但這只是產品形態類比：

- 資料來自 SP·資料庫的 `mate`、`sheet_*` 和 `content`；
- 讀寫入口是執行時提供的 `AutoCardUpdaterAPI`；
- 不讀取 MVU 的 `stat_data`；
- 不使用 MVU 的變數更新協議；
- 不把二維表資料偽裝成另一套變數樹。

### 1.2 正常遊玩的權威主鏈

本冊只討論以下常規鏈路：

```text
玩家在 ST 正常傳送訊息
        ↓
ST 呼叫模型並生成一條真實 AI 回覆樓層
        ↓
SP·資料庫在 AI 回覆後按自身配置觸發填表
        ↓
資料庫完成或提交本輪表格變更
        ↓
狀態列 / 控制中心重新讀取資料庫並渲染
        ↓
玩家繼續下一輪正常聊天
```

這裡有三個不可打亂的事實：

1. **劇情正文屬於真實 AI 回覆樓層。**資料庫前端不是劇情正文的替代品。
2. **資料庫填表發生在正常回復鏈之後或其配置的生命週期點。**前端只能觀察與呈現狀態，不能假定資料庫先於回覆產出完整樓層資訊。
3. **下一輪仍由 ST 正常聊天推進。**前端不得把對話主鏈改造成只在面板內部迴圈的私有協議。

### 1.3 C7 可以負責什麼

- 顯示當前資料庫狀態；
- 在表更新後重新整理區域性 UI；
- 提供經約束的玩家編輯入口；
- 展示載入、填表中、儲存中、衝突、失敗和空資料狀態；
- 將二維錶轉換為作品可消費的 domain model；
- 為人物、揹包、任務、關係等系統提供統一查詢與渲染層；
- 在訊息 iframe 或長生命週期宿主指令碼中安全接入資料庫 API。

### 1.4 C7 不負責什麼

- 不生成、替代、隱藏或映象劇情樓層；
- 不接管 ST 的玩家輸入、模型生成、Swipe、訊息樹或聊天曆史；
- 不承諾產出劇情正文、選項、路由、樓層號等完整應用協議；
- 不把外掛的內部物件直接暴露給每一個 UI 元件；
- 不用直接陣列突變冒充持久化；
- 不把一次已核原始碼快照寫成永久版本真相。

### 1.5 最小成立條件

一個前端要稱為資料庫二創前端，至少滿足：

- 以 SP·資料庫當前聊天的表資料為權威狀態；
- 透過公開 API 或經專案明確審計的相容層讀取資料；
- 透過公開 CRUD/SQL 能力寫回，不直接修改活動引用；
- 有明確表契約、業務主鍵和失敗重讀策略；
- 能在真實多樓層聊天中隨回覆與填表更新；
- 外掛缺失、能力不足或表結構不相容時能降級，而不是靜默顯示舊資料。

## 2. 與資料庫模板、MVU 前端及實驗路線的邊界

### 2.1 C4 與 C7 的職責

| 指南 | 回答的問題 | 主要交付物 |
|---|---|---|
| [C4 資料庫表格模板](./C4_資料庫表格模板.md) | 資料庫表怎樣設計、填表、約束和維護 | `mate`、`sheet_*`、列頭、填表規則、資料規範 |
| 本冊 C7 | 已有資料庫怎樣被做成玩家可用的作品級 UI | adapter、store、元件、互動、回撥、寫回與驗收 |

推薦順序：先用 C4 穩定資料契約，再用 C7 消費該契約。前端不能用 CSS 掩蓋表結構不穩定，也不能靠猜列名補救沒有版本管理的資料模型。

### 2.2 與 MVU 前端的類比只能停在體驗層

兩者可以擁有相似產品元件：

| 體驗元件 | MVU 前端 | 資料庫二創前端 |
|---|---|---|
| 狀態列 | 讀取 MVU 變數 | 讀取資料庫表 |
| 控制中心 | 呼叫 MVU 變數鏈寫回 | 呼叫資料庫 CRUD/SQL 寫回 |
| 訂閱更新 | MVU 對應事件 | 資料庫 table-update callback |
| 資料模型 | 路徑化變數樹 | 多張二維表及元資料 |
| 持久化邊界 | MVU 執行時 | 資料庫外掛執行時 |

因此可以說“資料庫版 MVU 前端”，但不能把它實現為 MVU：

```text
錯誤：UI → stat_data → JSONPatch
正確：UI → domain adapter → AutoCardUpdaterAPI → SP·資料庫
```

### 2.3 資料庫相容同層是另一條待驗證路線

SP·資料庫的常規公開表能力沒有為完整同層應用提供劇情正文、選項、路由和樓層資訊輸出契約。把資料庫狀態 UI 直接等同於完整同層應用，會遺漏真實回覆、樓層生命週期和生成主鏈。

相關設想單獨見 [C8 資料庫相容同層前端（待驗證）](./C8_資料庫相容同層前端-待驗證.md)。C8 是實驗路線，不是本冊的常規相容模式；在真機鏈路完成前，不應寫進 C7 的成熟能力清單。

## 3. 動態版本政策

### 3.1 為什麼不能寫死外掛基線

SP·資料庫仍在更新。標籤編號、提交時間和展示名稱不是一個可永久排序的版本字串：2026-07-14 查詢公開倉庫時，`spv7.9` 的建立時間為 2026-07-12，而編號更大的 `spv8.2` 創建於 2026-07-10。只比較數字會得出錯誤的“最新版本”。

本冊禁止：

- 宣稱某個 tag 永久最新；
- 只憑 `display_name` 或 manifest `version` 判斷 API；
- 因為 CDN URL 中有版本號，就把所有行為永久繫結到該版本；
- 未檢測方法存在便呼叫新 API；
- 用一次原始碼核驗替代每次釋出前的執行時迴歸。

### 3.2 三層相容策略

#### 第一層：最低能力契約

C7 的跨版本主鏈只依賴一組最小能力：

```text
讀取：exportTableAsJson
訂閱：registerTableUpdateCallback + unregisterTableUpdateCallback
寫入：updateCell / updateRow / insertRow / deleteRow（僅編輯型 UI 必需）
```

只讀狀態列可以只要求讀取與訂閱；編輯型控制中心還必須檢測 CRUD。

#### 第二層：已核原始碼快照

本冊記錄兩組可複核證據，而不是把它們當永久唯一基線：

| 核驗日期 | 快照 | 用途 |
|---|---|---|
| 歷史樣本 | tag `spv5.5.6`，commit `2020b14c0672e74409a3d98c8a9899e13069ca3f` | 精確核驗核心資料、CRUD、callback、lock、SQL 公開實現 |
| 2026-07-14 | `main` / tag `test10`，commit `708e66ba58dfe0a08d34cba7cb8730a8f8ff1e80` | 檢查近期主幹；manifest `display_name` 為 `SP·資料庫 VII` |

本輪原始碼差異檢查中，C7 使用的核心 export、CRUD、callback、lock API 仍存在，主幹同時增加了其他 API 組。這個結論只對表中快照負責。

#### 第三層：執行時能力檢測

真正執行時不問“你叫哪個版本”，而問“當前物件有沒有所需能力”。但要區分兩件事：API 方法有沒有掛載，以及當前 storage provider 是否真的允許使用該能力。已核快照會在原生模式也掛載 SQL 方法，原生 provider 呼叫時才返回失敗，因此 SQL 不能只靠 `typeof` 判定：

```js
function detectDatabaseCapabilities(api) {
  return {
    read: typeof api?.exportTableAsJson === 'function',
    subscribe:
      typeof api?.registerTableUpdateCallback === 'function' &&
      typeof api?.unregisterTableUpdateCallback === 'function',
    crud: ['updateCell', 'updateRow', 'insertRow', 'deleteRow']
      .every(name => typeof api?.[name] === 'function'),
    fillStart: typeof api?.registerTableFillStartCallback === 'function',
    manualFill: typeof api?.triggerUpdate === 'function',
    locks: typeof api?.getTableLockState === 'function',
    sqlApiPresent:
      typeof api?.querySql === 'function' &&
      typeof api?.executeSqlMutation === 'function',
  };
}

async function probeDatabaseCapabilities(api) {
  const capabilities = detectDatabaseCapabilities(api);
  if (!capabilities.sqlApiPresent) {
    return { ...capabilities, sqliteReady: false };
  }

  try {
    // 只做無副作用的只讀探針；原生 provider 在已核快照中會返回 null。
    const result = await api.querySql('SELECT 1 AS ok');
    const sqliteReady = Boolean(
      result &&
      Array.isArray(result.rows) &&
      Number(result.rows[0]?.ok) === 1,
    );
    return { ...capabilities, sqliteReady };
  } catch {
    return { ...capabilities, sqliteReady: false };
  }
}
```

產品應按能力降級：

- 沒有 `read`：顯示依賴缺失，停止初始化；
- 有 `read`、無 `subscribe`：允許手動重新整理，禁止宣稱即時；
- 無 `crud`：進入只讀模式；
- 無 `locks`：隱藏鎖 UI；
- `sqlApiPresent=false` 或 `sqliteReady=false`：關閉全部 SQL UI，繼續使用通用 export + CRUD 主鏈；
- 出現未知新 API：預設不用，先審計再接入。

### 3.3 釋出時儲存能力報告

建議在開發日誌中儲存：

```js
async function logDatabaseCapabilities(api) {
  console.table({
    checkedAt: new Date().toISOString(),
    ...await probeDatabaseCapabilities(api),
  });
}
```

能力報告只用於診斷，不應上傳玩家的表資料、聊天內容或鑑權資訊。

## 4. 分層架構

### 4.1 推薦五層

```text
┌──────────────────────────────────────┐
│ View：人物卡、揹包、任務、關係、地圖 │
├──────────────────────────────────────┤
│ Store：載入、就緒、填表、儲存、衝突  │
├──────────────────────────────────────┤
│ Domain：Character / Item / Quest     │
├──────────────────────────────────────┤
│ Adapter：表契約、歸一化、主鍵、寫回  │
├──────────────────────────────────────┤
│ Host：AutoCardUpdaterAPI             │
└──────────────────────────────────────┘
```

### 4.2 唯一允許的資料方向

```text
讀取：Host API → clone → adapter → domain → store → view
寫入：view intent → validator → adapter → Host CRUD/SQL → re-read
通知：Host callback → schedule refresh → clone → adapter → store
```

禁止：

```text
view → 直接改 content
元件 A → 自己猜表頭
元件 B → 長期快取 rowIndex
回撥引數 → 原地排序或 splice
儲存成功 → 只改本地 store、不重讀資料庫
```

### 4.3 UI 臨時狀態不進業務表

標籤頁、摺疊狀態、搜尋詞、排序方式、彈窗開關、滾動位置屬於前端臨時狀態。除非它們本身是角色卡規則的一部分，否則不應寫入資料庫業務表。

## 5. API 宿主發現與能力檢測

### 5.1 不要假設 API 一定在當前 window

訊息內容經常運行於 iframe。已核原始碼快照把 API 掛到宿主視窗；從同源訊息 iframe 接入時，常見入口是 `window.parent.AutoCardUpdaterAPI`，而外掛或宿主指令碼中也可能直接使用當前 `window.AutoCardUpdaterAPI`。

跨域訪問可能拋異常，因此查詢必須防禦式執行：

```js
function findDatabaseHost(start = window) {
  const candidates = [];

  try { candidates.push(start); } catch {}
  try { if (start.parent && start.parent !== start) candidates.push(start.parent); } catch {}
  try { if (start.top && !candidates.includes(start.top)) candidates.push(start.top); } catch {}

  for (const candidate of candidates) {
    try {
      if (candidate?.AutoCardUpdaterAPI) {
        return { hostWindow: candidate, api: candidate.AutoCardUpdaterAPI };
      }
    } catch {
      // 跳過不可訪問的視窗層級。
    }
  }

  return null;
}
```

### 5.2 有界等待 API 與資料

訊息 DOM 出現不代表外掛 API 與當前聊天資料已經就緒：

```js
async function waitForDatabase({ timeoutMs = 10_000, intervalMs = 100 } = {}) {
  const deadline = Date.now() + timeoutMs;

  while (Date.now() < deadline) {
    const host = findDatabaseHost();
    const api = host?.api;

    if (typeof api?.exportTableAsJson === 'function') {
      const raw = api.exportTableAsJson();
      if (raw && typeof raw === 'object' && Object.keys(raw).length > 0) {
        return host;
      }
    }

    await new Promise(resolve => setTimeout(resolve, intervalMs));
  }

  throw new Error('資料庫 API 或當前聊天表資料在限定時間內未就緒');
}
```

超時應呈現“資料庫尚未就緒/請檢查外掛與表配置”，不能無限轉圈。

### 5.3 不要把 API 物件永久快取到訊息 iframe

切換聊天、過載擴充套件或重建訊息 iframe 後，舊引用可能過期。短生命週期檢視應在 mount 時發現宿主，在 unmount 時登出回撥；長生命週期 bridge 則在聊天切換後重新讀取並廣播新快照。

## 6. 表契約與只讀快照

### 6.1 頂層結構

已核快照中，匯出物件通常包含：

```text
mate
sheet_0
sheet_1
...
```

業務表一般位於 `sheet_*`，每張表包含 `name` 與二維 `content`。不要把物件列舉順序當業務順序；優先使用穩定 `sheetKey`。

### 6.2 二維 content

```js
const content = [
  ['row_id', '角色ID', '姓名', '生命值'], // rowIndex 0：表頭
  ['1', 'char_001', '莉莉', '82'],        // rowIndex 1：第一條資料
  ['2', 'char_002', '阿爾法', '67'],      // rowIndex 2：第二條資料
];
```

關鍵約束：

- `content[0]` 是表頭；
- 已核模板把 `row_id` 放在第 0 列；它是資料庫物理標識，不代替作品業務主鍵；
- 第一條資料的資料庫 `rowIndex` 是 `1`；
- `content.slice(1)` 的陣列下標 `0` 不能直接傳給 CRUD；
- 單元格可能為空、數字字串、JSON 字串或普通文字；
- 表頭重名、空表頭和缺失必需列必須在 adapter 層報錯。

### 6.3 export 返回值按活動引用處理

歷史已核原始碼中，`exportTableAsJson()` 直接返回當前活動表物件，而不是深複製。即使未來版本改變實現，前端仍應把返回值視為只讀，並立即 clone/歸一化：

```js
function cloneSnapshot(value) {
  if (typeof structuredClone === 'function') {
    return structuredClone(value ?? {});
  }
  return JSON.parse(JSON.stringify(value ?? {}));
}

function readSnapshot(api) {
  return cloneSnapshot(api.exportTableAsJson());
}
```

直接寫 `raw.sheet_0.content[1][2] = 100` 不等於呼叫了外掛持久化，也可能汙染外掛當前記憶體狀態。

### 6.4 表契約必須顯式宣告

```js
const TABLE_CONTRACTS = {
  characters: {
    sheetKey: 'sheet_0',
    nameHint: '角色表',
    primaryKey: '角色ID',
    requiredHeaders: ['row_id', '角色ID', '姓名', '生命值'],
  },
  inventory: {
    sheetKey: 'sheet_1',
    nameHint: '揹包表',
    primaryKey: '物品ID',
    requiredHeaders: ['row_id', '物品ID', '名稱', '數量'],
  },
};
```

建議校驗：

- `sheetKey` 存在且為 `sheet_*`；
- `content` 是二維陣列；
- 表頭非空、無重複；
- 必需列齊全；
- 主鍵列每行非空且唯一；
- 數值列可解析且範圍合理；
- 表名提示僅用於報錯，不代替穩定 key。

## 7. 歸一化 adapter

### 7.1 通用歸一化

```js
function assertTable(raw, contract) {
  const table = raw?.[contract.sheetKey];
  if (!table) throw new Error(`缺少表：${contract.sheetKey}`);
  if (!Array.isArray(table.content)) throw new Error(`${contract.sheetKey}.content 不是陣列`);
  if (!Array.isArray(table.content[0])) throw new Error(`${contract.sheetKey} 缺少表頭`);

  const headers = table.content[0].map(value => String(value ?? '').trim());
  const duplicates = headers.filter((value, index) => value && headers.indexOf(value) !== index);
  if (headers.some(value => !value)) throw new Error(`${contract.sheetKey} 存在空表頭`);
  if (duplicates.length) throw new Error(`${contract.sheetKey} 存在重複表頭：${[...new Set(duplicates)].join('、')}`);

  const missing = contract.requiredHeaders.filter(header => !headers.includes(header));
  if (missing.length) throw new Error(`${contract.sheetKey} 缺少列：${missing.join('、')}`);

  const rows = table.content.slice(1).map((cells, index) => {
    const values = Array.isArray(cells) ? cells : [];
    const record = Object.fromEntries(headers.map((header, col) => [header, values[col] ?? '']));
    return {
      rowIndex: index + 1,
      record,
    };
  });

  const seen = new Set();
  for (const row of rows) {
    const key = String(row.record[contract.primaryKey] ?? '').trim();
    if (!key) throw new Error(`${contract.sheetKey} 第 ${row.rowIndex} 行缺少業務主鍵`);
    if (seen.has(key)) throw new Error(`${contract.sheetKey} 業務主鍵重複：${key}`);
    seen.add(key);
  }

  return {
    sheetKey: contract.sheetKey,
    name: String(table.name ?? contract.nameHint ?? contract.sheetKey),
    headers,
    rows,
  };
}
```

### 7.2 轉換為 domain model

```js
function toInteger(value, fallback = 0) {
  const number = Number.parseInt(String(value ?? ''), 10);
  return Number.isFinite(number) ? number : fallback;
}

function buildCharacterDomain(snapshot) {
  const table = assertTable(snapshot, TABLE_CONTRACTS.characters);

  return table.rows.map(({ rowIndex, record }) => ({
    id: String(record['角色ID']).trim(),
    name: String(record['姓名'] || '未命名'),
    hp: toInteger(record['生命值']),
    source: {
      sheetKey: table.sheetKey,
      observedRowIndex: rowIndex,
    },
  }));
}
```

`observedRowIndex` 只供顯示與診斷，不能成為長期寫回地址。

### 7.3 一次重新整理只匯出一次

```js
function buildDomainSnapshot(api) {
  const snapshot = readSnapshot(api);
  return {
    characters: buildCharacterDomain(snapshot),
    inventory: buildInventoryDomain(snapshot),
    readAt: Date.now(),
  };
}
```

所有元件消費同一份 domain snapshot，避免一幀內多次 export 得到交錯狀態。

## 8. 回撥與填表生命週期

### 8.1 table-update 必須同引用登出

已核快照公開：

```js
api.registerTableUpdateCallback(callback);
api.unregisterTableUpdateCallback(callback);
```

登出時必須傳入註冊時的同一個函式引用：

```js
function mountDatabaseView(api, refresh) {
  let queued = false;

  const onTableUpdate = () => {
    if (queued) return;
    queued = true;
    queueMicrotask(() => {
      queued = false;
      refresh();
    });
  };

  api.registerTableUpdateCallback(onTableUpdate);
  refresh();

  return () => api.unregisterTableUpdateCallback(onTableUpdate);
}
```

錯誤示例：

```js
api.registerTableUpdateCallback(() => refresh());
api.unregisterTableUpdateCallback(() => refresh()); // 不是同一個函式，登出失敗
```

### 8.2 fill-start 不能在短生命週期視圖裡隨意註冊

歷史快照公開了 `registerTableFillStartCallback(callback)`，但沒有對應的公開登出方法。若每次重繪訊息 iframe 都註冊一個新閉包，可能累積監聽和重複渲染。

安全順序：

1. 優先只依賴可成對登出的 table-update；
2. 確需填表開始狀態時，由長生命週期宿主 bridge 最多註冊一次；
3. bridge 再用專案自己的可退訂事件分發給檢視；
4. 外掛未來若新增公開登出能力，先做能力檢測與真機驗證，再接入。

### 8.3 沒有公開 fill-end 回撥

已核快照沒有 `registerTableFillEndCallback()`。table-update 也不能無條件視為填表結束，因為更新可能來自：

- AI 自動填表；
- 玩家 CRUD；
- SQL 寫入；
- 匯入、過載或其他外掛操作；
- 一次任務中的多次提交。

因此 store 應區分：

```text
filling：觀察到填表開始，但結束語義未知
refreshing：收到任意更新，正在重讀
ready：重讀和表契約校驗完成
stale：超過專案設定時間仍無可確認結果
error：重讀或校驗失敗
```

不要顯示“AI 填表已完成”，除非當前執行時確實提供並驗證了對應訊號。

### 8.4 triggerUpdate 的返回值要歸一化

`triggerUpdate` 屬於版本敏感能力。不同快照的文件、型別和實現可能對返回值表達不同，不能把某一版本的 `boolean` 或結果物件寫成永久契約。

```js
async function requestManualFill(api) {
  if (typeof api?.triggerUpdate !== 'function') {
    return { status: 'unsupported', ok: false };
  }

  try {
    const raw = await api.triggerUpdate();

    if (raw === true) return { status: 'settled', ok: true, raw };
    if (raw === false) return { status: 'rejected-or-noop', ok: false, raw };
    if (raw && typeof raw === 'object' && typeof raw.success === 'boolean') {
      return {
        status: 'settled',
        ok: raw.success === true,
        raw,
      };
    }

    return { status: 'unknown-result', ok: false, raw };
  } catch (error) {
    return { status: 'failed', ok: false, error };
  }
}
```

即使 Promise settle，也只說明這次呼叫返回；是否對應最終持久化、是否產生 callback、是否有後續提交，仍需針對當前外掛版本真機驗證並在返回後重讀。

### 8.5 宿主級單例 bridge

需要跨多個訊息 UI 共享狀態時，可建立長生命週期 bridge：

```js
function createDatabaseBridge(api) {
  const listeners = new Set();
  let snapshot = null;

  const publish = () => {
    snapshot = readSnapshot(api);
    for (const listener of listeners) listener(snapshot);
  };

  const onUpdate = () => publish();
  api.registerTableUpdateCallback(onUpdate);
  publish();

  return {
    getSnapshot: () => cloneSnapshot(snapshot),
    subscribe(listener) {
      listeners.add(listener);
      if (snapshot) listener(cloneSnapshot(snapshot));
      return () => listeners.delete(listener);
    },
    dispose() {
      api.unregisterTableUpdateCallback(onUpdate);
      listeners.clear();
      snapshot = null;
    },
  };
}
```

切換聊天時必須 dispose 舊 bridge，再從新聊天重新發現 API 與讀取表。

## 9. CRUD、安全寫回與行號漂移

### 9.1 已核公共簽名

歷史及 2026-07-14 已核快照中的核心呼叫形式包括：

```js
await api.updateCell(tableName, rowIndex, colIdentifier, value);
await api.updateRow(tableName, rowIndex, data);
await api.insertRow(tableName, data);
await api.deleteRow(tableName, rowIndex);
```

也支援物件引數的快照中，`updateCell` 的欄位名是 `colIdentifier`，不是 `column`：

```js
await api.updateCell({
  tableName: '角色表',
  rowIndex: 1,
  colIdentifier: '生命值',
  value: 90,
});
```

其他物件式呼叫應同樣在當前版本核對欄位後使用：

```js
const rowUpdated = await api.updateRow({
  tableName: '角色表',
  rowIndex: 1,
  data: { 生命值: 90, 狀態: '警戒' },
});

const insertedRowIndex = await api.insertRow({
  tableName: '揹包表',
  data: { 物品ID: 'item_017', 名稱: '繃帶', 數量: 1 },
});

const rowDeleted = await api.deleteRow({
  tableName: '揹包表',
  rowIndex: 4,
});
```

在兩組已核快照中，更新/刪除以 `false` 表示失敗，插入以 `-1` 表示失敗並在成功時返回新行位置。專案應把這些值封裝為自己的統一結果；未來版本若改變返回形狀，只改 repository，不讓檢視跟著漂移。

版本升級時應以執行時 API 和對應原始碼為準；不要僅憑本節程式碼假定新版本永不變化。

### 9.2 儲存必須是意圖驅動

檢視不要傳裸行號，而傳業務意圖：

```js
await characterRepository.setHp({
  characterId: 'char_001',
  expectedHp: 82,
  nextHp: 90,
});
```

repository 在寫回前：

1. 重新 export 並 clone；
2. 按業務主鍵定位當前行；
3. 校驗 `expectedHp`，檢測併發變化；
4. 獲取最新 `rowIndex`；
5. 呼叫公開 CRUD；
6. 檢查返回值；
7. 再次重讀，以資料庫真值覆蓋本地樂觀狀態。

### 9.3 行號會漂移

插入、刪除、排序、匯入和重新生成表都可能改變 `rowIndex`。長期儲存 `rowIndex = 7`，下一次很可能寫到另一條記錄。

```js
function findRowByBusinessKey(table, primaryKey, wanted) {
  return table.rows.find(row => String(row.record[primaryKey]) === String(wanted)) ?? null;
}
```

每次寫回前必須重新解析當前表。業務主鍵應：

- 建立後穩定；
- 不依賴顯示名稱；
- 同表唯一；
- 不因本地化而改變；
- 對刪除/重建有明確策略。

### 9.4 SQLite row_id 的邊界

SQLite 模式若公開穩定 `row_id`，可作為比陣列行號更可靠的定位線索；但它不是跨儲存模式通用契約。通用 UI 仍應保留業務主鍵，並在 adapter 中隔離 SQLite 專屬定位。

### 9.5 完整安全更新示例

```js
async function updateCellByBusinessKey({
  api,
  contract,
  key,
  column,
  expectedValue,
  nextValue,
}) {
  const snapshot = readSnapshot(api);
  const table = assertTable(snapshot, contract);
  const row = findRowByBusinessKey(table, contract.primaryKey, key);

  if (!row) throw new Error(`記錄不存在：${key}`);

  const currentValue = row.record[column];
  if (String(currentValue) !== String(expectedValue)) {
    const error = new Error('資料已被其他操作更新，請重新整理後重試');
    error.code = 'STALE_WRITE';
    throw error;
  }

  const result = await api.updateCell({
    tableName: table.name,
    rowIndex: row.rowIndex,
    colIdentifier: column,
    value: nextValue,
  });

  if (result === false || result == null) {
    throw new Error('資料庫拒絕或未確認本次更新');
  }

  return readSnapshot(api);
}
```

返回值的成功表達仍要按當前版本歸一化；上例保守地拒絕 `false/null`，專案可在原始碼核驗後擴充套件。

### 9.6 刪除和批次操作

- 刪除必須二次確認並顯示業務物件名稱；
- 多行刪除應從當前最大 `rowIndex` 向小執行，或使用外掛公開批處理；
- 批次靜默寫入後必須顯式重讀；
- 不要使用未公開的內部“跳過儲存”引數做效能最佳化；
- 寫入中停用重複提交，但要提供超時恢復；
- 失敗後不繼續維護本地偽成功狀態。

## 10. 鎖的座標與有限語義

### 10.1 鎖座標不能與 CRUD 座標混用

已核快照提供表、行、列、單元格鎖相關 API。讀鎖的精確呼叫是 `getTableLockState(sheetKey)`，返回 `{ rows, cols, cells } | null`；它不接收表名、CRUD 行號或列名。

不要在元件裡散寫：

```js
api.getTableLockState(tableName, rowIndex, columnName); // 未核對簽名就猜引數
```

兩套座標在已核快照中明確不同：

- CRUD 第一條資料是 `rowIndex=1`；鎖的第一條資料行是 `rowIndex=0`；
- 匯出表頭與數字 CRUD 列索引包含第 0 列 `row_id`；鎖的業務列 `colIndex=0` 從匯出表頭第 1 列開始；
- 單元格鎖 key 形如 `"鎖行:鎖列"`，例如第一條資料的第一個業務欄位是 `"0:0"`。

因此必須先按當前版本審計簽名，再封裝座標換算。已核快照可使用：

```js
function isCellLocked(api, sheetKey, crudRowIndex, exportedHeaderIndex) {
  const state = api.getTableLockState(sheetKey);
  if (!state) return false;

  const lockRowIndex = crudRowIndex - 1;
  const lockColIndex = exportedHeaderIndex - 1;
  if (lockRowIndex < 0 || lockColIndex < 0) return false;

  return state.rows.includes(lockRowIndex)
    || state.cols.includes(lockColIndex)
    || state.cells.includes(`${lockRowIndex}:${lockColIndex}`);
}
```

升級後重新核驗座標；不要把此換算外推為未來版本永久契約。

### 10.2 可視鎖不是事務鎖

歷史快照中，普通表鎖的內建執行範圍有限，主要參與特定原生 AI 更新路徑。不能由此推斷：

- 公開 CRUD 會自動拒絕所有鎖定內容；
- `insertRow/deleteRow` 一定受保護；
- raw SQL 一定受保護；
- SQLite 寫入一定服從同一把鎖；
- 鎖可以解決兩個 UI 同時寫入的併發衝突。

鎖 UI 若面向玩家，自己的寫回層必須執行相同規則：讀取鎖態、停用控制元件、提交前複核。併發仍靠 expected-value、重讀與衝突提示解決。

### 10.3 鎖狀態必須隨聊天切換重讀

已核實現按當前聊天與隔離維度儲存鎖態。切換聊天后不能沿用舊 store；進入新聊天必須重新讀取表與鎖。

## 11. SQLite 專屬能力

### 11.1 通用主鏈優先 export + CRUD

如果作品同時支援原生表與 SQLite，前端主鏈應優先使用跨模式的 export + CRUD。SQL 能力作為檢測後的增強，不應成為所有 UI 的隱含前提。

### 11.2 已核 SQL 組

已核快照包括：

- `querySql`：只讀 SQL；
- `queryTableRows`：結構化表查詢；
- `executeSqlMutation`：引數化寫入；
- `executeSqlBatch`：多語句批處理。

這些方法在已核快照的原生模式中也會掛載，**方法存在不等於 SQL 可用**。只有 `probeDatabaseCapabilities` 的只讀探針得到 `sqliteReady=true` 後，才能啟用查詢和寫入入口；不能為了探測模式執行試寫。

### 11.3 引數化查詢

```js
async function queryItemsByOwner(api, capabilities, ownerId) {
  if (!capabilities?.sqliteReady || typeof api?.querySql !== 'function') {
    throw new Error('當前 storage provider 未透過 SQLite 就緒探針');
  }

  const result = await api.querySql(
    'SELECT row_id, item_id, name, quantity FROM inventory WHERE owner_id = ?',
    [ownerId],
  );

  if (!result || !Array.isArray(result.rows)) {
    throw new Error('SQL 查詢未返回可識別結果，已停用 SQL UI');
  }
  return result;
}
```

不要把玩家輸入或 AI 文字拼進 SQL 字串。

### 11.4 寫後仍要重讀

```js
async function decrementItem(api, capabilities, itemId) {
  if (!capabilities?.sqliteReady || typeof api?.executeSqlMutation !== 'function') {
    throw new Error('當前 storage provider 未透過 SQLite 就緒探針');
  }

  const result = await api.executeSqlMutation(
    'UPDATE inventory SET quantity = quantity - 1 WHERE item_id = ? AND quantity > 0',
    [itemId],
  );

  if (result?.errors?.length) {
    throw new Error(result.errors.join('; '));
  }

  return readSnapshot(api);
}
```

SQL 結果也要進入 domain 層，檢視不直接繫結資料庫行物件。

## 12. UI store 與狀態機

### 12.1 推薦 store

```js
const store = {
  phase: 'idle',
  capabilities: null,
  domain: null,
  error: null,
  fillingSince: null,
  savingKeys: new Set(),
  revision: 0,
  chatToken: null,
};
```

### 12.2 狀態轉換

```text
idle
  → locating-host
  → loading
  → ready

ready
  → refreshing → ready
  → saving → refreshing → ready
  → filling → refreshing → ready/stale
  → incompatible
  → error
```

### 12.3 每種狀態都有明確 UI

| 狀態 | 玩家看到什麼 | 可以做什麼 |
|---|---|---|
| locating-host | 正在連線資料庫 | 取消或等待 |
| loading | 骨架屏 | 不提交編輯 |
| ready | 當前真實資料 | 正常檢視/編輯 |
| filling | 資料庫正在處理本輪狀態 | 繼續閱讀劇情；避免重複觸發 |
| refreshing | 正在同步最新資料 | 保留佈局，區域性忙碌態 |
| saving | 具體控制元件顯示提交中 | 禁止同一記錄重複提交 |
| stale | 狀態可能未完成同步 | 手動重新整理/檢視診斷 |
| incompatible | 表或 API 不滿足契約 | 顯示缺失項 |
| error | 可理解錯誤 | 重試、重新整理、複製診斷 |

### 12.4 丟棄過期渲染

```js
async function refreshStore(api, store) {
  const revision = ++store.revision;
  store.phase = 'refreshing';

  try {
    const domain = buildDomainSnapshot(api);
    if (revision !== store.revision) return;
    store.domain = domain;
    store.error = null;
    store.phase = 'ready';
  } catch (error) {
    if (revision !== store.revision) return;
    store.error = error;
    store.phase = 'error';
  }
}
```

切換聊天時遞增 revision、清空舊 domain、登出回撥並重建宿主連線。

## 14. 正常多樓層整合

### 14.1 訊息內狀態列

狀態列可以出現在 AI 回覆樓層內，但它的職責仍是顯示資料庫狀態：

```text
真實 AI 回覆正文
──────────────
資料庫狀態列（讀取當前表）
```

它不得：

- 用資料庫欄位拼出一份替代正文；
- 刪除或隱藏原 AI 回覆；
- 把後續輸入改成私有生成迴圈；
- 假裝資料庫已經提供當前樓層的完整敘事結構。

訊息 iframe 生命週期短，必須成對登出 table-update callback。

### 14.2 常駐控制中心

常駐指令碼或外掛面板適合：

- 多張表的導航；
- 複雜編輯表單；
- 宿主級單例 bridge；
- 跨訊息共享篩選和佈局；
- 大表虛擬列表。

常駐不代表永久有效：切聊天、切角色、切預設和擴充套件過載都必須重新發現 API 與清空舊資料。

### 14.3 每輪正常聊天的重新整理策略

推薦順序：

1. 玩家傳送正常訊息；
2. UI 保留上一輪資料，但顯示“等待本輪狀態更新”；
3. ST 建立真實 AI 回覆；
4. 資料庫按配置開始填表時，若有可靠訊號則進入 filling；
5. 收到 table-update 後合併重新整理請求；
6. export 一次、clone、校驗並更新 domain；
7. 無 update 或生命週期不明確時，允許玩家手動重新整理；
8. 下一輪繼續由 ST 正常聊天推進。

### 14.4 Swipe、刪樓與切聊天

這些動作可能改變資料庫所對應的聊天狀態。前端不能只看 DOM：

- Swipe 後重讀，不沿用舊回覆對應的 store；
- 刪除訊息後重讀並提示資料是否已同步回退；
- 切聊天立即清空舊角色/揹包資料；
- 過載後重新註冊 callback；
- 所有回退與重放行為留真機驗證，因為外掛策略可能隨版本變化。

## 15. 安全、效能與可訪問性

### 15.1 文字一律視為不可信

資料庫內容可能來自 AI 或玩家。預設使用 `textContent`：

```js
nameElement.textContent = character.name;
```

若必須渲染富文字，使用可信白名單 sanitizer，禁止事件屬性、指令碼、危險 URL 和任意 iframe。

### 15.2 寫入白名單

不要讓 DOM 自由傳入任意表、列和 SQL。每個操作都對映到預定義意圖：

```js
const EDITABLE_FIELDS = new Set(['生命值', '狀態']);

if (!EDITABLE_FIELDS.has(column)) {
  throw new Error('該欄位不可由前端編輯');
}
```

### 15.3 回調合並與大表

- 同一事件迴圈中的多次 update 合併成一次 refresh；
- 一次 refresh 只 export 一次；
- 大表使用分頁或虛擬列表；
- domain 層建立主鍵索引；
- 搜尋採用 debounce；
- 不在每次渲染重新解析大段 JSON 字串；
- 不在 callback 內直接做重型 DOM 全量重建。

### 15.4 移動端

- 寬表改為卡片/詳情抽屜，不做整表縮放；
- 觸控目標至少保持可點選尺寸；
- 關鍵操作不依賴 hover；
- 底部彈層避開系統安全區；
- 長名稱和長描述可換行；
- 儲存中狀態緊鄰被編輯控制元件。

### 15.5 可訪問性

- 真實按鈕使用 `<button>`；
- 輸入框有 label；
- 進度條提供文字值；
- 錯誤狀態使用可讀提示，不只靠顏色；
- modal 管理焦點並支援 Escape；
- 動態重新整理使用剋制的 live region；
- 尊重 `prefers-reduced-motion`。

### 15.6 日誌隱私

生產環境不要列印整張資料庫。診斷日誌只記錄：

- 時間；
- 能力布林值；
- sheetKey；
- 操作型別；
- 錯誤碼；
- 去敏後的業務主鍵。

## 17. 高頻錯誤

### 錯誤 1：把狀態 UI 當成劇情樓層生成器

修復：恢復正常 ST 多樓層主鏈；資料庫前端只消費填表後的狀態。

### 錯誤 2：把體驗類比寫成 MVU 實現

修復：只使用表契約和 `AutoCardUpdaterAPI`，不接 `stat_data`/JSONPatch。

### 錯誤 3：把一個 tag 寫成永久最新版

修復：記錄核驗日期與 commit，執行時檢測能力，釋出前重跑。

### 錯誤 4：直接修改 export 的 content

修復：立即 clone；寫回只走公開 CRUD/SQL。

### 錯誤 5：每個元件自己解析二維表

修復：統一 adapter 與 domain model。

### 錯誤 6：把陣列下標當資料庫 rowIndex

修復：資料行下標 `0` 對應 `rowIndex = 1`。

### 錯誤 7：長期快取 rowIndex

修復：按業務主鍵重新讀取並定位。

### 錯誤 8：用姓名或標題作主鍵

修復：使用不隨顯示文字變化的穩定 ID。

### 錯誤 9：監聽匿名函式無法登出

修復：儲存同一 callback 引用並在 unmount 呼叫 unregister。

### 錯誤 10：每個訊息 iframe 都註冊 fill-start

修復：不註冊，或僅由宿主單例 bridge 註冊一次。

### 錯誤 11：把任意 update 當 fill-end

修復：update 只觸發重讀；結束語義單獨建模。

### 錯誤 12：用一次 triggerUpdate 返回定義所有版本

修復：能力檢測、返回歸一化、重讀和真機驗證。

### 錯誤 13：鎖圖示只是裝飾

修復：寫回層複核鎖態，同時保留併發檢查。

### 錯誤 14：把可視鎖當事務鎖

修復：用 expected-value、最新行定位和衝突提示處理併發。

### 錯誤 15：原生模式無條件呼叫 SQL

修復：SQL 只作檢測後的 SQLite 增強。

### 錯誤 16：只 catch 異常，不檢查失敗返回

修復：按當前快照歸一化返回值，失敗後重讀。

### 錯誤 17：AI 文字直接 innerHTML

修復：textContent 或經過白名單清洗的富文字。

### 錯誤 18：切聊天仍顯示上一局資料

修復：登出、清 store、重新發現 API、重讀。

### 錯誤 19：拿 DC 截圖推斷 API

修復：DC 二創只作為需求與產品形態背景；API 事實必須來自原始碼或真機，不虛構具體作品與實現。

## 18. 驗收矩陣

### 18.1 定義與邊界

- [ ] 明確這是正常多樓層角色卡的資料庫狀態 UI；
- [ ] 主鏈保留玩家發言、真實 AI 回覆和後續正常聊天；
- [ ] UI 不替代、隱藏或映象劇情樓層；
- [ ] “資料庫版 MVU 前端”僅作為體驗類比；
- [ ] 實驗路線只導航到 C8，並標註待驗證。

### 18.2 版本相容

- [ ] 記錄核驗日期、commit/tag 和能力報告；
- [ ] 不宣稱某個 tag 永久最新；
- [ ] 讀取、訂閱、CRUD、鎖分別檢測；SQL 另外區分“方法已掛載”和“SQLite 已實測就緒”；
- [ ] 缺失能力有明確降級；
- [ ] 升級外掛後重跑原始碼抽樣與真機矩陣。

### 18.3 表契約

- [ ] export 後立即 clone；
- [ ] `sheetKey`、表頭、必需列和業務主鍵顯式宣告；
- [ ] 空表頭、重複列、缺列和重複主鍵會報錯；
- [ ] `rowIndex 0` 只作為表頭；
- [ ] 檢視只消費 domain model。

### 18.4 生命週期

- [ ] table-update callback 使用同引用登出；
- [ ] 多次 update 會合並重新整理；
- [ ] 短生命週期 iframe 不累積 fill-start callback；
- [ ] table-update 不被當成可靠 fill-end；
- [ ] 切聊天、過載和銷燬會清理 bridge/store。

### 18.5 寫回

- [ ] 元件傳業務意圖，不傳長期快取行號；
- [ ] 提交前按主鍵重定位；
- [ ] expected-value 衝突會阻止覆蓋；
- [ ] `updateCell` 使用 `colIdentifier`；
- [ ] 寫後重讀資料庫真值；
- [ ] 刪除、批次和失敗恢復有產品狀態。

### 18.6 UI 與安全

- [ ] 外掛缺失、載入、空表、填表、儲存、衝突、失敗都有介面；
- [ ] 玩家和 AI 文字不直接進入 `innerHTML`；
- [ ] SQL 引數化且只在相容模式啟用；
- [ ] 大表使用分頁/虛擬化；
- [ ] 移動端、鍵盤與輔助技術可用；
- [ ] 日誌不洩露整表和聊天內容。

### 18.7 必須真機驗證

| 場景 | 觀察點 |
|---|---|
| 新建聊天首輪 | API 與表資料何時就緒 |
| 正常連續三輪 | AI 回覆、填表、table-update、UI 重新整理的實際順序 |
| 本輪無表變化 | 是否有 callback；UI 如何退出等待態 |
| 手動 triggerUpdate | 返回形狀、settle、持久化和 callback 次數 |
| updateCell/updateRow | 返回值、儲存、重讀與錯誤表現 |
| insert/delete 後寫舊物件 | 業務主鍵能否避免 rowIndex 漂移誤寫 |
| Swipe | 資料庫是否回退/重算，UI 是否重新整理 |
| 刪除樓層 | 表狀態與聊天狀態是否一致 |
| 切換聊天 | 舊回撥、舊鎖態和舊資料是否清空 |
| 過載外掛/頁面 | API 引用與 bridge 是否安全重建 |
| 鎖 + 公共 CRUD | 當前版本是否自動攔截；自定義 UI 是否正確執行規則 |
| SQLite 模式 | 查詢、寫入、通知、row_id 與原生模式差異 |
| 大表與移動端 | 效能、觸控、滾動與錯誤恢復 |
