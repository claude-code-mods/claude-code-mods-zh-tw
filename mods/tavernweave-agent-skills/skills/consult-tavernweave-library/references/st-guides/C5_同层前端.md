# 同層前端 — 在單個訊息樓層內完成完整遊玩體驗

> 文件版本：v1.0.1 ｜ 最後更新：2026-07-14
>
> **本冊術語裁定（2026-07-14）**：“同層前端”特指在一個訊息樓層——通常是首樓 / 0 號樓層——閉合完整遊玩主鏈；玩家始終在這一樓完成輸入、生成、劇情閱讀、選項、角色狀態、揹包、地圖、設定、路由與回看，而不是隻看到一張開局頁或一個狀態面板。
>
> “同層”按**完整遊玩閉環所在樓層**定義，不按 DOM 是否只有一層定義。首樓完整應用內部可以有路由、Tab、Modal、元件樹，甚至受控子 iframe；與此同時，SillyTavern 的真實使用者訊息和 AI 訊息仍繼續生成，承擔提示詞上下文、Swipe、分支和聊天存檔。首樓應用負責驅動、組織並映象這些真實樓層。
>
> 這不是把 Tavern Helper 指令碼的 DOM 掛到 SillyTavern 主頁面，也不是把後續樓層刪掉、覆蓋成一條假記錄。後臺指令碼可以充當橋接服務，但它不是“同層前端”本身。
>
> 事實基線：`酒館助手開發完全指南/@types.txt` 的樓層、顯示與事件介面；本庫 `C1_前端基礎-TavernHelper與iframe.md`；卡A 3.9.6 開局頁的“短標記 → 遠端掛載 → 本地繫結”區域性生產樣本。卡A樣本只證明掛載鏈路，不是完整同層玩法成品。
>
> 職責導航：本冊負責在首樓 / 0 號訊息內完成輸入、生成、狀態、路由、回看等全部體驗；只在開局時收集配置、確認真實玩家訊息後退出的一次性初始化器歸 **《C10_開局頁與自定義開局.md》**。**《C7_資料庫二創前端.md》**只討論正常多樓層角色卡里的資料庫狀態列、控制中心和資料面板；SP·資料庫預設在正常 AI 回覆樓層生成後填表，本身不產出同層應用所需的劇情、選項、路由和樓層資訊，因此不能直接作為本冊的成熟狀態後端。實驗性相容研究另見 **《C8_資料庫相容同層前端-待驗證.md》**，在真機驗收前禁止當成已支援能力。

## 1. 定義、反定義與適用邊界

### 1.1 一句話定義

**同層前端 = 以單個真實訊息樓層為唯一可見應用 shell，在 shell 內完成全部玩家互動，同時讓 ST 的真實聊天樓層在後臺正常增長。**

預設將 0 號樓作為 shell，是因為它隨聊天建立、天然屬於該存檔，並可用樓層 iframe API 確認身份：

```typescript
const SHELL_MESSAGE_ID = 0;

$(() => {
  const current = getCurrentMessageId();
  if (current !== SHELL_MESSAGE_ID) {
    throw new Error(`同層前端必須執行在 ${SHELL_MESSAGE_ID} 號樓，當前為 ${current}`);
  }
  bootShell();
});
```

`getCurrentMessageId()` **只能在訊息樓層 iframe 內呼叫**；在指令碼 iframe 中呼叫會拋錯。來源：`@types.txt` 型別宣告 ｜ 置信度：high `[型別宣告]`

### 1.2 “同層”不等於 DOM 只有一層

以下結構仍然是同層前端：

```text
0 號訊息樓層（唯一可見 shell）
└─ App
   ├─ Router / 頁面狀態
   ├─ 劇情回看
   ├─ 角色 / 揹包 / 地圖 / 任務
   ├─ Modal / Drawer / Toast
   └─ 受控子 iframe（可選）
```

判斷標準不是“嵌套了幾層 DOM”，而是：玩家是否始終在同一個訊息樓層提供的應用介面內完成遊玩。

### 1.3 明確不屬於同層前端的形態

| 形態 | 為什麼不是本冊的同層前端 |
|---|---|
| 指令碼把按鈕、浮窗或面板插進 ST 宿主頁面 | UI 承載面是宿主介面，不是單個訊息樓層 |
| 每個 AI 樓層各帶一份狀態列 | 可見前端隨訊息樓層分散，不是單 shell |
| 只把首樓做成開局嚮導 | 只覆蓋開局階段，不等於完整遊玩體驗 |
| 刪除後續訊息，只在首樓變數裡模擬劇情 | 丟失 ST 原生上下文、Swipe 與存檔語義 |
| Web / App / PC 客戶端直接執行角色卡 | 已脫離 ST，屬於 `C6_獨立前端.md` |

### 1.4 適用與不適用

適用：

- 要把角色卡做成“遊戲應用”，不希望玩家滾動原生訊息流；
- 仍希望複用 ST 的角色卡、世界書、預設、模型連線、聊天曆史和 Swipe；
- 有多個遊戲子系統，需要統一路由和穩定入口；
- 願意維護一個後臺橋接服務處理訊息事件、shell 恢復和顯示模式。

不適用：

- 只要一個輕量狀態列或單次開局頁；
- 無法接受對 ST 顯示層做版本適配；
- 希望徹底擺脫 ST 的執行環境與依賴；
- 專案沒有能力做長聊天、重繪、Swipe 和失敗恢復的真機迴歸。

本節定義來自總監裁定 ｜ 置信度：high `[總監裁定·2026-07-14]`

## 2. 三層架構：真實訊息、首樓應用、橋接服務

### 2.1 總體結構

```text
┌──────────────────────────────────────────────┐
│ 真實訊息資料層（SillyTavern chat）            │
│ 0 shell / 1 user / 2 assistant / 3 user ... │
│ 上下文、Swipe、分支、樓層 data、存檔          │
└───────────────────┬──────────────────────────┘
                    │ Tavern Helper API / events
┌───────────────────▼──────────────────────────┐
│ 橋接服務層（常駐指令碼，可選但完整實現強烈建議）│
│ 事件匯聚、訊息讀取、生成狀態、顯示適配、遠端載入│
└───────────────────┬──────────────────────────┘
                    │ 共享介面 / 自定義事件 / 持久狀態
┌───────────────────▼──────────────────────────┐
│ 首樓應用層（0 號訊息 iframe）                 │
│ 唯一可見 shell、路由、渲染、輸入、回看、設定   │
└──────────────────────────────────────────────┘
```

### 2.2 真實訊息資料層

這一層是權威聊天記錄，不能為了介面效果被“前端狀態”取代：

- 玩家每次行動都建立真實 `user` 訊息；
- 正常主模型回覆建立真實 `assistant` 訊息；
- 當前啟用 Swipe 決定該樓實際進入上下文的內容；
- 訊息 `data` 可以攜帶樓層快照；
- ST 負責聊天檔案、角色繫結、提示詞歷史和原生分支語義。

首樓本身也是一條真實訊息，但其正文只應儲存短標記或輕量啟動 mount，不應用來反覆寫入完整劇情映象；完整同層應用由顯示期展開和常駐邏輯共同維持。

### 2.3 首樓應用層

首樓應用只做三件核心事：

1. **讀取**真實聊天、變數和生成狀態；
2. **呈現**劇情、選單與遊戲子系統；
3. **發起**玩家行為，讓行為回到真實訊息鏈路。

首樓不應自創第二套“劇情真相”。重新整理後，它必須能僅憑持久資料重新構建介面。

### 2.4 橋接服務層

完整同層前端建議使用常駐 Tavern Helper 指令碼承擔：

- 監聽 `CHAT_CHANGED`、訊息增刪改、Swipe、生成開始/結束；
- 聚合事件，防止首樓 iframe 重繪期間漏事件；
- 在首樓被銷燬時仍儲存生成狀態和待恢復資訊；
- 發現首樓 mount、載入遠端/構建產物、繫結互動；
- 只在 shell 健康時啟用“僅顯示首樓”模式；
- 首樓重繪後重新接線。

它可以透過 `initializeGlobal` / `waitGlobalInitialized` 暴露受控 API，或透過自定義 `eventEmit` / `eventOn` 傳遞通知。橋接指令碼是服務層，不因它接觸宿主 DOM 就改變“同層前端”的定義。

### 2.5 單向資料流

```text
真實聊天 / 變數後端
→ bridge 讀取並歸一化為 snapshot
→ shell store
→ router / components 渲染
→ 玩家 action
→ createChatMessages + /trigger
→ 真實聊天產生新樓層
→ bridge 再讀取 snapshot
```

不要讓元件直接在各處呼叫樓層 API。所有呼叫應收口到 `chat-service` / `game-state-adapter`，否則重繪、併發和測試都無法統一處理。

架構屬於基於裁定和 API 能力形成的工程基線 ｜ 置信度：medium·推導未驗證 `[架構推導]`；主鏈路 API 存在性為 high `[型別宣告]`

## 3. 首樓 shell 的短掛載與產物載入

### 3.1 為什麼首樓只放短標記

把幾百 KB 的完整 HTML 直接寫進開場白會同時帶來：

- 角色卡和聊天記錄膨脹；
- 開場白正文可能進入提示詞上下文；
- 每次樓層重繪都重複處理大段 HTML；
- 版本升級必須重導開場白；
- 正則、DOMPurify 與類名字首處理成本增大。

推薦鏈路：

```text
first_mes / alternate greeting
→ 只存唯一短標記
→ 顯示正則擴成輕量 mount + loading/error fallback
→ bridge 發現 mount
→ 載入固定版本構建產物或遠端 HTML
→ 注入 shell
→ 本地 binder / bundle 繫結互動
```

短標記必須唯一、穩定、不會被模型正常復讀，例如專案專屬標籤或文字哨兵。不要使用可能自然出現在劇情中的普通句子。

### 3.2 卡A 3.9.6 的區域性生產樣本

當前樣本鏈路為：

1. `first_message_opening.html` 只有短標記 `*卡A·開局頁*`；
2. `opening_expand_regex.html` 把它擴充套件成帶 `data-xy-opening-remote` 的載入 mount；
3. 當前 `rolecard-diy-workshop/runtime/xingyue/3.9.6/control-center.js` 整合多源 `fetch`、完整性/結構校驗、淨化、注入與 `bindOpeningPage`；
4. `rolecard-diy-workshop/runtime/xingyue/3.9.6/opening-page.html` 提供宣告式開局頁結構；
5. 聊天切換、訊息渲染、更新和 Swipe 後重新掃描。

這證明“短訊息正文 + 顯示期展開 + 遠端內容 + 本地繫結”可用於首樓複雜介面。它當前只覆蓋一次性開局頁，**不得冒充已驗證的完整同層玩法實現**。開局頁完整職責和提交鏈見 **《C10_開局頁與自定義開局.md》**。

來源：上述四個本地檔案 ｜ 置信度：high `[執行時原始碼·區域性生產樣本]`

### 3.3 兩種部署路線

#### 路線 A：固定版本的單檔案構建產物

- HTML、CSS、JS 構建為可部署產物；
- 角色卡或正則只保留 mount；
- bridge 載入鎖定版本的資源；
- 釋出時同步 bump shell 版本與快取鍵。

優點是可回滾、產物邊界清晰。缺點是網路失敗時必須有本地 fallback。

#### 路線 B：遠端宣告式 HTML + 本地 binder

- 遠端 HTML 只負責結構和樣式；
- 互動、訊息 API、金鑰邊界留在本地受信 binder；
- 遠端失敗時 mount 保留重試按鈕和錯誤說明。

不要指望 `mount.innerHTML = html` 自動可靠執行其中的 `<script>`；互動應由已載入的 binder 明確接管。

### 3.4 遠端載入最低安全線

- URL 鎖定發行版本或內容雜湊，禁止無審計地追 `latest`；
- 主源、備源必須指向同一構建版本；
- 設定超時、失敗態、手動重試和離線降級；
- 非同步結果提交前核對當前 chat id 與 mount 是否仍存活；
- HTML、JSON、圖片分別限定允許來源；
- 不在遠端 HTML 內放模型 API key、使用者 token 或高許可權邏輯；
- 新版本結構變化時由 binder 做協議版本檢查，不能靜默錯綁。

### 3.5 mount 契約

建議 mount 至少提供：

```html
<div
  data-same-floor-shell="1"
  data-shell-protocol="1"
  data-shell-state="loading"
  aria-busy="true"
>
  <p role="status" aria-live="polite">遊玩介面載入中……</p>
  <button type="button" data-shell-retry hidden>重新載入</button>
</div>
```

載入狀態只能從 `loading` 進入 `ready` 或 `error`。只有進入 `ready` 且完成首輪聊天映象後，橋接服務才可以隱藏原生樓層顯示。

## 4. 啟動、重繪與恢復

### 4.1 啟動狀態機

```text
detect-floor
→ locate-mount
→ connect-bridge
→ load-assets
→ read-chat-and-state
→ render-accessible-transcript
→ ready
→ enable-single-floor-display
```

任一步失敗都進入可見 `error`，並保持原生聊天可訪問。禁止在 shell 尚未 ready 時先把其他樓層隱藏。

### 4.2 首樓權威讀取

首樓內容和樓層資料可以直接讀取：

```typescript
const [shellMessage] = getChatMessages(0);
if (!shellMessage) throw new Error('0 號樓不存在，無法啟動同層前端');

const shellData = shellMessage.data ?? {};
```

`getChatMessages(0)` 返回 0 號樓當前被採用的訊息頁。若要讀取全部開局 Swipe，使用 `{ include_swipes: true }`。來源：`@types.txt` ｜ 置信度：high `[型別宣告]`

### 4.3 什麼會讓 shell 重建

以下動作都必須按“舊 shell 可能已經銷燬”設計：

- `refreshOneMessage(0)`；
- `setChatMessages(..., { refresh: 'affected' | 'all' })` 影響 0 號樓；
- 0 號樓 Swipe 切換；
- 聊天切換或整個訊息列表過載；
- 正則配置變化導致聊天重新渲染；
- 瀏覽器重新整理、擴充套件過載、熱更新。

訊息樓層 iframe 的記憶體 store、定時器、請求和事件監聽都不能視為持久狀態。

### 4.4 受控重繪

當首樓顯示損壞或必須應用新 mount 時，可以：

```typescript
await refreshOneMessage(0);
```

該函式只重新整理顯示，不修改真實訊息內容；如果 0 號樓當前沒有顯示在網頁上，它會什麼也不做。來源：`@types.txt` ｜ 置信度：high `[型別宣告]`

呼叫後當前 shell 自身可能被銷燬，因此：

- 重繪前先把路由、草稿和滾動錨點寫入可恢復儲存；
- 最好由 bridge 發起重繪；
- shell 自己發起時，把它作為當前呼叫棧最後一步，不依賴呼叫後的程式碼；
- 新例項啟動後重新讀取真實聊天，不繼承舊閉包物件。

### 4.5 恢復優先順序

```text
真實聊天與遊戲資料
> chat / message 級持久 UI 狀態
> localStorage 中的本機偏好
> 當前 iframe 記憶體
```

如果記憶體路由與持久聊天狀態衝突，以當前 chat id 對應的持久狀態為準。所有非同步任務攜帶啟動時的 chat id / epoch；切聊天后舊任務即使返回，也不得提交到新 shell。

### 4.6 失敗恢復要求

- shell 載入失敗：恢復原生樓層顯示；
- bridge 不可用：允許只讀回看，並清楚停用傳送按鈕；
- 資源源全部不可達：顯示來源和重試，不留白屏；
- 資料後端不可用：顯示診斷，不把空物件寫回覆蓋真實資料；
- 0 號樓不在當前 DOM：不得假裝 `refreshOneMessage(0)` 已成功；
- 熱過載：舊請求、observer、listener、interval 全部取消。

## 5. 玩家輸入到真實 AI 回覆的主鏈路

### 5.1 唯一推薦主鏈路

```text
玩家在首樓輸入 / 點選選項
→ shell 校驗並生成 action_id
→ createChatMessages 建立真實 user 樓層
→ triggerSlash('/trigger') 觸發 ST 正常生成
→ ST 建立真實 assistant 樓層
→ 變數框架按其規則處理該樓
→ bridge 收到訊息 / 生成事件
→ 重新讀取真實聊天
→ 首樓映象最新劇情和狀態
```

這條鏈路保留 ST 的預設、世界書、角色定義、聊天曆史和原生存檔語義。

### 5.2 最小發送骨架

```typescript
let sending = false;
let activeActionId: string | null = null;

async function submitPlayerTurn(rawText: string): Promise<void> {
  const text = rawText.trim();
  if (!text || sending) return;

  sending = true;
  activeActionId = crypto.randomUUID();
  renderGenerationState('sending');

  try {
    await createChatMessages([{
      role: 'user',
      message: text,
      data: { same_floor_ui: { action_id: activeActionId } },
    }]);

    renderGenerationState('generating');
    await triggerSlash('/trigger');
  } catch (error) {
    sending = false;
    activeActionId = null;
    renderGenerationError(error);
  }
}
```

`createChatMessages` 只建立訊息；建立使用者訊息後仍需 `/trigger` 才觸發 AI。來源：`@types.txt` 與 `references/api.md` ｜ 置信度：high `[型別宣告]`

不要僅依賴 `triggerSlash` Promise 的返回時機解除 busy；以生成結束/停止事件和真實訊息重讀為準，並準備事件漏收後的超時對賬。

### 5.3 生成結束後的權威提交

推薦至少監聽：

| 事件 | shell 行為 |
|---|---|
| `MESSAGE_SENT` | 重讀使用者樓層，確認 action 已落庫 |
| `GENERATION_STARTED` | 顯示生成態、鎖定重複提交 |
| `MESSAGE_RECEIVED` | 重讀完整聊天，提交 assistant 正文 |
| `MESSAGE_UPDATED` | 延遲重讀變數/訊息 data，等待解析器落庫 |
| `GENERATION_ENDED` | 結束流式預覽，做最終對賬 |
| `GENERATION_STOPPED` | 解鎖並保留使用者訊息，提示可重試 |
| `MESSAGE_EDITED` / `MESSAGE_DELETED` / `MESSAGE_SWIPED` | 全量重建受影響的回看索引 |
| `CHAT_CHANGED` | 取消舊任務，重啟 shell 會話 |

同一輪可能連續觸發多個事件。用 debounce + 單飛鎖聚合讀取，不要每個事件都併發跑一遍完整渲染。

### 5.4 為什麼不把 `generate()` 當普通回合

`generate()` / `generateRaw()` 自行生成文字時不會自動建立真實訊息樓層，MVU 也不會因此自動按普通樓層管線解析。它們適合第二 API、預覽、摘要等專門任務，不適合替代同層前端的正常劇情回合。

正常玩法繞開真實樓層，會導致回看、Swipe、上下文、變數解析與存檔出現兩套真相。

### 5.5 選項和自由輸入統一成 action

```typescript
type PlayerAction = {
  id: string;
  source: 'free_text' | 'choice' | 'system_panel';
  text: string;
  created_at: number;
};
```

無論按鈕還是輸入框，最終都應生成玩家能看懂的真實 user message。不要只發送隱藏控制碼；必要的結構化元資料放 `data`，正文保留可回看語義。

## 6. 訊息回看、Swipe 與分支

### 6.1 首樓映象的是訊息，不是複製一份存檔

活動聊天讀取：

```typescript
function readActiveTranscript(): ChatMessage[] {
  return getChatMessages('0-{{lastMessageId}}')
    .filter(message => message.message_id !== 0);
}
```

shell 可以把這些真實訊息渲染為聊天氣泡、章節、視覺小說對話或戰報，但每個 UI 節點必須保留：

- `message_id`；
- `role`；
- 當前 `swipe_id`（若讀取全部 Swipe）；
- 內容版本或更新時間；
- 是否仍處於流式臨時態。

不要用陣列下標代替 `message_id`，因為刪除、插入和歷史操作會改變順序。

### 6.2 讀取全部 Swipe

```typescript
const floors = getChatMessages('0-{{lastMessageId}}', {
  include_swipes: true,
});

for (const floor of floors) {
  const activeText = floor.swipes[floor.swipe_id];
  const alternatives = floor.swipes.map((text, swipeId) => ({ swipeId, text }));
  // 顯示當前頁和可選頁；不要在這裡修改真實聊天
}
```

`ChatMessageSwiped` 直接提供 `swipe_id`、`swipes`、`swipes_data`、`swipes_info`。來源：`@types.txt` ｜ 置信度：high `[型別宣告]`

### 6.3 切換 Swipe

```typescript
async function selectSwipe(messageId: number, swipeId: number): Promise<void> {
  await setChatMessages([{ message_id: messageId, swipe_id: swipeId }], {
    refresh: 'affected',
  });
  await reconcileFromRealChat();
}
```

切換必須寫回 ST 的真實 Swipe 狀態，不能只改 shell 的選中樣式。歷史樓層換 Swipe 後，下游分支如何處理屬於 ST 版本和操作語義敏感項；執行後必須重讀整段聊天，不能假定後續訊息仍有效。

### 6.4 “訊息樹”能力邊界

`include_swipes:true` 能得到“每樓有哪些候選頁、當前選了哪頁”，但型別宣告沒有直接給出一個完整的跨樓層父子圖。因此：

- 可穩定實現：當前活動線、單樓 Swipe 選擇、按樓層回看；
- 需要額外驗證：歷史 Swipe 對後續樓層的裁剪/分叉行為；
- 若產品要完整視覺化分支樹，需要自建 branch metadata，並與 ST 原生操作做一致性對賬；
- 不得僅憑 `swipes[]` 宣稱已恢復全部歷史分支拓撲。

當前邊界 ｜ 置信度：medium·推導未驗證 `[型別能力推導]`

### 6.5 長聊天效能

- 初次只渲染最近 N 樓，回看時向前分頁；
- 歸一化快取以 `message_id + swipe_id` 為鍵；
- `MESSAGE_UPDATED` 只失效對應樓，刪除/重排/歷史 Swipe 才全量重建；
- 大段訊息使用虛擬列表或分章摺疊；
- 流式預覽單獨維護，不在每個 token 後重建全部歷史；
- 任何摘要都只能是顯示索引，不能替換真實聊天。

## 7. 狀態劃分、已支援後端與資料庫實驗邊界

### 7.1 四類狀態不能混放

| 狀態 | 示例 | 推薦位置 |
|---|---|---|
| 真實聊天 | user / assistant 文字、Swipe | ST 訊息樓層 |
| 遊戲狀態 | 屬性、揹包、任務、關係 | 已驗證主線使用變數或 MVU；資料庫相容另列待驗證路線 |
| 可恢復 UI 狀態 | 當前路由、未發草稿、回看錨點 | namespaced chat 變數或 0 號樓 data |
| 本機偏好 | 主題、字號、動效 | `localStorage`，帶卡片與版本字首 |

當前 iframe 的 Pinia/React state 只是快取，不是任何一類持久真相源。

### 7.2 原生變數後端

適合不採用 MVU、結構較輕的卡：

- chat 變數儲存當前存檔共享狀態；
- message 變數儲存樓層快照；
- `updateVariablesWith` 用於受控讀改寫；
- 正式欄位統一放在專案名稱空間下，避免與其他指令碼衝突。

前端讀取後先做 schema 校驗和預設值歸一。不得把空物件當成“載入成功”再覆蓋原值。

### 7.3 MVU 後端

適合已有 `stat_data`、變數更新規則和 schema 的卡：

```typescript
await waitGlobalInitialized('Mvu');

const latest = Mvu.getMvuData({
  type: 'message',
  message_id: 'latest',
});

const statData = latest.stat_data ?? {};
```

主回合繼續走真實 user → AI → assistant → MVU 解析鏈；普通玩家操作不要由 shell 直接改 `stat_data`。前端直接寫只保留給有明確事務、schema 校驗、審計和回滾的管理工具。

### 7.4 SP·資料庫不是預設相容後端

SP·資料庫是 MVU 之外的表格變數 / AI 填表方案，常規流程是在正常多樓層聊天中讀取已經生成的 AI 回覆，再更新資料庫。它本身不向同層應用提供劇情正文、選項、路由或樓層資訊輸出契約，所以不能僅靠“接一個數據庫 adapter”就完成本冊主鏈。

任何資料庫相容嘗試都必須另加訊息/樓層橋，驗證“真實回覆生成 → 樓層可讀 → 資料庫填表 → 首樓渲染”的完整時序，以及 Swipe、重生成、編輯、刪樓、回滾和切聊天恢復。該路線僅在 [C8_資料庫相容同層前端-待驗證.md](./C8_資料庫相容同層前端-待驗證.md) 中討論；透過轉正門前，本冊不把它列為可用後端。

### 7.5 統一介面卡

```typescript
type Unsubscribe = () => void;

interface GameStateAdapter<T> {
  readonly kind: 'variables' | 'mvu';
  init(): Promise<void>;
  read(): Promise<T>;
  subscribe(onChange: () => void): Unsubscribe;
  dispose(): void;
}
```

元件只消費歸一化 snapshot；不要在元件中用 `if (Mvu)` 到處分叉。後端切換必須是專案級選型，不是執行時把多套資料悄悄合併。待驗證的資料庫相容層不得提前塞進這個穩定介面冒充第三種已支援實現。

### 7.6 UI 恢復狀態示例

```typescript
type ShellUiState = {
  protocol_version: 1;
  route: string;
  draft: string;
  transcript_anchor?: number;
  last_seen_message_id?: number;
};
```

建議寫到獨立名稱空間，例如 `same_floor_ui`。遊戲狀態後端遷移不應順帶覆蓋 UI 狀態；UI 協議升級需要顯式 migration。

## 8. 只隱藏顯示，不改變提示詞語義

### 8.1 最高優先順序警告

> **嚴禁為了“玩家只看首樓”而把後續真實訊息設定為 `is_hidden: true`。**

`is_hidden` 不是 CSS 顯隱，它會改變訊息是否傳送給 LLM。把真實 user / assistant 樓層設為 hidden，會直接破壞提示詞上下文和連續劇情。

來源：`ChatMessage.is_hidden` 語義、`references/api.md` ｜ 置信度：high `[型別宣告]` + `[本庫介面核對]`

同樣禁止為視覺效果刪除、清空、旋轉或改寫真實訊息。

### 8.2 正確做法：展示適配層

只改變 ST 頁面上原生訊息容器的**視覺呈現**，不修改聊天檔案欄位：

```text
bridge 檢測 shell ready
→ 給宿主聊天檢視開啟專案專屬 presentation mode
→ 視覺摺疊 / 隱藏非 shell 訊息容器
→ 保留 0 號 shell 可見
→ 新樓層渲染後重新應用
→ shell error / destroy / chat change 時立即撤銷
```

這層可以使用專案專屬 class、樣式節點或受控 DOM 操作，但必須：

- 選擇器加專案名稱空間；
- 只作用當前聊天的訊息顯示區；
- 不修改 `is_hidden`、role、message 或 data；
- 不遮蔽 ST 系統彈窗、輸入區和錯誤提示；
- 有“一鍵顯示原生訊息”逃生開關；
- shell 心跳丟失時自動恢復原生顯示；
- ST 版本變化導致選擇器失效時安全失敗為“都可見”，不能失敗為“全消失”。

### 8.3 可訪問性前提

若原生訊息容器被 `display:none`，螢幕閱讀器也無法訪問它們。因此 shell 必須在進入單層模式前提供：

- 可鍵盤導航的完整活動線回看；
- role / 說話者語義；
- 新訊息通知；
- 跳到最新與向前載入；
- 顯示原生聊天的恢復按鈕。

### 8.4 自動滾動與 shell 位置

ST 生成新樓層時可能自動滾到訊息列表底部，而 shell 位於 0 號樓。展示適配層必須真機解決：

- shell 是否固定在可視區域；
- 原生自動滾動會不會把玩家帶到空白底部；
- 長聊天未載入 0 號樓時如何恢復；
- 移動端軟鍵盤開啟後 shell 是否仍可操作。

這些不能只靠離線 CSS 宣稱完成，見懸案 U1/U4。

## 9. 套娃式路由、元件與子 iframe

### 9.1 單 shell 內部路由

推薦用應用內狀態路由，不把 ST 樓層號當頁面：

```typescript
type ShellRoute =
  | { name: 'story' }
  | { name: 'characters'; selectedUid?: string }
  | { name: 'inventory' }
  | { name: 'map'; locationId?: string }
  | { name: 'quests' }
  | { name: 'settings' };
```

路由切換隻改變首樓檢視；真實訊息繼續按回合增長。需要重新整理恢復的 route 寫入 `ShellUiState`。

### 9.2 推薦層級

```text
ShellFrame
├─ TopBar：角色 / 時間 / 資源 / 生成狀態
├─ Viewport
│  ├─ StoryView：真實訊息映象、選擇欄、輸入
│  ├─ CharacterView
│  ├─ InventoryView
│  ├─ MapView
│  └─ SettingsView
├─ ModalHost：詳情、確認、診斷
└─ RecoveryRail：原生聊天、過載 shell、匯出診斷
```

劇情檢視必須始終可達，不能讓玩家進入設定頁後失去生成進度或新訊息提示。

### 9.3 Modal 與 Drawer

- 在 shell 根容器內統一管理 z-index；
- 只允許一個頂層互動焦點；
- ESC 關閉最上層，不穿透到 ST；
- 開啟時記錄焦點，關閉後歸還；
- 不用依賴宿主 viewport 的 `position: fixed` 解決樓層內彈窗；
- shell 重繪前關閉或持久化關鍵確認流程。

### 9.4 受控子 iframe

子 iframe 適合：地圖渲染器、複雜編輯器、第三方視覺化、重 CSS 子應用。它仍屬於首樓 shell 的內部子檢視，所以產品體驗仍是同層。

最低要求：

- 顯式 `sandbox`，按需開放最小能力；
- 父子通訊使用版本化 `postMessage` 協議；
- 校驗 `event.source`、`event.origin`、channel 和 schema；
- 子 iframe 不直接接觸 Tavern Helper 高許可權 API，由 shell/bridge 提供白名單 RPC；
- 用 `ResizeObserver` 或明確尺寸協議同步高度；
- route 離開時銷燬 listener、observer、worker 與媒體資源。

不要把“嵌了子 iframe”誤判為 `C6` 獨立前端；只要執行仍依賴 ST，且完整遊玩閉環仍在首樓內完成，它就是本冊範圍。

## 10. 流式、併發與重複提交

### 10.1 生成狀態機

```typescript
type GenerationPhase =
  | 'idle'
  | 'sending'
  | 'generating'
  | 'streaming'
  | 'reconciling'
  | 'stopped'
  | 'error';
```

按鈕文案、輸入停用、停止/重試和流式預覽都由同一狀態機驅動。不要讓每個元件各維護一個 `isLoading`。

### 10.2 流式顯示

- 正常 `/trigger` 生成監聽 Tavern 生成/流式事件；
- `iframe_events.STREAM_TOKEN_RECEIVED_*` 是 `generate()` 系列的事件，不要和正常 ST 回合無條件混用；
- token 只更新臨時 preview，不寫進真實聊天或遊戲狀態；
- `MESSAGE_RECEIVED` 後丟棄 preview，重新讀取持久 assistant 訊息；
- 流式區使用節流，避免每 token 重排整棵元件樹；
- `aria-live` 不逐 token 朗讀，完成句或完成回合再通知。

事件範圍隨生成入口而異 ｜ 置信度：high `[型別宣告]`；具體正常 `/trigger` 流式矩陣需真機確認，見 U2。

### 10.3 重複提交防護

至少同時具備：

1. UI busy 鎖；
2. 持久 `action_id`；
3. 提交前檢查是否已有同 action 的真實 user 訊息；
4. bridge 維護當前 generation epoch；
5. 網路/重繪後透過真實訊息對賬，而不是盲目重發；
6. 超時只顯示“狀態未知，先檢查聊天”，不能自動再發一次。

### 10.4 非同步競態

```typescript
let refreshEpoch = 0;

async function reconcile(): Promise<void> {
  const epoch = ++refreshEpoch;
  const snapshot = await readAllSources();
  if (epoch !== refreshEpoch) return;
  if (snapshot.chatId !== currentChatId()) return;
  applySnapshot(snapshot);
}
```

`MESSAGE_RECEIVED`、`MESSAGE_UPDATED`、變數更新結束可能很接近。舊讀取結果不得覆蓋新狀態。

### 10.5 停止、失敗與重試

- 生成停止後保留真實 user 訊息並標出“未獲回覆”；
- 重試前讓玩家選擇繼續生成、重新生成或編輯輸入；
- 不自動刪除上一條使用者訊息；
- assistant 已落樓但變數後端仍在處理時顯示 `reconciling`，不要過早解鎖依賴狀態的操作；
- shell 重新整理後從最後樓層 role 和生成事件狀態恢復，不僅看記憶體 busy。

## 11. 移動端、可訪問性與安全

### 11.1 訊息 iframe 佈局

- 禁止把 `100vh` 當作可靠可視高度；ST 外層、瀏覽器工具欄和軟鍵盤都會改變實際空間；
- 以內容流 + 內部可控滾動區設計，避免無限撐高整個訊息樓層；
- 透過 `ResizeObserver` 觀察 shell 主區域，不要對每個子節點各開 observer；
- 窄屏 Tab 使用橫向滾動或底部導航，不維護兩套業務 DOM；
- 觸控目標約 44×44 CSS px，輸入按鈕不依賴 hover；
- 尊重安全區和 `prefers-reduced-motion`。

### 11.2 鍵盤與焦點

- shell 根提供“跳到劇情”“跳到輸入”“開啟恢復工具”；
- 傳送後焦點回到合理位置，不因全量重渲丟失；
- Modal 焦點陷阱只限制在當前 Modal；
- ESC 不冒泡觸發 ST 的無關快捷鍵；
- 鍵盤導航能完成選項、Swipe、回看和傳送；
- 路由變化更新標題或 live region，不能只靠視覺動畫表達。

### 11.3 AI 內容全部不可信

- 預設 `textContent` / 框架轉義插值；
- 禁止把 AI 正文、變數值、資料庫單元格直接交給 `innerHTML` / `v-html`；
- 若需要 Markdown/正則顯示效果，優先走 `formatAsDisplayedMessage`，仍對最終插入點做邊界審計；
- URL 協議白名單至少限制為專案需要的 `https:` / 受控媒體協議；
- 移除事件屬性、指令碼標籤、危險 SVG 與任意 iframe；
- 匯入存檔、工坊包和遠端 JSON 與 AI 文字同等不可信。

### 11.4 遠端供應鏈

- 鎖版本、可回滾、保留本地最小錯誤殼；
- 釋出清單記錄 HTML/JS/CSS 雜湊；
- 資源協議版本不匹配時拒絕繫結；
- 不讓遠端展示產物直接獲得世界書寫入、角色卡覆蓋或模型金鑰；
- 高許可權動作透過 bridge 白名單方法，並在 UI 明確確認。

### 11.5 隱私與日誌

- 診斷匯出預設脫敏 API 地址、token、persona 私密欄位；
- 不把完整聊天自動上傳到遠端分析服務；
- localStorage key 帶專案/角色/協議字首，正式遊戲狀態不得只存本機；
- console 預設不列印完整提示詞、世界書和玩家隱私內容。

## 12. 工程結構與職責契約

```text
src/same-floor/
├─ shell/
│  ├─ index.ts                 # 0 號樓入口、啟動狀態機
│  ├─ App.*                    # 唯一 UI shell
│  ├─ router.ts                # 應用內路由
│  ├─ store.ts                 # snapshot 快取與 UI 狀態
│  └─ views/                   # story / character / inventory / map ...
├─ services/
│  ├─ chat-service.ts          # get/create/set chat messages
│  ├─ generation-service.ts    # /trigger、生成狀態與停止
│  ├─ transcript-index.ts      # 活動線 / Swipe / 回看
│  ├─ game-state-adapter.ts    # 已驗證的 variables / MVU 適配
│  ├─ bridge-client.ts         # 與常駐指令碼協議
│  └─ persistence.ts           # UI state migration
├─ bridge/
│  ├─ index.ts                 # 常駐指令碼入口
│  ├─ event-hub.ts             # ST / Tavern 事件聚合
│  ├─ mount-loader.ts          # 短 mount、遠端產物、版本校驗
│  ├─ presentation-mode.ts     # 僅視覺摺疊原生樓層
│  └─ lifecycle.ts             # chat change / dispose / recovery
├─ protocol/
│  ├─ bridge.ts                # channel、version、payload schema
│  └─ snapshot.ts              # shell 消費的統一 DTO
└─ styles/
```

### 12.1 shell 與 bridge 的最小協議

```typescript
interface SameFloorBridge {
  protocolVersion: 1;
  getSnapshot(): Promise<SameFloorSnapshot>;
  submit(text: string, actionId: string): Promise<void>;
  selectSwipe(messageId: number, swipeId: number): Promise<void>;
  requestShellRefresh(): Promise<void>;
  setPresentationMode(enabled: boolean): Promise<void>;
  subscribe(listener: (event: BridgeEvent) => void): () => void;
}
```

bridge 不應把整個 `window.SillyTavern` 或 `TavernHelper` 原樣暴露給 shell 子元件。協議越小，重繪恢復和許可權審計越清楚。

### 12.2 版本號至少三處

- shell 構建版本；
- bridge 協議版本；
- UI 持久狀態 schema 版本。

三者不是一個概念。只 bump 檔名而不遷移 UI 狀態，會在升級後讀到舊草稿結構並崩潰。

## 13. 高頻錯誤

1. **把宿主 DOM 浮窗叫同層前端**：完整互動閉環不在單個訊息樓層；一個宿主按鈕或浮窗不構成本冊所說的同層前端。
2. **首樓只是開局嚮導卻宣稱完整同層玩法**：必須覆蓋整個回合、回看和恢復鏈。
3. **後續劇情只寫 shell store**：沒有真實訊息，提示詞與存檔都斷鏈。
4. **用 `is_hidden` 隱藏原生樓層**：改變 LLM 上下文語義，是最高風險事故。
5. **直接 `generate()` 當正常回合**：不自動建立樓層，變數管線和回看分裂。
6. **點選選項只改變數不發 user 訊息**：劇情 AI 看不到玩家行為，審計也沒有記錄。
7. **每 token 全量重渲歷史**：長聊天立即卡頓。
8. **事件一來就併發讀取**：舊 snapshot 反蓋新狀態。
9. **重繪前不儲存草稿和 route**：`refreshOneMessage(0)` 後全部丟失。
10. **shell 未 ready 就隱藏其他樓層**：遠端失敗時玩家只剩空白。
11. **遠端 HTML 內塞高許可權邏輯**：供應鏈一旦被替換即可改卡、讀聊天或發訊息。
12. **把 `swipes[]` 當完整分支樹**：它只直接證明單樓候選頁和當前頁。
13. **只適配桌面**：移動端軟鍵盤、自動滾動和 iframe 高度會讓核心輸入不可用。
14. **原生訊息隱藏後沒有無障礙回看**：螢幕閱讀器使用者失去劇情。
15. **切聊天后舊請求仍提交**：A 存檔資料汙染 B 存檔 shell。
16. **橋接指令碼被當作 UI 真相源**：指令碼重啟或熱更新後狀態無法恢復。
17. **錯誤態仍保持 presentation mode**：shell 崩了，原生訊息也看不見。
18. **巨大首樓 HTML 直接進開場白**：提示詞、渲染與升級成本同時爆炸。

## 14. 驗收清單

### 14.1 術語與架構

- [ ] 玩家全程只需使用一個訊息樓層的 shell
- [ ] “同層”按完整遊玩閉環所在樓層定義，不限制應用內部 DOM/iframe 巢狀
- [ ] 真實 user / assistant 樓層持續存在並作為上下文真相源
- [ ] bridge 明確是服務層，不冒充同層 UI 本體
- [ ] 開局頁樣本只被引用為區域性掛載證據

### 14.2 啟動與恢復

- [ ] 0 號樓讀取使用 `getChatMessages(0)` 並處理不存在
- [ ] 入口確認 `getCurrentMessageId() === 0`
- [ ] shell 未 ready 時原生聊天仍可見
- [ ] `refreshOneMessage(0)` 後 route、草稿、回看錨點可恢復
- [ ] 遠端源全部失敗時有本地錯誤殼和重試
- [ ] 聊天切換後舊非同步結果不能寫入新聊天

### 14.3 回合主鏈

- [ ] 玩家行為建立真實 user 訊息
- [ ] `createChatMessages` 後顯式觸發 `/trigger`
- [ ] AI 回覆落為真實 assistant 訊息
- [ ] `MESSAGE_RECEIVED` 後以真實訊息覆蓋流式 preview
- [ ] 穩定主線只選定並適配變數或 MVU 後端
- [ ] 若研究資料庫相容，明確標為 C8 待驗證路線，不併入生產驗收
- [ ] 普通玩家行為不繞過變數框架直接寫正式遊戲狀態

### 14.4 回看與分支

- [ ] 回看節點保留 `message_id` 與 Swipe 標識
- [ ] Swipe 切換寫回 ST，再重讀聊天
- [ ] 編輯、刪除、Swipe、重排後索引能恢復
- [ ] 長聊天有分頁、虛擬化或分章策略
- [ ] 未把單樓 `swipes[]` 誤稱完整分支圖

### 14.5 顯示模式

- [ ] 沒有為視覺目的寫 `is_hidden:true`
- [ ] 沒有刪除、清空或改寫真實樓層正文
- [ ] presentation mode 只改顯示 DOM/CSS
- [ ] shell error / destroy / chat change 會恢復原生訊息
- [ ] 有玩家可操作的“顯示原生聊天”逃生口
- [ ] 新樓層渲染後顯示模式能重新對齊

### 14.6 併發、安全與可訪問性

- [ ] busy 鎖、action_id、epoch 對賬三者都有
- [ ] 停止/失敗不會靜默重複發訊息
- [ ] AI、資料庫、工坊和遠端內容均按不可信輸入處理
- [ ] 子 iframe 使用最小 sandbox 和校驗後的訊息協議
- [ ] 鍵盤、焦點、螢幕閱讀器、減弱動效可用
- [ ] 移動端軟鍵盤、窄屏、旋轉、自動滾動已真機檢查

## 15. 真機懸案

以下均不得以離線推導替代目標版本真機驗證。

| 編號 | 問題 | 當前置信度 | 真機驗證路徑 |
|---|---|---|---|
| U1 | 長聊天或“載入更多訊息”後，0 號樓是否持續保留在 DOM；不在 DOM 時 shell 如何重新呈現 | medium·推導未驗證 | 生成 100+ 樓，重新整理、滾動、載入更多，記錄 0 號 mount 和 `refreshOneMessage(0)` 行為 |
| U2 | `/trigger` 正常生成時各流式、生成、訊息事件的精確順序及停止分支 | medium·推導未驗證 | 記錄時間戳、事件名、message_id、dry_run；分別測試流式完成/停止/報錯 |
| U3 | 歷史 assistant 樓切換 Swipe 後，目標 ST 版本如何處理其後樓層與分支 | medium·推導未驗證 | 建立至少三輪聊天，在中間樓切 Swipe，比較 API 返回、UI 與實際下輪提示詞 |
| U4 | presentation mode 所需宿主訊息容器選擇器在桌面/移動端/主題中的穩定性 | medium·推導未驗證 | 桌面、移動端、不同主題逐項測試新訊息、編輯、刪除、Swipe、聊天切換 |
| U5 | 0 號樓 `data`、chat 變數和 localStorage 在重繪、開局 Swipe、匯出匯入中的具體保留邊界 | medium·推導未驗證 | 分別寫入哨兵值，執行重繪/切 Swipe/匯出匯入後對賬 |
| U6 | 子 iframe 的高度回傳、sandbox 許可權與移動端滾動是否滿足所選子應用 | medium·推導未驗證 | 用最小 sandbox 起一頁地圖/編輯器，測試 resize、焦點、觸控與銷燬 |
| U7 | 遠端 shell 更新時快取、主備源版本不一致和舊 binder 的失敗模式 | medium·推導未驗證 | 故意部署錯版主/備源與斷網，確認協議拒絕、回滾和原生聊天恢復 |
| U8 | 變數後端在 assistant 樓產生後到最終落庫之間的事件延遲 | medium·推導未驗證 | 同輪記錄 `MESSAGE_RECEIVED`、`MESSAGE_UPDATED`、MVU/資料庫完成事件與最終 snapshot |

### 15.1 最小真機迴歸矩陣

至少跑完：

1. 新建聊天首次載入；
2. 傳送一輪自由輸入；
3. 快速雙擊選項；
4. 流式生成完成；
5. 中途停止並重試；
6. Swipe 最新樓；
7. Swipe 歷史樓；
8. 編輯、刪除一條訊息；
9. `refreshOneMessage(0)`；
10. 切換聊天再切回；
11. 遠端源斷網；
12. shell 載入失敗時恢復原生聊天；
13. 100+ 樓長聊天回看；
14. 手機窄屏、軟鍵盤、橫豎屏；
15. 鍵盤與螢幕閱讀器走完整回合；
16. 注入惡意 HTML、URL、資料庫文字驗證轉義。

離線檢查透過不能替代這套門檻。
