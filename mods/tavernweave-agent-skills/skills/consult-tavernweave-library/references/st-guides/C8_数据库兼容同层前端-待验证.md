## 1. 裁決、定義與反定義

### 1.1 本冊研究的物件

**資料庫相容同層前端**是一個待驗證的組合架構：

- [C5 同層前端](./C5_同層前端.md)負責把完整遊玩體驗集中在一個訊息樓層；
- 獨立訊息生成 / 樓層橋負責建立、讀取和恢復真實聊天樓層；
- [C7 資料庫二創前端](./C7_資料庫二創前端.md)負責把資料庫狀態做成作品 UI；
- [C4 資料庫表格模板](./C4_資料庫表格模板.md)負責表結構、填表協議、持久化和公開 API；
- 本冊只研究這幾條鏈如何額外協調，不改變任何一冊的職責。

目標不是讓資料庫“變成同層引擎”，而是讓同層應用在保留真實訊息鏈的同時，安全消費資料庫狀態。

### 1.2 預設裁決

預設結論必須寫清楚：

1. **SP·資料庫常規用於正常多樓層角色卡。**
2. **資料庫不產出樓層資訊。**
3. **資料庫不產出同層完整應用所需的劇情正文、選項和路由。**
4. **資料庫更新回撥不等於“新 assistant 樓已完整提交”。**
5. **資料庫預設不相容 C5。**
6. 相容同層需要另一條獨立訊息 / 樓層橋路線，且當前待驗證。

這不是措辭差異，而是責任邊界。若省略這些前提，後續實現很容易把表格變化誤判成完整回合。

### 1.3 本冊不是什麼

本冊不是：

- 不是“把 C7 放進首樓”就自動完成的部署教程；
- 不是 SP·資料庫官方支援同層的證明；
- 不是讓 `AutoCardUpdaterAPI` 返回劇情正文或訊息 ID 的 API 設計；
- 不是用資料庫表格重建一套偽聊天記錄；
- 不是用狀態欄位代替 SillyTavern 的真實訊息、Swipe 和分支；
- 不是讓資料庫負責呼叫模型、建立樓層或管理路由；
- 不是已驗證的 DC 成品案例清單；
- 不是對任何未公開作品內部實現的推測；
- 不是當前可直接用於生產角色卡的成熟方案。

### 1.4 與 C5 的關係

C5 的功能和量級遠高於開局頁、狀態列或資料庫面板。它要在單個可見樓層內閉合：

- 玩家輸入；
- 正常 AI 生成；
- 劇情正文閱讀；
- 選項與自由行動；
- Swipe、重生成和歷史回看；
- 狀態、揹包、任務、地圖等遊戲系統；
- 路由、設定、恢復和異常降級。

資料庫只覆蓋其中的“結構化遊戲狀態”部分。即使 C7 已經有完整的狀態列和控制中心，也沒有因此獲得 C5 的樓層生成、劇情映象和訊息生命週期能力。

## 2. 為什麼資料庫預設不相容同層

### 2.1 正常多樓層的常規鏈路

SP·資料庫的常規角色可以抽象為：

```text
玩家在正常聊天中傳送訊息
→ SillyTavern 建立真實 user 樓
→ 主模型生成真實 assistant 回覆
→ SP·資料庫監聽 / 消費該回復
→ 解析填表指令或執行對應更新
→ 表格狀態持久化
→ 普通訊息狀態列或 C7 前端讀取新狀態
```

這裡的劇情正文和樓層身份來自 SillyTavern 的正常訊息鏈，不來自資料庫。

### 2.2 C5 額外要求的鏈路

C5 把後續真實訊息隱藏在統一首樓體驗之後，但仍需可靠取得：

```text
本回合玩家輸入
本回合 user 樓 ID
本回合 assistant 樓 ID
當前啟用 Swipe
完整且穩定的 assistant 正文
生成中 / 停止 / 失敗狀態
本回合對應的資料庫更新狀態
首樓應該提交的組合檢視
```

這些欄位不能從資料庫快照推導。表格中“體力減少 5”並不能告訴首樓：

- 哪個樓層觸發了變化；
- 對應哪次 Swipe；
- 劇情正文是什麼；
- 回覆是否仍在流式生成；
- 使用者是否剛剛編輯或刪除了相關樓層；
- 表格變化屬於 AI 填表、玩家手動 CRUD、匯入還是聊天恢復。

### 2.3 狀態更新不等於回合提交

資料庫更新可能來自多種來源：

| 更新來源 | 是否一定有新 assistant 樓 | 是否一定有新劇情正文 |
|---|---:|---:|
| 正常 AI 回覆後的自動填表 | 通常有，但仍需真機確認時序 | 有，正文屬於訊息層 |
| C7 前端手動 CRUD | 否 | 否 |
| 匯入資料庫資料 | 否 | 否 |
| 切聊天后的資料裝載 | 否 | 否 |
| 恢復 / 重放日誌 | 否 | 否 |
| SQLite 批次寫入 | 否 | 否 |

因此，`registerTableUpdateCallback()` 只能說明“表發生了可觀察更新”，不能單獨作為“同層新回合完成”的訊號。

### 2.4 無變化填表也是回合

某一輪劇情可能沒有改變任何表格。若同層應用只等資料庫更新回撥：

- assistant 樓已經生成；
- 劇情正文已經可讀；
- 資料庫快照與上一輪相同；
- 資料庫可能沒有產生同層前端期待的更新通知；
- 首樓會永久停在“等待狀態”。

所以“收到資料庫更新”不能成為唯一提交條件，“沒有資料庫變化”也不能被當成生成失敗。

## 3. 缺失的輸出與關聯契約

### 3.1 資料庫不提供的核心契約

截至本冊列出的兩個已核原始碼快照，不能把公開資料庫 API 當成以下資訊的來源：

| 同層需要的資訊 | 資料庫是否負責 | 正確責任層 |
|---|---:|---|
| 新 assistant 訊息 ID | 否 | 訊息 / 樓層橋 |
| 當前啟用 Swipe ID 或索引 | 否 | 訊息 / 樓層橋 |
| 完整劇情正文 | 否 | 真實訊息層 |
| 流式正文是否結束 | 否 | 生成 / 訊息事件層 |
| 本次動作對應哪個 user 樓 | 否 | 訊息 / 樓層橋 |
| 路由應該進入哪個劇情頁面 | 否 | 同層應用 |
| 選項屬於哪個正文版本 | 否 | 同層應用 + 訊息 / 樓層橋 |
| 表格快照 | 是 | SP·資料庫 |
| 表格 CRUD 結果 | 是 | SP·資料庫公開 API |
| 表格是否發生更新 | 部分可觀察 | 資料庫更新回撥 |

**資料庫不產出樓層資訊**，也沒有義務為每個表格提交附帶訊息 ID。

### 3.2 當前缺少的跨層關聯鍵

理想介面會提供類似：

```typescript
interface HypotheticalTurnCommit {
  chatId: string;
  userMessageId: number;
  assistantMessageId: number;
  swipeId: number;
  generationId: string;
  databaseRevision: string;
}
```

這只是用於說明缺口的假想型別，**不是現有 API**。不得把它複製進專案並聲稱外掛會返回這些欄位。

當前實驗必須自己維護本地 `turnToken`，並透過訊息層證據和資料庫快照變化做關聯。關聯是否足夠穩定，是本冊最關鍵的待驗證專案。

### 3.3 填表開始不等於填表結束

已核快照存在填表開始回撥，但不能據此虛構公開的 fill-end 事件。實驗實現必須承認：

- fill-start 只能證明資料庫開始某段填表流程；
- table-update 可能由非填表寫入觸發；
- 無變化填表未必帶來可觀察的資料差異；
- 多次表更新可能屬於同一輪；
- 回撥先後與訊息樓層可讀時點仍待真機驗證。

在沒有可靠結束契約之前，“資料庫本回合已穩定”只能是帶超時和重讀的推導狀態，不能包裝成確定事實。

## 4. 實驗架構與責任分層

### 4.1 五層責任圖

```text
┌──────────────────────────────────────────────┐
│ 首樓應用 C5                                  │
│ 輸入、劇情、選項、路由、回看、錯誤與降級 UI  │
└───────────────────┬──────────────────────────┘
                    │ action / composite snapshot
┌───────────────────▼──────────────────────────┐
│ 回合協調器 Turn Coordinator（本冊實驗層）     │
│ turnToken、狀態機、時序門、超時、恢復、降級   │
└──────────────┬──────────────────┬────────────┘
               │                  │
┌──────────────▼────────────┐ ┌───▼──────────────────────┐
│ 訊息生成 / 樓層橋          │ │ 資料庫介面卡             │
│ 真實 user/assistant 樓、   │ │ 快照、訂閱、CRUD、       │
│ 正文、Swipe、生成狀態       │ │ revision hint、表契約     │
└──────────────┬────────────┘ └───┬──────────────────────┘
               │                  │
┌──────────────▼──────────────────▼────────────┐
│ SillyTavern 真實聊天 + SP·資料庫持久狀態      │
└──────────────────────────────────────────────┘
```

### 4.2 訊息生成 / 樓層橋

樓層橋必須獨立承擔：

- 把玩家 action 寫入正常訊息鏈；
- 觸發正常主模型生成；
- 等待目標 assistant 樓成為真實可讀訊息；
- 讀取當前啟用 Swipe 的正文；
- 區分流式中、完成、停止和失敗；
- 監聽訊息新增、更新、刪除和聊天切換；
- 在首樓 iframe 重繪後恢復當前回合；
- 把樓層資訊交給協調器，而不是寫入資料庫冒充狀態。

具體樓層 API 與顯示策略以 C5 和目標版本型別宣告為準。本冊不復制一套未經真機核驗的固定事件名。

### 4.3 資料庫介面卡

資料庫介面卡只承擔：

- 執行時發現 `AutoCardUpdaterAPI`；
- 讀取並 clone 當前資料庫快照；
- 歸一化 `mate / sheet_* / content`；
- 訂閱資料庫更新；
- 執行受支援的 CRUD / SQL；
- 記錄可比較的快照指紋或外掛 revision 資訊；
- 在聊天切換時清空舊引用並重新讀取；
- 把“資料更新證據”交給協調器。

它不能返回虛構的樓層 ID，也不能把“資料庫已更新”轉換成“劇情已完成”。

### 4.4 回合協調器

協調器是本冊新增的實驗責任層：

```typescript
interface ExperimentalTurnToken {
  epoch: number;               // 每次切聊天 / 恢復遞增
  localTurnId: string;         // 本應用生成，不是外掛返回值
  startedAt: number;
  userMessageId?: number;
  assistantMessageId?: number;
  swipeIndex?: number;
  floorReadable: boolean;
  generationSettled: boolean;
  dbObserved: 'unknown' | 'filling' | 'changed' | 'unchanged-timeout';
}
```

這段型別是實驗應用自己的狀態，不代表資料庫公開協議。`epoch` 用來讓舊非同步結果失效，避免切聊天后把舊回合提交到新聊天。

### 4.5 首樓應用

首樓只消費協調器給出的組合快照：

```typescript
interface ExperimentalCompositeSnapshot {
  turn: ExperimentalTurnToken;
  narrative: {
    messageId: number;
    swipeIndex: number;
    text: string;
  };
  gameState: unknown;          // 資料庫 adapter 的歸一化結果
  consistency: 'observed' | 'timed-out' | 'degraded';
}
```

首樓不得自己並行猜測訊息和資料庫狀態，否則同一 UI 會出現兩個互不一致的提交路徑。

## 5. 優先路線：真實樓層先生成，再映象到首樓

### 5.1 為什麼優先真實樓層

優先路線必須保留 SillyTavern 正常訊息鏈：

```text
首樓 action
→ 樓層橋建立真實 user 樓並觸發正常生成
→ SillyTavern 建立真實 assistant 樓
→ 樓層橋確認正文可讀且生成結束
→ SP·資料庫按正常方式消費 AI 回覆並填表
→ 資料庫介面卡觀察更新或超時重讀
→ 協調器形成組合快照
→ 首樓提交劇情 + 狀態 UI
```

優勢：

- 不繞過角色卡、世界書、預設與正常提示詞鏈；
- 真實 assistant 樓仍是劇情權威來源；
- Swipe、歷史、聊天存檔仍有宿主語義；
- SP·資料庫仍在它熟悉的多樓層訊息鏈上工作；
- 同層只是顯示和互動層，不偽造資料庫能力。

### 5.2 “先生成”指責任順序，不預判事件順序

“真實樓層先生成，再映象”表示首樓必須先拿到真實樓層證據，不能表示所有目標版本一定按固定順序發出事件。

真機中可能觀察到：

- assistant 訊息先出現、正文隨後流式更新；
- 資料庫 fill-start 與訊息完成接近；
- 一次填表觸發多次表更新；
- 表更新早於某個樓層 UI 的最終重繪；
- 無表變化時只有訊息完成證據。

因此協調器必須收集兩條鏈的證據，而不是把某個回撥排在程式碼前面就當成宿主保證。

### 5.3 最小提交門

建議實驗提交條件：

```text
必須滿足：
1. epoch 仍屬於當前聊天
2. assistantMessageId 已確定
3. 當前 Swipe 正文可讀
4. 正常生成已停止或確認完成

資料庫側滿足其一：
A. 觀察到本輪開始後的資料庫變化，並在短穩定窗內不再變化
B. 超過有上限的等待窗後重讀快照，標記 unchanged-timeout

然後：
提交組合快照，並把 consistency 明確顯示為 observed 或 timed-out
```

這個門仍是待驗證演算法。穩定窗和超時值必須透過實際卡、模型和資料庫版本測量，不能在指南里宣稱存在通用常數。

### 5.4 不要阻塞劇情到無限等待

資料庫更新慢、無變化或失敗時，首樓不能永遠不顯示已完成的真實劇情。達到有界等待後應：

1. 先展示真實劇情；
2. 狀態區顯示“資料庫狀態仍在核對”；
3. 後續若觀察到安全的新快照，再做一次狀態補提交；
4. 無法確認歸屬時停止自動合併並進入降級；
5. 保留返回正常多樓層聊天的入口。

## 6. 其他候選路線及風險

### 6.1 路線 B：擷取流式文字直接渲染

設想：生成時把流式片段直接映象到首樓，完成後再確認真實樓層。

風險：

- 流式文字不是最終 Swipe；
- 中止、重試或宿主修訂會讓首樓殘留舊片段；
- 資料庫可能只在最終文字階段處理；
- 片段與表格更新沒有可靠關聯；
- 惡意或未閉合 HTML 的增量渲染風險更高。

結論：可以作為視覺最佳化實驗，但不能代替真實樓層提交門，待驗證。

### 6.2 路線 C：`generate()` / `generateRaw()` 後手動造樓

設想：在首樓直接呼叫額外生成介面，拿到文字後手動建立 assistant 樓，再讓資料庫處理。

風險：

- 可能繞過正常主回合的提示詞、事件或訊息語義；
- 資料庫是否會消費這種後建樓層取決於目標實現；
- Swipe、停止生成、聊天儲存和錯誤恢復都要自行重建；
- 很容易形成“文字生成成功但資料庫沒填表”的分叉。

結論：不是預設路線。只有在目標版本逐項驗證等價性後，才可保留為專用適配，不得推廣成通用方案。

### 6.3 路線 D：讓資料庫表格儲存劇情正文

設想：把每輪正文、選項和路由都寫進資料庫，再由首樓讀取。

風險：

- 把狀態表變成第二套聊天曆史；
- 與真實訊息、Swipe、編輯、刪樓產生雙事實源；
- 長正文進入表格會惡化 token、效能和遷移；
- 表格仍然沒有宿主的樓層與分支語義。

結論：禁止作為相容方案。資料庫存業務狀態，不存替代真實聊天的完整事件流水。

### 6.4 路線 E：只憑資料庫更新觸發“新回合”

設想：每次 `registerTableUpdateCallback()` 觸發就向首樓追加一輪劇情卡片。

風險：

- 回撥不攜帶劇情正文；
- 同一輪可能多次更新；
- 手動 CRUD 會被誤判為新回合；
- 無變化回合完全丟失；
- 切聊天裝載可能生成假回合。

結論：架構錯誤，不進入真機實驗。

### 6.5 路線 F：資料庫解析完成後再找“最後一樓”

設想：收到表更新後讀取聊天尾部，把最後一個 assistant 樓當成本輪正文。

風險：

- 並發動作、重生成和聊天切換會改變尾部；
- 延遲更新可能對應更早一輪；
- 手動 CRUD 沒有對應樓層；
- 多 tab 或重複觸發會產生競態。

結論：只可作為診斷對照，不能作為生產關聯演算法。

## 7. 回合關聯與組合快照

### 7.1 本地 `turnToken` 的作用

協調器發起玩家 action 時，立即建立本地 token：

```typescript
function beginExperimentalTurn(epoch: number): ExperimentalTurnToken {
  return {
    epoch,
    localTurnId: crypto.randomUUID(),
    startedAt: Date.now(),
    floorReadable: false,
    generationSettled: false,
    dbObserved: 'unknown',
  };
}
```

`localTurnId` 只用於應用內部去重和日誌。它不能注入資料庫後再聲稱成為外掛事務 ID。

### 7.2 必須記錄的證據

每輪至少記錄：

- 聊天 epoch；
- action 建立時間；
- user 樓 ID；
- assistant 樓 ID；
- 當前 Swipe；
- 訊息最後更新時間或內容指紋；
- 生成開始、停止、失敗時點；
- 資料庫 fill-start 時點（若可觀察）；
- 資料庫 update 回撥次數；
- 更新前後快照指紋；
- 最終提交狀態與超時原因。

日誌中不得輸出完整私密正文或完整資料庫快照；使用 ID、計數、表名、雜湊和耗時即可。

### 7.3 組合快照不是新事實源

組合快照只是一份渲染投影：

```text
narrative 仍由真實 assistant 樓決定
gameState 仍由 SP·資料庫決定
turnToken 只記錄本次協調證據
UI router 只記錄本機呈現狀態
```

重新整理後應從真實訊息和資料庫重新構建。不能只靠記憶體中的組合快照恢復全部遊戲。

### 7.4 快照指紋只用於觀察

可以對 clone 後的歸一化資料庫快照計算穩定雜湊，用來判斷“看起來是否變化”。但它：

- 不是資料庫 revision；
- 不能證明沒有內部提交；
- 不能證明變化屬於當前樓層；
- 不能代替公開 CRUD 返回值；
- 不能代替 V2 日誌的真實 revision 語義。

雜湊只用於實驗觀測和 UI 去重。

### 7.5 同一輪多次資料庫更新

一輪可能更新多個表或分批提交。協調器應：

1. 把同一觀察窗內的回調合併為 dirty 標記；
2. 每次都從公開 API 重讀新快照；
3. 不直接使用回撥給出的活動物件作為 UI 可變 store；
4. 在短穩定窗結束後才標記 `observed`；
5. 後續遲到更新無法確定歸屬時，顯示狀態修訂，而不是重放劇情。

穩定窗策略仍待驗證。

## 8. 事件、狀態機與提交條件

### 8.1 實驗狀態機

```text
IDLE
  │ 玩家 action
  ▼
ACTION_QUEUED
  │ 真實 user 樓已建立
  ▼
GENERATING
  │ assistant 樓可讀
  ▼
FLOOR_READABLE
  │ 生成已停止 / 完成
  ▼
WAITING_DATABASE
  ├─ 觀察到更新 ──> DB_RECONCILING
  ├─ 有界超時 ────> DB_UNCHANGED_TIMEOUT
  └─ 錯誤 ────────> DEGRADED

DB_RECONCILING / DB_UNCHANGED_TIMEOUT
  │ 組合快照提交
  ▼
READY

任意狀態：切聊天 / epoch 變化 → CANCELLED → 恢復新聊天
任意狀態：證據衝突 → DEGRADED → 顯示正常多樓層入口
```

### 8.2 狀態含義

| 狀態 | 含義 | 首樓允許做什麼 |
|---|---|---|
| `IDLE` | 沒有活動回合 | 可提交 action |
| `ACTION_QUEUED` | action 已鎖定，尚未確認 user 樓 | 禁止重複提交 |
| `GENERATING` | 正常主模型生成中 | 顯示進度，可停止 |
| `FLOOR_READABLE` | assistant 樓存在，但生成狀態仍需確認 | 可預覽，不最終提交 |
| `WAITING_DATABASE` | 劇情已穩定，資料庫證據未收齊 | 顯示劇情，狀態區提示核對中 |
| `DB_RECONCILING` | 觀察到表變化，等待短穩定窗 | 只更新狀態草稿 |
| `DB_UNCHANGED_TIMEOUT` | 沒觀察到變化，已重讀快照 | 允許帶標記提交 |
| `READY` | 組合檢視已提交 | 可進入下一 action |
| `DEGRADED` | 證據衝突或關鍵能力缺失 | 恢復正常多樓層顯示 |
| `CANCELLED` | 舊 epoch 的非同步任務失效 | 禁止寫入當前 UI |

### 8.3 併發門

一個聊天 epoch 預設只允許一個活動的劇情回合 token。以下行為必須被拒絕或排隊：

- 生成中再次點選項；
- fill-start 後又提交第二個 action；
- 舊 assistant 樓尚未確認就開始重生成；
- 切聊天過程中繼續寫回舊資料庫；
- 首樓重繪導致重複繫結後再次傳送同一 action。

若作品確實需要並行生成，必須為每條生成鏈建立宿主可驗證的獨立關聯鍵；當前本冊不聲稱已有這種能力。

### 8.4 遲到事件

每個非同步回撥在提交前都檢查：

```typescript
function isCurrentTurn(epoch: number, localTurnId: string): boolean {
  return coordinator.epoch === epoch
    && coordinator.activeTurn?.localTurnId === localTurnId;
}
```

舊 epoch、舊 token 或已取消任務的結果只能寫診斷日誌，不能更新首樓 store。

## 9. 資料庫回撥、競態與生命週期

### 9.1 更新回撥的正確定位

資料庫更新回調適合：

- 標記資料庫 store dirty；
- 觸發一次去抖後的權威重讀；
- 更新 C7 狀態 UI；
- 給協調器增加“資料庫發生變化”的證據。

不適合：

- 建立 assistant 樓；
- 推斷劇情正文；
- 推斷當前 Swipe；
- 宣告生成結束；
- 自動把最後一樓繫結到當前 token；
- 直接觸發下一輪劇情。

### 9.2 同一函式引用登出

如果目標版本提供 `registerTableUpdateCallback()` / `unregisterTableUpdateCallback()`，必須保留同一個函式引用：

```typescript
const onTableUpdate = () => {
  coordinator.markDatabaseDirty();
};

api.registerTableUpdateCallback(onTableUpdate);

function disposeDatabaseSubscription() {
  api.unregisterTableUpdateCallback(onTableUpdate);
}
```

首樓 iframe 會重繪。每次 mount 建立新匿名函式卻不登出，會造成重複回撥、重複重讀和錯誤的“多次填表”證據。

### 9.3 fill-start 的洩漏風險

在已核 `spv5.5.6` 快照中可見公開 fill-start 註冊入口，但沒有與之對稱的公開登出入口。若目標安裝版本仍是這種能力形狀：

- 不要讓短命首樓 iframe 每次 mount 註冊新閉包；
- 把 fill-start 監聽收口到常駐指令碼 bridge；
- bridge 內只註冊一次，再向首樓釋出自有可登出事件；
- 或完全不依賴 fill-start，只用訊息狀態與表更新做實驗觀測；
- 切聊天時清空 bridge 內的當前 token，不重複註冊外掛回撥。

升級版本可能改變該能力，必須執行時檢測並對實際安裝版本真機複核。

### 9.4 沒有公開 fill-end 時怎麼辦

不得發明 `registerTableFillEndCallback()`。缺少可靠結束訊號時只能：

1. 以訊息生成結束作為劇情鏈完成證據；
2. 用資料庫 update 回撥觸發重讀；
3. 用有上限的穩定窗觀察是否繼續變化；
4. 超時後帶 `timed-out` 標記提交；
5. 後續遲到變化作為狀態修訂，不重複追加劇情；
6. 把實際回撥序列記錄進真機報告。

這仍是待驗證折中，不是強一致事務。

### 9.5 手動 CRUD 與自動填表衝突

當資料庫正在核對本回合更新時，C7 的手動編輯應：

- 預設停用對同一業務記錄的提交；
- 或把草稿排到回合協調完成後；
- 提交前重讀最新快照並按業務鍵重新定位行；
- 檢查公開 CRUD 返回值；
- 寫後再次讀取權威快照；
- 衝突時顯示明確錯誤，不靜默覆蓋。

資料庫 UI 鎖不是跨層事務鎖，不能解決劇情生成、AI 填表和手動 CRUD 的全部競態。

## 10. Swipe、重生成、編輯、刪樓與回滾

### 10.1 Swipe 是獨立劇情版本

切換 Swipe 後，首樓必須至少重新讀取：

- assistant 訊息 ID；
- 當前 Swipe 索引；
- 當前正文；
- 該樓之後的有效訊息鏈；
- 當前資料庫快照；
- 資料庫是否已隨 Swipe 回滾或重算。

不能只切換首樓的文字標籤。資料庫能否自動回到與該 Swipe 對應的狀態、何時完成、V2 日誌怎樣對映，必須逐目標版本真機驗證。

### 10.2 重生成

重生成可能保持訊息位置但產生新 Swipe，也可能觸發不同事件序列。實驗實現必須：

1. 取消舊 token 的待提交任務；
2. 建立新的 `localTurnId`；
3. 記錄重生成前資料庫指紋；
4. 等待新 Swipe 真實可讀；
5. 重新觀察資料庫更新；
6. 無法證明資料庫與新 Swipe 一致時進入降級。

禁止沿用上一 Swipe 的資料庫“已觀察”標誌。

### 10.3 編輯 user 或 assistant 樓

編輯歷史訊息會改變上下文，但不保證資料庫自動重放。需要分別驗證：

- 編輯 user 樓是否觸發任何資料庫動作；
- 編輯 assistant 正文是否重新解析填表；
- 歷史編輯是否使後續資料庫狀態過期；
- 資料庫是否有恢復到某 revision 的公開、安全路徑；
- 首樓怎樣標記“劇情和狀態可能不一致”。

在答案不明確前，歷史編輯後應停止同層自動狀態合併並顯示正常聊天 / 資料庫檢查入口。

### 10.4 刪除樓層

刪樓後必須假設以下內容都可能失效：

- 當前活動 token；
- 已快取 message ID；
- Swipe 選擇；
- 後續劇情映象；
- 資料庫與訊息鏈的對應關係。

首樓不能只從回看列表移除一條記錄。它應取消活動任務、重讀整段訊息鏈、重讀資料庫，並在無法證明回滾一致時進入降級。

### 10.5 回滾與 checkpoint

資料庫自身的 V2 checkpoint / log 語義由 C4 負責。本冊不得：

- 透過前後快照 diff 偽造資料庫 operation；
- 把 UI 的“返回上一頁”當資料庫回滾；
- 用匯入舊 JSON 冒充與 Swipe 對齊的事務回退；
- 在不清楚 revision 父子關係時重放寫入。

真正的“訊息分支與資料庫 revision 對齊”是 C8 轉正前必須解決的待驗證核心。

### 10.6 失敗後的使用者選擇

發生 Swipe / 編輯 / 刪樓衝突時，至少給使用者三種可理解的操作：

1. 返回正常多樓層聊天檢查真實訊息；
2. 開啟資料庫原生或 C7 檢查介面確認狀態；
3. 放棄本次同層映象並從已確認節點重新開始。

不得只彈出“未知錯誤”後繼續自動寫表。

## 11. 切聊天、重新整理與恢復

### 11.1 聊天 epoch

切聊天時必須原子地：

1. `epoch += 1`；
2. 取消舊聊天的 active turn；
3. 清空舊訊息快取；
4. 丟棄舊資料庫物件引用；
5. 等待新聊天訊息鏈可讀；
6. 等待新聊天資料庫資料就緒；
7. 分別重建 narrative 和 gameState；
8. 完成健康檢查後再決定是否啟用同層顯示。

舊回撥遲到時因為 epoch 不匹配而被丟棄。

### 11.2 首樓 iframe 重繪

首樓 iframe 不是常駐程序。重繪後：

- 不重新向外掛註冊無法登出的 fill-start 閉包；
- 從常駐 bridge 獲取當前 epoch 和活動回合摘要；
- 重新讀取真實訊息，而不是相信舊 DOM；
- 重新 clone 資料庫快照；
- 恢復 UI router 之前先驗證對應聊天 ID；
- action 按鈕直到恢復完成前保持停用。

### 11.3 頁面重新整理

頁面重新整理後記憶體 token 會丟失。恢復邏輯不能假裝知道重新整理前某個 fill-start 屬於哪一樓：

- 若沒有持久的、可驗證的回合關聯證據，標記為 `recovered-uncertain`；
- 讀取當前真實聊天尾部和資料庫快照；
- 不自動補做 CRUD；
- 不自動重觸發生成；
- 讓使用者選擇繼續同層觀察或回到正常多樓層。

### 11.4 新聊天與空資料庫

新聊天可能先出現首樓，而資料庫仍未裝載或尚無表資料。啟動必須區分：

- API 尚未出現；
- API 已出現但資料未就緒；
- 合法空表；
- 模板尚未匯入；
- 資料庫載入失敗；
- 當前外掛版本沒有所需方法。

這些狀態不能統一顯示成“沒有角色資料”。

## 12. 正常多樓層降級與止損

### 12.1 降級原則

相容同層失敗時，系統必須回到資料庫本來支援的正常多樓層玩法，而不是讓整張卡不可用：

```text
同層健康
→ 首樓統一呈現，真實樓層僅做可逆顯示隱藏

同層不健康
→ 解除顯示隱藏
→ 恢復正常訊息流
→ 保留普通 C7 狀態列 / 控制中心
→ 禁止協調器繼續自動提交
```

顯示隱藏不得修改提示詞語義，不得把真實訊息永久標成不參與上下文。

### 12.2 觸發降級的條件

任一條件成立即降級：

- 無法發現訊息 / 樓層橋；
- 資料庫公開 API 缺少必要能力；
- assistant 樓在有界時間內不可讀；
- 聊天 epoch 在回合中變化；
- 收到無法歸屬的遲到資料庫更新；
- Swipe 後資料庫一致性無法確認；
- 回撥重複註冊或次數異常；
- 首樓 mount 失敗；
- 資料庫寫入返回失敗；
- 真實訊息和首樓映象內容指紋不一致；
- 使用者主動選擇“返回正常聊天”。

### 12.3 失敗時禁止的動作

進入降級後禁止：

- 自動重發玩家訊息；
- 自動重新生成 assistant 回覆；
- 自動匯入舊資料庫快照；
- 猜測最後一樓並繼續填表；
- 隱藏錯誤並把狀態標成 READY；
- 在未知聊天上繼續執行舊 CRUD。

### 12.4 工程止損

本路線若在同一核心問題上連續除錯 2–3 輪仍無法穩定復現，應暫停繼續堆補丁，做架構複審：

- 宿主是否能提供足夠的訊息完成證據；
- 資料庫是否有可用的提交 / revision 關聯資訊；
- 是否應保留正常多樓層 + C7，而砍掉同層相容；
- 是否需要外掛上游新增正式橋接契約；
- 是否應把實驗重寫成只讀映象，而不是可互動完整 C5。

未解決關聯鍵和回滾前，不得因 UI 看起來能跑就轉正。

## 13. 版本政策與執行時能力檢測

### 13.1 不寫死外掛基線

SP·資料庫會持續更新。本冊不規定“只有某個固定版本才是基線”，也不承諾未來版本保留當前方法和時序。

截至 2026-07-14，本冊可列出的只是兩份**已核原始碼快照**：

| 快照 | commit | 用途 |
|---|---|---|
| 釋出標籤 `spv5.5.6` | `2020b14c0672e74409a3d98c8a9899e13069ca3f` | 對照公開 API 與歷史實現 |
| 2026-07-14 所見 upstream `main` | `708e66ba58dfe0a08d34cba7cb8730a8f8ff1e80` | 檢查主線相對釋出標籤的能力變化 |

這兩項不是永久基線，也不等於“已驗證支援 C8”。實際施工必須以使用者當前安裝版本為準。

### 13.2 啟動時能力檢測

示意：

```typescript
function inspectDatabaseCapabilities(api: unknown) {
  const x = api as Record<string, unknown> | null;
  return {
    exportSnapshot: typeof x?.exportTableAsJson === 'function',
    subscribeUpdate: typeof x?.registerTableUpdateCallback === 'function',
    unsubscribeUpdate: typeof x?.unregisterTableUpdateCallback === 'function',
    subscribeFillStart: typeof x?.registerTableFillStartCallback === 'function',
  };
}
```

能力檢測只回答“方法是否存在”，不證明：

- 簽名沒有變化；
- 回撥時序適合當前協調演算法；
- 方法在當前 provider 模式行為一致；
- 訊息 iframe 可以直接訪問宿主 API；
- 同層相容已經驗證。

### 13.3 記錄實際環境

每份真機報告至少記錄：

- SillyTavern 版本；
- Tavern Helper / 酒館助手版本；
- SP·資料庫實際安裝來源、標籤或 commit；
- 原生模式或 SQLite 模式；
- 角色卡與資料庫模板版本；
- 瀏覽器 / WebView 與裝置；
- 是否使用流式；
- 模型來源與是否經過代理；
- 首樓構建版本、bridge 協議版本；
- 實際檢測到的 API 能力表。

不能只寫“最新版”。

### 13.4 版本不匹配策略

若執行時能力與本冊實驗預期不一致：

1. 不繼續猜 API 名；
2. 不讀取外掛內部全域性變數補洞；
3. 關閉同層協調器；
4. 恢復正常多樓層玩法；
5. 保留只讀診斷資訊；
6. 對照實際版本原始碼後再更新 C8 文件版本。

## 14. 最小實驗原型

### 14.1 P0：只讀雙源觀測器

第一階段禁止隱藏正常訊息流，只做：

- 首樓顯示當前真實 assistant 樓 ID、Swipe 和正文摘要；
- 顯示資料庫快照指紋、表數量和更新時間；
- 記錄訊息事件與資料庫回撥時間線；
- 手動生成仍從正常 ST UI 發起；
- 不執行資料庫寫入；
- 不宣稱回合已經關聯。

驗收目標：證明兩條鏈都能穩定觀察，且重新整理、切聊天不串資料。

### 14.2 P1：首樓發起正常回合

在 P0 穩定後增加：

- 首樓 action → 真實 user 樓；
- 正常主模型生成；
- assistant 樓真實可讀；
- 有界等待資料庫；
- 組合快照只顯示，不隱藏原生樓層；
- 所有 action 有冪等鍵和重複提交保護。

驗收目標：同一 action 只產生一條預期訊息鏈，資料庫無變化回合不會卡死。

### 14.3 P2：健康門控下的可逆顯示模式

只有 P1 通過後才增加：

- 首樓健康時隱藏普通樓層的顯示；
- 真實樓層仍參與上下文與存檔；
- 任一健康檢查失敗立即解除隱藏；
- 使用者始終有顯式“顯示正常聊天”按鈕；
- 重新整理後預設先顯示正常聊天，健康確認後再切同層。

驗收目標：顯示適配失敗不影響角色卡繼續遊玩。

### 14.4 P3：高風險生命週期

最後才驗證：

- Swipe；
- 重生成；
- 編輯歷史訊息；
- 刪除樓層；
- 資料庫回滾 / 恢復；
- 切聊天；
- 長聊天；
- 移動端；
- 原生 / SQLite 雙模式。

P3 任一主鏈無法證明一致性，C8 繼續保持待驗證狀態。

### 14.5 原型不包含什麼

最小原型階段不要同時開發：

- 大型地圖和複雜動畫；
- 多套皮膚；
- 跨裝置雲同步；
- 批次資料庫編輯器；
- 第二 API；
- 多模型並行劇情；
- 自定義資料庫持久化替代方案。

先證明“真實樓層與資料庫狀態能安全協調”，再擴充套件產品功能。

### 15.2 元件不得直接碰兩套 API

UI 元件只能讀取組合 store、傳送 action。禁止一個元件同時：

- 呼叫樓層 API；
- 讀取 `AutoCardUpdaterAPI`；
- 修改 router；
- 猜測生成結束；
- 寫本地恢復狀態。

否則任何一次重繪都可能產生重複監聽和交叉寫入。

### 15.3 診斷時間線

建議統一記錄：

```typescript
interface DiagnosticEvent {
  at: number;
  epoch: number;
  localTurnId?: string;
  source: 'shell' | 'chat' | 'generation' | 'database' | 'coordinator';
  type: string;
  messageId?: number;
  swipeIndex?: number;
  snapshotHash?: string;
  detail?: string;
}
```

需支援匯出脫敏時間線，以便判斷真實順序，而不是靠 UI 觀感猜測。

### 15.4 必備不變數

測試至少斷言：

1. 同一 `localTurnId` 最多提交一份最終劇情；
2. 舊 epoch 永遠不能更新新聊天 store；
3. 每個更新回撥註冊都有可證明的單例或登出路徑；
4. 未確認 assistant 樓時不能標記 READY；
5. 資料庫回撥不能建立劇情樓；
6. 超時必須有上限；
7. 降級必須恢復正常多樓層顯示；
8. 手動 CRUD 不得被識別為新劇情回合；
9. 無資料庫變化的回合仍能展示真實劇情；
10. 重新整理恢復不能自動重發 action。

### 15.5 安全邊界

- AI 正文、資料庫單元格和錯誤資訊都按不可信輸入渲染；
- 禁止把正文或表格值直接交給 `innerHTML` / `v-html`；
- 遠端前端資源使用可審計版本和失敗殼；
- 診斷匯出預設脫敏角色名、正文和使用者輸入；
- bridge 對 shell 暴露最小方法，不透傳整個宿主視窗；
- 寫操作必須檢查聊天 epoch 和業務許可權；
- 錯誤降級不應刪除、編輯或隱藏真實資料。

## 16. 真機驗證矩陣

### 16.1 基礎回合

| 編號 | 場景 | 必查證據 | 透過條件 |
|---|---|---|---|
| B01 | 新聊天第一輪 | user/assistant 樓、生成狀態、資料庫時間線 | 只提交一次，劇情與狀態可讀 |
| B02 | 連續三輪 | 每輪 token、樓層 ID、快照指紋 | 不串輪、不重複、不丟輪 |

| B04 | 資料庫無變化 | assistant 樓與超時路徑 | 劇情正常顯示，不無限等待 |

## 17. 轉正門檻

### 17.1 文件狀態門

C8 當前是 `v0.1.0`、待驗證。只有同時滿足以下條件，才可以討論升為生產指南：

- 實際安裝版本和宣告支援版本均有完整環境記錄；
- 訊息 / 樓層橋的生成完成、樓層可讀和 Swipe 契約有真機證據；
- 資料庫回撥真即時序已記錄，不再依賴虛構 fill-end；
- 無變化填表回合不會卡死；
- 手動 CRUD、匯入和恢復不會被誤判為劇情回合；
- 切聊天、重新整理和 iframe 重繪無回撥洩漏；
- Swipe、重生成、編輯、刪樓和回滾有明確一致或安全降級結果；
- 原生 / SQLite 的聲明範圍分別透過；
- 正常多樓層降級在所有嚴重錯誤下可用；
- 至少一張真實角色卡完成長聊天迴歸，而非只跑合成 demo；
- 關鍵鏈路經過獨立審查；
- 所有“推導未驗證”項要麼獲得證據，要麼明確移出支援範圍。

### 17.2 強一致性門

若仍無法回答下面三個問題，禁止轉正：

1. 當前資料庫狀態如何證明對應當前 assistant 樓與 Swipe？
2. Swipe / 編輯 / 刪樓後，資料庫如何證明已回到一致 revision？
3. 無資料庫變化時，協調器如何區分“合法無變化”和“填表流程失效”？

允許的答案可以是“目標上游新增了正式契約”，也可以是“專案收窄功能，停用無法一致處理的操作並可靠降級”；不允許用時間猜測冒充證據。

### 17.3 產品體驗門

技術鏈路通過後，還需確認：

- 首樓完整遊玩體驗達到 C5 的功能和量級，不是開局頁或資料庫面板；
- 載入、生成、核對、超時、衝突和降級狀態玩家能理解；
- 返回正常聊天的入口始終可用；
- 移動端輸入、鍵盤、滾動和焦點可用；
- 長劇情與大量表格不會阻塞渲染；
- 錯誤不會讓玩家誤以為存檔已安全提交。

### 17.4 轉正文件流程

滿足門檻後也不能直接刪掉“待驗證”字樣。應：

1. 彙總逐項真機證據；
2. 明確支援的 ST、酒館助手和資料庫版本範圍；
3. 把仍未驗證的路線移到懸案；
4. 由總監確認是否升版與改名；
5. 同步 C4、C5、C7、批次說明和收集藍圖；
6. 保留本冊 `v0.x` 的歷史裁決記錄。

在總監確認之前，本冊繼續標註：**待驗證，禁止生產引用。**

本冊不能被概括成“SP·資料庫支援同層”。準確說法只能是：

> 正常多樓層是 SP·資料庫的常規角色卡使用方式；資料庫不產出樓層資訊，預設不相容 C5。C8 研究由獨立訊息 / 樓層橋補齊劇情與樓層契約、再與資料庫狀態協調的額外路線；該路線截至 2026-07-14 仍待驗證，禁止作為成熟生產方案引用。
