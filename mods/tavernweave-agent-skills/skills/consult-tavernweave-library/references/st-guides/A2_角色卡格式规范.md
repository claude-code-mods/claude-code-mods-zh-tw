## 置信度分級體系

**三級分類**
- **high**：多源一致 + 執行時原始碼直接驗證，可直接施工
- **medium**：單源或推斷，施工前建議真機驗證

## 1. 格式演進脈絡

### 1.1 版本對照表

| 版本 | `spec` 值 | `spec_version` | 關鍵新增 |
|---|---|---|---|
| V1 | 無（欄位即頂層） | 無 | name/desc/personality/scenario/first_mes/mes_example 六欄位 |
| V2 | `"chara_card_v2"` | `"2.0"` | data 包裝層 + character_book + extensions + creator/tags/system_prompt 等 |
| V3 | `"chara_card_v3"` | `"3.0"`（接受 ≥3.0 <4.0） | ccv3 PNG chunk 優先 + data.assets（CharX 格式新增）；ST 服務端對 data 內容驗證極寬鬆 |

來源：`src/validator/TavernCardValidator.js`、`src/character-card-parser.js` | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

### 1.2 雙 spec 並存問題

ST 的 `charaFormatData` 函式在寫入時**只寫 V2**（`spec: 'chara_card_v2'`），但 `character-card-parser.js` 的 `write()` 函式同時嵌入 chara（V2）和 ccv3（V3）兩個 PNG chunk；`read()` 時 ccv3 優先。

> 原始碼校準注：`write()` 函式頭註釋寫"ccv3 is not supported and removed"，但實際程式碼（行 32-40）確實寫入了 ccv3 chunk（try/catch 包裹，失敗則跳過），註釋與實現矛盾，以程式碼實際行為為準。

**關鍵行為**：
- 磁碟上 JSON 檔案通常是 V2 格式（`spec: 'chara_card_v2'`）
- 卡內 PNG 同時包含兩個 chunk，V3 chunk 僅新增 `spec='chara_card_v3'` + `spec_version='3.0'` 兩個欄位
- 本地實戰卡（卡A/卡B）**直接存 V3 JSON**（`spec: 'chara_card_v3'`），ST 驗證器對 data 內容檢查極寬鬆（只驗 data 存在且是物件）

來源：`src/character-card-parser.js` write()/read() 函式 | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

## 3. data 層欄位參考

### 3.1 V2 data 層標準欄位（完整列表）

```
data: {
  // ── V1 同名欄位（全部保留在 data 內，頂層也複製一份）──
  name, description, personality, scenario, first_mes, mes_example,

  // ── V2 新增欄位 ──
  creator_notes,              // 創作者備註，不注入提示詞
  system_prompt,              // 替換全域性 system prompt；支援 {{original}} 佔位
  post_history_instructions,  // 替換 UJB/jailbreak；支援 {{original}}
  alternate_greetings,        // string[]，開場訊息 swipe 列表
  tags,                       // string[]，大小寫不敏感
  creator,                    // 創作者署名
  character_version,          // 版本字串，供前端排序
  extensions,                 // object，第三方擴充套件名稱空間
  character_book,             // 可選，內嵌世界書

  // ── V3 新增欄位（ST validator 未強制校驗）──
  group_only_greetings,       // string[]（spec 定義，本地生產卡未使用）
  assets,                     // CharX 格式專用，見第 6 章
}
```

**V2 必須透過 ST 驗證器的欄位**（`TavernCardValidator.js #validateDataV2()`）：

`name, description, personality, scenario, first_mes, mes_example, creator_notes, system_prompt, post_history_instructions, alternate_greetings, tags, creator, character_version, extensions`

其中 `alternate_greetings` 和 `tags` 必須是 Array，`extensions` 必須是 object。

**V3 驗證器**（`#validateDataV3()`）僅驗證 `data` 存在且 `typeof data === 'object'`，data 內部欄位**不檢查**，這是"ST 驗證極寬鬆"的準確範圍（僅對 V3 成立，V2 有14欄位強校驗）。

來源：`src/validator/TavernCardValidator.js` | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

## 4. character_book（內嵌世界書）

### 4.1 書級欄位

```json
{
  "name": "世界書名稱",
  "description": "描述（可空）",
  "extensions": {},
  "entries": []
}
```

**ST 驗證器要求**：`extensions`（object）+ `entries`（array）必須存在；`name`、`description` 為可選。

`scan_depth`、`token_budget`、`recursive_scanning` 是 spec_v2.md 中定義的書級欄位，但 ST 實際儲存在 `extensions` 內而非書頂層（見 12.2 懸案）。

來源：`TavernCardValidator.js #validateCharacterBookV2()` | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

### 4.2 entry 核心欄位（spec 標準）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | number | 條目 ID（內部序號） |
| `keys` | string[] | 主觸發關鍵詞陣列 |
| `secondary_keys` | string[] | 次級關鍵詞（配合 selective + selectiveLogic 使用） |
| `comment` | string | 人類可讀備註/標題 |
| `content` | string | 注入提示詞內容（可含 Markdown、HTML、自定義標籤） |
| `constant` | boolean | 常駐觸發（無需關鍵詞啟用） |
| `selective` | boolean | 是否啟用次級關鍵詞過濾 |
| `insertion_order` | number | 同 position 組內插入順序（數值越小越前） |
| `enabled` | boolean | 是否啟用 |
| `position` | string | 插入位置字串列舉，見 4.3 |
| `use_regex` | boolean | 關鍵詞匹配是否允許正則 |
| `extensions` | object | ST 擴充套件欄位，見 4.4 |

來源：`src/endpoints/characters.js convertWorldInfoToCharacterBook()` + 本地實戰卡 | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

### 4.3 position 欄位列舉（雙軌機制）

`position` 欄位有**兩套值**，必須同時正確設定，是最高頻踩坑點。

**字串形式**（character_book 條目頂層 `position` 欄位，僅兩個值）：

| 字串值 | 含義 |
|---|---|
| `"before_char"` | 角色定義之前（position 數字 0） |
| `"after_char"` | 角色定義之後（所有其他位置的通用兜底值） |

**數字形式**（`extensions.position`，ST 內部完整 8 位置列舉）：

```javascript
export const world_info_position = {
    before: 0,       // "before_char" / Before Char Defs
    after: 1,        // "after_char" / After Char Defs
    ANTop: 2,        // Author's Note 頂部
    ANBottom: 3,     // Author's Note 底部
    atDepth: 4,      // @ Depth（需配合 extensions.depth 和 extensions.role）
    EMTop: 5,        // Example Messages 頂部
    EMBottom: 6,     // Example Messages 底部
    outlet: 7,       // Outlet（透過 {{outlet::Name}} 宏手動插入）
};
```

**轉換規則**：`convertWorldInfoToCharacterBook()` 將 position 0 對映為 `"before_char"`，其他全部對映為 `"after_char"`——因此字串形式**僅能表達兩種位置**，完整的 8 位置體系存於 `extensions.position`（數字）。

**本地實戰卡驗證**（卡B v2.6.0 實測精確資料）：
- 頂層 `position: "before_char"` 的共 19 條，其中 `extensions.position: 4`（atDepth）9 條，`extensions.position: 0` 10 條
- 頂層 `position: "after_char"` 的共 9 條，這 9 條的 `extensions.position` 全部為 **0**（before_char 數字值）
- **重要發現**：生產卡的頂層 position 字串與 `extensions.position` 數字存在**系統性不對應**——生產卡是直接組裝的 JSON，未經過 `convertWorldInfoToCharacterBook()` 轉換對映。ST 讀取時以 `extensions.position` 數字為實際語義，頂層字串欄位形同虛設。
- **施工規範**：直接手寫卡時，頂層 `position` 字串只需寫合法值（`"before_char"` 或 `"after_char"` 任一），真實位置**只看 `extensions.position` 數字**。

來源：`src/endpoints/characters.js` + `public/scripts/world-info.js` + 本地實戰卡 | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]` `[本地實戰]`

```json
{
  "position": 0,
  "exclude_recursion": false,
  "display_index": 0,
  "probability": 100,
  "useProbability": true,
  "depth": 4,
  "selectiveLogic": 0,

  "group": "",

  "prevent_recursion": false,
  "delay_until_recursion": false,
  "scan_depth": null,

  "delay": 0,
  "match_persona_description": false,
  "match_character_description": false,
  "match_character_personality": false,
  "match_character_depth_prompt": false,
  "match_scenario": false,
  "match_creator_notes": false,
  "triggers": [],
  "ignore_budget": false,
  "cfSortKey": 0
}
```

**關鍵欄位語義**：
- `selectiveLogic`：0 = AND（主+次），1 = NOT（非次），2 = OR（主或次）
- `role`：atDepth 時的訊息 role：0 = system，1 = user，2 = assistant
- `sticky`：觸發後持續 N 樓
- `cooldown`：觸發後冷卻 N 樓
- `delay`：至少有 N 樓才啟用
- `cfSortKey`：同源卡工作流私有排序鍵

> 校準注：`convertWorldInfoToCharacterBook()` 原始碼中 `sticky/cooldown/delay/group_weight/probability` 的預設值為 `?? null`（源欄位缺失時填 null）；但生產卡（卡B 2.6.0）中這些欄位的實際值為 `sticky:0, cooldown:0, delay:0, group_weight:100, probability:100`——因為生產卡的 entries 由 ST 世界書編輯器初始化（有各自預設值），而非來自外部轉換。正規化程式碼中的值（0/100）來自生產卡實測，是正確的卡內實際值；`?? null` 僅在從外部 world info 檔案匯入時出現。

來源：`convertWorldInfoToCharacterBook()` 函式完整程式碼 + 本地實戰卡 | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]` `[本地實戰]`

## 5. PNG tEXt chunk 嵌入格式

### 5.1 讀寫機制

**寫入（`write()` 函式）**：
1. 刪除所有現有 `chara` 和 `ccv3` chunk
2. 將完整 JSON 字串 UTF-8 → Base64 編碼
3. 插入 `chara` chunk（V2）：`PNGtext.encode('chara', base64Data)`，插入 IEND 之前
4. 嘗試解析 JSON，加 `spec='chara_card_v3'`、`spec_version='3.0'`，再插入 `ccv3` chunk（V3）

**讀取（`read()` 函式）**：
1. 提取所有 tEXt chunk
2. 優先匹配 `ccv3`（V3），其次 `chara`（V2），均大小寫不敏感
3. Base64 解碼 → UTF-8 字串 → JSON.parse

```javascript
// V2 chunk key: 'chara'
// V3 chunk key: 'ccv3'
// 編碼: Buffer.from(jsonString, 'utf8').toString('base64')
```

**當前僅支援 PNG**（WEBP 格式未實現），非 PNG 格式丟擲錯誤。

來源：`src/character-card-parser.js` | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

### 5.2 匯入格式支援

| 格式 | 函式 | 關鍵邏輯 |
|---|---|---|
| PNG | `importFromPng` | 讀 tEXt chunk → `getCharaCardV2()` |
| JSON | `importFromJson` | `spec !== undefined` → readFromV2；`name !== undefined` → V1；`char_name` → Pygmalion/gradio |
| YAML | `importFromYaml` | YAML 解析後同 JSON 流程 |
| CharX | `importFromCharX` | ZIP 包含 card.json + assets/ 目錄 |
| BYAF | `importFromByaf` | ZIP 包含聊天背景、角色影像等資源 |

來源：`src/endpoints/characters.js` | 適用版本：ST v1.14.0 | **置信度：high** `[執行時原始碼]`

## 6. V3 新增特性：data.assets（CharX 格式）

CharX（.charx）是 ZIP 包裝格式，`card.json` 內的 `data.assets` 陣列支援以下結構：

```json
{
  "uri": "embedded://sprites/happy.png",
  "type": "emotion",
  "name": "happy",
  "ext": "png"
}
```

**`type` 合法值**：`"icon"` / `"user_icon"` / `"emotion"` / `"expression"` / `"background"` / 其他（歸為 misc）

**URI 字首**：`"embeded://"` 或 `"embedded://"` 或 `"__asset:"` 均支援（拼寫容錯）

**影像副檔名支援**：png、jpg、jpeg、webp、gif、apng、avif、bmp、jfif

**group_only_greetings**：spec 定義存在，但 ST 服務端程式碼無處理邏輯，本地生產卡未使用（見 12.1 懸案）。

來源（assets）：`src/charx.js` | 來源（group_only_greetings）：spec_v2.md | 適用版本：ST v1.14.0 | **置信度：high**（assets）`[執行時原始碼]` / **medium·單源孤證**（group_only_greetings）`[文件·單源]`

## 7. regex_scripts（卡內正則指令碼）

### 7.1 欄位結構

```javascript
// RegexScriptData typedef（來源 public/scripts/char-data.js）
{
  id: string,            // UUID，唯一標識
  scriptName: string,    // 指令碼顯示名稱
  findRegex: string,     // 正則表示式字串（含標誌，如 /pattern/gi）
  replaceString: string, // 替換字串（支援特殊宏，見 7.3）
  trimStrings: string[], // 替換後從結果中移除的字串列表
  placement: number[],   // 執行作用域陣列（見 7.2）
  disabled: boolean,
  markdownOnly: boolean, // 僅在 markdown 渲染時執行
  promptOnly: boolean,   // 僅在 prompt 組裝時執行
  runOnEdit: boolean,    // 訊息編輯時也執行
  substituteRegex: number, // 0=不替換宏, 1=原始替換, 2=轉義後替換
  minDepth: number | null, // 最小樓深限制（null=不限；typedef 宣告為 number，實測可為 null）
```

## 11. 高頻避坑

### 11.1 頂層 spec 與 data 層必須同步

ST 在 `readFromV2()` 時讀 `data` 層，在直接訪問時讀頂層，兩層均要寫且保持一致。本地生產卡直接存 V3 JSON（`spec: "chara_card_v3"`），但 ST 服務端的 `charaFormatData()` 寫 V2；PNG 嵌入時 `write()` 會在 V2 基礎上追加 V3 chunk。

**置信度：high** `[執行時原始碼]` `[本地實戰]`

### 11.2 character_book.extensions 必須存在

`TavernCardValidator` 的 `#validateCharacterBookV2()` 要求 `character_book` 必須同時包含 `extensions`（object）和 `entries`（array），否則驗證失敗導致匯入報錯。手寫卡常見遺漏 `character_book.extensions: {}`。

> 實測補充：卡A 3.0.2 生產卡的 `character_book` 頂層只有 `{entries, name, description}`，**缺少 `extensions`**——但該卡是 V3（`spec: "chara_card_v3"`），V3 驗證器（`#validateDataV3`）只驗 data 存在，不呼叫 `#validateCharacterBookV2`，因此不會報錯。此陷阱僅對 V2（`spec: "chara_card_v2"`）匯入路徑有效；V3 卡繞過此檢查。

**置信度：high** `[執行時原始碼]`

### 11.3 position 欄位的雙軌坑

`entry.position`（字串）只有 `"before_char"` 和 `"after_char"` 兩個值，**永遠**不應寫 `"atDepth"` 等字串。atDepth 等高階位置必須透過 `entry.extensions.position = 4` 來指定，同時 `entry.position` 寫 `"before_char"` 作為相容值。

**置信度：high** `[執行時原始碼]` `[本地實戰]`

### 11.4 正則 findRegex 必須是完整正則字串（含 `/flags`）

ST 的 `RegexProvider.instance.get(regexString)` 期望傳入類似 `/pattern/gi` 形式的字串，而非裸 pattern。本地實戰卡全部使用該格式：`"findRegex": "/<tag>/gi"`。

**置信度：high** `[本地實戰]` `[執行時原始碼]`

### 11.5 `markdownOnly: true` + `placement: [2]` 是 AI 輸出美化的標準組合

`promptOnly: true` 的正則**不在**渲染層執行，只作用於發給 AI 的提示詞。狀態列/氣泡等顯示類正則必須 `markdownOnly: true, promptOnly: false, placement: [2]`。

**置信度：high** `[執行時原始碼]` `[本地實戰]`

> 校準補充：`engine.js` 中 `getRegexedString` 邏輯已驗證：`markdownOnly && isMarkdown` 和 `promptOnly && isPrompt` 分別控制執行路徑，原始碼與生產卡實踐一致。

### 11.6 `substituteRegex: 0` 是預設安全值

生產卡預設用 0（不替換宏），僅當 findRegex 裡需要 `{{char}}` 等宏替換時才改為 1 或 2。值 2 會轉義所有正則元字元，導致複雜正則失效。

**置信度：high** `[執行時原始碼]` `[本地實戰]`

### 11.7 extensions 名稱空間應隔離

spec_v2.md 規定：第三方工具寫入 `extensions` 時必須用命名字首（如 `agnai_xxx` 或 `{"myapp": {...}}`），不得直接寫裸欄位。ST 官方欄位：`talkativeness`、`fav`、`world`、`depth_prompt`、`regex_scripts`。

**置信度：medium·單源孤證** `[文件·單源]`

### 11.8 `json_data` 欄位的特殊地位

ST 服務端儲存時會在頂層附加 `json_data` 欄位（包含完整原始 JSON），用於保留未知欄位。`charaFormatData()` 第一步就從 `json_data` 解析出 `char` 物件。匯出時會 `unsetPrivateFields()` 移除該欄位，不會出現在匯出卡中。

**置信度：high** `[執行時原始碼]`

## 12. 懸案與不確定項

### 12.1 group_only_greetings 的實際 ST 實現狀態

**現象**：spec_v2.md 定義了該欄位，本地生產卡（卡A/卡B）的 `data` 層有該欄位但為空陣列，ST 服務端程式碼（`characters.js`）無任何處理邏輯。

**兩種可能**：(a) ST 客戶端側（`public/scripts/`）有處理，服務端不需要；(b) 該欄位僅為 spec 預留，ST 尚未實現。

**真機驗證路徑**：在 ST 中建立 `group_only_greetings` 非空的角色卡，加入群聊，觀察開場訊息是否切換。

**置信度：low** `[文件·單源]`

### 12.2 character_book.scan_depth / token_budget / recursive_scanning 的儲存位置

spec_v2.md 定義這些書級欄位，但本地實戰卡的 `character_book` 頂層只有 `name`、`description`、`entries`（卡A）或加 `extensions`（卡B）。

**回源結論（原始碼+生產卡已明確）**：
- `convertWorldInfoToCharacterBook()` 返回值只有 `{entries, name}`，不輸出這三個欄位
- 卡B 2.6.0 的 `character_book.extensions` 只含 `world/export_source/mvu_worldbook_name`，無 `scan_depth/token_budget/recursive_scanning`
- 兩生產卡頂層均無這三欄位
- **結論**：這三個書級欄位在 ST v1.14.0 的卡內 `character_book` 中**不被寫入或儲存**，由 ST 全域性世界書設定覆蓋管理，不隨卡匯出

仍存疑：客戶端 `world-info.js` 讀取 character_book 時是否會用到這些欄位（若存在的話），需真機在 character_book 中手動寫入這三欄位後驗證 ST 是否識別。

**置信度：medium·推導有佐證** `[執行時原始碼]` `[本地實戰]`（欄位不寫入已雙重確認；客戶端讀取行為未驗證）

### 12.3 atDepth position 的 extensions.role 取值 1/2 的實際作用

`role: 0/1/2`（對應 system/user/assistant）僅在 `extensions.position = 4`（atDepth）時有意義。本地實戰卡的 atDepth 條目全部使用 `role: 0`（system）。其他 position 值下 role 欄位是否被忽略未經原始碼驗證。

**真機驗證路徑**：建立 atDepth + role=1(user) 的條目，檢視 ST prompt 組裝時該條目的 message role。

**置信度：medium·推導未驗證** `[本地實戰]`（role=0 已實測；role=1/2 推斷有效但未真機確認）

### 12.4 ccv3 chunk 與 chara chunk 同時存在時的客戶端行為

服務端 `read()` 明確 ccv3 優先，客戶端 `public/scripts/utils.js` 的 `extractDataFromPng(data, identifier = 'chara')` 是獨立實現，預設 identifier 為 `'chara'`，**不讀 ccv3**。

**回源結論（客戶端原始碼已明確）**：
- 服務端（`character-card-parser.js read()`）：ccv3 優先 → chara 回退
- 客戶端（`utils.js extractDataFromPng()`）：只讀 `'chara'`（V2），**不識別 ccv3**

實際影響：ST 中 PNG 匯入走服務端路徑（服務端解析後存 JSON），客戶端的 `extractDataFromPng` 主要用於本地預覽或前端操作場景，通常不直接影響匯入流程。真機影響未驗證。

**置信度：high** `[執行時原始碼]`（兩端行為已分別在原始碼中確認）

### 12.5 世界書繫結（data.extensions.world）與 character_book 的關係

本地實戰卡兩者均存在且同名。`charaFormatData()` 在有 `data.world` 時讀取世界書檔案後賦給 `data.character_book`。

**回源結論（原始碼已明確）**：兩個分支（`file.originalData` 和 `file.entries`）均使用 `_.set(char, 'data.character_book', ...)` 直接**覆蓋**，不合並。若 `data.world` 指向有效檔案，原有 `character_book` 內容會被完全替換。

仍存疑：`readWorldInfoFile` 第三個引數 `false` 的含義（是否控制是否讀 `originalData`），以及兩個分支 if 之間是否互斥——需閱讀 `readWorldInfoFile` 實現確認。

**置信度：high** `[執行時原始碼]`（覆蓋邏輯已直接讀取原始碼確認）
