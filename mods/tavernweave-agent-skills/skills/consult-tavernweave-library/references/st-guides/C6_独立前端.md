# 獨立前端：把單張角色卡作品做成 Web / App / PC 產品

> 文件版本：v1.0.0 ｜ 最後更新：2026-07-14

> **第一原則：程式本身就是這一張角色卡。**
>
> 獨立前端不是“另做一個能匯入角色卡的聊天客戶端”，也不是把 SillyTavern 頁面包進另一個容器。角色設定、世界觀、初始場景、提示詞規則、變數或資料庫結構、劇情規則、UI、資產、模型接入和存檔協議，全部是該作品應用工程內部的版本化原始碼與內建資源。開發倉庫即使把它們編譯成內部只讀內容包，那也只是程式模組，不是供玩家匯入、匯出或獨立流通的“角色卡封裝體”。玩家執行程式後建立的是這一個作品的存檔、角色例項或周目，不是匯入另一張 PNG / JSON 卡。

本冊討論單張角色卡的**產品化獨立執行**。Web、移動 App、PC 軟體只是同一作品的三個發行殼；共享內容域與執行時核心，不依賴 SillyTavern、Tavern Helper、MVU 或 ST-Prompt-Template 才能工作。

相關邊界：

- ST 樓層內的常規狀態列、控制中心見 [C2_前端應用-狀態列與控制中心.md](./C2_前端應用-狀態列與控制中心.md)。
- 全部遊玩介面集中在 ST 首樓的“同層前端”見 [C5_同層前端.md](./C5_同層前端.md)。
- 本冊的獨立前端**完全脫離 ST 執行時**；ST 只可能在開發期作為舊作品素材的遷移來源。

## 1. 定義與反定義

### 1.1 正確定義

獨立前端是將一張角色卡從“宿主中的內容包”升級為“可獨立發行的互動作品”：

```text
單張作品內容
  ├─ 角色、世界、劇情規則
  ├─ Prompt、Lore、宏、變數 Schema
  ├─ UI、玩法系統、音畫資產
  └─ 內容版本與遷移
          │
          ▼
共享執行時核心
  ├─ Prompt 編譯與 Lore 掃描
  ├─ 模型閘道器與流式生成
  ├─ 狀態事務與存檔
  ├─ 訊息分支 / Swipe / 檢查點
  └─ 安全渲染
          │
          ├─ Web 殼
          ├─ 移動 App 殼
          └─ PC 殼
```

三個殼執行的是**同一作品、同一內容版本、同一存檔語義**。平臺層只處理檔案、金鑰、網路、更新、通知和視窗等能力差異。

### 1.2 明確不是

- 不是 SillyTavern 內的 iframe、擴充套件、指令碼或首樓頁面。
- 不是套殼開啟一個 ST 網址。
- 不是“匯入任意角色卡後聊天”的通用客戶端。
- 不是角色卡 PNG / JSON 的檢視器或啟動器。
- 不是執行時再解析一份卡片封裝體。
- 不是把 Tavern Helper、MVU、EJS 或酒館正則原樣複製出去。
- 不是把模型回覆當 HTML 或 JavaScript 直接執行。

### 1.3 獨立性的硬門

滿足以下條件才可以稱為獨立前端：

1. 在沒有安裝或啟動 ST 的裝置上能新建周目、遊玩、儲存、退出和恢復。
2. 生產構建不讀取 ST 的目錄、資料庫、全域性物件、事件或外掛 API。
3. 作品內容作為原始碼或經過編譯的內容包隨應用釋出。
4. 執行時只管理本作品的存檔；沒有“角色卡匯入”作為主入口。
5. Web、App、PC 的同一存檔遵循同一 Schema 和遷移序列。
6. 模型不可繞過 Schema 校驗直接改狀態，也不可直接執行宿主程式碼。

## 2. 目標玩家體驗

獨立前端的產品體驗應從“開啟一張卡”改寫為“開啟一個作品”：

1. 首次啟動：閱讀作品說明、隱私與模型配置。
2. 建立玩家 Persona：名稱、稱謂、頭像、代詞和作品允許的自定義項。
3. 選擇開局：難度、路線、預設身份、可選內容或隨機種子。
4. 建立周目：由內建初始化器生成狀態，不依賴聊天樓層變數。
5. 進入主介面：劇情、狀態、地圖、角色、揹包、任務等模組按作品設計呈現。
6. 玩家輸入文字或點選玩法動作。
7. 引擎編譯 Prompt、選擇 Lore、請求模型並流式顯示。
8. 結構化狀態變更經過校驗後與本回合訊息原子提交。
9. 玩家可以重試、Swipe、分支、回到檢查點或另開周目。
10. 應用更新後，舊存檔經過顯式遷移繼續使用；失敗時保留可回滾備份。

“角色卡感”來自作品內容與玩法閉環，不來自是否保留 ST 的介面。

## 3. 總架構：內容域與引擎域分離

### 3.1 內容域：這張卡是什麼

內容域只描述本作品：

- `work.json`：作品 ID、名稱、內容版本、最低引擎版本、語言和分級。
- `characters/`：主角、NPC、關係錨點、臺詞約束。
- `world/`：世界觀、地點、組織、事件和 Lore 條目。
- `prompts/`：系統契約、文風、行為規則、輸出協議和裝配計劃。
- `state/`：狀態 Schema、初值工廠、遷移、可寫路徑和約束。
- `rules/`：玩法動作、劇情門檻、數值聯動、結局條件。
- `scenes/`：開場、教程、固定事件、可選章節。
- `ui/`：本作品專屬的頁面、面板、文案和主題 Token。
- `assets/`：角色立繪、背景、音訊、字型、影片等受控資源。
- `locales/`：面向玩家的本地化文字；Prompt 本地化應另設版本。

內容域應該能被構建工具做靜態檢查：缺失引用、重複 ID、無效狀態路徑、超預算 Prompt、孤立資產和遷移斷檔都應在釋出前失敗。

### 3.2 引擎域：這張卡怎樣執行

引擎域提供與作品內容解耦的執行能力：

- 內容註冊與版本檢查。
- 周目和 Persona 初始化。
- Prompt 編譯、宏替換、Lore 掃描和 Token 預算。
- 模型供應商適配、流式事件、取消、重試和錯誤歸一化。
- 訊息樹、Swipe、分支、檢查點和摘要。
- 狀態操作解析、Schema 校驗、許可權檢查和事務提交。
- 存檔、備份、遷移、匯出和同步衝突處理。
- Markdown / 富文字安全渲染。
- 音畫資產解析、快取和生命週期。
- 平臺能力埠。

引擎可以在多個內部專案複用，但**發行產物鎖定到當前作品內容**。複用引擎不等於在產品裡提供多卡匯入。

### 3.3 平臺域：同一作品怎樣發行

平臺域只實現埠：

- 檔案選擇、儲存和分享。
- 金鑰安全儲存。
- HTTP / SSE / 流式請求。
- 資料庫、原子寫和備份目錄。
- 通知、剪貼簿、視窗、深鏈和系統主題。
- 更新檢查、簽名校驗和崩潰恢復。

作品規則不能散落在平臺殼中；否則三個端會產生不同劇情和不同存檔語義。

## 4. 內建內容包與構建產物

### 4.1 內容清單

建議每次釋出生成不可變清單：

```ts
export interface WorkManifest {
  workId: string;
  contentVersion: string;
  schemaVersion: number;
  promptVersion: string;
  minEngineVersion: string;
  defaultLocale: string;
  entrySceneId: string;
  assetManifestHash: string;
  contentHash: string;
}
```

`workId` 一經發布不可改。顯示名稱可以改，但存檔、雲同步和更新定位都依賴穩定 ID。

### 4.2 構建期而非執行時裝配

構建工具應完成：

1. 讀取本作品內容原始碼。
2. 校驗所有 ID、引用和 Schema。
3. 編譯 Prompt 模板和 Lore 索引。
4. 為資產計算雜湊並生成清單。
5. 生成初始狀態的確定性測試樣本。
6. 驗證從所有受支援舊 Schema 到當前 Schema 的遷移鏈。
7. 輸出 Web / App / PC 共用的只讀內容包。

生產執行時不應臨時猜測條目關係，也不應從一張外部角色卡中動態拼出作品規則。

### 4.3 資源定址

內部資源使用作品自己的邏輯 URI：

```text
work://character/lily/portrait/default
work://background/academy/night
work://audio/bgm/home
```

構建器將邏輯 URI 對映為帶雜湊的 Web URL、App bundle path 或 PC asset path。劇情和狀態只儲存邏輯 URI，不儲存某個平臺的絕對路徑。

### 4.4 內容可更新但不可漂移

- 內容包與程式碼包分別版本化。
- 每個內容包宣告 `minEngineVersion`。
- Prompt、狀態 Schema、資產清單分別有版本或雜湊。
- 線上增量包必須簽名並校驗雜湊。
- 已開始的周目記錄建立時的內容版本；更新後由遷移器顯式升級。
- 不能在伺服器無版本地熱改 Prompt，讓同一存檔第二天出現不可追溯的行為變化。

## 5. 一回合的主鏈路

推薦把一回合實現為可觀察事務：

```text
玩家輸入 / UI 動作
  → Command 規範化
  → 讀取當前周目快照
  → 規則前置校驗
  → Lore 掃描與 Prompt 編譯
  → ModelGateway 流式生成
  → 回覆正文與結構化操作分離
  → 狀態操作 Schema + 許可權校驗
  → 訊息、狀態、生成記錄原子提交
  → UI 投影重新整理
```

必須保留以下證據：

- 本次使用的內容、Prompt、Schema 和模型配置版本。
- 編譯後的 Prompt Trace，而不一定長期儲存完整敏感 Prompt。
- 命中的 Lore ID 與裁剪原因。
- 請求 ID、開始和結束時間、取消或失敗原因。
- 原始結構化操作、校驗結果和最終提交差異。

若正文成功但狀態操作非法，預設策略應由作品明確選擇：

- **嚴格模式**：整回合不提交，提示重試。
- **正文保留模式**：提交正文但拒絕狀態操作，並標記該回合需要修復。
- **修復模式**：向專用修復器請求一次受限重寫，再校驗；禁止無限重試。

不能靜默吞掉非法操作，否則玩家看到的劇情和真實狀態會長期分叉。

## 6. 狀態、資料庫與多周目

### 6.1 一個作品，多份例項

執行時的主要實體建議為：

```text
Work（唯一作品）
  ├─ Persona（玩家身份，可跨周目複用）
  ├─ Playthrough / 周目
  │    ├─ 當前狀態快照
  │    ├─ 訊息與分支
  │    ├─ 檢查點
  │    ├─ 摘要與長期記憶
  │    └─ 生成審計記錄
  └─ Settings（模型、顯示、無障礙）
```

“新建角色”在這裡通常是新建周目中的玩家例項或劇情角色例項，不是把另一張角色卡匯入角色庫。

### 6.2 狀態 Schema

Schema 是本作品狀態的唯一事實源。除型別外，還應宣告：

- 預設值與首次建立規則。
- 玩家、規則引擎、模型各自允許寫的路徑。
- 數值範圍、列舉、引用完整性和容量上限。
- 哪些欄位是派生值，不允許持久化或由模型寫。
- 哪些欄位涉及敏感資訊，需要加密或匯出脫敏。

推薦把模型寫入限制為顯式操作：

```ts
export type StateOperation =
  | { op: 'set'; path: string; value: unknown }
  | { op: 'increment'; path: string; delta: number }
  | { op: 'append'; path: string; value: unknown }
  | { op: 'remove'; path: string };

export interface StatePolicy {
  canWrite(actor: 'player' | 'engine' | 'model', op: StateOperation): boolean;
  validate(nextState: unknown): ValidationResult;
}
```

不要允許模型提交任意 JavaScript、SQL 或表示式。

### 6.3 初始狀態

初始狀態由純函式建立：

```ts
createInitialState({
  persona,
  routeId,
  difficulty,
  seed,
  contentVersion,
}): WorkState
```

相同輸入應得到可重放的基線。需要隨機性的部分使用記錄在存檔中的種子。

### 6.4 存檔事務

單次成功提交至少原子寫入：

- 新訊息或新 Swipe。
- 啟用分支指標。
- 狀態版本和差異。
- 摘要失效標記。
- 生成元資料。

推薦採用“快照 + 受控事件日誌”：

- 快照用於快速載入。
- 事件用於審計、檢查點和遷移除錯。
- 定期壓縮，避免無限增長。
- 事件日誌不是讓模型自由寫入的流水賬。

### 6.5 遷移與回滾

```ts
export interface SaveMigration {
  from: number;
  to: number;
  migrate(input: unknown): unknown;
  verify(output: unknown): ValidationResult;
}
```

規則：

1. 遷移只向前逐級執行，不能跳過中間版本。
2. 遷移前建立備份。
3. 新 Schema 校驗失敗時不覆蓋原檔。
4. 遷移器必須冪等或明確拒絕重複執行。
5. 發行前用匿名化真實舊檔回放。
6. 降級開啟高版本存檔時只讀或拒絕，禁止猜測性回寫。

## 7. Prompt 編譯器

### 7.1 Prompt 是編譯產物

不要在 UI 點擊發送時臨時字串拼接。編譯器接收確定輸入並返回訊息列表、預算報告和來源軌跡：

```ts
export interface PromptCompiler {
  compile(input: {
    manifest: WorkManifest;
    persona: Persona;
    state: WorkState;
    branch: MessageBranch;
    command: PlayerCommand;
    model: ModelProfile;
  }): Promise<PromptCompilation>;
}

export interface PromptCompilation {
  messages: Array<{ role: 'system' | 'user' | 'assistant'; content: string }>;
  trace: PromptTraceItem[];
  estimatedInputTokens: number;
  reservedOutputTokens: number;
}
```

### 7.2 推薦裝配順序

下列順序是**作品工程建議，不是 Character Card 規範強制順序**：

1. 引擎安全契約和結構化輸出契約。
2. 本作品總規則、角色核心和文風錨點。
3. 當前場景和玩法模式規則。
4. 當前 Persona 與經過過濾的狀態投影。
5. 本回合命中的 Lore。
6. 長期摘要和關鍵記憶。
7. Token 預算內的近期訊息。
8. 當前玩家輸入或 UI 動作描述。
9. 狀態操作允許路徑與本回合特殊約束。

作品可以調整，但裝配順序必須配置化、版本化、可做 Golden Test，不能藏在多個頁面元件裡。

### 7.3 Token 預算

建議先計算：

```text
可用輸入 = 模型上下文上限
         - 預留輸出
         - 協議安全餘量
```

裁剪優先順序由作品明確：

1. 安全契約、輸出協議和當前玩家輸入不可裁。
2. 角色核心和當前狀態只允許使用預先定義的緊湊投影。
3. Lore 按優先順序、劇情相關性和預算選擇。
4. 近期歷史按完整回合裁剪，不從中間截斷角色訊息。
5. 較舊歷史先進入摘要，再移出近期視窗。

每次編譯輸出 `PromptTrace`，至少列出“加入、裁剪、原因、估算 token”。沒有 Trace 的 Prompt 最佳化只能靠猜。

## 8. 內建 Lore、宏與劇情規則

### 8.1 Lore 掃描器

獨立作品應定義自己的穩定 `LoreEntry`，而不是在執行時借用 ST 世界書物件：

```ts
export interface LoreEntry {
  id: string;
  enabled: boolean;
  constant?: boolean;
  keys?: string[];
  secondaryKeys?: string[];
  matchMode?: 'any' | 'all' | 'regex';
  scanTurns?: number;
  priority: number;
  insertion: 'before-core' | 'after-core' | 'history-depth' | 'state';
  contentTemplateId: string;
  recursive?: boolean;
}
```

掃描流程：

1. 取配置範圍內的玩家輸入、近期訊息和允許參與匹配的狀態文字。
2. 啟用 constant 條目。
3. 做主鍵、次鍵和條件匹配。
4. 需要遞迴時，用已啟用內容繼續掃描；設定 visited 集合與最大輪數。
5. 去重，每個條目一次。
6. 按優先順序與插入位點排序。
7. 在獨立 Lore 預算內裁剪。
8. 輸出命中與裁剪軌跡。

正則關鍵詞使用 RE2 類引擎或 Worker 超時；不得讓一個惡意或失控模式凍結 UI。

### 8.2 宏系統

宏只讀顯式上下文：

```ts
export interface TemplateContext {
  char: CharacterView;
  user: PersonaView;
  state: Readonly<WorkStateProjection>;
  turn: number;
  locale: string;
  seed: string;
}
```

原則：

- 使用白名單註冊的純函式宏。
- 相同種子下的隨機宏可重放。
- 未知宏在構建期報錯，或在執行時以可見診斷降級。
- 不提供任意檔案、網路、DOM、資料庫或程式碼執行能力。
- Prompt 模板和玩家顯示模板分開，避免敏感狀態意外顯示。

### 8.3 劇情與玩法規則

“滿足條件才能解鎖地點”“使用物品扣除數量”這類確定性規則優先由引擎執行，不交給模型自由判斷。推薦分三層：

- **確定性層**：狀態機、數值、許可權、冷卻、任務門檻。
- **生成約束層**：本回合必須表現或避免的內容。
- **敘事層**：模型在邊界內自由生成。

模型負責敘事，不應同時充當唯一資料庫和唯一規則裁判。

## 9. 模型閘道器與流式生成

### 9.1 統一埠

```ts
export interface ModelGateway {
  generate(
    request: ModelRequest,
    options: { signal: AbortSignal; requestId: string },
  ): AsyncIterable<ModelEvent>;
}

export type ModelEvent =
  | { type: 'text-delta'; text: string }
  | { type: 'usage'; inputTokens?: number; outputTokens?: number }
  | { type: 'structured-output'; value: unknown }
  | { type: 'finish'; reason: string }
  | { type: 'error'; code: string; retryable: boolean; message: string };
```

供應商介面卡只負責：

- 請求格式轉換。
- 鑑權頭。
- SSE / chunk 流解析。
- 錯誤歸一化。
- Tokenizer 選擇。
- 能力宣告，例如 system role、JSON Schema、圖片、工具呼叫。

作品規則不得寫進供應商介面卡。

### 9.2 取消、重試與遲到資料

- 每次生成有唯一 `requestId`。
- 玩家取消時觸發 `AbortController`，並把嘗試標記為 cancelled。
- 取消後到達的 chunk 必須丟棄，不能寫入下一次請求。
- 自動重試只用於確定可重試的網路錯誤，並有上限和退避。
- 已收到正文後不得隱式全量重試；由玩家選擇繼續、重試或保留部分內容。
- 同一個重試產生新的生成嘗試，但可以掛在同一 Swipe 組下。

### 9.3 BYOK、代理與本地模型

可以支援：

- 玩家自帶 API Key 直連。
- 作品方受控代理。
- OpenAI-compatible 本地或遠端端點。
- PC 端本地模型。

不同接入方式必須顯示資料流向、計費主體和隱私邊界。應用“可離線啟動”不等於“無模型也能生成”；離線能力要拆成 UI/存檔可用與本地推理可用兩項說明。

## 10. 訊息、Swipe、分支與一致性

### 10.1 資料模型

不要只存一條可變字串陣列。建議：

```ts
export interface TurnNode {
  id: string;
  parentId: string | null;
  role: 'user' | 'assistant' | 'system-event';
  activeVariantId: string;
  variants: MessageVariant[];
}

export interface MessageVariant {
  id: string;
  content: string;
  status: 'streaming' | 'complete' | 'cancelled' | 'failed';
  generationId?: string;
  stateCommitId?: string;
  createdAt: number;
}
```

### 10.2 一致性規則

- Swipe 建立新 variant，不覆蓋舊文字。
- 從舊訊息改寫並繼續時建立分支，不偷偷改寫原分支後代。
- 每個 assistant variant 繫結它提交的狀態版本。
- 切換 Swipe 時，如果後續狀態依賴不同，必須切換對應分支或明確重放。
- 刪除訊息前列出將失效的後代、摘要、檢查點和狀態提交。
- 編輯歷史訊息後，舊摘要與 Prompt cache 標記失效。
- 每次生成儲存模型、取樣引數、Prompt 版本和內容版本，便於復現。

### 10.3 檢查點

檢查點至少包含：

- 活躍分支末端。
- 狀態快照 ID。
- 摘要版本。
- 隨機種子狀態。
- 內容與 Schema 版本。

回到檢查點要建立新分支，不破壞原時間線。

## 11. UI 與玩法系統

### 11.1 UI 是作品的一部分

獨立前端不必模仿聊天軟體。可以按作品設計：

- 劇情閱讀區與輸入框。
- 地圖、任務、揹包、角色關係、日曆。
- 視覺小說式立繪和背景。
- 戰鬥、調查、經營等專用操作面板。
- 開局嚮導、章節選擇、結局圖鑑。
- 存檔管理、分支樹和 Prompt 診斷頁。

UI 只通過 selector 讀狀態，透過 command dispatch 改狀態；頁面元件不得直接寫資料庫。

### 11.2 玩家動作統一為 Command

```ts
export type PlayerCommand =
  | { type: 'send-text'; text: string }
  | { type: 'choose-option'; optionId: string }
  | { type: 'use-item'; itemId: string; targetId?: string }
  | { type: 'travel'; locationId: string }
  | { type: 'system'; action: 'retry' | 'continue' | 'checkpoint' };
```

每個 Command 經過相同的規則、Prompt、生成和事務鏈路，避免按鈕玩法與文字輸入形成兩套互相不同步的狀態。

### 11.3 安全渲染

- 模型回覆先作為不可信文字處理。
- Markdown 轉換後再用嚴格白名單清洗。
- 預設刪除 `script`、事件屬性、危險 URL 和可執行嵌入。
- 結構化玩法元件由應用根據受信任 DSL 渲染，不執行模型返回的 HTML。
- 外鏈開啟前提示域名；遠端圖片預設可停用或走代理。
- CSS 使用元件作用域或 Shadow DOM，不能讓回覆修改整站樣式。

### 11.4 無障礙與移動體驗

- 鍵盤可完成傳送、取消、切換 Swipe 和打開面板。
- 流式區域使用節制的 live region，避免每個 token 都朗讀。
- 支援系統字型縮放、減少動畫、高對比度與觸控目標。
- 輸入法組合期間不得誤傳送。
- 移動端軟鍵盤彈出時保證輸入框和取消按鈕可見。

## 12. Web / App / PC 三殼

### 12.1 共享邊界

共享：

- 內容包和內容版本。
- Prompt、Lore、宏、規則和狀態引擎。
- 訊息樹、存檔模型和遷移。
- 模型閘道器協議。
- 絕大多數 UI 元件與主題。

不強行共享：

- 金鑰儲存實現。
- 檔案、資料庫和原子寫介面卡。
- 更新、通知和系統選單。
- 原生 HTTP、深鏈和視窗行為。
- 後臺執行與生命週期。

### 12.2 Web 殼

建議能力：

- IndexedDB 儲存存檔和資源快取。
- PWA 快取應用殼與內建內容，可離線開啟和管理存檔。
- File System Access API 僅作為增強，保留下載/上傳兜底。
- Service Worker 更新必須顯示“等待重啟”，不要在生成中途換版本。
- 瀏覽器直連供應商受 CORS 限制；失敗時使用受控代理或明確告知不支援。
- 瀏覽器端 API Key 不應放在普通 LocalStorage；至少使用隔離儲存、會話模式與清除入口，並明確其安全上限。

### 12.3 移動 App 殼

可以使用 Capacitor、React Native、Flutter 或其他方案；選擇不改變共享 core 邊界。

需要處理：

- iOS / Android 安全金鑰庫。
- 系統分享、檔案匯入匯出和照片許可權。
- App 進入後臺時的網路暫停、WebView 回收和流式中斷。
- 前臺恢復後的生成狀態核對；不能假設長連線仍存在。
- 大資源解壓、低記憶體和磁碟配額。
- 商店隱私清單、內容分級和賬戶刪除要求。

後臺被殺時，未完成生成標記為 interrupted；恢復後讓玩家選擇重試，不能把半截流當成完整回合提交。

### 12.4 PC 殼

可以使用 Tauri、Electron 或原生 UI：

- 系統 Keychain / Credential Manager 儲存金鑰。
- 原子檔案備份、可選擇的存檔目錄和自動備份。
- 原生 HTTP 可繞過瀏覽器 CORS，但仍要做目標域名限制和 SSRF 防護。
- 支援本地模型、GPU 能力檢測和下載管理時，要與雲端介面卡走同一閘道器協議。
- 自動更新必須簽名；失敗能回滾到上一版本。
- 檔案關聯只應面向本作品自己的存檔或內容包格式，不應把產品變成通用角色卡匯入器。

### 12.5 成熟專案實證的正確用法

固定 commit 的 RisuAI 同時存在 Vite 前端、Capacitor Android 配置和 Tauri 桌面配置，證明共享前端向多殼發行可行。它同時也是通用 AI 客戶端，因此：

- 可參考其跨平臺工程拆分和平臺能力適配。
- 不照搬其“匯入多角色、多供應商通用客戶端”的產品邊界。
- 不將其外掛許可權模型直接視作安全標準。

## 13. 從舊 ST 角色卡遷移：一次性開發流程

### 13.1 遷移不是執行時功能

若作品最初在 ST 中開發，可以寫**開發期一次性轉換工具**提取文字、世界書、狀態 Schema、正則意圖和資產。轉換結果經人工審查後提交到本應用的 `content/` 原始碼。

生產應用不得攜帶“匯入任意 ST 卡並執行”的入口。遷移工具也不應成為執行時依賴。

### 13.2 能遷什麼，必須重寫什麼

| 舊專案內容 | 獨立作品中的去向 | 處理方式 |
|---|---|---|
| 角色描述、世界觀、開場白 | `content/characters`、`world`、`scenes` | 可抽取文字，人工拆分和版本化 |
| 世界書條目 | 內建 `LoreEntry` | 轉欄位後複核啟用、遞迴、預算和插入語義 |
| system prompt / PHI / 預設 | `prompts` 與裝配計劃 | 重排並建立 Golden Test |
| ST 宏 | 自有白名單宏 | 逐個對映；未知宏構建失敗 |
| MVU Schema / InitVar | `state/schema`、初值工廠 | 遷移資料模型，不攜帶 MVU 執行時 |
| MVU 更新規則 | StateOperation 協議與規則引擎 | 重寫寫許可權、校驗和事務 |
| EJS 條目 | 型別化模板、selector 或規則函式 | 禁止原樣 eval |
| 酒館正則 | 渲染轉換、輸出解析或 UI 元件 | 按“隱藏/解析/美化”意圖重寫 |
| Tavern Helper 指令碼 | 引擎 service、command、selector | 逐功能重實現，不執行原指令碼 |
| 卡內 HTML | 作品 UI 元件 | 按頁面功能重建並做安全審查 |
| 圖片、音訊、影片 | `assets` | 檢查授權、格式、大小和雜湊 |
| 舊聊天 | 可選的開發期存檔遷移器 | 只服務本作品，轉換後過當前 Schema |

### 13.3 相容等級

獨立作品不應用“能匯入卡”衡量相容性，而用行為遷移等級：

| 等級 | 目標 |
|---|---|
| M0 · 文字遷移 | 角色、世界觀、開場、示例和資產進入內容域 |
| M1 · 基礎遊玩遷移 | Prompt、歷史、流式生成、Persona、存檔閉環一致 |
| M2 · 玩法遷移 | Lore、宏、變數、UI 動作、正則意圖完成原生重實現 |
| M3 · 行為對齊 | 分支、群像、複雜更新規則和舊存檔達到作品驗收清單 |
| M4 · 原生增強 | 利用獨立應用能力重做通知、離線、音畫、更新和跨端同步 |

“欄位讀進來了”只等於 M0，不代表玩法相容。

### 13.4 ST 專屬機制不能憑空執行

- Tavern Helper API 依賴它自己的宿主和事件系統。
- MVU 依賴訊息變數、解析和更新生命週期。
- EJS 條目依賴對應模板執行環境與注入上下文。
- 酒館正則依賴 ST 的訊息、Prompt 和 Markdown 執行階段。
- ST 世界書擴充套件欄位依賴 ST 掃描器的具體實現。

獨立應用必須為每項選擇：原生重實現、構建期轉換、明確降級或不支援。禁止在 README 寫“相容”卻沒有測試矩陣。

Character Card V3 規範中的欄位、Lorebook、宏和資源 URI 可幫助理解舊內容；它不要求本作品繼續以卡片封裝體執行。**high · 規範**

## 14. 安全與隱私

### 14.1 信任邊界

| 輸入 | 預設信任 |
|---|---|
| 隨簽名發行的程式碼與內容包 | 校驗簽名和雜湊後可信 |
| 玩家輸入 | 不可信文字 |
| 模型輸出 | 不可信文字和不可信結構化資料 |
| 外部 API 響應 | 不可信網路資料 |
| 遠端圖片、音訊、連結 | 不可信資源 |
| 匯出的舊存檔 | 匯入前不可信 |
| Mod / 外掛 | 不可信程式碼 |

### 14.2 API Key

- Web 端優先會話金鑰或作品方代理；不得記錄在分析日誌和崩潰報告。
- App / PC 使用系統安全儲存。
- 設定頁能檢視金鑰歸屬、測試連線、替換和徹底刪除。
- 匯出存檔預設不包含金鑰。
- 代理必須鑑權、限流、限制上游、過濾敏感日誌並防 SSRF。
- 自定義端點要顯示完整域名和資料風險，預設拒絕內網與元資料地址。

### 14.3 狀態寫入安全

- 對模型操作做 JSON 結構校驗、路徑白名單和範圍校驗。
- 單回合運算元量、陣列增長和文字長度設上限。
- 禁止原型汙染鍵。
- 規則引擎計算派生欄位，模型無權覆蓋。
- 提交前比較 base revision；併發或遲到結果不能覆蓋新狀態。

### 14.4 內容與更新供應鏈

- 程式碼、內容包和增量資產都簽名。
- 清單記錄每個檔案的雜湊和大小。
- 解壓內容包防路徑穿越、壓縮炸彈和同名覆蓋。
- 更新前確認磁碟空間，失敗保留舊版本。
- 內容熱更新與 Schema 遷移必須繫結，不能只換 Prompt 不遷存檔。

### 14.5 外掛與 Mod

單作品 MVP 建議不提供任意程式碼外掛。若確實需要：

- 使用許可權清單：網路域、存檔只讀/寫、檔案、UI 插槽分別授權。
- 預設在 Worker 或受限程序執行，不給 DOM、金鑰和完整資料庫。
- 每個外掛獨立 KV 名稱空間。
- 使用者可撤銷許可權、停用並檢視來源與簽名。
- 外掛崩潰不能破壞主存檔。
- 作品內容包中的指令碼也遵守同一許可權邊界，不能因為“隨作品釋出”就無限制執行。

### 14.6 資料與遙測

- 本地存檔預設屬於玩家，可完整匯出和刪除。
- 雲同步前明確加密、衝突策略和保留期。
- 敏感 Persona、聊天和狀態支援裝置級加密。
- 遙測預設最小化並可關閉；不得上傳完整 Prompt、聊天或 API Key。
- 崩潰日誌先脫敏，再詢問是否上傳。

## 17. 最小可用里程碑

- Prompt 裝配順序和輸出協議。
- 頁面與主玩法閉環。
- 從舊卡遷移的“保留、重寫、放棄”對照表。

穩定門：

- 所有 ST 專屬依賴均有處置結論。
- 沒有執行時卡片匯入器。
- 新周目的唯一來源是本作品初始化器。

### P1 · 單端垂直切片

建議先選 Web 或 PC：

- 新建 Persona 和周目。
- 一條完整生成鏈。
- 流式、取消、重試。
- 狀態操作校驗並原子提交。
- 儲存、退出、恢復。

穩定門：

- 斷網、取消、重新整理、崩潰不產生“訊息成功但狀態丟失”。
- Prompt Trace 與狀態 diff 可檢查。

### P2 · 玩法與分支

- Lore、宏、摘要。
- Swipe、分支和檢查點。
- 作品專屬地圖、揹包、任務等核心系統。
- 安全渲染與無障礙。

穩定門：

- 分支切換帶著正確狀態版本。
- Lore 與 Prompt Golden Test 穩定。

### P3 · 三殼共享

- Web、App、PC 接入同一 core。
- 平臺金鑰、檔案、更新和生命週期適配。
- 同一匿名測試存檔跨殼讀取。

穩定門：

- 同樣輸入和固定模型 mock 產生同樣 Prompt Trace、狀態 diff 和分支結構。
- 平臺特有錯誤都有可恢復路徑。

### P4 · 發行

- 簽名安裝包和內容清單。
- 更新、遷移、回滾。
- 隱私、許可、分級和第三方資產清單。
- 崩潰恢復、備份和玩家匯出。

穩定門：

- 從所有公開舊版本升級的自動化回放透過。
- 生產構建不包含開發期遷移器、測試金鑰或除錯後門。

## 18. 測試矩陣

| 面 | 最低用例 |
|---|---|
| 內容構建 | 重複 ID、斷引用、缺資產、Prompt 超預算、無遷移鏈必須失敗 |
| 新周目 | 不同 Persona / 路線 / 難度；固定 seed 可復現 |
| Prompt | Golden Test、裁剪順序、Prompt Trace、不同模型能力降級 |
| Lore | constant、主/次鍵、遞迴環、預算、無效正則、最大輪數 |
| 宏 | 未知宏、轉義、隨機種子、敏感狀態不可見 |
| 模型 | 正常流、碎片邊界、空流、限流、超時、取消、遲到 chunk |
| 狀態 | 越權路徑、型別錯、範圍錯、超大操作、revision 衝突 |
| 訊息 | Swipe、編輯、分支、刪祖先、檢查點恢復、摘要失效 |
| 存檔 | 原子提交、斷電模擬、備份、損壞檢測、逐級遷移、降級拒絕 |
| Web | IndexedDB 配額、PWA 更新、CORS、重新整理恢復、多標籤頁衝突 |
| App | 後臺/前臺、程序回收、低記憶體、分享匯出、安全金鑰庫 |
| PC | 原子檔案、Keychain、簽名更新、路徑許可權、本地模型中斷 |
| 渲染 | XSS、危險 URL、超長 Markdown、惡意圖片、CSS 汙染 |
| 網路 | SSRF、代理鑑權、證書錯誤、DNS 失敗、離線 |
| 更新 | 內容雜湊錯、簽名錯、空間不足、遷移失敗、回滾 |
| 跨殼 | 同一存檔結構、同一 Prompt Trace、同一狀態事務語義 |

模型行為不穩定時，用固定 mock 流驗證引擎確定性，再單獨做真實模型驗收；不要把兩種失敗混在一起。

## 19. 驗收清單

### 19.1 定義對齊

- [ ] 開篇和產品入口都明確“程式本身就是角色卡”。
- [ ] 沒有執行時角色卡匯入、通用卡解析器或多卡角色庫。
- [ ] Web / App / PC 是同一作品的發行殼。
- [ ] 多存檔表示同一作品的不同周目。

### 19.2 內容與引擎

- [ ] 角色、世界、Prompt、Lore、狀態、規則、UI 和資產全部版本化內建。
- [ ] 內容構建可靜態校驗並生成雜湊清單。
- [ ] Prompt 裝配可追蹤、可做 Golden Test。
- [ ] 狀態寫入經過 Schema、許可權和事務校驗。
- [ ] UI Command 與文字輸入走同一主鏈路。

### 19.3 脫離 ST

- [ ] 無 ST、Tavern Helper、MVU、EJS 執行時依賴。
- [ ] 舊世界書、宏、正則和指令碼均已重實現或明確降級。
- [ ] 舊卡遷移工具只存在於開發工具，不進入生產包。
- [ ] 沒有用“欄位已匯入”代替玩法相容驗收。

### 19.4 資料與平臺

- [ ] 訊息和狀態原子提交。
- [ ] Swipe、分支和檢查點繫結正確狀態版本。
- [ ] 所有公開舊存檔有遷移和備份路徑。
- [ ] 三殼共享 Schema 與 core，平臺差異封裝在 adapter。
- [ ] 後臺、斷網、取消、更新失敗都有恢復策略。

### 19.5 安全與發行

- [ ] 模型輸出不執行 HTML / JavaScript。
- [ ] API Key 不進入存檔、日誌和遙測。
- [ ] 內容與更新包校驗簽名和雜湊。
- [ ] 匯入舊存檔、外鏈和遠端資源按不可信輸入處理。
- [ ] 生產包無除錯金鑰、遷移臨時指令碼和無限許可權外掛。

## 20. 懸案與真機驗證項

以下不能僅靠架構文件判定：

1. **作品範圍**：首版必須支援哪些玩法系統，哪些留到後續單功能迭代。
2. **狀態輸出協議**：目標模型在 JSON Schema / tool call / 文字標籤之間的穩定性。
3. **Prompt 順序**：不同模型對系統訊息、狀態投影和後置約束的響應差異。
4. **移動後臺**：iOS / Android 在真實長流、鎖屏和低記憶體下的中斷行為。
5. **Web BYOK**：目標供應商的 CORS、瀏覽器鑑權和合規限制。
6. **跨端同步**：是否需要雲同步；需要時的端到端加密和衝突策略。
7. **本地模型**：最低硬體、模型大小、量化、首 token 延遲與電量。
8. **內容更新**：舊周目是否鎖內容版本，還是強制遷移到新版劇情規則。
9. **Mod 能力**：是否真的需要；若需要，首版允許到“資料 Mod”還是“程式碼外掛”。
10. **發行合規**：模型供應商條款、應用商店分級、成人內容和使用者生成內容政策。

每項必須給出“測試裝置 / 應用版本 / 內容版本 / 模型 / 結果 / 結論”，不以單次成功代替穩定驗收。
