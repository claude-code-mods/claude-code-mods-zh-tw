## 0. 置信度分級體系（全手冊適用）

> **收集日期統一宣告**：本手冊全部條目收集於 **2026-06-27**，交叉驗證跨 6 個獨立來源。原始碼級斷言的回源核實基於本地 SillyTavern **v1.14.0**（`world-info.js` 等）；手冊中標註的 commit/sha（如 5e68410、staging）為**採集時快照**，與本地 v1.14.0 機制一致但行號可能漂移。

每條結論採用 **置信度等級 + 依據型別** 雙軸標註。

### ① 置信度三級

| 級別 | 含義 | 判定標準 |
|---|---|---|
| **high** | 已坐實，可直接施工 | 有執行時證據（真機實測 / 讀到執行時實現原始碼 / 生產卡驗證）；結論是原始碼/文件的**直接事實**而非下游推導；不在懸案清單 |
| **medium** | 待驗證，施工前須實測 | 強制二選一子標籤：`medium·單源孤證`（單一來源、無第二源、無實測）/ `medium·推導未驗證`（原始碼或邏輯推導成立但未跑通，**須隨附真機驗證路徑**）|
| **low** | 孤證無源，禁止據此施工 | 零來源猜測 / 純歷史快照（須標年份 + 窄縮適用範圍）|

### ② 依據型別標籤（與置信度正交，強制標註）

`[執行時原始碼]`、`[真機]`、`[文件·多源]`、`[文件·單源]`、`[歷史孤證:年份]`、`[無源·待考]`

### ③ 兩條鐵規

1. **「從原始碼事實再推一步」的下游推導（如 sort→注入位置、splice→reverse→落位、getScore→啟用門檻），即使原始碼本身已直讀，該推導結論最高只能 `medium·推導未驗證`**——除非已真機驗證；原始碼內部事實仍標 `high [執行時原始碼]`。
2. **節級標註 = 節內條目下確界**——禁止整節標 high 卻內含懸案條目；衝突即在節內區域性降級（**§7.1 是正面範例**）。正文斷言凡命中懸案章（本手冊 §21 U 系列）的，置信度不得高於該懸案對應級別，並交叉引用。

## 1. 基本定義與核心概念

**核心結論（high）**：World Info（Lorebook / Memory Book）是動態字典，僅當關鍵詞出現在掃描緩衝區時才將對應條目內容插入 prompt。內容對 AI 可見，但不保證 AI 一定使用。

| 屬性 | 說明 |
|---|---|
| 作用域 | Global WI：全形色共用；Character Lorebook：繫結到特定角色；Chat Lorebook：繫結到單個聊天（v1.17.0）；Persona Lorebook：繫結到 Persona（v1.17.0） |
| 啟用時機 | 每次生成前掃描聊天曆史，關鍵詞命中 → 內容注入 prompt |
| 效果保證 | 僅保證內容進入 context，不保證模型遵循 |

來源：docs.sillytavern.app ｜ 適用版本：v1.12.x+ ｜ 置信度：high `[文件·多源]`

## 3. 啟用策略（Strategy）

**核心結論（high）**：三種策略透過 UI 圖示切換，決定條目的啟用觸發方式。

| 圖示 | 名稱 | 行為 |
|---|---|---|
| 🔵 Blue Circle | Constant | 無需關鍵詞，始終啟用（仍受 Budget 約束，仍受 Probability 過濾，sticky 期間 Probability 跳過） |
| 🟢 Green Circle | Conditional | 需要關鍵詞命中才啟用（預設） |
| 🔗 Chain Link | Vectorized | 允許向量相似度啟用（仍可被關鍵詞啟用，不互斥） |

**避坑**：
- Constant 條目會消耗 token budget，大量 Constant 條目可能擠佔 Conditional 條目空間
- 🔗 標記不停用關鍵詞啟用；只想純向量啟用必須同時刪除 Key 欄位

來源：docs.sillytavern.app + world-info.js ｜ 適用版本：v1.12.x+ ｜ 置信度：high `[文件·多源 + 執行時原始碼]`

## 4. 關鍵詞匹配機制

### 4.1 基礎規則

**核心結論（high）**：

- Key 欄位逗號分隔，預設大小寫不敏感（全域性 Case-sensitive Keys 預設關）
- 支援 JavaScript regex（需 `/pattern/flags` 格式，所有 flags 允許）
- regex key 與 plaintext key 可在同一條目共存
- plaintext key 內部不能有逗號（逗號視為分隔符）；regex 內部可有逗號

### 4.2 v1.12.6+ \\x01 訊息邊界分隔

**核心結論（high）**：v1.12.6 起掃描緩衝區中每條訊息前額外追加 `\x01`（ASCII 1）分隔符，可用 regex 精確限定發言者。

```
# 正規化：僅匹配使用者訊息中包含「keyword」，AI 說的不觸發
/\x01{{user}}:[^\x01]*?keyword/i
```

來源：SillyTavern-Docs/main (commit ca6a171) ｜ 適用版本：v1.12.6+ ｜ 置信度：high `[文件·單源]`

### 4.3 全詞匹配（Match Whole Words）

**核心結論（high）**：預設啟用，單詞 key 只在完整獨立單詞出現時匹配（空格邊界判斷）。**對中文/日文有破壞性影響**，寫非英文條目時應在條目級或全域性關閉此設定。

來源：docs.sillytavern.app + worldinfo.md ｜ 適用版本：v1.12.x+ ｜ 置信度：high `[文件·多源]`

### 4.4 Include Names（包含名稱）

**核心結論（high）**：開啟（預設）時，訊息字首加入角色名（如 `Alice: `），角色名本身可作為關鍵詞觸發條目。

## 5. Optional Filter（次級關鍵詞邏輯）

### 5.1 四種邏輯的精確定義

**核心結論**——來源交叉驗證（docs + world-info.js release 實現完全一致）：列舉值↔邏輯名對映 = `high [文件·多源 + 執行時原始碼]`；但 NOT_ANY/NOT_ALL 的**啟用行為**列 = `medium·推導未驗證`（其門控實現位置 + 歷史 bug #2009，見 §21 U2）：

| 列舉值 | 名稱 | selectiveLogic JSON 值 | 行為 | 短路最佳化 |
|---|---|---|---|---|
| AND_ANY | 任意次級匹配 | 0（預設） | 主鍵命中 + 次級至少一個命中 | ✅ 找到即返回 |
| NOT_ALL | 非全部次級 | 1 | 主鍵命中 + 次級未全部命中時啟用（全部命中則阻止） | ✅ 找到不匹配即返回 |
| NOT_ANY | 無次級匹配 | 2 | 主鍵命中 + 次級全部未命中時啟用 | ❌ 必須完整遍歷 |
| AND_ALL | 全部次級匹配 | 3 | 主鍵命中 + 次級全部命中 | ❌ 必須完整遍歷 |

**重要**：主鍵命中是所有模式的必要前提，次級 key 為空時 `selectiveLogic` 無效。

```json
// 正規化：NOT_ANY 排除詞
{
  "key": ["角色名"],
  "keysecondary": ["戰鬥", "敵對"],
  "selective": true,
  "selectiveLogic": 2
}
// 含義：角色名出現、且戰鬥/敵對詞均未出現時，啟用此條目
```

### 5.2 getScore 與 NOT_ANY/NOT_ALL 的分數關係

**核心結論（high）**：`getScore()` 函式的 switch-case 只處理 AND_ANY 和 AND_ALL；NOT_ANY/NOT_ALL 不加分，直接返回 `primaryScore`。這意味著 Group Scoring 模式下負向邏輯條目的競爭分數僅取決於主鍵匹配數，次級關鍵詞匹配情況不提升分數。

來源：world-info.js release (L428-473)；本地 v1.14.0 L461-473 逐字核實 ｜ 置信度：getScore **內部計分邏輯**（AND_ANY/AND_ALL 加分、NOT 系列僅返回 primaryScore）= `high [執行時原始碼]`；但"計分是否等於**啟用門檻**" = `medium·推導未驗證`（getScore 之外是否另有布林門控未定，見 §21 U1/U2）

⚠️ **分歧標註**：DeepWiki 來源指出 AND_ALL 當次鍵未全中時 getScore 返回 primaryScore（非 0），與官方文件"ALL secondary keys required"語義存在潛在矛盾——實際啟用門檻是否在 getScore 外層另有布林檢查，**懸而未決，見§21**。

## 7. Insertion Order 與排序機制

### 7.1 Prompt 構建階段的排序（影響注入位置）

**核心結論（high）**——來源：world-info.js L88 + L5082（原始碼直接讀取）：

```javascript
const sortFn = (a, b) => b.order - a.order;  // 單一比較器，order 降序，無 uid tiebreak
```

高 order 值條目排在前面（sort 後），由於 prompt 構建時用 `unshift`，**order 越大，在最終 context 中越靠近最新訊息（越靠末尾，影響力越強）**。

**直覺反轉警告**：order 100 出現在 context 中 order 250 的**前面**（更遠離最新訊息），order 250 更靠近最新訊息端，影響力更強。

> ⚠️ **置信度修正**：`sortFn` 比較器本身原始碼直讀（high）；但「order 越大 → 越靠末尾 → 影響力越強」這一步經過了「sort → unshift → 最終 prompt 排布」的推導鏈，**未獨立真機驗證 prompt 實際排布**，方向性結論按 medium 對待。重建時若依賴此方向，先用 Prompt Manager 預覽實測一次（參 §17.2 的 splice+reverse 推導）。

### 7.2 UI 編輯器顯示排序（與 prompt 構建無關）

`sortWorldInfoEntries` 函式有三級排序（primarySort → order 降序 → uid 升序），uid tiebreak 隻影響**編輯器顯示順序**，不影響 prompt 構建和啟用判斷。

來源：world-info.js release (L88, L5082-5084, sortWorldInfoEntries) ｜ 適用版本：v1.12.x+ ｜ 置信度：high `[執行時原始碼]`（sortFn 比較器本地核實；§7.1 的方向性推導已自降 medium）

## 8. Token 預算（Budget）機制

**核心結論（high）**：

- `world_info_budget`：百分比，預設 25%，基於 API max-context 計算
- `world_info_budget_cap`：絕對 token 上限（0=不限）
- budget 耗盡後即使關鍵詞命中也不再啟用新條目
- Constant 條目優先插入（先消耗 budget）
- Max Entries（向量模式）只限結果數量，不影響 token budget

**避坑**：大量 Constant 條目可能耗盡 budget 導致 Conditional 條目無法插入。

來源：docs.sillytavern.app + world-info.js exports ｜ 適用版本：v1.12.x+ ｜ 置信度：high `[文件·多源 + 執行時原始碼]`

## 9. Inclusion Group 完整機制

### 9.1 基礎邏輯

**核心結論（high）**：同一 Group 標籤的多條目同時啟用時，只有一條實際插入 prompt。選擇演算法分三個序列階段：

**階段① filterGroupsByTimedEffects**：sticky 條目保留，cooldown/delay 條目移除

**階段② filterGroupsByScoring**（僅 group scoring 開啟時）：按 getScore 分數保留最高分子集，同分全部保留

**階段③ 主競爭**：
- 有 `groupOverride=true`（Prioritize Inclusion）的條目 → 按 `sortFn`（order 降序）取第一個，確定性勝出
- 無 groupOverride → 加權隨機（Group Weight 預設 100）：

```javascript
// 精確實現（來自 world-info.js release L5325-5354）
const totalWeight = group.reduce((acc, item) => acc + (item.groupWeight ?? 100), 0);
const rollValue = Math.random() * totalWeight;
let currentWeight = 0;
for (const entry of group) {
    currentWeight += (entry.groupWeight ?? 100);
    if (rollValue <= currentWeight) { winner = entry; break; }
}
```

### 9.2 Group Weight 理解

**核心結論（high）**：Group Weight 是**相對權重**而非百分比。權重 100 和 300 的兩條目，後者被選中機率為 300/400 = 75%，不是 300%。

### 9.3 Use Group Scoring 評分規則

**核心結論（high）**——來源：docs + world-info.js getScore 函式：

| 情況 | 得分 |
|---|---|
| 主鍵 1 個匹配 | +1 分 |
| AND_ANY 次級 1 個匹配 | +1 分 |
| AND_ALL 次級全部匹配 | 每個次鍵 +1 分 |
| NOT_ANY / NOT_ALL 次級 | 不加分（僅返回 primaryScore） |

```
# 正規化：通用條目 vs 特化條目
Entry A: keys=[song, sing],            group=songs, use_group_scoring=ON
Entry B: keys=[song, sing, Black Cat], group=songs, use_group_scoring=ON

輸入「sing me a song」→ AB 各得 2 分 → 加權隨機選一
輸入「sing a Black Cat song」→ B 得 3 分，A 得 2 分 → B 確定性勝出
```

### 9.4 多組成員資格

**核心結論（high）**：一個條目可屬於多個 Group（逗號分隔）。該條目勝出後，它所屬所有組的其他成員均被停用（跨組級聯停用）。

⚠️ **避坑**：條目 A 屬於 group1,group2，A 勝出後會同時停用 group1 和 group2 的其他所有條目，可能意外遮蔽無關條目。

### 9.5 probability 與 Inclusion Group 的互動

**核心結論（high，來源：world-info.js checkWorldInfo 順序）**：Inclusion Group 競爭淘汰發生在 probability 檢查**之前**（L4893 filterByInclusionGroups vs L4900+ probability check）。勝出者仍可能被 probability 過濾掉，其餘同組落敗條目不會補位。

來源：world-info.js release L5188-5354 ｜ 適用版本：v1.12.x+ ｜ 置信度：Inclusion Group 競爭**發生在** probability 檢查之前的原始碼順序 = `high [執行時原始碼]`；"勝出者被 probability 淘汰後是否補位" = `medium·推導未驗證`（傾向不補位，見 §21 U4）

## 10. Timed Effects（定時效果）

### 10.1 三種效果

**核心結論（high）**——來源：docs + worldinfo.md 雙源一致：

| 效果 | 欄位 | 含義 |
|---|---|---|
| Sticky | `sticky=N` | 啟用後保持 N **條訊息**有效（sticky 期間跳過 Probability 檢查） |
| Cooldown | `cooldown=N` | 啟用後 N 條訊息內不可再啟用 |
| Delay | `delay=N` | 聊天訊息數少於 N 時不可啟用（閾值檢查，非倒計時） |

### 10.2 五條鐵律

**核心結論（high）**：

1. 時間單位是**訊息數**（不是對話輪次/問答對）
2. 效果僅在啟用該條目的那個聊天內有效；分支聊天繼承父狀態
3. 最後訊息被 swipe 或刪除 → 效果清除（聊天未推進）
4. 對條目做任何修改 → 強制清除當前 timed effect
5. 關鍵詞再次命中不重新整理已生效的 duration

### 10.3 組合時間線示例

**核心結論（high）**——來源：worldinfo.md 範例（兩源一致）：

```
配置：sticky=3, cooldown=2, delay=2

Message 0：delay（聊天訊息數不足，不觸發）
Message 1：首次啟用
Message 2：sticky（強制插入，跳過 Probability）
Message 3：sticky
Message 4：sticky
Message 5：cooldown（不可啟用）
Message 6：cooldown
Message 7+：可再次啟用
```

**說明**：delay=2 表示"至少有 2 條歷史訊息才能啟用"，Message 0 時有 0 條歷史。

來源：SillyTavern-Docs/main + sillytavern.wiki ｜ 適用版本：v1.12.2+ ｜ 置信度：high `[文件·多源]`

## 11. 遞迴掃描（Recursion）

### 11.1 基本機制

**核心結論（high）**：已啟用條目的 content 文字追加到 recurseBuffer，下一輪掃描時此 buffer 也參與關鍵詞匹配，實現鏈式啟用。全域性開關 `world_info_recursive` 控制啟用。

```
正規化：角色 → 關係 → 場所 三級鏈
Entry#1: keys=[貝西], content=「貝西是一頭奶牛，是魯弗斯的朋友」
Entry#2: keys=[魯弗斯], content=「魯弗斯是一隻狗，住在老農場」
Entry#3: keys=[老農場], delay_until_recursion=true

訊息提及「貝西」→ #1 啟用 → content 提到魯弗斯 → #2 啟用 → content 提到老農場 → #3 啟用
```

### 11.2 三種遞迴控制選項

**核心結論（high）**：

| 選項 | 說明 |
|---|---|
| Non-recursable | 不被其他條目遞迴啟用（保護靜態資訊） |
| Prevent further recursion | 該條目啟用後不再觸發其他條目（阻斷鏈） |
| Delay until recursion | 僅在遞迴檢查階段參與，不在初始掃描中啟用 |

### 11.3 Delay until Recursion Level（遞迴層級，v1.12.6+）

**核心結論（high）**：支援為 delay_until_recursion 條目指定層級數字。初始只匹配最小層級編號的條目；該層無命中後，下一層級開放；依次類推。

```
Entry A: delay_until_recursion=1（層級1，由主掃描內容觸發）
Entry B: delay_until_recursion=2（層級2，需A先啟用內容出現B的key才開放）
```

來源：SillyTavern-Docs/main (1.12.6 release notes) ｜ 適用版本：v1.12.6+ ｜ 置信度：high `[文件·單源]`

⚠️ **注意**：`Delay until recursion` 與 `Min Activations` 互斥，不能同時使用。

### 11.4 Max Recursion Steps

**核心結論（high）**：限制遞迴總掃描輪數。

| 值 | 含義 |
|---|---|
| 0 | 無步數限制（僅受 budget 約束） |
| 1 | 停用遞迴（只做初次掃描） |
| 2 | 允許遞迴觸發一次 |
| N | 允許遞迴觸發 N-1 次 |

**與 Min Activations 互斥**，UI 層強制一個為 0。

來源：world-info.js release (L4654-4658) ｜ 適用版本：v1.12.5+ ｜ 置信度：high `[執行時原始碼]`

### 11.5 Min Activations

**核心結論（high）**：非零時無視 Scan Depth 限制，向上掃描整個聊天記錄直到啟用足夠數量條目（仍受 Max Depth 和 Budget 限制）。追加掃描不檢查遞迴新增的條目。與 Max Recursion Steps 互斥。

**注意**：`scan_state.MIN_ACTIVATIONS` 狀態下 `#recurseBuffer` 不被納入掃描上下文（world-info.js get() 內有守衛），遞迴觸發詞在此狀態下不生效。

## 12. @@activate / @@dont_activate 裝飾器

⚠️ **此功能在官方文件中未記載，來源為 world-info.js release 原始碼直接讀取，置信度 high（原始碼層面），但屬於隱藏實現細節。**

**核心結論（high，原始碼直讀）**：兩個裝飾器寫在條目 **content 欄位頂部**（不是 key 欄位），由 `parseDecorators()` 函式預處理。

| 裝飾器 | 效果 |
|---|---|
| `@@activate` | 無條件啟用該條目（跳過關鍵詞檢查） |
| `@@dont_activate` | 無條件跳過該條目 |

```
// content 欄位示例
@@activate
這裡是正文內容，第一個非 @@ 開頭的行即為正文開始。

// 轉義（不觸發裝飾器，輸出字面量 @@activate）
@@@activate
```

**執行順序約束**（裝飾器**存在性** = `high [執行時原始碼]`；下方與 disable/timed effect 的**互動結論** = `medium·推導未驗證`，見 §21 U11）：
- 裝飾器處理在 `disable` 檢查**之後** → `disable=true` 的條目 `@@activate` 無法復活
- 裝飾器處理在 timed effect 檢查（sticky/cooldown/delay）**之後** → delay 期間（聊天訊息數未達閾值）的條目 `@@activate` 也無效
- ⚠️ **v1.14.0 回源補正**：sticky/cooldown 等前置檢查帶 `!isSticky` 短路（sticky 期間會繞過這些檢查），但 **delay 檢查（L4568）無 `!isSticky` 守衛**，故"delay 期間 @@activate 無效"這一方向在 v1.14.0 成立；其餘互動未逐一真機驗證。
- 同一條目同時寫 `@@activate` 和 `@@dont_activate` 時，`@@activate` 先被檢查並短路，勝出

> 來源：world-info.js release **commit 5e68410**（採集快照）+ 本地 v1.14.0 回源（L4568 delay / L4594 裝飾器判斷）— L100 `KNOWN_DECORATORS`、L4540 `parseDecorators()` ｜ 置信度：裝飾器**存在 / 寫在 content 首行 / `@@@` 轉義** = `high [執行時原始碼]`（二次回源確認存在）；與 disable / timed effect 的**執行順序互動** = `medium·推導未驗證`（原始碼順序推斷 + 部分 v1.14.0 驗證，見 §21 U11）

## 13. Outlet（插槽注入）

**核心結論（high）**——來源：SillyTavern-Docs/main + docs.sillytavern.app 雙源一致：

### 13.1 工作原理

Outlet 位置的條目不自動注入 prompt，而是存入命名插槽，透過宏 `{{outlet::Name}}` 在 Prompt Manager 或 Advanced Formatting 中手動呼叫。

多個同名 Outlet 條目按 Insertion Order 排序後換行合併。

### 13.2 正規化

```
# WI 條目設定
Insertion Position: Outlet
Outlet Name: SystemRules
Content: [系統規則內容...]

# Prompt Manager 中
{{outlet::SystemRules}}
```

### 13.3 五條限制（高置信，雙源一致）

1. **不能在 WI 條目 content 裡放 outlet 宏**（評估順序衝突 + 無限迴圈）
2. **不支援巢狀 outlet**（outlet 內容中再呼叫另一個 outlet）
3. **角色卡欄位（Description/Personality/Scenario 等）無法展開 outlet 宏**（欄位在 WI 評估前解析）
4. **Author's Note 編輯器無法解析 outlet 宏**
5. Outlet Name **區分大小寫**，首尾空格被忽略（儲存時帶空格的名字調宏時不匹配）

來源：SillyTavern-Docs/main (PR #4523, commit 50feb85) ｜ 適用版本：v1.13.5+ ｜ 置信度：high `[文件·多源]`

## 14. 向量化匹配（Vector Storage）

### 14.1 啟用路徑

**核心結論（high）**——來源：docs + vectors/index.js staging 雙源：

1. 擴充套件總開關 `enabled_world_info=true`
2. 條目 `vectorized=true`（🔗 標記）或全域性 `enabled_for_all=true`
3. 擴充套件用最近 `settings.query`（預設 2）條訊息文字做查詢
4. 經 `queryMultipleCollections()` 返回相似度超過 `score_threshold`（預設 0.25）的結果
5. 透過 `WORLDINFO_FORCE_ACTIVATE` 事件寫入 `WorldInfoBuffer.externalActivations` Map
6. 下游 `checkWorldInfo` 按正常 WI 流程處理（仍受 Probability/Character Filter/Inclusion Group 約束）

### 14.2 關鍵引數預設值

| 引數 | 預設值 | 說明 |
|---|---|---|
| `enabled_world_info` | false | 總開關 |
| `enabled_for_all` | false | 批次模式 |
| `max_entries` | 5 | 每次最多匹配條目數 |
| `score_threshold` | 0.25 | 相似度下限（0~1） |
| `query` | 2 | 查詢訊息數（不是 Scan Depth） |

來源：vectors/index.js staging ｜ 適用版本：Vector Storage 擴充套件啟用後 ｜ 置信度：引數預設值與啟用路徑 = `high [執行時原始碼]`（staging 快照）；其中第 5 步強制啟用**事件名** `WORLDINFO_FORCE_ACTIVATE` = `medium·推導未驗證`（來自 DeepWiki 描述，未在截斷程式碼直接確認拼寫，見 §21 U8）

### 14.3 關鍵約束

- **Scan Depth 對向量模式無效**，查詢深度由 `Query messages` 控制（兩者是不同設定入口）
- `vectorized` 標記只替換關鍵詞檢查，其餘啟用條件（trigger%、char filter、inclusion group）仍然全部生效
- `vectorized=true` + 有關鍵詞 → 兩種方式都能獨立觸發（非互斥）；純向量啟用必須刪除 key
- 向量啟用走相同 token budget 管道，Max Entries 不繞過 budget
- 與 LLM 提示快取（KV cache）不相容，頻繁重排 prompt prefix 導致快取失效，付費場景成本上升

來源：docs.sillytavern.app + vectors/index.js ｜ 適用版本：Vector Storage 擴充套件啟用後 ｜ 置信度：high `[文件·多源 + 執行時原始碼]`

## 15. Automation ID 與 STscript 聯動

### 15.1 機制

**核心結論（high）**：WI 條目設定 Automation ID，與 Quick Replies 擴充套件中同 ID 的 QR 命令繫結。條目啟用時自動執行對應 STscript，執行時機為**訊息生成之前**（pre-generation）。

### 15.2 執行順序

藍圈（Constant）條目優先 → 按 Order 值排序 → 遞迴觸發條目最後處理

### 15.3 注意事項

- 依賴 Quick Replies 擴充套件已安裝並配置，擴充套件未啟用則無效
- 多個同 Automation ID 條目同時啟用時，文件稱指令碼只執行一次

**⚠️ 分歧：Automation ID 去重保證**

- **官方文件（medium）**：同 ID 多條目啟用時指令碼只執行一次
- **原始碼分析（medium，AutoExecuteHandler.js）**：`automationIds` 陣列無 Set 去重；若兩個 QR Set 各有一個不同 QR 例項攜帶相同 automationId，兩者均會執行

結論：單 QR Set 單 QR 例項場景文件結論成立；多 QR Set 場景需真機驗證。

**⚠️ 分歧：執行時機是否支援 post-generation**

- **當前實現（high）**：Automation ID 在生成**前**執行，無法讀取同輪 AI 生成內容
- **GitHub Issue #3419（medium）**：使用者請求 post-generation 執行，2025-02-03 提出，當前狀態（2026-06-27）未知

來源：SillyTavern-Docs/main + AutoExecuteHandler.js release + Issue #3419 ｜ 適用版本：Quick Replies 擴充套件版本相關 ｜ 置信度：pre-generation 時機 = `medium·單源孤證 [文件·單源]`（AutoExecuteHandler.js 本地無、當前實現是否仍純 pre-gen 見 §21 U7）；去重保證 = `medium·推導未驗證`（官方文件與原始碼分析分歧，見正文 ⚠️）

## 16. 多 Lorebook 來源與優先順序

### 16.1 來源優先順序（v1.17.0+）

**核心結論（high）**——來源：SillyTavern-Docs/main (commit bad9492, c5f7a56)：

```
Chat Lore → Persona Lore → Character Lore 或 Global Lore
```

後兩者順序由全域性策略決定：

| 策略 | 行為 |
|---|---|
| Sorted Evenly（預設） | 全部混合，按 Insertion Order 統一排序 |
| Character Lore First | Character Lore 按 Order 插入後，再 Global |
| Global Lore First | 反之 |

**原始碼級實現（world-info.js L4494-4513）**：

```javascript
switch (Number(world_info_character_strategy)) {
  case evenly:   entries = [...globalLore, ...characterLore].sort(sortFn); break;
  case char_first: entries = [...characterLore.sort(sortFn), ...globalLore.sort(sortFn)]; break;
  case global_first: entries = [...globalLore.sort(sortFn), ...characterLore.sort(sortFn)]; break;

entries = [...chatLore.sort(sortFn), ...personaLore.sort(sortFn), ...entries];
```

Chat Lore 和 Persona Lore 始終放在最前面（優先掃描），與策略無關。

### 16.3 重新命名自動重連結（v1.17.0）

重新命名 WI 檔案時彈出確認提示，可選擇自動更新引用該檔案的所有角色繫結到新檔名。

## 17. WI 在 Prompt 中的精確位置（OpenAI path）

**核心結論（high）**——來源：world-info.js + openai.js + script.js release (commit 51ad27fb) 原始碼直讀。

### 17.1 atDepth 條目的四步流水線

1. `checkWorldInfo()` 收集啟用條目到 `WIDepthEntries`（按 {depth, role} 分組）
2. `script.js` 呼叫 `setExtensionPrompt(id, content, IN_CHAT=1, depth, false, role)` 註冊
3. `openai.js populationInjectionPrompts()` 在迴圈 depth=i 時呼叫 `getExtensionPrompt(IN_CHAT, i, sep, role)` 讀取
4. `splice` 進 newest-first messages 陣列，最後 `reverse()`

### 17.2 depth 語義（splice + reverse 雙步邏輯）

messages 初始為 newest-first（最新訊息在 index 0）：

```
depth=D 時 splice(D, 0, injected) → reverse()

推導：
depth=0 → 插在 index 0 → reverse 後落在整個陣列最末尾（最新訊息之後）
depth=1 → 插在 newest 和 2nd 之間 → reverse 後緊靠在 newest 之前
depth=N → 最終在 prompt 中位於倒數第 N+1 位（距末端 N 條訊息）
```

**預設值**：條目未設定 depth 時取 `DEFAULT_DEPTH=4`。

### 17.3 同 depth 多條目合併

相同 depth + role 的多條 WI 條目在 world-info.js 層面已合併為單字串（`join('\n')`），注入時是**一條訊息**，不是多條分離訊息。

### 17.4 worldInfoBefore / worldInfoAfter 的路徑差異

`position=0/1`（Before/After Char Defs）的條目走 PromptManager/RELATIVE 路徑，作為固定位置的 system 訊息，**不經過 depth 注入管線**，不進入聊天曆史區。

### 17.5 flushWIInjections

每次 `getWorldInfoPrompt` 呼叫前執行，刪除 `extension_prompts` 中所有 `customDepthWI` 和 `customWIOutlet_` 字首的鍵，防止舊一輪條目殘留疊加。

來源：openai.js + script.js + world-info.js release ｜ 適用版本：v1.18.0（本地為 v1.14.0，openai.js 未逐一回源）｜ 置信度：atDepth 四步流水線 / flushWIInjections 等**呼叫鏈** = `high [執行時原始碼]`；§17.2 depth 的 **splice+reverse 最終落位** = `medium·推導未驗證`（推導鏈未真機，見 §21 U5/U6）

## 19. 高階觸發控制（Triggers / Character Filter / Additional Sources）

### 19.1 Triggers（生成型別過濾，v1.13.2+）

**核心結論（high）**：可限制條目只在特定生成型別時啟用。

| 型別 | 說明 |
|---|---|
| Normal | 常規生成 |
| Continue | 點選繼續 |
| Impersonate | 扮演 |
| Swipe | 划動重生成 |
| Regenerate | 重新生成（群聊不可用，群聊走 Normal） |
| Quiet | 後臺靜默生成（擴充套件/STscript 觸發） |

留空 = 對所有型別生效。

### 19.2 Character Filter

**核心結論（high）**：白名單（列表內角色名/標籤才能啟用），Exclude 模式反轉為黑名單。支援角色名和 tag 雙模式過濾。

### 19.3 Additional Matching Sources（v1.13.0+）

**核心結論（high）**：預設只掃描聊天記錄。可額外開啟以下欄位作為關鍵詞匹配來源（不依賴聊天訊息內容）：

- Character Description
- Character Personality
- Scenario
- Persona Description
- Character's Note（即 depth prompt）
- Creator's Notes

來源：SillyTavern-Docs/main (PR #3889) ｜ 適用版本：v1.13.0+ ｜ 置信度：high `[文件·單源]`

### 19.4 Probability（觸發百分比）

**核心結論（high）**：啟用後的隨機過濾器。100=必然插入，50=50% 機率，0=永不插入（軟性停用，key 仍被掃描）。

| 觸發方式 | 受 Probability 約束？ |
|---|---|
| Constant 啟用 | ✅ 受約束 |
| 關鍵詞啟用 | ✅ 受約束 |
| 遞迴啟用 | ✅ 受約束 |
| Sticky 保持期間 | ❌ 跳過（強制插入） |

## 20. 工程實踐與正規化程式碼

### 20.1 隨機事件（低機率 Probability）

```
Key: 長老神名字
Content: 長老神被喚醒，開始干預當前場景...
Probability: 1
Strategy: 🟢
```

每次關鍵詞命中時有 1% 機率插入，實現隨機事件觸發。

### 20.2 Inclusion Group 回退序列

```
Entry_Specific: keys=[common_key, specific_key], group=scene_pool
  order=200, groupOverride=ON (Prioritize Inclusion)
Entry_Default:  keys=[common_key],               group=scene_pool
  order=100, groupOverride=ON

→ specific_key 也出現時：Entry_Specific (order=200) 確定性勝出
→ 只有 common_key 時：Entry_Default (order=100) 勝出
```

### 20.3 Sticky + Cooldown 狀態機

```
Entry: 戰鬥狀態
Keys: 攻擊, 戰鬥, 開戰
sticky=5 cooldown=3 delay=0
Content: [當前處於戰鬥狀態的規則...]

→ 戰鬥觸發後保持 5 條訊息，結束後 3 條訊息冷卻防重複啟用
```

### 20.4 遞迴鏈配置

## 21. 懸而未決：重建前需真機驗證的問題

> **本章 U1–U11 = `low / 懸案級`，禁止據此施工**；正文凡引用某 U 項的斷言，其置信度已按鐵規②不高於 `medium·推導未驗證` 並交叉引用。

以下問題文件/原始碼未明確或存在矛盾，重建時遇到相關功能須先實測確認。

---

### U1. AND_ALL 啟用門檻（高優先順序）

**問題**：`getScore()` 函式（world-info.js）在 AND_ALL 且次鍵未全中時返回 `primaryScore`（非 0）。若啟用判斷僅依賴 `score > 0`，則次鍵未全中時主鍵命中也會啟用——這與官方文件"必須全部次鍵都存在"相矛盾。

**驗證路徑**：設定 AND_ALL 條目（2 個次鍵，只滿足 1 個），確認條目是否啟用。若啟用 = 有外層布林門控；若不啟用 = getScore 之外另有檢查。

---

### U2. NOT_ANY / NOT_ALL 的完整實現位置（高優先順序）

**問題**：`getScore()` switch-case 只處理 AND_ANY 和 AND_ALL，NOT_ANY/NOT_ALL 不進 switch。否定門控邏輯是在 getScore 外層還是另有函式？DeepWiki 提及 GitHub issue #2009 記錄過 NOT_ANY 未按預期工作的歷史 bug。

**驗證路徑**：設定 NOT_ANY 條目（主鍵+次鍵），分別測試次鍵存在/不存在時是否按文件預期啟用。

---

### U3. Recursion Level 同層多條目行為（中優先順序）

**問題**：同一層級（如 recursion_level=1）有多個條目時，是全部參與匹配還是隻匹配最高優先順序？某層有命中後是否完全跳過後續層，還是繼續評估？官方文件僅有簡略描述。

**驗證路徑**：在同一層級放 2 個條目，驗證是否都能被觸發；放 2 層後在第 1 層有命中時驗證第 2 層是否被跳過。

---

### U4. Inclusion Group 競爭失敗後 probability 補位（中優先順序）

**問題**：Group 競爭（filterByInclusionGroups）發生在 probability check 之前。勝出條目被 probability 過濾掉後，其餘同組條目是否有機會補位？

**當前原始碼傾向（參 §9.5，high）**：原始碼順序裡競爭淘汰在 probability 之前、且無重新競爭邏輯 → **傾向「不補位」**（勝出者被 probability 淘汰後該組本輪直接落空）。下方實測僅為最終確認。

**驗證路徑**：同組 2 條目，probability=1（近似 0%），重複觸發多次觀察是否偶有其他條目插入。

---

### U5. 同 depth 多 role 注入順序（低優先順序）

**問題**：同一 depth 下 system/user/assistant 三種 role 按 `['system','user','assistant']` 順序 splice，reverse 後相對順序的推導結論（assistant 比 system 更靠近最新訊息）未真機實測。

**驗證路徑**：同 depth 各設一條 system 和 assistant WI 條目，用 Prompt Manager 預覽確認實際順序。

---

### U6. depth 超出聊天訊息數時的行為（低優先順序）

**問題**：openai.js 無 `Math.min` clamp，`Array.prototype.splice` 對超出長度的 index 靜默追加到末尾；reverse 後這些超大 depth 條目可能落在 oldest 訊息之前（最開頭）。

**驗證路徑**：聊天只有 2 條訊息時設 depth=10 的條目，驗證其在 prompt 中的實際位置。

---

### U7. Automation ID post-generation 執行（中優先順序）

**問題**：GitHub Issue #3419（2025-02-03）請求 post-generation Automation ID 執行，2026-06-27 狀態未知。

**驗證路徑**：檢查 AutoExecuteHandler.js 當前 release 分支是否有 `handleAfterGeneration` 型別的 WI 處理邏輯。

---

### U8. externalActivations 事件名拼寫（中優先順序）

**問題**：向量啟用透過 `eventSource.emit(WORLDINFO_FORCE_ACTIVATE, ...)` 寫入 externalActivations，事件名來自 DeepWiki 描述，未在截斷程式碼中直接確認。

**驗證路徑**：在 vectors/index.js 完整原始碼中搜索 `emit` 呼叫，確認事件名拼寫。
