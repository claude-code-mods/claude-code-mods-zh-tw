## 置信度分級體系

本手冊採用三級置信度標註，格式為 `置信度 [依據型別]`：

- **high**：多源一致 + 原始碼直接驗證 / 生產卡實戰佐證，可直接施工
- **medium**：單源或推斷，可參考施工，宜在真機驗證後再大規模應用；強制子標籤：`medium·單源孤證` / `medium·推導未驗證`（須隨附真機驗證路徑）
- **low**：孤證無源，**禁止據此施工**，須先真機驗證

依據型別軸：`[執行時原始碼]` / `[文件·多源]` / `[文件·單源]` / `[社群]` / `[推斷]` / `[本地實戰]`

收集日期：2026-06-28
證據基線：SillyTavern v1.14.0 + 本地成熟卡（卡A 2.5.0 / 卡B 2.6.0）；控制流以當前官方 macros 文件核對

**兩條鐵規：**

1. **「從原始碼事實再推一步」的下游推導，即使原始碼本身已直讀，該推導結論最高只能 `medium·推導未驗證`**——除非已真機驗證；原始碼內部事實仍標 `high [執行時原始碼]`。
2. **節級標註 = 節內條目下確界**——禁止整節標 high 卻內含懸案條目；衝突即在節內區域性降級，並交叉引用懸案章對應條目。

## 1. 訊息渲染完整管線

> **核心結論** | 來源：`script.js` `messageFormatting()` 函式直讀 + `engine.js`/`chats.js` | 適用版本：v1.14.0+ | **high [執行時原始碼]**
>
> 注：草稿原標註「engine.js 原始碼分析 + ST 擴充套件開發文件」不夠精確。v1.14.0 中 `messageFormatting()` 是主渲染函式（script.js:1618），管線可在此直讀。`[hook] beforeRegex/afterRegex/afterMarkdown` 為 messageFormatter API（v1.14.0 不存在），故從管線圖中區分標註。

訊息從 LLM 產生到最終在 `.mes_text` DOM 中渲染，經過以下完整管線（宏求值在管線最前，見第 2 章）：

```
LLM 原始文字
  │
  ▼ prompt-bias 剝離（替換開頭的 prompt bias 字串）
  │  ← script.js:1645-1648 直讀
  │
  ▼ 正則指令碼（placement=[2] AI_OUTPUT 且 markdownOnly=true 時，此階段執行）
  │  ← getRegexedString(raw, AI_OUTPUT, { isMarkdown: true }) [high 執行時原始碼]
  │
  ▼ encode_tags 處理（若開啟，轉義 < >）+ 雙引號 <q> 包裹
  │  ← script.js:1685-1736 直讀
  │
  ▼ Showdown 轉 HTML（markdown → HTML）
  │   開啟: simpleLineBreaks / tables / strikethrough / ghCodeBlocks
  │   ← script.js:1745 直讀
  │
  ▼ encodeStyleTags（<style>→<custom-style>，DOMPurify 前保護）
  │   ← chats.js:538-543 直讀 [high 執行時原始碼]
  │
  ▼ DOMPurify.sanitize(mes, config)
  │   config: MESSAGE_SANITIZE=true / ADD_TAGS: ['custom-style']
  │   hook A: uponSanitizeAttribute → class 名加 custom- 字首
  │   hook B: uponSanitizeElement → HTMLUnknownElement 內 \n→<br>
  │   ← chats.js:1906-1977 直讀 [high 執行時原始碼]
  │
  ▼ decodeStyleTags（<custom-style>→<style>，CSS AST 重寫選擇器字首）
  │   ← chats.js:553-702 直讀 [high 執行時原始碼]
  │
  ▼ 渲染進 .mes_text DOM
```

**關於 messageFormatter hook（BEFORE_REGEX/AFTER_REGEX/AFTER_MARKDOWN）：**
- 這三個 hook 點在 v1.14.0 **不存在**（getContext() 無此 API）
- 屬官方文件記錄的擴充套件點，可能在更高版本引入 | **medium·推導未驗證 [文件·多源]**

**關鍵時序說明（v1.14.0 實測）：**

- `markdownOnly: true` 的正則指令碼在 **showdown 之前**、encode_tags 之前執行 | **high [執行時原始碼]**（script.js:1674-1678 直讀）
- `promptOnly: true` 的正則指令碼在**傳送給模型時**執行，不影響 display 層 | **high [執行時原始碼]**
- `{{trim}}` 已在宏求值階段（管線最前）處理，不屬於此管線內部 | **high [執行時原始碼]**
- DOMPurify 是 display 層最後淨化關；之後 decodeStyleTags 再 decode CSS | **high [執行時原始碼]**

## 2. 宏求值管線三階段

> **核心結論** | 來源：`macros.js` `evaluateMacros()` 原始碼 | 適用版本：v1.14.0+ | **high [執行時原始碼]**

宏求值發生在訊息渲染管線之前，適用於世界書、系統提示、角色卡欄位、訊息體所有字串：

```
原始字串
  │
  ▼ Phase 1 — Pre-env Macros
  │   包含：骰子/instruct/newline/trim/legacy <USER><BOT> 標籤
  │   getVariableMacros() 返回值也在此（變數宏最早執行）
  │
  ▼ Phase 2 — Env Variables
  │   使用者傳入 macro map，支援函式值
  │
  ▼ Phase 3 — Post-env Macros
  │   包含：token 限制/訊息訪問/時間/random/pick/banned
  │
  ▼ 求值完成字串 → 進入訊息渲染管線
```

**重要特性：**
- 變數宏（`{{getvar::}}` 等）處於 Phase 1，是最早執行的宏之一 | high [執行時原始碼]
- 舊引擎中宏求值順序不穩定；新引擎保證 stable evaluation order | high [執行時原始碼]

## 3. 宏系統雙引擎架構

### 3.1 兩套引擎對比

> **medium·推導未驗證** | 來源：官方宏文件 [文件·多源] | 適用版本：**v1.14.0 後某版本引入，v1.14.0 本地原始碼未見** | ~~high~~ → **medium·推導未驗證 [文件·多源]**
>
> **降級原因**：本地 v1.14.0 `macros.js` + `st-context.js` 直讀——未發現 `experimental_macro_engine` 開關、chevrotain 依賴、新引擎任何痕跡；`getContext()` 不暴露 `macros` 物件。雙引擎架構在官方文件中有記錄，但屬於 v1.14.0 之後引入的特性，本地版本無法驗證。**若仍使用 v1.14.0，下表描述不適用。**
>
> 真機驗證路徑：在目標 ST 版本設定頁搜尋 "experimental macro"，或 grep `experimental_macro_engine` 確認是否存在。

| | 舊引擎 MacrosParser | 新引擎 MacroEngine（Macros 2.0） |
|---|---|---|
| 儲存結構 | 靜態 `Map` | chevrotain CST 樹 |
| 處理管線 | 正則逐條替換 | Lexer → Parser → CstWalker |
| 巢狀支援 | **不支援** | **支援**：`{{getvar::{{char}}_mood}}` |
| 求值順序 | 不保證 | stable evaluation order |
| 開關 | 舊安裝預設（未開啟實驗選項） | `power_user.experimental_macro_engine`（新安裝預設開） |
| `{{pick}}` 相容性 | 舊 hash 演算法 | 新 hash 演算法，結果不相容 |

**切換風險**：從舊引擎切換到新引擎時，`{{pick}}` 的結果會因 hash 演算法不同而改變，同 chat 同位置的"穩定隨機"結果將全部重新整理。已有依賴 `{{pick}}` 的卡需告知使用者此風險。

來源 | 適用版本 | 置信度：medium·推導未驗證 [文件·多源]（v1.14.0 本地無此特性）

### 3.2 宏處理技術細節

> 來源：`macros.js` + `variables.js` 原始碼 | 適用版本：v1.14.0+ | **high [執行時原始碼]**（v1.14.0 直讀，以下各條分別標註）

**`{{trim}}`**
正則 `/(?:\r?\n)*{{trim}}(?:\r?\n)*/gi` → 替換為空字串，連同前後換行一併清除。在 Phase 1（Pre-env）階段處理，早於所有其他使用者可見宏。| **high [執行時原始碼]**（macros.js:521 直讀）

**`{{pick}}`**
雜湊公式：`seedrandom(getStringHash("${chatIdHash}-${rawContentHash}-${offset}"))` — 三因子（chat ID、內容 hash、偏移量）保證同 chat 同位置一致。**注意：v1.14.0 只有一套 hash 實現，「跨引擎不相容」說法僅適用於新引擎已引入的更高版本。** | **high [執行時原始碼]**（macros.js:404-432 直讀）

**`{{random}}`**
使用 `seedrandom('added entropy.', { entropy: true })` 加密種子真隨機，每次求值結果不同，不具備跨輪次一致性。| **high [執行時原始碼]**（macros.js:391 直讀）

**變數宏求值**
變數名不經過宏預處理，直接字串 trim 後匹配。`resolveVariable()` 查詢順序：
`scoped → local (chat_metadata) → global (extension_settings) → 返回原字串（靜默回退）`
| **high [執行時原始碼]**

**新引擎巢狀宏與變數速記語法**（需啟用 experimental_macro_engine，v1.14.0 無此特性）：| **medium·推導未驗證 [文件·多源]**（v1.14.0 無此功能，官方文件記錄屬更高版本）
- `.varname` = local 變數讀
- `$varname` = global 變數讀
- 運算子：`++/--/+=/=/-=`
- 空值合併：`||` / `??`
- 比較：`==/!=/>/</>=/<=`（返回字串 "true"/"false"）

    return transformedString; // 必須同步返回字串

## 8. DOMPurify 與 custom-style 陷阱

### 8.1 style 屬性與 style 標籤的 DOMPurify 處理機制

> 來源：`chats.js` 原始碼直讀 + Issue #3844 | 適用版本：v1.14.0+ | 整體 **medium·單源孤證→部分 high**（兩種機制需分開標註）

**【重要糾錯】草稿原描述「style= 屬性名被改為 custom-style=」是錯誤的。實際存在兩套獨立機制：**

---

**機制 A：`<style>` 標籤 → `<custom-style>` 標籤（encode/decode 方案）** | **high [執行時原始碼]**（chats.js:538-543, 553-702 直讀）

流程：
1. `encodeStyleTags()` 在 DOMPurify 前將 `<style>CSS內容</style>` 替換為 `<custom-style>URL編碼內容</custom-style>`
2. DOMPurify 執行時 `ADD_TAGS: ['custom-style']`，`<custom-style>` 標籤被保留
3. DOMPurify 後 `decodeStyleTags()` 將 `<custom-style>` decode 回 `<style>` 並透過 CSS AST 解析對所有選擇器加 `.mes_text ` 字首，防止跨樓層樣式汙染

**結論：`<style>` 標籤能穿越 DOMPurify，最終在 DOM 中正常工作。** CSS 規則中的 class 選擇器（如 `.foo`）會被改寫為 `.custom-foo`（見 8.3 節）。

---

**機制 B：`style="..."` 內聯屬性處理** | **medium·版本敏感 [原始碼觀察]**

原始碼中未見把屬性名重新命名為 `custom-style=` 的邏輯，但這不足以推出“DOMPurify 預設禁止所有 style”。現有 C3 與當前 release 觀察也不支援把“必然刪除”寫成跨版本事實。應把內聯 style 視為版本/淨化配置敏感能力，而不是穩定契約。

> 真機驗證路徑：在最低支援版與當前版傳送同一 `<span style="color:red">x</span>`，F12 同時檢查最終屬性與 computed style。

**生產結論：**
- 關鍵視覺使用 `<style>` 塊 + class，避免依賴內聯 style 是否保留；
- `<style>` 塊在已核管線中經 encode/decode 保護；
- 動態數值使用 `data-*` + 受信 JS 或 iframe，不把使用者資料拼進 style 字串。

**繞坑方案（生產卡實戰驗證）：**

| 方案 | 適用場景 | 成本 | 置信度 |
|---|---|---|---|
| 使用 `<style>` 塊 | 靜態樣式規則 | 低 | **high [執行時原始碼 + 本地實戰]** |
| `data-*` 屬性 + JS 後處理 | 需要動態資料的樣式 | 中；需要配套 JS | **high [本地實戰]** |
| iframe + Blob URL | 完整獨立 UI 元件（如狀態列） | 高；完全繞開 ST sanitization | **high [本地實戰]** |

來源：`chats.js` `encodeStyleTags()`/`decodeStyleTags()` 直讀 + `<local-guide-db>\本地證據\卡A歷史\3.0.2\components\*.html` [本地實戰]

### 8.2 自定義 XML 標籤 + simpleLineBreaks 雙重 bug（#3996）

> 來源：GitHub Issue #3996 + 本地實戰 | 適用版本：受 Chromium 136+ 影響更嚴重 | **high [執行時原始碼]**

**三重疊加機制：**

1. Showdown `simpleLineBreaks: true` → 把標籤內部的 `\n` 轉為 `<br>`
2. DOMPurify `uponSanitizeElement` hook → 對 `HTMLUnknownElement`（未在 ADD_TAGS 宣告的自定義標籤）再次把 `\n` 轉為 `<br>`
3. Chromium 136+ 對 HTML 解析更嚴格 → 雙重 `<br>` 堆疊，版面破壞

**修復方案（#3996 採納）：**
```javascript
// 在 DOMPurify ADD_TAGS 中宣告自定義標籤，避免被當做 HTMLUnknownElement
DOMPurify.sanitize(mes, {
    ADD_TAGS: ['custom-style', 'UpdateVariable', 'JSONPatch', 'analysis', 'content', ...],
    // ...
});
```

**角色卡工程繞坑（卡A卡實戰）：**
在 AI 回覆正文中的 `<UpdateVariable>` 塊由正則替換為 HTML，不讓裸 XML 標籤進入 showdown 處理流程。這是更徹底的方案：正則在 showdown 前消費自定義標籤，根本不存在 HTMLUnknownElement 問題。

### 8.3 CSS class 字首（雙層字首行為：存在且需區分）

> 來源：`chats.js` 原始碼直讀 + Issue #3844 | **high [執行時原始碼]**（chats.js:1915-1939 直讀）

**【重要糾錯】草稿「ST 不對 CSS class 名稱加字首」是錯誤的。v1.14.0 原始碼有兩套 class 字首機制：**

---

**機制 A：`class` 屬性 → `custom-` 字首（DOMPurify `uponSanitizeAttribute` hook）** | **high [執行時原始碼]**

在 `MESSAGE_SANITIZE` 模式（訊息渲染時）下，DOMPurify hook 將每個 class 名加上 `custom-` 字首，**例外**：
- 以 `fa-` 開頭的 class（FontAwesome 圖示）保留原名
- 以 `note-` 開頭的 class 保留原名
- `monospace` 保留原名
- 當 `config['MESSAGE_ALLOW_SYSTEM_UI']` 為 true 且節點包含 `menu_button` class 時，整個節點豁免

```javascript
// chats.js:1926-1939（直讀）
case 'class': {
    data.attrValue = data.attrValue.split(' ').map((v) => {
        if (v.startsWith('fa-') || v.startsWith('note-') || v === 'monospace') {
            return v;  // 豁免
        }
        return 'custom-' + v;  // 所有其他 class 加字首
    }).join(' ');
}
```

**實際影響**：正則注入 `<div class="foo">` → DOM 中變為 `<div class="custom-foo">`。**角色卡若在 JS 裡用 `.querySelector('.foo')` 或 CSS 用 `.foo {}` 選擇器，將全部失效。須改用 `.custom-foo` 或 `data-` 屬性選擇。**

---

**機制 B：`<style>` 塊內的 CSS 選擇器字首（CSS AST 重寫）** | **high [執行時原始碼]**（chats.js:562-598 直讀）

`decodeStyleTags()` 在將 `<custom-style>` decode 回 `<style>` 時，透過 CSS AST 將所有選擇器加 `.mes_text ` 字首（如 `.foo` → `.mes_text .foo`）。同時將選擇器中的 `.foo` 改寫為 `.custom-foo`（與機制 A 一致）。目的是防止跨樓層 CSS 汙染。

**「Issue #3844 not planned」的正確解讀**：該 Issue 申請的是給 class 加字首的功能，官方"not planned"指的是拒絕此功能——但實際上相關行為已經透過另外方式（DOMPurify hook + CSS AST 重寫）實現，只是與 Issue 描述的方案不同。

### 11.2 正規化 B：佔位符 + 狀態列 iframe 注入

### 11.3 正規化 C：對話氣泡正則（data-* 屬性繞過 DOMPurify）

**使用場景**：把 `<xy-dialog>` 自定義標籤替換為攜帶資料的 span，由後續 JS 處理視覺渲染。

```
findRegex:
  /<xy-dialog\s+speaker=["']([^"']+)["'](?:\s+avatar=["']([^"']*)["'])?\s*>([\s\S]*?)<\/xy-dialog>/gi

replaceString:
  <span class="xy-dialog-render"
        data-xy-dialog-render
        data-xy-dialog-speaker="$1"
        data-xy-dialog-avatar="$2">
    <textarea class="xy-dialog-content-source"
              data-xy-dialog-content-source
              hidden readonly>$3</textarea>
  </span>
```

**核心設計**：不把動態資料拼入樣式字串，改用 `data-*` 儲存，再由受信 JS 讀取並渲染。這樣避免依賴內聯 `style=` 的版本差異，也降低樣式注入風險。

### 11.4 正規化 D：first_mes 開局頁佔位 HTML

**使用場景**：在開局訊息（`first_mes`）欄位中放置唯一短標記，由顯示正則展開為本地 loading/error mount，再由受信指令碼非同步載入宣告式開局頁。

```html
<div data-xy-opening-remote="1">
  <div data-xy-opening-title>示例學園</div>
  <div data-xy-opening-loading>
    開局介面載入中…<br>
    首次開啟需從雲端載入開局頁，請稍候。
  </div>
</div>
```

**注意**：訊息 HTML 的內聯樣式、`<style>` 和 class 改名行為隨 ST 渲染管線版本變化；本地 v1.14.0 歷史觀察不能推廣為永久規則。可見 fallback 不依賴單一易變樣式機制，正式載入還必須有超時、hash/協議/結構校驗、淨化、重試和完整銷燬。開局草稿、預覽、提交與正常訊息鏈統一見 **《C10_開局頁與自定義開局.md》**。

## 12. 高頻避坑清單

> 綜合來源：本地實戰 + 原始碼分析 + GitHub Issues

| # | 坑 | 根本原因 | 解法 | 置信度 |
|---|---|---|---|---|
| P1 | `style=` 內聯屬性在不同版本/配置表現不一致 | 訊息正則、showdown、DOMPurify 與 hook 會隨版本變化 | 可見 fallback 不依賴內聯 style；目標版本真機檢查 computed DOM | **medium [版本敏感原始碼]** |
| P1-b | `class="foo"` 在 DOM 中變為 `class="custom-foo"` | DOMPurify `uponSanitizeAttribute` hook 給所有 class 加 `custom-` 字首（見 8.3 節） | JS 選擇器改用 `.custom-foo`；CSS 選擇器同步改寫；或用 `data-*` 屬性 | **high [執行時原始碼]**（chats.js:1926-1939 直讀）|
| P2 | 自定義標籤內容 `<br>` 爆炸 | simpleLineBreaks=true + DOMPurify HTMLUnknownElement hook 雙重轉換（Chromium 136+ 更嚴重） | 正則提前消費自定義標籤，不讓裸標籤進 showdown；或在 ADD_TAGS 中宣告 | **high [執行時原始碼]**（chats.js:1942-1976 直讀）|
| P3 | `{{pick}}` 切換引擎後結果全變 | 新舊引擎 hash 演算法不同，不相容 | 確定引擎後不切換；版本遷移要告知使用者 | **medium·推導未驗證 [文件·多源]**（雙引擎在 v1.14.0 不存在，該坑僅適用更高版本）|
| P4 | 巢狀宏 `{{getvar::{{char}}_x}}` 不生效 | 舊引擎不支援巢狀宏 | 確認目標版本已有新引擎且 `experimental_macro_engine` 已開啟後再使用 | **medium·推導未驗證 [文件·多源]**（v1.14.0 無雙引擎）|
| P5 | 正則注入的 HTML 被 showdown 加 `<br>` | 正則在 showdown 前執行（markdownOnly:true），HTML 標籤內換行被轉換 | 注入 HTML 時保持標籤緊湊，換行內容改用 `data-` 屬性 | **high [執行時原始碼]**（script.js:1674 直讀，markdownOnly:true 在 showdown 前跑）|
| P6 | 變數名找不到時靜默返回原字串 | `resolveVariable()` 的 fallback 行為 | 讀前用 `{{hasvar::name}}` 檢查；或速記 `{{.name??defaultValue}}` | **high [執行時原始碼]**（variables.js 直讀）|
| P7 | `markdownOnly:true` 指令碼在流式生成中重複跑 | ST 每次新增 token 都重新渲染，指令碼重複執行 | 確保正則替換冪等（替換前先檢測目標是否已存在） | **medium·推導未驗證 [推斷]**（邏輯合理但無文件確認）|
| P8 | `<style>` 塊選擇器被自動加 `.mes_text ` 字首且 class 被改為 `.custom-*` | `decodeStyleTags()` 透過 CSS AST 重寫選擇器，防跨樓層汙染（見 8.3 節 B 機制） | 編寫 `<style>` 時直接寫 `.custom-foo` 而不是 `.foo`；利用字首隔離而不是繞開它 | **high [執行時原始碼]**（chats.js:553-702 直讀）|
