## 1. MVU 系統三層架構

**核心結論**：MVU（MagVarUpdate）由三層構成，各層職責分離，缺一不可。

| 層 | 載體 | 職責 |
|---|---|---|
| **世界書條目** | `[mvu_update]`標記的WI條目 | 向LLM傳遞變數JSON + 更新規則/schema描述 |
| **bundle指令碼** | `artifact/bundle.js` | 解析LLM輸出的`<UpdateVariable>`塊，執行JSONPatch操作，觸發生命週期事件 |
| **zod schema指令碼** | `zod_schema.js` | 定義變數結構約束，註冊到MVU做變數合法性驗證 |

**變數儲存結構**（MvuData）：

| 變數 | 用途 | 注入給 LLM |
|---|---|---|
| `stat_data` | 下一輪 LLM 讀取當前狀態 | 是（透過世界書條目） |
| `display_data` | 前端狀態列渲染（純值/純物件，無二元組） | 否 |

**VWD [value, desc] 二元組狀態 — 核心結論**：**VWD [value, desc] 格式已在實戰卡中徹底廢棄。** 本地 InitialVariables.json（卡A2.5.0、卡B2.6.0）均為純值結構，路徑直接指向值本身（如 `/環境/時間`），不是 `/環境/時間/0`。描述職責已完全遷移到 zod schema 的 `.describe()` 和 `prefault` 機制。bundle.js 仍保留 VWD 檢測程式碼僅用於相容舊卡，新卡**不應**生產此格式。

**CDN 地址**：

```
# 主映象
https://cdn.jsdelivr.net/gh/MagicalAstrogy/MagVarUpdate/artifact/bundle.js

# 備用映象（部分生產卡以此為主，如卡A2.5.0 mvu_zod_cn.js）
https://testingcf.jsdelivr.net/gh/MagicalAstrogy/MagVarUpdate/artifact/bundle.js
```

> 實測：卡A2.5.0 的 mvu_zod_cn.js 第一選擇是 testingcf 映象，mvu_zod_global.js 第一選擇是 cdn.jsdelivr.net。兩者內容相同，按網路情況二選一，不存在絕對的"生產推薦"之分。

來源：`[執行時原始碼]` + `[本地實戰]`（卡A2.5.0 mvu_zod_cn.js / mvu_zod_global.js 實測） | 置信度：**high**

## 2. JSONPatch (RFC 6902 方言) 完整規範

### 2.1 UpdateVariable 塊結構

**核心結論**：LLM輸出必須包裹在 `<UpdateVariable>` 塊內，分 analysis 和 JSONPatch 兩段。

```xml
<UpdateVariable>
<analysis>
變數預分析（詳述正文中哪些狀態發生了變化，每行對應至少一個path）
</analysis>
<JSONPatch>
[
  {"op":"replace","path":"/環境/時間","value":"14:25"},
  {"op":"add","path":"/任務/任務名","value":{...完整物件...}}
]
</JSONPatch>
</UpdateVariable>
```

**bundle.js 標籤解析正則**：

```javascript
/<(update(?:variable)?|variableupdate)>/gi  // 外層匹配（大小寫不敏感）
we(t, 'Analysis')        // 提取 analysis 內容
we(t, 'json_?patch')     // 提取 JSONPatch 內容（匹配 JSONPatch 和 json_patch 兩種寫法）
```

> 注：`we()` 函式實現為 `e.match(new RegExp('^\\s*<${t}>\\s*([\\s\\S]*?)\\s*</${t}>\\s*$','i'))`，第二引數傳 `'json_?patch'`（正則模式），因此同時相容 `<JSONPatch>` 和 `<json_patch>` 兩種標籤寫法。

來源：`[執行時原始碼]`（bundle.js CDN 實測） | 置信度：**high**

---

### 2.2 op 型別完整列舉（MVU方言，非純RFC6902）

**核心結論**：MVU支援6種op，但LLM輸出層只應使用4種。

| op | RFC6902標準 | MVU特有 | LLM可用 | 說明 |
|---|---|---|---|---|
| `replace` | ✅ | — | ✅ | 替換已存在路徑的值；路徑不存在則報錯 |
| `add` | ✅ | 擴充套件 | ✅ | 新增欄位/record項；也用於追加陣列元素 |
| `remove` | ✅ | — | ✅ | 刪除指定路徑 |
| `move` | ✅ | — | ✅ | 欄位遷移，`from`→`path`（或`to`） |
| `delta` | ❌ | ✅ | ❌ | MVU專有：數值增量操作，`value`須為number；等同`field += value` |
| `insert` | ❌ | ✅ | ❌ | MVU專有：在陣列指定位置插入；與`add`等價，在anyOf中合併處理 |

**關鍵區別**：

- `delta`：`{"op":"delta","path":"/user/體力","value":-10}` → 在當前值基礎上加減
- `add` vs `insert`：功能幾乎等價（兩者在 anyOf 中合併為 `'insert'|'add'`），均可新增record/追加陣列
- `replace`：**路徑必須已存在**，否則禁止使用；路徑不存在時必須用 `add`

**本地 mvu_update_full.txt 規則**（卡A2.5.0）明確只允許：`add、replace、remove、move`，未包含 delta 和 insert。

來源：`[執行時原始碼]`（bundle.js 確認 delta/insert op 存在）+ `[本地實戰]`（卡A2.5.0 mvu_update_full.txt 規則文字確認 LLM 只用4種 op）| 置信度：op 技術存在：**high**；"delta/insert LLM不可用"結論：**high**（來自生產卡世界書強制規則文字，屬規則層而非 bundle 強制攔截）

### 2.3 路徑語法

**核心結論**：路徑格式為 `/頂層容器/鍵名/子欄位`，使用 JSON Pointer 風格的 `/` 分隔符。

| 規則 | 說明 |
|---|---|
| 分隔符 | `/`（JSON Pointer風格） |
| 陣列追加 | `/-` 等效於陣列末尾追加（bundle.js 中 `'-' === o ? c.length : o`） |
| 轉義 | 使用 `lodash.toPath()` 而非標準 RFC6902 的 `~0`/`~1` 轉義 |
| 中文鍵名 | 直接使用，不需轉義 |

**巢狀路徑示例**：

```
/環境/時間                          → string欄位
/user/基本屬性/等級                  → 巢狀物件欄位
/當前互動角色/張三/衣著/上裝          → record下的子欄位
/當前互動角色/張三                    → 整個record項（add/replace完整物件）
/成就/-                              → 追加到陣列末尾
```

來源：`[執行時原始碼]` + `[本地實戰]` | 置信度：**high**

## 3. Zod Schema 整合

### 3.1 prefault 詳解

**核心結論**：`prefault` 是 Zod v4 的**標準內建方法**（非prototype擴充套件、非TavernHelper注入），與 `default` 和 `catch` 有本質區別。

**定義**："pre-parse default"——在驗證前應用後備值。當輸入為 `undefined` 時，prefault 值被送入完整的驗證管道（包括transform）。

```javascript
// prefault vs default 的關鍵區別
z.string().transform(val => val.length).prefault("tuna")
  .parse(undefined)  // → 4（"tuna"經過transform變為4）

z.string().transform(val => val.length).default("tuna")
  .parse(undefined)  // → "tuna"（繞過transform直接返回預設值）
```

**三者對比**：

| 方法 | 觸發條件 | 後備值經過驗證pipeline | 適用場景 |
|---|---|---|---|
| `prefault(v)` | 輸入為 `undefined` | ✅ 是 | 後備值需經transform處理時 |
| `default(v)` | 輸入為 `undefined` | ❌ 否（繞過） | 後備值已是最終型別時 |
| `catch(v)` | **任何驗證失敗** | ❌ 否 | 不可信輸入的全兜底 |

**在角色卡中的慣用法**：

```javascript
// 字串欄位：undefined → ''
z.string().prefault('')

// 物件欄位：undefined → {}（再經內部欄位各自prefault）
z.object({ 上裝: z.string().prefault('') }).prefault({})

// 數值欄位（配合coerce）：undefined → 0
z.coerce.number().transform(v => _.clamp(v, 0, 100)).prefault(0)

// 布林欄位
z.coerce.boolean().prefault(false)
```

**`passthrough()` 的作用**：允許 schema 物件接受未宣告的額外欄位。LLM可能寫入任意擴充套件欄位時使用。

來源：`[文件·多源]`（Zod v4官方文件 + DeepWiki + Medium文章）+ `[本地實戰]` | 置信度：**high**（prefault/default/catch 三者行為對比）；prefault 在 z.preprocess 巢狀中的觸發順序：**medium·推導未驗證**（見 §9 懸案 7.3）

### 3.2 registerMvuSchema API

**核心結論**：`registerMvuSchema` 由 StageDog/tavern_resource 的 mvu_zod.js 提供，是連線 zod schema 與 MVU 變數管理器的橋接層。

**匯入與註冊**：

```javascript
// 1. 匯入（帶fallback）
let registerMvuSchema;
try {
  ({ registerMvuSchema } = await import(
    'https://cdn.jsdelivr.net/gh/StageDog/tavern_resource/dist/util/mvu_zod.js'
  ));
} catch (error) {
  ({ registerMvuSchema } = await import(
    'https://testingcf.jsdelivr.net/gh/StageDog/tavern_resource/dist/util/mvu_zod.js'
  ));
}

// 2. 定義schema（必須是z.object(...)，對應stat_data層級）
export const Schema = z.preprocess(normalizeRoot, z.object({
  環境: z.object({...}).prefault({}),
  user: z.object({...}).prefault({}),
  // ...其他頂層容器
}));

// 3. 註冊（必須在$()回撥中）
$(() => { registerMvuSchema(Schema); });
```

**內部原理（mvu_zod.js實現）**：

```javascript
function registerMvuSchema(r) {
  const schema = () => {
    const t = typeof r === 'function' ? r() : r;
    const e = t instanceof z.ZodObject ? z.looseObject(t.shape) : t;
    // 包裝為 {stat_data: schema} 註冊到MVU變數管理器
    if (typeof registerVariableSchema === 'function') {
      registerVariableSchema(z.object({ stat_data: e }), { type: 'message' });
    }
    return e;
  };
  // 監聽MVU生命週期事件，在變數初始化/命令解析/更新結束時執行驗證
}
```

**Zod import URL（mvu_zod.js內部）**：

```
https://testingcf.jsdelivr.net/npm/zod/v4/core/+esm
```

**`registerVariableSchema`（底層函式）**：由 JS-Slash-Runner（TavernHelper v4.3.7+）注入到全域性環境，`mvu_zod.js` 只是檢測並呼叫它。

來源：`[執行時原始碼]`（mvu_zod.js CDN 實測）+ `[本地實戰]`（卡A2.5.0 zod_schema.js）+ `[文件·單源]`（TavernHelper官方更新日誌，v4.3.7 明確記錄"新增 registerVariableSchema 函式"）| 置信度：**high**

### 3.3 $meta 結構詳解

**核心結論**：`$meta` 是變數 JSON 中可附加的元資訊物件，控制 MVU 對該變數的處理行為。**生產卡中不使用**（依賴 zod schema 約束結構）。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `$meta.extensible` | boolean | 物件/陣列是否允許新增未在schema中宣告的新欄位 |
| `$meta.recursiveExtensible` | boolean | 遞迴地對所有子欄位啟用extensible |
| `$meta.template` | object/array | 模板，新增陣列/物件元素時的預設結構 |
| `$meta.required` | string[] | 必需欄位名陣列（缺失時驗證失敗） |
| `$meta.strictTemplate` | boolean | 嚴格模板模式（新值必須符合template結構） |
| `$meta.strictSet` | boolean | 嚴格設定模式（禁止新增template以外的欄位） |
| `$meta.concatTemplateArray` | boolean | 陣列模板時是否拼接（true）還是替換（false） |

來源：`[執行時原始碼]`（bundle.js CDN 摘要讀取） | 置信度：欄位名稱存在：**medium·單源孤證**；各欄位具體行為：**medium·推導未驗證**（生產卡不用 $meta，無真機驗證）

### 3.4 MvuData.schema / SchemaNode

**核心結論**：bundle.js 中未找到獨立的 `MvuData.schema(SchemaNode)` 公開 API。實際使用路徑是透過 `registerMvuSchema` 註冊 Zod schema 物件，bundle 內部透過 `mag_command_parsed_for_zod` 事件處理驗證和路徑操作。

`SchemaNode` 是 Zod schema 物件樹的節點型別（ZodObject、ZodString、ZodNumber等），無獨立自定義型別。

來源：`[執行時原始碼]`（bundle.js CDN 摘要）+ `[推斷]` | 置信度：**medium·推導未驗證**

## 4. zod 體系與跨例項風險

### 4.1 三套 schema 體系對比

**核心結論（已回源坐實）**：「變數 schema」在 ST 生態裡有**三套完全獨立、互不呼叫**的體系，重建時務必認清當前用的是哪套（混淆是 zod_schema.js bug 的根源領域）：

| 體系 | API / 形態 | 作用 | 執行時是否攔截寫入 |
|---|---|---|---|
| **JS-Slash-Runner** | `registerVariableSchema(schema, {type})` 單函式，type ∈ 5 種作用域 | 僅變數管理器 UI 校驗顯示 | 否（純 UI） |
| **MagVarUpdate (MVU)** | 內嵌 `MvuData.schema`（自定義 `SchemaNode` 型別，**非 zod**），寫在變數結構裡 | 指導路徑校驗 / 模板填充 / extensible 控制 | 是（執行時起效） |
| **ST-Prompt-Template** | `setVariableSchema()`（EJS 路線，已廢棄） | EJS 寫入前攔截校驗 | 是 |

來源：`[執行時原始碼]`（本地 variables.d.ts JSDoc 逐字核實）| 置信度：JS-Slash-Runner 側 **high**；MVU SchemaNode 側 **medium·單源孤證**（MVU 私有倉，本地無佐證）

### 4.2 registerVariableSchema 純 UI 不攔截寫入

**核心結論（已回源坐實）**：`registerVariableSchema` **僅影響變數管理器 UI 的校驗顯示**，對程式碼層面零影響——不影響 `parseMessage` / `replaceMvuData` 的實際寫入，不會在執行時攔截非法寫入。

依據 `@types/function/variables.d.ts` 的 JSDoc 原文：「這只是方便使用變數管理器這一 UI 檢視和管理變數，對於程式碼層面沒有任何影響」

它是**單一函式**靠 `option.type`（global/preset/character/chat/message）切換作用域，**不存在** `registerGlobalVariableSchema` 等多個獨立函式。

```typescript
// 簽名
function registerVariableSchema(
  schema: z.ZodType<any>,
  option: { type: 'global' | 'preset' | 'character' | 'chat' | 'message' }
): void;
```

來源：`[執行時原始碼]`（本地 variables.d.ts 行190 JSDoc + TavernHelper CHANGELOG v4.3.7）| 置信度：**high**

### 4.3 跨 zod 例項風險（三例項地雷）

**核心結論**：JS-Slash-Runner 內建 zod `^4.4.3`、MVU（mvu_zod.js）內部從 CDN 載入 zod `v4/core`，卡內若再從 CDN 引第三個 zod → `instanceof` 跨例項必失敗、`._def` 取不到、`parse` 靜默產出 NaN/undefined。

**鐵律：卡內一律複用 `window.z`（JS-Slash-Runner 注入的同一例項），絕不自帶 CDN zod。**

```javascript
// 推薦：直接用全域性 z（JS-Slash-Runner 掛載的 Zod v4）
const Schema = z.object({ 積分: z.number() });

// 危險：從 CDN 引入獨立 Zod（可能是不同 v4 patch 或 v3）
// import { z } from 'https://cdn.jsdelivr.net/npm/zod@3/...'; // 禁止
```

**Zod v4 重大 API 變化**：`._def` 內部屬性遷移到 `._zod.def`；`ZodType` 類不再互通。跨版本例項 `instanceof z.ZodType` 必然失敗。

**暴露機制**：

```typescript
// src/third_party_object.ts
import * as z_object from 'zod';
globalThis.z = z_object;  // 掛到 window.z

// src/iframe/predefine.js
result = result.merge(_.pick(window.parent, ['EjsTemplate', 'TavernHelper', 'YAML', 'showdown', 'toastr', 'z']));
// iframe 內的 window.z 與 parent.z 是同一物件引用
```

來源：`[執行時原始碼]`（本地 third_party_object.ts + iframe/predefine.js + package.json 逐字核實）| 置信度：**high**

## 8. 高頻避坑

來源：`[本地實戰]` + `[執行時原始碼]` | 置信度：**high**

1. **replace路徑不存在報錯**：`replace` 要求路徑已存在。首次寫入 record 項必須 `add` 完整物件，不能直接 `replace` 其子欄位。

2. **新增record子欄位的順序**：先 `add /頂層容器/recordKey`（完整物件），才能對其子欄位使用 `replace`。

3. **VWD格式已廢棄**：InitialVariables.json 中不寫 `[value, desc]` 二元組，直接寫純值（字串/數字/空物件）。路徑直接是 `/環境/時間` 而非 `/環境/時間/0`。

4. **prefault vs default的選擇**：物件欄位用 `.prefault({})`（值先經過 transform），不要與 `.default({})` 混用；`.default` 的後備值繞過 transform。

5. **passthrough()的必要性**：LLM 可能寫入 schema 中未宣告的欄位時，需在物件末尾加 `.passthrough()`，否則這些欄位會被 stripping 掉。

6. **$meta在生產卡中不用**：生產卡透過 zod schema 約束結構，不用 `$meta` 來控制 extensible 等。

7. **registerMvuSchema 需在`$()`回撥中呼叫**：必須等 DOM 就緒後註冊，不能在模組頂層直接呼叫。

8. **z 是全域性變數，無需 import**：TavernHelper（v3.3.2+）自動注入 `z`，直接使用 `z.object()` 等，無需 import zod。卡內絕不從 CDN 另引 zod 例項（三例項地雷，見 §4.3）。

9. **analysis每行必須有對應patch**：`<analysis>` 中每行描述至少對應一個 JSONPatch 操作，禁止分析中提到變化但 patch 中遺漏。

10. **LLM輸出不使用 delta/insert**：這兩個 op 僅限指令碼程式碼呼叫；LLM輸出的 JSONPatch 只用 `add / replace / remove / move` 四種。

11. **VARIABLE_INITIALIZED 必須用常量引用**：事件字串值中有 typo（`initiailized`，多一個 i），硬編碼極易出錯，必須用 `Mvu.events.VARIABLE_INITIALIZED` 引用（見 §5.2）。

12. **iframe_events 有 `js_` 字首**：iframe 內監聽 ST 事件要用 `iframe_events.GENERATION_STARTED`（`'js_generation_started'`），不是 `tavern_events.GENERATION_STARTED`（`'generation_started'`）。

13. **registerVariableSchema 不攔截寫入**：呼叫此函式隻影響變數管理器 UI 顯示，無法在執行時阻止 LLM 寫非法值。真正的執行時攔截靠 zod schema 經 `registerMvuSchema` 註冊（見 §4.2）。

## 9. 懸案（未決項）

### 懸案 P1 — delta op 是否為 LLM 可用 op

**狀態**：已有傾向性結論，但未真機驗證  
**描述**：MVU bundle.js 使用 `delta` op（數值增量）但 RFC6902 標準中無此 op。本地 mvu_update_full.txt 規則（卡A2.5.0）明確只允許 `add、replace、remove、move`，**未包含 delta**。  
**傾向結論**：LLM輸出格式僅用4種op（add/replace/remove/move），`delta` 是內部API或早期版本遺留，不暴露給LLM。  
**驗證路徑**：檢視卡的世界書條目中 `[mvu_update]` 的op限制說明；或在 JSONPatch 中使用 `delta` 後觀察 bundle 是否接受。  
置信度：**medium·推導未驗證**

置信度：**medium·推導未驗證**

### 懸案 P6 — z.preprocess 中 prefault 的觸發時機

**狀態**：推斷，官方文件未明確  
**描述**：如 `z.preprocess(normalizeRoot, z.object({...})).prefault({})` 中，prefault 何時觸發——是 normalizeRoot 之前還是之後？  
**傾向結論**：外層 `.prefault({})` 先將 `undefined` 換成 `{}`，然後 `{}` 進入內層 `z.preprocess(fn, ...)` 的 fn 函式。實戰中 `{}` 是安全初始值，無論順序如何結果一致，因此該角落場景未被驗證。  
置信度：**medium·推導未驗證**
