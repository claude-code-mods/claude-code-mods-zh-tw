## 1. 定義、邊界與選型

### 1.1 它是什麼

SP·資料庫是一套執行在 SillyTavern 中、由自身指令碼管理的**二維表格變數系統**：

```text
劇情正文 / 世界書 / 人設
          ↓
獨立填表提示詞與 API
          ↓
AI 輸出表格編輯指令
          ↓
原生二維陣列服務 或 SQLite 執行時
          ↓
V2 checkpoint + operation log
          ↓
寫回當前聊天訊息，並可同步到世界書
```

它的核心不是一棵 JSON 變數樹，而是多張有表頭、資料行、建表說明和增刪改觸發語義的表。

來源：`src/shared/models/table-data.ts`、`src/shared/table-storage-provider.ts` ｜ 置信度：high `[已核快照原始碼]`

### 1.2 它不是 MVU

| 維度 | SP·資料庫 | MVU |
|---|---|---|
| 基本模型 | `mate + sheet_* + Sheet.content` 二維表 | 訊息變數中的 `stat_data` 物件樹 |
| 結構約束 | 表頭、DDL、Note、SQL 約束 | zod schema / 變數規則 |
| AI 更新 | 獨立填表提示詞，輸出 DSL、SQL 或嚴格 JSON | 主回覆或額外解析模型輸出變數命令/JSONPatch |
| 持久化 | 外掛自有聊天欄位、V2 checkpoint/log | MVU 訊息變數快照 |
| 前端入口 | 宿主視窗的 `AutoCardUpdaterAPI` | `window.Mvu` / Tavern Helper 變數介面 |
| 世界書 | 可把表格檢視同步成外掛生成條目 | 通常用 EJS/宏讀取訊息變數 |

因此，本文嚴禁把表格稱為“MVU schema”，也不使用 `registerMvuSchema`、`defineMvuDataStore`、`stat_data` 或 JSONPatch 來解釋 SP·資料庫的內部機制。

兩套系統可以同時裝在一張卡上，但必須明確誰擁有哪一份狀態。不要讓同一項數值同時由 MVU 和資料庫寫入，否則會出現雙寫、回滾不一致和提示詞互相覆蓋。

來源：兩套系統已核原始碼介面對照 ｜ 置信度：high `[原始碼邊界]`

### 1.3 什麼時候選資料庫表格

適合：

- 角色、揹包、任務、紀要、陣營等天然按“行 × 列”組織的資料；
- 作者希望在視覺化編輯器裡直接檢視和修改；
- 需要 SQL 查詢、聚合、排序、條件更新或多表關聯；
- 希望使用獨立填表模型，而不是讓劇情模型同時承擔變數更新；
- 需要把指定表或索引同步到世界書。

不適合：

- 只有少量巢狀開關，二維表反而增加複雜度；
- 必須與 MVU 狀態列、MVU 更新事件完全同鏈；
- 沒有能力維護表結構、提示詞、持久化和遷移；
- 把所有劇情正文無限塞進單元格，導致提示詞與存檔膨脹。

## 2. 一份資料庫到底由什麼組成

### 2.1 頂層結構

當前合併後的執行時資料形態是：

```ts
type TableDataObject = {
  mate: Mate;
  [sheetKey: `sheet_${string}`]: Sheet | Mate;
};
```

典型佈局：

```text
currentJsonTableData_ACU
├─ mate
├─ sheet_global_state
├─ sheet_inventory
├─ sheet_characters
└─ sheet_custom_xxx
```

`sheet_*` 是內部鍵；給人和 AI 看的表名是 `sheet.name`。模板製作時建議讓物件鍵與 `sheet.uid` 保持一致並長期穩定，不要用中文表名充當內部鍵。

來源：`TableDataObject_ACU`、內建表預設定義 ｜ 置信度：high `[已核快照原始碼]`

### 2.2 `mate` 元資訊

```ts
interface Mate {
  type: string;                 // 當前模板為 chatSheets
  version: number;
  updateConfigUiSentinel: number;
  globalInjectionConfig: {
    readableEntryPlacement: PlacementConfig;
    wrapperPlacement: PlacementConfig;
  };
}
```

`mate` 描述整個模板，而不是某張表。`importTemplateFromData()` 的當前校驗要求至少滿足：

- 有 `mate`；
- `mate.type === "chatSheets"`；
- 至少有一個 `sheet_*`；
- 每張表有 `name`、`content`、`sourceData`。

來源：`API_DOCUMENTATION.md`、`template-preset-api.ts` ｜ 置信度：high `[已核快照原始碼 + 專案 API 文件]`

### 2.3 `Sheet` 完整結構

```ts
interface Sheet {
  uid: string;
  name: string;
  sourceData: {
    note: string;
    initNode: string;
    insertNode: string;
    updateNode: string;
    deleteNode: string;
    ddl?: string;
  };
  content: (string | null)[][];
  updateConfig: {
    uiSentinel: number;
    contextDepth: number;
    updateFrequency: number;
    batchSize: number;
    skipFloors: number;
    sendRowsSqlTemplate?: string;
  };
  exportConfig: SheetExportConfig;
  orderNo: number;
  seedRows?: (string | null)[][];
}
```

### 2.4 `content` 是二維表

```js
content: [
  ['row_id', '物品名稱', '數量', '描述/效果', '類別'], // 表頭
  ['1', '鐵劍', '3', '鋒利的鐵製長劍', '武器'],       // 第 1 條資料
  ['2', '治療藥水', '10', '恢復體力', '消耗品'],      // 第 2 條資料
]
```

鐵律：

1. `content[0]` 是表頭，不是資料。
2. 第一條資料是 `content[1]`，外部 CRUD 的 `rowIndex=1` 也表示第一條資料。
3. SQLite 模式仍保留這份 JSON 二維檢視，供上層 UI 與相容 API 使用。
4. SQLite 表的首列必須是 `row_id`；不要讓業務欄位冒充內部行號。
5. 表頭中文名、DDL 中文註釋、Note 中的列名必須一致。

來源：`models/table-data.ts`、`syntax-reference.md` ｜ 置信度：high `[已核快照原始碼 + 專案文件]`

### 2.5 `sourceData` 是 AI 的表格說明書

| 欄位 | AI 何時使用 | 應寫什麼 |
|---|---|---|
| `note` | 每次把該表發給填表 AI | 一行代表什麼、每列含義、範圍與格式 |
| `initNode` | 表為空或初始化時 | 初始應建立什麼；不需要時明確禁止 |
| `insertNode` | 判斷是否新增行 | 新實體判定條件；SQLite 模式附 INSERT 示例 |
| `updateNode` | 判斷是否改已有行 | 變化條件、定位鍵、增量/覆蓋語義；附帶 WHERE 的示例 |
| `deleteNode` | 判斷是否刪除行 | 只在什麼情況下刪除；禁止時直接寫“禁止刪除。” |
| `ddl` | SQLite 建表和中英文對映 | 英文物理表名、欄位型別、約束、中文註釋 |

這些內容是填表提示詞的一部分，不是僅供作者閱讀的備註。

## 3. 原生 DSL 與 SQLite 雙模式

### 3.1 共同上層，兩個儲存 Provider

外掛以 `ITableStorageProvider` 統一兩種模式：

| 能力 | 原生模式 `native` | SQLite 模式 `sqlite` |
|---|---|---|
| 執行時 | JSON 二維陣列 | sql.js 執行時資料庫 + JSON 相容檢視 |
| AI 看到的結構 | 表 ID、列號、Note、Trigger、當前行 | DDL、SQL 註釋、Note、當前資料 |
| AI 舊式編輯 | `insertRow/updateRow/deleteRow` DSL | `INSERT/UPDATE/DELETE` SQL |
| 複雜查詢 | 前端遍歷 `content` | SQL、ORM 模板變數、JOIN/聚合 |
| 外部 CRUD | 四個 API 均支援 | 四個 API 均支援，並翻譯中英文名 |
| 原始 SQL API | 不支援 | 支援 |

兩種模式的模板外殼一致；SQLite 多用 `sourceData.ddl` 建立物理表和 NameMapper。

來源：`table-storage-provider.ts`、`syntax-reference.md` ｜ 置信度：high `[已核快照原始碼]`

### 3.2 原生模式發給 AI 的摘要

```text
[4:揹包物品表]
  Columns: [0:物品名稱], [1:數量], [2:描述/效果], [3:類別]
  - Note: ...
  - Insert Trigger: ...
  - Update Trigger: ...
  - Delete Trigger: ...
  [0] 鐵劍, 3, 鋒利的鐵製長劍, 武器
```

AI 依賴表 ID、行號和列號生成 DSL。

### 3.3 SQLite 模式發給 AI 的摘要

```sql
CREATE TABLE inventory ( -- 揹包物品表
  row_id INTEGER PRIMARY KEY, -- 行號
  item_name TEXT NOT NULL UNIQUE, -- 物品名稱
  quantity INTEGER NOT NULL DEFAULT 1 CHECK(quantity > 0), -- 數量
  description TEXT, -- 描述/效果
  category TEXT -- 類別
);
-- Note: ...
-- INSERT: ...
-- UPDATE: ...
-- DELETE: ...
-- 當前資料 (... rows)
```

DDL 註釋同時承擔中文顯示名到英文物理名的對映。漏寫註釋會導致自定義表的中文查詢和 CRUD 翻譯失敗。

### 3.4 模式切換不是換變數名

切換模式會重建或過載 Provider；它不是把 DSL 文字機械改成 SQL 文字。生產卡應先確定主模式，再圍繞該模式寫模板與測試。需要雙模式相容時：

- `note/init/insert/update/delete` 都要避免只在一種模式可理解；
- SQLite `insert/update/delete` 中附 SQL 示例；
- 原生模式仍需確保列語義和觸發條件不依賴 SQL 才能讀懂；
- 前端優先使用四個跨模式 CRUD API，只有複雜事務才直接寫 SQL。

## 4. AI 填表協議與提示詞流水線

### 4.1 舊式 `<tableEdit>`：原生模式

預設設定 `strictJsonTableFillEnabled=false` 時，原生模式要求 AI 輸出：

```text
<tableEdit>
insertRow(2, {"0":"月影傭兵團","1":"中立","2":"0"})
updateRow(2, 1, {"1":"友好","2":"15"})
deleteRow(2, 3)
</tableEdit>
```

語義：

- `insertRow(tableIndex, {"colIndex":"value"})`；
- `updateRow(tableIndex, rowIndex, {"colIndex":"value"})`；
- `deleteRow(tableIndex, rowIndex)`；
- 表 ID、行號是數字；物件列號是雙引號字串；
- `rowIndex` 對當前發給 AI 的資料快照負責，不能憑顯示排序後的 UI 猜。

來源：`DEFAULT_CHAR_CARD_PROMPT_ACU`、DSL parser ｜ 置信度：high `[已核快照原始碼]`

### 4.2 舊式 `<tableEdit>`：SQLite 模式

```text
<tableEdit>
INSERT INTO faction_relations
  (row_id, faction_name, relation_status, favor_level)
VALUES
  ((SELECT COALESCE(MAX(row_id), 0) + 1 FROM faction_relations), '月影傭兵團', '中立', 0);

UPDATE faction_relations
SET relation_status = '友好', favor_level = favor_level + 15
WHERE faction_name = '月影傭兵團';
</tableEdit>
```

規則：

- 表名、列名使用 DDL 的英文物理名；
- `UPDATE`、`DELETE` 必須帶 `WHERE`；
- 定位優先使用 `UNIQUE` 業務主鍵，單行表才固定 `WHERE row_id = 1`；
- 不輸出 `BEGIN/COMMIT/ROLLBACK`，事務由外掛管理；
- 不在 AI 編輯裡執行 `CREATE/DROP/ALTER`；結構變化走模板/視覺化編輯器；
- 多條語句都以分號結尾。

來源：`DEFAULT_CHAR_CARD_PROMPT_SQL_ACU`、`prompt-prepare.ts` ｜ 置信度：high `[已核快照原始碼]`

### 4.3 嚴格 JSON 是可選的新協議

已核快照還提供“嚴格 JSON 填表響應”，預設值為關閉。開啟後 AI 不直接輸出 `<tableEdit>`：

原生模式：

```json
{
  "format": "table_edit_ops_v1",
  "ops": [
    {
      "op": "update",
      "sheet": "陣營關係表",
      "where": { "陣營名稱": "月影傭兵團" },
      "set": { "關係狀態": "友好", "好感度": 15 }
    }
  ]
}
```

SQLite 模式：

```json
{
  "format": "table_edit_sql_v1",
  "sql": "UPDATE faction_relations SET relation_status = '友好' WHERE faction_name = '月影傭兵團';"
}
```

解析器會把透過校驗的嚴格 JSON 歸一化到內部編輯文字再進入提交鏈。嚴格模式與舊式 `<tableEdit>` 不應混寫；開啟嚴格模式後，裸 `<tableEdit>` 會被拒絕。

來源：`strict-json-table-fill.ts`、`table-edit-parser.ts`、預設設定 ｜ 置信度：high `[已核快照原始碼]`

### 4.4 提示詞槽位和資料流

預設填表提示詞把資訊分成：

```text
$U  使用者基礎設定
$C  角色/卡片設定
$4  世界書內容
$1  正文資料
$0  當前表格資料
$8  手動額外提示
```

實際流程：

```text
收集劇情上下文與世界書
→ 根據更新頻率/手動選擇確定目標表
→ 格式化當前表格與 sourceData
→ 解析該入口支援的模板變數
→ 呼叫填表 API/profile
→ 提取嚴格 JSON 或 <tableEdit>
→ Provider 應用 DSL/SQL
→ V2 提交併儲存聊天
→ 重新整理合併檢視、世界書與 UI 回撥
```

不要把 Note、DDL、輸出協議重複塞入劇情世界書；它們本來就由資料庫提示詞流水線提供。

## 5. 自定義表設計流程

### 5.1 先回答六個問題

1. 一行代表什麼實體？
2. 是單行表還是多行表？
3. 多行表用哪個業務欄位唯一定位？
4. 哪些欄位必須非空、唯一、限定範圍或限定列舉？
5. 初始化、新增、更新、刪除各在什麼劇情條件觸發？
6. 這張表是否需要同步到世界書；按整表、按行還是隻輸出索引？

任何一項答不出來，都先不要寫 DDL。

### 5.2 定中文顯示名與英文物理名

建議：

- 中文表名：名詞短語，以“表”結尾，例如“陣營關係表”；
- 英文表名：小寫蛇形，例如 `faction_relations`；
- 英文欄位：小寫蛇形，例如 `relation_status`；
- DDL 每列行尾寫精確中文註釋；
- DDL 註釋中文名必須與 `content[0]` 表頭、Note 列名完全一致。

### 5.3 DDL 硬規則

```sql
CREATE TABLE english_table_name ( -- 中文表名
  row_id INTEGER PRIMARY KEY, -- 行號
  business_key TEXT NOT NULL UNIQUE, -- 業務主鍵
  status TEXT NOT NULL CHECK(status IN ('選項A', '選項B')), -- 狀態
  score INTEGER NOT NULL DEFAULT 0 CHECK(score BETWEEN -100 AND 100), -- 數值
  note TEXT -- 備註
);
```

必須滿足：

- 第一列為 `row_id INTEGER PRIMARY KEY`；
- 多行表至少有一個真正的 `UNIQUE` 業務主鍵；
- 列舉用 `CHECK(... IN (...))`；
- 數值範圍用 `CHECK`；
- 必填欄位用 `NOT NULL`；
- 可推導預設值用 `DEFAULT`；
- 每列都寫中文註釋；
- 最後一列不留多餘逗號；
- 儲存後在 UI 執行 DDL 校驗。

### 5.4 Note 的標準格式

```text
記錄主角陣營與其他已知陣營之間的關係；每個對方陣營佔一行。
- 列1: 陣營名稱 - 對方陣營的正式名稱，必須唯一。
- 列2: 關係狀態 - 只允許“友好”“敵對”“中立”“同盟”。
- 列3: 好感度 - 整數，範圍 -100 到 100。
- 列4: 首領姓名 - 當前首領；未知時留空。
- 列5: 備註 - 補充資訊，不超過 150 字。
```

`row_id` 是內部定位列，業務 Note 從列1開始寫最不容易混淆。需要與現有模板合併時，以該模板的列號慣例為準，不要同一批表混用兩套編號。

### 5.5 Trigger 必須有正反邊界

好的新增規則：

```text
劇情中出現之前未記錄、且與主角發生明確互動的新陣營時新增。
僅被路人提及、沒有劇情相關性的陣營不要新增。
SQL示例: INSERT INTO ...;
```

好的更新規則：

```text
已有陣營的關係、好感度、首領或實力發生變化時更新。
好感度變化使用加減表示式，不要把“本次變化量”誤當作新總值。
SQL示例: UPDATE ... WHERE faction_name = '...';
```

好的刪除規則：

```text
僅在陣營被明確徹底消滅或正式解散時刪除。
暫時失勢、潛伏或被佔領只更新狀態，不刪除。
SQL示例: DELETE FROM ... WHERE faction_name = '...';
```

單行表的 `insertNode` 寫“禁止操作。”，`deleteNode` 寫“禁止刪除。”；不要同時給出禁止文字和可執行示例。

### 5.6 資料量和拆表

單表建議控制在 7～8 個業務欄位以內。超過後按實體或更新頻率拆表：

- “角色基本檔案”與“角色關係變化”分表；
- “任務當前狀態”與“任務歷史記錄”分表；
- 高頻數值與低頻長文字分表；
- 不要一列塞入難以穩定解析的多層 JSON，失去二維表優勢。

此處為專案建表指南的經驗門檻，不是 SQLite 引擎硬限制。置信度：medium-high `[專案維護文件]`

## 7. 模板變數與條件表示式

### 7.1 這是“發給 AI 前的字串模板”，不是持久變數

模板語法寫在外掛支援的提示詞入口，傳送前由資料庫解析器替換。它與前端直接呼叫 `AutoCardUpdaterAPI` 是兩條獨立鏈路。

支援的主要入口：

1. 酒館預設提示詞；
2. 填表預設提示詞；
3. 正文最佳化提示詞；
4. 劇情推進世界書與最終指令；
5. 劇情推進任務內容。

不同入口支援的語法子集不同。尤其填表入口和劇情推進最終指令不執行 `<calc>/<max>/<min>`；不要因為某個標籤在酒館預設裡能用，就假定它在所有入口都能用。

來源：`syntax-reference.md`、對應 prompt pipeline ｜ 置信度：high `[已核快照行為]`

### 7.2 雙模式共同語法

```html
<random id="luck" min="1" max="100" />
<calc id="double" expr="cell:揹包物品表/鐵劍/數量 * 2" />
<max id="top" values="3, 5, $calc:double" />

<if seed="戰鬥">本輪發生戰鬥。</if>
<if cell="揹包物品表/鐵劍/數量 >= 1">仍持有鐵劍。</if>
```

注意：

- `random` 的 `min/max` 只接受非負整數字面量；
- `<calc>` 結果會 `Math.floor`；
- 標籤變數只在當前訊息處理過程中有效，不跨訊息持久化；
- `<if>` 是否執行還取決於對應入口和條件模板開關。

### 7.3 SQLite 專屬讀取語法

ORM：

```text
{[db.揹包物品表.where('物品名稱','鐵劍').get('數量')]}
{[db.inventory.where('item_name','鐵劍').get('quantity')]}
{[db.重要角色表.where('是否離場','否').count()]}
```

原生 SELECT：

```text
{[sql "SELECT SUM(quantity) FROM inventory"]}
```

臨時變數：

```text
{[db.inventory.where('item_name','鐵劍').get('quantity') as sword_count]}
鐵劍數量：$v:sword_count
```

邊界：

- `{[db...]}`、`{[sql...]}` 只在 SQLite 模式替換；原生模式會原樣保留；
- `{[sql ...]}` 是隻讀查詢，不能拿它執行 `UPDATE/INSERT/DELETE`；
- `as` 後的變數名只能使用英文、數字和下劃線，並且不能以數字開頭；
- `$v:` 是當前單條訊息的臨時值，不是資料庫持久欄位。

### 7.4 處理順序

一條支援完整模板語法的訊息大致按以下順序處理：

```text
1. <random>，再替換 $random:
2. <calc>
3. <max>/<min>
4. 替換 $calc/$max/$min
5. SQLite 模式替換 db、sql 與 $v
6. 遞迴解析 <if>
```

因此 `<calc expr="$v:x + 1">` 不會按預期工作：`$v:` 在 calc 之後才替換。SQLite 中應改用 `db.calc()`，或者重新組織模板。

## 8. 前端讀取、CRUD 與 SQL API

### 8.1 唯一公開入口

```js
const hostWindow = window.parent;
const API = hostWindow.AutoCardUpdaterAPI;
if (!API) throw new Error('SP·資料庫尚未就緒');
```

所有外部功能統一掛在資料庫識別出的宿主視窗 `AutoCardUpdaterAPI` 上。Tavern Helper 訊息 iframe 不是宿主視窗，應在確認同源後從 `window.parent.AutoCardUpdaterAPI` 取，不能預設讀取訊息 iframe 自身的 `window.AutoCardUpdaterAPI`，也不能用 Tavern Helper 的 `waitGlobalInitialized()` 等待它。若前端內部還有更深層子 iframe，由上層應用注入受控 adapter，不要繼續猜 `parent.parent`。API 物件出現也不代表表資料已完成載入，正式前端應有限時輪詢並處理空物件。

來源：`api-registry.ts` ｜ 置信度：high `[已核快照原始碼]`

### 8.2 讀取全部表格

```js
// 返回值是資料庫內部活動物件的引用，不是 clone；先複製再交給 UI。
const tableData = structuredClone(API.exportTableAsJson() ?? {});

const factionSheet = Object.values(tableData).find(

const headers = factionSheet?.content?.[0] || [];
const rows = factionSheet?.content?.slice(1) || [];
```

`exportTableAsJson()` 同步返回當前合併資料的**活動物件引用**，尚未載入時可能是 `{}`；更新回撥拿到的也是活動引用。不得直接修改它。先 `structuredClone()` 或在 adapter 中歸一化成自己的只讀 DTO，再交給元件；正式寫入走 CRUD、SQL 或匯入 API。

### 8.3 跨模式 CRUD

```js
await API.updateCell('陣營關係表', 1, '好感度', 20);

await API.updateRow('faction_relations', 1, {
  relation_status: '友好',
  favor_level: 20,
});

const newRowIndex = await API.insertRow('陣營關係表', {
  陣營名稱: '白塔議會',
  關係狀態: '中立',
  好感度: 0,
  大致實力: '強大',
});

await API.deleteRow('陣營關係表', newRowIndex);
```

四個方法都支援原生和 SQLite 模式，並支援中英文名稱翻譯。關鍵返回值：

| 方法 | 成功 | 失敗 |
|---|---:|---:|
| `updateCell` | `true` | `false` |
| `updateRow` | `true` | `false` |
| `insertRow` | 新 `rowIndex` | `-1` |
| `deleteRow` | `true` | `false` |

`rowIndex=0` 是表頭，禁止改刪；第一條資料是 1。

### 8.4 物件引數與批次靜默

```js
await API.updateCell({
  tableName: '陣營關係表',
  rowIndex: 1,
  colIdentifier: '好感度',
  value: 25,
  skipNotify: true,
});
```

`skipNotify/silent` 只跳過外部更新回撥，不跳過寫入。批次操作可以逐項靜默，最後主動重新整理一次：

```js
await API.refreshDataAndWorldbook();
```

`skipChatSave/skipSave/isImportMode` 會跳過聊天儲存，正常遊玩寫入不要開啟；它更接近匯入或臨時執行時操作，不是效能開關。

### 8.5 SQLite 只讀查詢

```js
const result = API.querySql(
  'SELECT faction_name, favor_level FROM faction_relations WHERE favor_level > ?',
  [0],
  { limit: 50, offset: 0 },
);

console.table(result?.rows || []);
```

也可使用宣告式單表查詢：

```js
const result = API.queryTableRows({
  tableName: '陣營關係表',
  columns: ['row_id', '陣營名稱', '好感度'],
  where: { 關係狀態: ['友好', '同盟'] },
  orderBy: { column: '好感度', direction: 'DESC' },
  limit: 20,

```

只讀入口拒絕多語句和寫操作。原生模式沒有 SQL 引擎，呼叫會返回空值並記錄錯誤。

### 8.6 SQLite 寫入

優先用四個 CRUD。確實需要複雜批次更新時：

```js
const result = await API.executeSqlMutation(
  `UPDATE faction_relations
   SET favor_level = MIN(100, favor_level + ?)
   WHERE relation_status IN ('友好', '同盟')`,
  [5],
  { targetSheetKeys: ['sheet_faction_relations'] },

if (result?.errors?.length) console.error(result.errors);
```

多表或多語句使用 `executeSqlBatch`，並儘量顯式提供 `targetSheetKeys`，讓事務鎖和儲存範圍準確。引數化 SQL 優先於字串拼接；不要把玩家輸入直接拼進 SQL。

## 9. 回撥、鎖與併發邊界

### 9.1 更新回撥

```js
const onTableUpdate = tableData => {
  // 它只表示“資料可能變化”，不是“本次 AI 填表成功結束”。
  renderFromDto(normalizeTableData(structuredClone(tableData ?? {})));
};

API.registerTableUpdateCallback(onTableUpdate);

// 頁面銷燬時必須用同一個函式引用登出
API.unregisterTableUpdateCallback(onTableUpdate);
```

`registerTableUpdateCallback()` 是通用失效通知：CRUD、匯入、過載、視覺化儲存和 AI 填表都可能觸發，一次填表也可能觸發多次；它沒有任務 ID、成功狀態或錯誤資訊，不能當作 fill-end。

在 2026-07-14 兩個已核快照中，`registerTableFillStartCallback()` 有公開註冊方法，但**沒有對應登出方法，也沒有公開 fill-end 回撥**。會隨樓層重繪銷燬的訊息 iframe 不應直接註冊匿名閉包，否則舊閉包會留在宿主回撥陣列。確實需要開始訊號時，只能由常駐 bridge 以單例方式註冊，再把受控事件轉發給短生命週期 UI；否則用更新回撥重新讀取資料，並以超時、重新讀取和錯誤態完成 UI 對賬。升級外掛後必須重新檢查回撥方法集，不能把這一缺口假定為永久存在。

不要在更新回撥裡無條件再次寫表，否則會形成“寫入 → 回撥 → 寫入”的迴圈。

### 9.2 UI 表格鎖不是事務鎖

公開的 `lockTableRow/Col/Cell`、`setTableLockState` 儲存視覺化編輯層的行、列或單元格鎖狀態，作用域為“當前聊天 + isolationKey”。在 2026-07-14 兩個已核快照中，普通鎖只在原生模式 AI DSL 的 `updateRow` 路徑執行檢查；它不阻止 AI `insertRow/deleteRow`、公開 CRUD、raw SQL，SQLite AI SQL 路徑也不能據此視為受保護。自定義前端若把某欄位定義為不可編輯，必須在自己的 adapter/UI 寫入門同時校驗，不能把公開鎖當權限或資料庫約束；升級後重新核驗執行點。

外掛內部另有多粒度事務鎖：

```text
maintenance lock
→ sheet mutation lock
→ isolation commit lock
```

前者只是原生 AI `updateRow` 的有限保護和 UI 狀態，後者才保護執行時資料、V2 log、checkpoint 和 `saveChat`。不要以為呼叫 `lockTableRow()` 就能代替只讀規則、許可權或併發控制，也不要繞過公開寫 API 直接修改 `content`。

兩套索引也不同：CRUD 的第一條資料是 `rowIndex=1`，數字 `colIdentifier` 包含 `row_id`；UI 鎖的第一條資料行是 `rowIndex=0`，業務列 `colIndex=0` 排除了 `row_id`。不可把 CRUD 行列座標直接傳給鎖 API。

來源：`table-lock-api.ts`、`table-write-transaction.ts`、併發設計文件 ｜ 置信度：high `[已核快照結構]`

### 9.3 併發寫入規則

- AI 請求可以併發收集，但應用編輯和提交進入統一事務；
- 同一 sheet 的 CRUD/AI/SQL 寫入必須序列 mutation；
- 不同 sheet 可並行準備，但同一 isolation 的 V2 commit 必須序列；
- raw SQL 無法確定目標表時會擴大鎖範圍；外部呼叫應顯式給 `targetSheetKeys`；
- 清理樓層、compaction、匯入、Provider 過載會改變恢復鏈，應使用排他維護事務；
- 外部前端只調用公開 API，不自行構造 V2 operation、revision 或鎖 key。

### 9.4 衝突時不要靜默覆蓋

V2 日誌帶 `baseRevision/parentRevision/commitRevision/writeSet`；提交端可對不相交寫集 rebase，對同一行/單元格或 schema 衝突應失敗或重試。前端看到 `false/-1/errors` 必須提示使用者並重新讀取快照，不要拿舊 UI 草稿立即覆蓋新資料。

## 10. 聊天持久化、V2 日誌與隔離

### 10.1 資料儲存在聊天鏈裡

SQLite 是執行時引擎，不是獨立永久資料庫檔案。當前設計的持久化主鏈是：

```text
SQLite / 原生 Provider
→ 匯出 TableDataObject JSON 檢視
→ 寫入 SillyTavern 聊天訊息的資料庫欄位
→ 切換聊天時從訊息鏈恢復
```

因此匯出聊天、刪除樓層、清理本地欄位、切換 isolation 都可能影響恢復結果。不能把“瀏覽器內 SQL 查詢成功”當作“已經持久化成功”。

來源：`ITableStorageProvider.saveToChat/loadFromChat`、chat service ｜ 置信度：high `[已核快照原始碼]`

### 10.2 V2 幀

```ts
interface TableStorageFrameV2 {
  version: 2;
  headRevision?: string | null;
  checkpoint?: {
    kind: 'full';
    reason: 'init' | 'periodic' | 'manual' | 'schema_change' |
            'compaction' | 'import' | 'migration';
    data: TableDataObject;
    scheduleSummary?: Record<string, {
      lastFilledAiFloor?: number;
      lastChangedAiFloor?: number;
    }>;
  };
  logEntries: TableMutationLogEntryV2[];
}
```

`checkpoint.data` 是可恢復全量快照；`logEntries[].operations` 是 checkpoint 之後的可重放增量。兩者不能互相冒充。

### 10.3 operation 必須來自真實執行動作

| 寫入來源 | 正確 operation |
|---|---|
| SQLite AI/SQL | `sql_batch`，保留語句和繫結引數 |
| 原生 DSL | `table_edit_dsl` 或結構化行 patch |
| 前端 CRUD | 行/單元格級結構化 operation |
| 整表匯入 | `sheet_replace` |
| 全庫匯入/災難恢復 | `data_replace` |

禁止透過執行前後快照 diff 猜造 operation；普通 CRUD 或 AI 填表也不得為了“儲存成功”靜默退化成 `data_replace`。

來源：`v2-storage-commit-constraints.md` ｜ 置信度：high `[已核快照約束文件 + 實現型別]`

### 10.4 checkpoint 必須保留排程摘要

壓縮日誌前要把歷史填表/變更樓層彙總到 `scheduleSummary`。狀態面板恢復自動填表節奏時應讀：

- `lastFilledAiFloor`：上次嘗試填表；
- `lastChangedAiFloor`：上次確有資料變化。

只看當前 `logEntries` 或 `checkpoint.event` 會把已填過的表誤判成未初始化。

### 10.5 資料隔離

V2 資料以：

```text
當前聊天 + 當前 isolationKey
```

為恢復和遷移單位，存放在訊息的 `TavernDB_ACU_IsolatedData[isolationKey]` 分槽中。不同標籤可儲存不同模板/資料鏈；切換標籤本質上會重新載入當前聊天下相應槽位。

隔離標籤不是表名名稱空間。切換後前端必須重新獲取快照，不能繼續持有舊標籤物件引用。

## 11. 匯入、恢復、遷移與備份

### 11.1 模板和資料是兩種東西

| 操作 | 物件 | 典型 API |
|---|---|---|
| 模板匯入 | 表結構、Note、Trigger、DDL、預設配置 | `importTemplateFromData` |
| 資料匯出 | 當前合併後的表格內容 | `exportTableAsJson` |
| 資料匯入 | 覆蓋當前資料庫並持久化 | `importTableAsJson` |
| 執行時恢復 | 刪除樓層後的記憶體恢復，不製造新持久化事件 | `restoreTableAsJson` |

不要用模板匯入代替存檔恢復，也不要把當前資料 JSON 當作全域性模板到處覆蓋。

### 11.2 外部匯入與恢復語義不同

```js
const backup = JSON.stringify(API.exportTableAsJson());

// 正常外部匯入：寫入當前聊天持久化
await API.importTableAsJson(backup);

// 刪除樓層/回滾後的執行時恢復：不新增 data_replace/checkpoint/log
await API.restoreTableAsJson(backup);
// 等價：await API.importTableAsJson(backup, { persist: false });
```

把恢復誤用成普通匯入，會在剛刪除樓層後又建立新的持久化事件；把普通匯入誤用成恢復，則重新整理或重開聊天后可能丟失。

來源：`API_DOCUMENTATION.md`、`core-data-api.ts` ｜ 置信度：high `[已核快照原始碼]`

### 11.3 舊聊天遷移

載入當前聊天和 isolationKey 時，舊格式會被合併成 V2 full checkpoint：

```text
legacy 頂層欄位 / V1 隔離槽
→ 按舊語義合併可見資料
→ reason: migration 的 full checkpoint
→ scheduleSummary 遷移歷史樓層狀態
→ logEntries: []
→ 成功後清理當前槽位舊欄位
```

舊資料沒有真實 V2 operation 語義，所以遷移不反向偽造 SQL、DSL 或 patch。遷移失敗時不應初始化空庫或清理舊欄位。

來源：`docs/v2-storage-legacy-migration.md` ｜ 置信度：high `[已核快照約束文件]`

### 11.4 安全備份流程

結構升級前：

1. 固定當前指令碼版本與模板預設名；
2. `exportTableAsJson()` 儲存當前資料；
3. 匯出當前表格模板；
4. 記錄 storage mode 和 isolation code；
5. 在複製聊天中匯入新模板並遷移資料；
6. 對賬表數、表頭、行數、業務主鍵和關鍵欄位；
7. 過載聊天，確認不是僅執行時成功；
8. 再同步世界書並檢查舊生成條目是否清理。

不要只備份 SQLite 查詢截圖；永久恢復需要可匯入的模板和 JSON 資料。

## 12. 世界書同步與 0TK 邊界

### 12.1 世界書是派生檢視

表格資料可以透過 `exportConfig` 生成世界書條目：

- `enabled`：啟用該表的自定義匯出；
- `injectIntoWorldbook`：是否生成主條目；
- `splitByRow`：按行拆分；
- `injectionTemplate` / `sqlInjectionTemplate`：自定義內容；
- `extraIndexEnabled`：生成附加索引；
- `entryPlacement` / `extraIndexPlacement`：位置、深度、順序；
- `preventRecursion`：控制遞迴。

主事實源仍是資料庫聊天持久化；世界書條目是可刪除、可重建的派生物。不要反過來手改生成條目，再期待它自動回寫表格。

### 12.2 同步 API

```js
await API.syncWorldbookEntries({ createIfNeeded: true });

// 重新載入聊天表格、合併資料、同步世界書並通知前端
await API.refreshDataAndWorldbook();
```

`deleteInjectedEntries()` 只刪除外掛生成條目。不要用模糊名稱批次刪除使用者自己維護的世界書條目。

### 12.3 0TK 的準確含義

```js
await API.setZeroTkOccupyMode(true);
```

在當前 API 語義中：

- `true`：把對應資料庫生成世界書條目設為停用；
- `false`：允許條目啟用；
- 它控制世界書條目的 `enabled` 狀態，不會刪除資料庫、不停止聊天持久化，也不等於關閉填表；
- 紀要索引與其他特殊模式可以保留/更新內容，但 0TK 仍控制條目是否啟用。

所以“0TK”是**提示詞佔用控制**，不是“資料庫處於零資料”或“完全不執行”。

來源：`worldbook-ai-api.ts`、`injection-engine-custom.ts` ｜ 置信度：high `[已核快照原始碼]`

### 12.4 開場白階段抑制

當前世界書流水線在沒有使用者訊息的新對話開場階段，會抑制自動建立/更新，並執行舊生成條目清理；使用者開始對話後再解除。開場白剛載入時看不到新條目，不應立即判定同步失敗。

來源：`worldbook/pipeline.ts` ｜ 置信度：high `[已核快照原始碼]`

### 12.5 Token 控制

- 不需要進主提示詞的表不要啟用世界書匯出；
- 大表按行拆分並設定關鍵詞，避免整表常駐；
- 索引只選真正用於召回的短列；
- 注入模板不要重複 DDL、Note 和完整 Trigger；
- 預設 `preventRecursion:true`，除非明確設計了遞迴召回；
- 資料為空時應清理舊派生條目，防止陳舊狀態繼續進提示詞。

## 13. 效能與維護

### 13.1 控制填表輸入

`updateConfig` 可按表控制上下文深度、更新頻率、批大小和跳過樓層。先做低頻、分表更新，再考慮把所有表每輪全送給 AI。

原則：

- 高頻小狀態與低頻長檔案分表；
- 手動更新只選擇需要的 `sheetKey`；
- 紀要類設定明確的合併/壓縮策略；
- 不把 UI 展示快取寫回業務表；
- 先記錄“本輪嘗試填表”與“本輪確有變化”的差異，避免重複觸發。

### 13.2 前端批次寫入

大量逐格寫入會產生通知風暴。推薦：

1. 儘量合併為 `updateRow`；
2. 批次內使用 `skipNotify:true`；
3. 最後 `refreshDataAndWorldbook()`；
4. 多表原子業務用引數化 SQL batch；
5. 提供準確的 `targetSheetKeys`；
6. 檢查返回值後再更新 UI 的成功狀態。

### 13.3 DDL 變更是遷移，不是隨手改名

欄位改名或拆表會同時影響：

- DDL 英文物理名；
- DDL 中文註釋；
- `content[0]` 表頭；
- Note 列說明；
- init/insert/update/delete 示例；
- 模板變數與 SQL；
- 前端 CRUD；
- 世界書匯出模板；
- 已有聊天資料與 V2 checkpoint。

先設計舊→新對映，在複製聊天中驗證，再應用正式存檔。只改表頭或只改 DDL 都會造成對映錯位。

### 13.4 不依賴內部全域性變數

`currentJsonTableData_ACU`、Provider、V2 frame 型別是理解機制的原始碼真相源，不是穩定的外部 API。角色卡前端只依賴宿主視窗 `AutoCardUpdaterAPI` 的文件化方法；訊息 iframe 從同源 `window.parent` 訪問，版本升級時重新核對方法簽名。

## 14. 高頻錯誤

### 錯誤 1：繼續按 MVU 設計

症狀：寫 zod、`stat_data`、JSONPatch，卻沒有 `mate/sheet/content/sourceData`。

處理：停止；這不是 SP·資料庫模板。重新按二維表與填表協議設計。

### 錯誤 2：DDL 中文註釋、表頭和 Note 不一致

症狀：中文 CRUD 找不到列，AI 把值寫錯列。

處理：三處逐字對齊；所有列都寫註釋。

### 錯誤 3：多行表沒有業務 `UNIQUE`

症狀：同一角色/物品/陣營反覆 INSERT。

處理：為穩定業務主鍵加 `NOT NULL UNIQUE`，並在 Trigger 明確“未記錄才新增”。

### 錯誤 4：UPDATE/DELETE 沒有 WHERE

症狀：整表被更新或刪除。

處理：所有示例都帶 WHERE；多行表按業務主鍵，單行表按 `row_id=1`。

### 錯誤 5：把 `{[sql "UPDATE..."]}` 當寫入口

症狀：模板文字被替換為空或寫入沒有發生。

處理：模板 SQL 只讀。AI 寫入走編輯協議，前端寫入走 CRUD/SQL mutation API。

### 錯誤 6：直接修改 `exportTableAsJson()` 返回物件

症狀：直接汙染資料庫內部活動物件，頁面看似改變，但沒有形成受支援的提交和持久化鏈。

處理：讀取後先 clone/歸一化；寫入用公開 CRUD、SQL mutation 或資料匯入 API。

### 錯誤 7：普通寫入開啟 `skipChatSave`

症狀：UI 更新成功，重開聊天恢復舊值。

處理：正常遊玩不要跳過持久化；該選項只用於受控匯入/執行時場景。

### 錯誤 8：用 UI 行鎖代替併發事務

症狀：公開 CRUD、SQL、插入或刪除仍能越過鎖，兩路寫入也可能互相覆蓋或日誌衝突。

處理：所有寫入走外掛 API；自定義 UI 另做只讀規則和寫前校驗。已核快照中的普通鎖只對原生 AI DSL `updateRow` 提供有限保護，不能代替許可權、資料庫約束或事務鎖；升級後重新核驗。

### 錯誤 9：匯入與恢復混用

症狀：刪除樓層後又生成新持久化事件，或匯入後重新整理丟失。

處理：外部資料匯入預設持久化；樓層回滾用 `restoreTableAsJson`。

### 錯誤 10：把世界書當主資料

症狀：手改生成條目後，下一次同步被覆蓋。

處理：改表格主資料或匯出模板，再重新同步。

### 錯誤 11：原生模式使用 SQLite 模板語法

症狀：`{[db...]}`、`{[sql...]}` 原樣發給 AI。

處理：切 SQLite，或改用原生支援的 `cell:`/共同語法。

### 錯誤 12：嚴格 JSON 與 `<tableEdit>` 混寫

症狀：解析器拒絕輸出。

處理：確認 `strictJsonTableFillEnabled`；嚴格模式只輸出對應 JSON 根物件，舊模式才輸出 `<tableEdit>`。

## 15. 驗收清單

### 15.1 模板靜態驗收

- [ ] 頂層有 `mate`，且 `type="chatSheets"`。
- [ ] 每張表鍵以 `sheet_` 開頭，`uid` 穩定且不重複。
- [ ] 每張表都有 `name/sourceData/content/updateConfig/exportConfig/orderNo`。
- [ ] `content[0]` 是表頭，SQLite 首列為 `row_id`。
- [ ] DDL 使用英文物理表名和欄位名。
- [ ] DDL 每列有與表頭一致的中文註釋。
- [ ] 多行表有業務 `UNIQUE`，列舉/範圍有 `CHECK`。
- [ ] Note 說明一行實體、每列語義、格式和上限。
- [ ] init/insert/update/delete 都非空；禁止操作明確寫禁止。
- [ ] 所有 UPDATE/DELETE 示例都有 WHERE。
- [ ] 世界書匯出按需開啟，預設不無意常駐大表。

### 15.2 執行驗收

1. 在複製聊天匯入模板，確認 DDL 校驗透過。
2. 初始化空表，確認單行/多行語義正確。
3. 各製造一次 INSERT、UPDATE、DELETE 劇情。
4. 檢視 AI 原始輸出，確認協議與當前模式一致。
5. 檢視 API 快照，確認值落在正確表、行、列。
6. 過載聊天，確認資料從持久層恢復。
7. 切換 isolationKey，確認資料不串槽。
8. 註冊更新回撥，確認一次業務提交不會形成回撥迴圈。
9. 若啟用世界書，檢查條目內容、位置、遞迴與 0TK enabled 狀態。
10. 匯出備份，在複製聊天分別驗證“外部匯入”和“執行時恢復”。

離線模板檢查不能替代真實 ST 中的 AI 輸出、持久化過載和世界書注入驗收。
