# 開局頁與自定義開局

> 文件版本：v1.0.0 ｜ 最後更新：2026-07-15
>
> **定位**：從普通 `first_mes`、`alternate_greetings` 到一次性自定義開局嚮導，建立可驗證的載入、草稿、預覽、提交、失敗恢復和正常訊息鏈。
>
> **硬邊界**：自定義開局頁是一次性初始化器。確認後產生真實玩家開局發言並回到正常多樓層遊玩；如果此後每一輪仍由首樓承擔輸入、生成、劇情閱讀、回看和功能路由，那已進入 **《C5_同層前端.md》**，不再是開局頁。

## 1. 三層能力與邊界

### 1.1 三類開局

| 型別 | 生命週期 | 玩家互動 | 提交後 |
|---|---|---|---|
| 普通 `first_mes` | 展示一條首訊息 | 使用 ST 原生輸入 | 正常多樓層 |
| `alternate_greetings` | 首訊息的 Swipe/候選 | 選擇喜歡的開場 | 正常多樓層 |
| 自定義開局頁 | 一次性初始化嚮導 | 選擇、編輯、預覽、確認 | 傳送真實玩家開局訊息後退出 |

### 1.2 與同層前端的硬判定

| 能力 | 自定義開局 | C5 同層前端 |
|---|---|---|
| 首樓職責 | 初始化配置 | 整場遊玩應用 |
| 玩家輸入 | 最終提交一次真實開局發言 | 每回合由首樓應用代理 |
| 後續 AI 樓層 | ST 正常顯示 | 首樓長期映象/組織 |
| 路由 | 只服務開局步驟 | 劇情、角色、揹包、地圖、設定等完整路由 |
| Swipe/回看 | 提交後交還 ST | 應用內長期代理 |
| 退出條件 | 已確認真實玩家訊息樓建立成功 | 聊天結束或應用解除安裝 |

“介面看起來像大型開局頁”不能作為分類依據，職責和生命週期才是。

### 1.3 與控制中心的邊界

開局嚮導可以複用控制中心的世界書、身份、工坊和變數能力，但不應讓控制中心成為隱藏的第二套提交真值。所有選項最終必須由一個草稿模型和一個提交事務統一解釋。

## 2. ST 原生首訊息語義

### 2.1 First Message 是真實訊息

`first_mes` 不是僅展示的歡迎頁，它會成為當前聊天中的真實 assistant 首訊息，參與：

- 使用者看到的敘事起點；
- 後續上下文與角色語氣示範；
- 訊息編輯、Swipe、分支和匯出；
- Markdown/HTML 渲染；
- 宏替換與相關正則處理。

因此首訊息不能只按 UI 營銷頁寫法設計。即使可見層被擴成開局頁面，送入模型的版本也必須短、穩定、可理解。

### 2.2 Alternate Greetings

`alternate_greetings` 是首訊息的額外候選。在單聊中通常作為首訊息 Swipe；群聊可能從預設首訊息與 alternates 中隨機選擇，具體行為隨版本與群聊邏輯核驗。

適合 alternate 的情況：

- 只需不同場景、時間、關係或敘事視角；
- 每個開局都能直接進入正常聊天；
- 不需要跨步驟組合複雜初始配置；
- 不需要持久化多個世界因子或身份欄位。

如果只是三種固定開場，不要為了“更像產品”製造整套遠端開局頁。

### 2.3 可見訊息與送模內容

複雜 UI 應把“玩家看到的可見 mount”和“模型看到的短說明”分開。常見路線是兩條正則：

```text
first_mes 短標記
  ├─ display-only → loading/error mount
  └─ prompt-only  → 簡短敘事/狀態說明
```

具體正則順序、`markdownOnly` 和 prompt-only 行為屬於版本敏感項，必須在目標 ST/正則環境實測；不能只憑預覽認為模型沒有收到整頁 HTML。

## 3. 普通開局寫作與 Alternate Greetings

### 3.1 普通開局四要素

一個可直接遊玩的首訊息至少建立：

1. **場景**：時間、地點、正在發生什麼；
2. **角色聲音**：說話和行為符合角色，而不是系統說明；
3. **關係與邊界**：雙方如何稱呼、已知資訊與未知資訊；
4. **行動鉤子**：給玩家明確可回應的情境，不替玩家做關鍵決定。

### 3.2 多開局一致性

每個 alternate 都要檢查：

- 角色和玩家身份是否一致；
- 世界狀態是否互斥；
- 變數初始化假設是否相同；
- 世界書常駐條目是否能解釋該場景；
- 後續同一套提示詞是否能承接；
- 不同開局是否誤寫成不同作品。

需要真正不同的世界規則時，應在提交時持久化對應世界因子，而不是隻在首訊息文字裡暗示。

### 3.3 宏與副作用

展示宏和寫入宏不是一回事。首訊息/alternate 在預覽、Swipe、編輯、重渲染時可能多次經過處理；任何帶寫入副作用的宏都必須確認執行時機與冪等性。無法確認時，只在提交事務中進行顯式持久化。

## 4. 自定義開局的狀態分層

推薦拆成四層：

```text
DraftState            使用者尚未確認的選擇與自由輸入
UiState               當前步驟、摺疊、滾動、錯誤提示
PersistentSetup       身份、世界因子、工坊包等確認後持久資料
OpeningMessage        最終可讀的真實玩家開局發言
```

### 4.1 草稿不等於遊戲變數

草稿可以頻繁修改、撤銷、重新整理恢復；MVU/資料庫遊戲變數通常應在正常訊息/生成鏈中初始化。不要每改一個下拉框就修改正式存檔變數，否則使用者取消開局也會留下半套狀態。

### 4.2 UI 狀態不汙染業務資料

“當前第 4 步”“某 accordion 展開”“預覽滾動位置”不應寫進世界書、角色卡或 MVU。它們可以存於記憶體或聊天草稿的 `ui` 子物件，並允許丟失後安全回預設。

### 4.3 持久設定

只有明確確認的內容才進入：

- Persona/身份；
- 聊天級 metadata；
- 角色繫結世界書；
- 工坊來源條目；
- 後續提示詞需要的穩定配置。

每類寫入都需要所有權、預覽、失敗策略和回滾，不把“點選開始”變成不可審計的一串跨系統副作用。

## 5. 推薦生產架構

```text
first_mes 唯一短標記
  → 顯示正則生成可見 mount（loading/error/retry）
  → prompt-only 正則避免 UI 汙染模型上下文
  → 受信本地 binder 找到 mount
  → 拉取宣告式 opening-page.html
  → 協議/版本/hash/結構/淨化校驗
  → 注入 HTML
  → binder 繫結互動和草稿
  → 使用者預覽並確認
  → 提交事務持久化配置
  → 組裝可讀真實玩家訊息
  → 再核對聊天與輸入框
  → 走 ST 正常傳送鏈
  → AI 生成真實下一樓
```

### 5.1 短 mount 的意義

- 角色卡首訊息保持小而穩定；
- 遠端視覺可以更新；
- loading/error 不依賴遠端頁面自身；
- prompt-only 版本可控制送模體積；
- 失敗時仍能重試或人工進入普通聊天。

### 5.2 宣告式遠端頁面

遠端 `opening-page.html` 只提供結構與樣式，不承擔可信業務邏輯。載入器應移除 `script/iframe/object/embed/base/link/meta/form` 等危險或不需要的節點，互動由角色卡內本地 binder 繫結。

這樣遠端頁面更新不會自動獲得任意宿主 API，也減少 CSP、指令碼執行時序和供應鏈風險。

### 5.3 本地 binder

binder 負責：

- 檢查頁面協議和必需節點；
- 繫結輸入、按鈕、Tab 和可訪問狀態；
- 載入/儲存當前聊天草稿；
- 呼叫已審計的世界書/身份/工坊介面；
- 執行校驗和預覽；
- 發起唯一提交事務；
- 切聊天、Swipe、編輯、解除安裝時銷燬。

## 6. 遠端頁面載入與供應鏈安全

### 6.1 多源不是無條件信任

主源失敗可嘗試備用源，但每個源都必須滿足同一協議和完整性要求：

```javascript
const sources = [PRIMARY_URL, FALLBACK_URL];
let lastError = null;

for (const url of sources) {
  const controller = new AbortController();
  try {
    const html = await fetchWithTimeout(url, 10_000, {
      signal: controller.signal,
    });
    await verifySha256(html, EXPECTED_HASH);
    const document = parseAndSanitize(html);
    assertOpeningProtocol(document, EXPECTED_PROTOCOL);
    return document;
  } catch (error) {
    lastError = error;
  } finally {
    controller.abort();
  }
}

throw new Error('所有開局頁來源均載入失敗', { cause: lastError });
```

每個源獨立捕獲失敗並清理自己的 timeout/AbortController，只有全部失敗才統一報錯。不同源內容不應“誰先成功就信誰”；若 hash 隨釋出變化，必須由受信本地配置一併更新。

### 6.2 必驗內容

- HTTPS 或本地可信資源；
- 響應大小上限；
- 超時；
- SHA-256 或等價完整性；
- 頁面協議版本；
- 必需根節點和 action ID；
- HTML 淨化；
- 禁止遠端指令碼、巢狀 iframe、base URL 劫持和自動錶單；
- 失敗時保留宿主 mount 的錯誤與重試。

### 6.3 結構校驗

```javascript
function assertOpeningDocument(doc) {
  const root = doc.querySelector('[data-opening-protocol="1"]');
  if (!root) throw new Error('開局頁協議不匹配');
  for (const id of ['opening-next', 'opening-preview', 'opening-submit']) {
    if (!doc.getElementById(id)) throw new Error(`缺少節點: ${id}`);
  }
}
```

不要遇到結構不匹配還“儘量 bind”。按鈕繫結到錯誤節點會比直接失敗更危險。

### 6.4 iframe 不是天然安全沙盒

若選擇 iframe，仍需考慮 `allow-same-origin`、`allow-scripts`、postMessage origin/source、宿主 bridge 許可權和導航。**同源內容同時獲得 `allow-scripts` 與 `allow-same-origin` 會顯著削弱 sandbox 隔離**，不能把這一組合當普通預設值。對於宣告式開局頁，淨化後注入受控容器通常比允許遠端指令碼更簡單。

## 7. 嚮導 UX 與依賴門

### 7.1 依賴先檢查

進入正式編輯前展示依賴狀態：

- Tavern Helper 是否存在；
- 目標世界書 API 是否存在；
- 角色是否繫結目標世界書；
- 控制中心/執行時版本是否相容；
- MVU/資料庫是否真的屬於本開局提交鏈；
- 工坊包 schema 與 cardScope 是否匹配；
- 遠端頁面是否透過完整性檢查。

不使用的依賴不要硬設為必需。工坊橋若只寫世界書，就不應僅因 MVU 缺失而阻斷。

### 7.2 步驟設計

建議：

```text
依賴與說明
→ 身份/關係
→ 場景/時間/年級
→ 世界因子與功能包
→ 自由正文/高階項
→ 預覽
→ 最終確認
```

步驟數取決於真實決策，不為了“像產品”強行六步。允許返回修改；跳步限制必須解釋缺失項。

### 7.3 預覽必須可追溯

預覽展示：

- 最終真實玩家訊息；
- 將寫入的身份/世界配置摘要；
- 將安裝/升級的工坊內容；
- 僅本次生效項；
- 不能自動完成、需使用者後續處理的專案。

預覽使用與提交相同的 `buildOpeningMessage(draft)`，不能另寫一個“看起來差不多”的模板。

### 7.4 移動端與無障礙

- 320px 不橫向溢位；
- 軟鍵盤彈出仍能看到當前輸入與下一步；
- 按鈕熱區至少約 44px；
- 每步有標題和當前進度；
- 錯誤使用 `aria-live` 或等價可讀狀態；
- 焦點在步驟切換後落到新標題或首個錯誤；
- 不只靠顏色表示已完成/錯誤；
- Reduced Motion 下取消大幅頁面轉場。

## 8. 草稿、聊天隔離與遷移

### 8.1 每聊天唯一鍵

草稿必須繫結穩定聊天身份，而不是隻用角色名：

```javascript
function draftKey({ characterId, chatId, chatUuid }) {
  if (chatUuid) return `opening-draft:v2:${chatUuid}`;
  // 僅供舊環境無穩定 UUID 時降級；聊天重新命名後需遷移。
  return `opening-draft:v2:fallback:${characterId}:${chatId}`;
}
```

穩定 `chatUuid` 是主鍵；`characterId/chatId` 記錄在草稿正文中用於校驗、顯示和無 UUID 環境的 fallback，不與 UUID 拼成會隨重新命名改變的新鍵。分支應產生新 UUID，並可記錄 `originUuid`；聊天重新命名和群聊需要單獨測試。

### 8.2 草稿 schema

```javascript
const draft = {
  schemaVersion: 2,
  chatUuid: '...',
  updatedAt: '...',
  identity: {},
  world: {},
  packages: [],
  openingBody: '',
  ui: { step: 1 },
};
```

儲存前做 schema 校驗和大小上限，避免把 DOM、函式、Blob 或完整包體塞進 metadata。

### 8.3 debounce + flush

輸入時防抖儲存，以下時機同步 flush：

- 切步驟；
- 頁面 `pagehide`；
- 切聊天前；
- 開啟預覽；
- 最終提交；
- 執行時銷燬。

### 8.4 損壞與遷移

讀取舊草稿：

1. 校驗 JSON 和 schemaVersion；
2. 逐版本遷移；
3. 遷移失敗時隔離原記錄；
4. 提示使用者重置當前聊天草稿；
5. 不用空物件覆蓋所有聊天；
6. 記錄不含敏感正文的診斷。

## 9. 校驗、預覽與唯一真相源

### 9.1 業務校驗

至少覆蓋：

- 必填身份/場景；
- 空白正文；
- 正文位元組上限；
- 允許/未知宏；
- 身份與年級/世界設定的相容；
- 工坊包重複、衝突和 cardScope；
- 依賴是否仍可用；
- 當前聊天是否仍是草稿所屬聊天。

字元數不等於 UTF-8 位元組數：

```javascript
const byteLength = new TextEncoder().encode(text).byteLength;
```

### 9.2 唯一訊息構建器

```javascript
function buildOpeningMessage(draft) {
  return [
    `我的身份：${draft.identity.summary}`,
    `開局條件：${draft.world.summary}`,
    draft.openingBody.trim(),
  ].filter(Boolean).join('\n\n');
}
```

預覽、位元組校驗、最終傳送全部呼叫它。預設值也要先寫回 draft，再由構建器讀取；不能 UI 顯示一個預設值而提交器又偷偷使用另一個。

### 9.3 預覽不是寫入

預覽階段禁止：

- 安裝世界書條目；
- 修改 Persona；
- 寫 MVU 正式變數；
- 向聊天插入隱藏訊息；
- 自動開始生成。

如需計算 diff，只讀當前狀態並展示。使用者確認後再進入事務。

## 10. 提交事務

### 10.1 凍結上下文

提交開始時捕獲：

```javascript
// 概念適配層：禁止照抄為未宣告的 iframe 全域性函式。
const token = OpeningContextAdapter.capture({
  draftHash: hashDraft(draft),
});
```

適配層應從實際執行上下文組合證據：例如 `SillyTavern.getContext()` 的當前聊天標識、聊天 metadata 中的 draft UUID，以及確需時對 0 號樓當前 Swipe/訊息修訂的讀取。`getCurrentMessageId()` 屬於訊息樓 iframe 便利 API，控制中心/宿主 binder 不得假定它是任意上下文的全域性函式。

最終傳送前再次比較。使用者在確認對話方塊期間切聊天、修改草稿或首訊息 Swipe，舊提交必須取消。

### 10.2 推薦順序

```text
freeze context
→ flush draft
→ validate draft and dependencies
→ build preview/message
→ show final diff/confirm
→ snapshot persistent targets
→ persist identity/world/workshop configuration
→ verify writes by reread
→ rebuild message from frozen draft
→ recheck chat/input/runtime
→ place text into ST input
→ trigger normal send
→ confirm a real user message was created
→ mark opening committed / archive draft
```

### 10.3 跨系統事務

瀏覽器、Persona、世界書和聊天傳送通常沒有真正原子事務。應用層需要：

- 變更前快照；
- 每步結果記錄；
- 可逆步驟的回滾；
- 不可逆步驟放在最後；
- 失敗時明確哪些已生效；
- 重試冪等，不能重複安裝條目或重複傳送。

建議先完成可驗證的身份/世界書寫入，最後才傳送真實玩家訊息。若持久化失敗，預設停止；可允許使用者顯式選擇“僅本次繼續”，但必須說明相關配置不會常駐。

### 10.4 輸入框仲裁

若透過 `#send_textarea` / `#send_but` 走宿主傳送鏈：

- 這是版本敏感私有 DOM 路線；
- 寫入前記錄輸入框原內容；
- 若使用者已經修改輸入框，取消自動覆蓋；
- 觸發正常 input/change 事件；
- 點擊發送失敗時保留文字，讓使用者手動傳送；
- 不直接 `generate()` 生成一段遊離文字冒充訊息。

---

## 11. 回到正常生成鏈

正確完成鏈：

```text
真實 user 訊息
  → ST 正常生成請求
  → 真實 assistant 下一樓
  → 變數框架按正常回復鏈初始化/更新
  → 狀態列與控制中心讀取正式狀態
  → 開局頁退出使命
```

### 11.1 為什麼不直接 generate

直接呼叫裸生成可能：

- 不建立真實 user 樓；
- 繞過正常事件、正則或變數更新鏈；
- 產生不能 Swipe/編輯/匯出的遊離文字；
- 在切聊天競態中落錯上下文；
- 讓首回合和後續回合使用不同路徑。

開局頁的最終動作應儘可能等同於使用者在 ST 輸入框傳送一條正常訊息。

### 11.2 提交標記

成功確認真實 user 訊息存在後，寫入當前聊天的“開局已提交”標記。該標記用於避免重新整理後重復提交，不應用來禁止使用者編輯或分支。若使用者回到首訊息重新開局，應明確提供“重置開局”流程並提示影響。

## 12. 失敗降級與人工接管

| 失敗 | 預設行為 | 可選恢復 |
|---|---|---|
| 遠端頁面斷網 | mount 顯示錯誤，不白屏 | 手動重試/簡化原生開局 |
| hash/協議不匹配 | 拒絕注入 | 更新受信資源後重試 |
| **必需**依賴缺失 | 禁止正式提交 | 只讀預覽/說明安裝步驟；未使用依賴不阻斷 |
| 草稿損壞 | 隔離當前記錄 | 重置當前聊天草稿 |
| 身份持久化失敗 | 停止 | 重試/顯式僅本次繼續 |
| 世界書事務失敗 | 只回滾本事務擁有且 revision 未變化的可逆寫入 | 併發/不可逆時停止並展示部分提交 diff |
| 確認後切聊天 | 取消舊提交 | 在新聊天重新確認 |
| 輸入框被使用者修改 | 不覆蓋 | 複製文字或重新預覽 |
| 自動點擊發送失敗 | 保留文字 | 使用者手動傳送 |
| 頁面解除安裝 | abort 請求和提交 | 重新掛載後恢復草稿 |

所有錯誤都應保留原生 ST 的可用性。開局頁不能把聊天鎖在“必須遠端頁面成功才可退出”的死狀態。

## 13. 生命週期與重複掛載

### 13.1 會觸發重綁的場景

- 首訊息 Swipe；
- 編輯/儲存首訊息；
- 單條訊息重渲染；
- 切聊天/Persona/分支；
- 瀏覽器重新整理；
- 指令碼熱過載；
- 遠端頁面重試；
- DOM 被第三方擴充套件替換。

### 13.2 單例 binder

每個 mount 使用穩定例項鍵：

```javascript
const BIND_KEY = '__openingBinder';

function bindMount(mount, descriptor) {
  const current = mount[BIND_KEY];
  if (current?.isCompatible?.(descriptor)) return current;
  current?.destroy?.();
  mount[BIND_KEY] = createBinder(mount, descriptor);
  return mount[BIND_KEY];
}
```

`isCompatible` 至少比較 owner/runtime、頁面協議和內容 revision。重複掃描發現同一有效例項時直接複用；只有 mount 已失效或協議/revision 變化時才銷燬重建，避免定時掃描反覆取消請求、丟焦點或打斷提交。

destroy 清理：

- fetch AbortController；
- debounce/timeout；
- DOM listeners；
- window message；
- Tavern Helper event disposer；
- observers；
- 開啟的模態框；
- 正在進行的提交鎖；
- 對舊 chat/draft 的閉包引用。

### 13.3 不依賴單一 DOMContentLoaded

卡內指令碼和訊息 mount 可能在頁面已載入後建立。初始化應使用當前執行時推薦的就緒方式，並對目標 mount 做冪等發現/重綁，而不是隻監聽一次 `DOMContentLoaded`。

## 14. 工程目錄與協議

```text
opening/
  protocol.ts             # 版本、schema、action ID
  mount.html              # 極短可見 fallback
  opening-page.html       # 宣告式頁面
  binder.js               # 受信互動邏輯
  draft.js                # schema、儲存、遷移
  validation.js
  build-message.js        # 唯一訊息組裝器
  persistence.js          # 身份/世界書/工坊事務
  submit.js               # 上下文凍結與正常傳送
  lifecycle.js
  tests/
```

### 14.1 頁面協議

至少約定：

- `protocolVersion`；
- 必需根節點；
- 穩定 `data-action`；
- 表單欄位 ID/名稱；
- 錯誤/狀態容器；
- 頁面內容 hash；
- 可選能力標記；
- binder 支援的最小/最大協議。

CSS class 可隨視覺修改，業務 binder 不應依賴裝飾性類名。

### 14.2 測試層次

- schema/訊息構建器單測；
- 草稿遷移與壞資料測試；
- HTML 協議/淨化測試；
- 提交事務的 mock 上下文測試；
- 本地 ST DOM 整合；
- 真機訊息鏈、Swipe、切聊天與斷網測試。

## 16. 高頻錯誤

| 錯誤 | 後果 | 修復方向 |
|---|---|---|
| 把開局頁當 C5 | 邊界和後續職責無限膨脹 | 以提交後退出為硬門 |
| 只是幾個 alternate 卻造遠端應用 | 成本和故障面過大 | 優先原生首訊息/Swipe |
| 整頁 HTML 送模 | token 膨脹、提示詞汙染 | display/prompt 分離 |
| 遠端 `<script>` 執行業務 | 供應鏈可任意控制宿主 | 宣告式 HTML + 本地 binder |
| 只看 HTTP 200 | 結構錯誤仍繫結 | hash/協議/結構/淨化 |
| 草稿按角色名存 | 多聊天串檔 | chat UUID 隔離 |
| UI 預設值不進 draft | 預覽和提交不一致 | 唯一草稿真相源 |
| 預覽時寫正式資料 | 取消後留下半套狀態 | 預覽只讀，確認後事務 |
| 直接改 MVU 作為開局草稿 | 正常變數鏈被繞過 | 正常回復鏈初始化 |
| 直接 `generate()` | 沒有真實 user 樓 | 走 ST 正常傳送 |
| 確認後不復核聊天 | 寫進舊聊天 | context token 二次檢查 |
| 自動傳送覆蓋使用者輸入 | 丟失使用者文字 | 輸入框仲裁 |
| 載入失敗白屏 | 無法繼續聊天 | 本地 mount 錯誤/重試/降級 |
| 重綁不銷燬 | 多次提交、監聽洩漏 | mount 單例 + destroy |
| 把私有 DOM 當 API | ST 更新後失效 | 能力檢測 + 相容矩陣 |

## 17. 驗收矩陣

| 維度 | 必驗場景 |
|---|---|
| 普通開局 | 預設 first message、每個 alternate、Markdown/HTML、宏 |
| 群聊 | first + alternate 選擇；無首訊息角色行為 |
| 顯示/送模 | UI 可見；模型上下文不含整頁 HTML/CSS |
| 載入 | 主源、備源、超時、全斷網、hash 錯、協議錯、重試 |
| 草稿 | 輸入後重新整理恢復、清空、舊版遷移、損壞隔離 |
| 聊天隔離 | A/B 聊天、分支、Persona、重新命名，不串檔 |
| 嚮導 | 前進、後退、限制、預覽、修改後預覽更新 |
| 校驗 | 空正文、超上限、未知宏、身份/世界不相容 |
| 依賴 | TH、控制中心、世界書、變數框架分別缺失 |
| 持久化 | 成功、失敗重試、回滾、僅本次繼續、取消 |
| 提交競態 | 確認後切聊天、解除安裝、輸入框被改、重複點選 |
| 傳送失敗 | 文字仍在輸入框，可人工傳送 |
| 正常主鏈 | 真實 user 樓→真實 AI 樓→變數初始化 |
| 生命週期 | 首樓 Swipe、編輯、重渲染、重新整理、熱過載 |
| 移動/無障礙 | 320px、軟鍵盤、ARIA 狀態/錯誤、44px、焦點 |
| 退出邊界 | 提交後恢復普通多樓層，不繼續承擔 C5 功能 |

穩定完成門：必須用目標卡真機完成“開頁→改草稿→重新整理恢復→確認→真實 user 樓→真實 AI 樓→變數初始化”，並透過切聊天、斷網和重複提交對抗測試。靜態頁面截圖不算完成。
