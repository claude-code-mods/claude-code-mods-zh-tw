## 1. 定義與邊界

本文所說的“自定義 CoT”是作者寫給模型的推演協議。它規定生成前要檢查什麼、按什麼順序判斷、何時跳過模組、失敗時如何降級，以及最終允許輸出什麼。

自定義 CoT 是模型可見的 Prompt，不是作者無法直接檢視的模型內部推理。作者可以設計和驗收這套協議，但不能借此讀取、儲存或證明模型的隱藏思維過程。驗收應檢查輸入、路由和最終行為，不要求模型展示完整推理。

以下概念必須分開：

| 概念 | 用途 | 是否屬於自定義 CoT | 輸出邊界 |
| --- | --- | --- | --- |
| 作者無法直接檢視的模型內部推理 | 模型自身完成生成所需的內部處理 | 否 | 不由卡片定義，不要求展示 |
| 作者編寫的自定義 CoT Prompt | 規定判斷問題、順序、跳過條件和輸出檢查 | 是 | 預設只輸出最終正文或協議要求的結果，不輸出逐步分析 |
| 正文中的角色內心活動 | 塑造角色、視角和敘事體驗 | 否 | 是正文，可按文風展示 |
| MVU `<analysis>` 變數更新依據 | 解釋或約束本輪為何需要更新變數 | 僅是可選更新模組 | 只服務變數更新協議，不代表完整 CoT |
| 更新模型專用分析 | 從劇情結果提取源事件、源狀態和合法更新 | 是獨立更新 Prompt 的一部分 | 不寫劇情正文，不接收無關文風與角色表演規則 |
| 指令碼計算過程 | 執行確定性公式、批次派生和資料整理 | 否 | 由程式碼執行，不改寫成冗長自然語言推演 |

“角色在猶豫什麼”可以出現在正文中；“當前事實是否足以支援角色背叛”屬於行為判斷；“好感度是否應更新”屬於可選變數判斷；“好感度加成後總值是多少”若公式確定，應由指令碼計算。四者不要寫進同一個步驟。

## 2. 部署位置

先判斷規則的複用範圍、啟用條件和接收模型，再決定放置位置。

| 放置方式 | 適用場景 | 不應放入的內容 |
| --- | --- | --- |
| 預設中的通用自定義 CoT | 多張卡都需要的輸入檢查、場景識別、行為選擇、連貫性和輸出檢查 | 單一卡片的人名、專屬能力、固定劇情答案 |
| 角色卡中的專項補充 | 該卡獨有的行為限制、敘事機制、專屬判斷條件 | 已由預設提供的完整通用步驟 |
| 世界書條件觸發的 CoT 模組 | 僅在地點、事件、角色、戰鬥或系統條件成立時需要的判斷 | 無條件常駐的整套主 CoT |
| 按深度或順序注入的 CoT 片段 | 已驗證執行時能夠把片段穩定送到目標階段，並且上下文位置會影響語義 | 未查證的欄位名、宏、順序值或注入 API |
| 獨立劇情模型 CoT | 劇情推進、角色行為、NPC 排程、敘事輸出 | 低層變數寫入格式和確定性指令碼公式 |
| 獨立變數更新模型 Prompt | 從已生成劇情提取源事件和源狀態，執行合法變數更新 | 劇情風格、角色表演、候選劇情和正文格式 |

預設採用：

```text
預設通用 CoT
  + 角色卡常駐專項增量
  + 當前條件啟用的 CoT 模組
```

不要讓每張卡複製一整套完整 CoT。只有在目標環境不支援可靠拼接時，才生成一份完整回退版本；完整版本應由主 CoT 和增量源合成，不應成為第二份手工維護的源。

按以下順序做位置判斷：

1. 多張卡都成立的規則放預設。
2. 只對當前卡成立、每輪都需要的規則放卡片專項增量。
3. 只在明確條件下成立的規則放條件世界書或專案已驗證的條件注入層。
4. 只給劇情模型或更新模型使用的規則進入各自 Prompt，不放進共享上下文。
5. 依賴具體 SillyTavern、擴充套件、宏、欄位、深度或順序語義時，交給 `$sillytavern-api-reference` 查證目標版本；本文不定義這些 API。

## 3. 模組設計

### 3.1 模組契約

每個模組只解決一個明確問題。為模組記錄：

- 穩定模組 ID；
- 要回答的問題；
- 所需輸入；
- 判斷條件；
- 產生的結論或下游輸入；
- 結論是否允許出現在最終輸出；
- 跳過條件；
- 資訊不足或衝突時的降級方式；
- 接收模型；
- 預估 Token 成本。

這些欄位是作者側設計契約，不是 SillyTavern API 或世界書 JSON 格式。

### 3.2 可刪減的通用流程

常用流程可以是：

```text
輸入檢查
→ 當前場景識別
→ 角色狀態判斷
→ 目標與衝突判斷
→ 行為選擇
→ 連貫性檢查
→ 輸出組織
```

按卡片需要刪減這套流程，不必固定執行七步。沒有群像就刪除 NPC 排程；沒有戰鬥就跳過戰鬥判斷，交易、資源消耗等其他系統判斷按實際需要保留。沒有變數系統就刪除 MVU 更新判斷；純格式轉換任務可以只保留輸入檢查和輸出格式檢查。

### 3.3 模組庫

| 模組 | 解決的問題 | 可檢查條件 | 何時跳過 |
| --- | --- | --- | --- |
| 輸入檢查 | 本輪必須回應什麼，哪些事實和約束有效 | 最近使用者輸入、當前場景、已確認事實、有效協議是否齊全 | 輸入已由上游結構化且無歧義 |
| 當前場景識別 | 人物、地點、時間、進行中的事件是什麼 | 只採用上下文已出現或規則明確給出的事實 | 與輸出無關的純格式任務 |
| 劇情判斷 | 本輪應推進、維持還是收束哪條線 | 當前懸念、已發生因果、使用者可行動空間 | 無劇情推進要求 |
| 角色狀態判斷 | 角色知道什麼、想要什麼、能做什麼 | 已知資訊、動機、關係、能力、身體與情緒狀態 | 無角色行為或僅處理系統資料 |
| 目標與衝突判斷 | 哪些目標相容，哪些約束髮生衝突 | 目標優先順序、風險、代價、角色底線、使用者行動 | 沒有選擇或衝突 |
| 行為選擇 | 哪個行為最符合當前事實並保留後續空間 | 行為必須可由角色狀態和場景支援，不提前保證結果 | 行為已由使用者或確定性規則指定 |
| 群像 / NPC 排程 | 本輪誰需要行動、誰只需保持在場 | 在場性、知情範圍、行動必要性、發言重複、鏡頭佔用 | 單角色場景 |
| 戰鬥或系統判斷 | 需要哪些語義判定，哪些交給指令碼 | 行動意圖、目標、前置條件、敘事結果類別、指令碼所需源輸入 | 沒有系統事件，或結果完全由指令碼給出 |
| 連貫性檢查 | 是否出現越權、瞬移、失憶、重複、無因結果 | 與最近事實、角色知識、時間線和未解決事件比對 | 上游已提供經過驗證的確定性結果 |
| 輸出格式檢查 | 最終輸出是否滿足正文和結構協議 | 必填區塊、順序、標籤、禁止內容、只出現一次的約束 | 目標沒有格式契約時仍應做最小正文檢查 |
| 卡片專項 CoT | 當前卡獨有規則要補充哪個階段 | 規則只引用卡片專屬差異，並宣告插入階段 | 觸發條件不成立或主 CoT 已覆蓋 |
| 可選 MVU 更新判斷 | 本輪產生了哪些需要持久化的源事件或源狀態 | 只依據已生成劇情和現有變數，不重寫劇情 | 無 MVU、沒有變數變化，或由獨立更新模型處理 |

### 3.4 按任務組合

- 普通文字卡：輸入檢查 → 場景 → 角色狀態 → 行為選擇 → 連貫性 → 輸出。
- 劇情導演：輸入檢查 → 場景 → 劇情目標與衝突 → NPC 排程 → 連貫性 → 輸出。
- 群像卡：輸入檢查 → 場景 → 角色狀態 → NPC 排程 → 行為選擇 → 鏡頭與重複檢查 → 輸出。
- 戰鬥 / 系統卡：輸入檢查 → 前置條件 → 語義結果判斷 → 指令碼輸入整理 → 連貫性 → 輸出。
- MVU 卡：先使用適合該卡的劇情 CoT；變數更新判斷作為可選後續模組，或交給獨立更新模型。它不替代前面的劇情與行為判斷。

## 4. 編寫規範與 Token 預算

### 4.1 寫成可執行判斷

- 每個步驟只解決一個問題，並說明判斷依據。
- 把“深入思考”“仔細分析”“全面考慮”改成可檢查條件。
- 引用角色設定和世界事實，不在 CoT 中複製全文。
- 只決定本輪行動和輸出組織，不提前鎖死後續劇情結果。
- 示例用於說明結構或邊界，不寫成模型每輪都能照抄的完整答案。
- 標明哪些結論僅供判斷，哪些欄位或正文允許輸出。
- 為每個可選模組寫明跳過條件。
- 為缺失輸入、規則衝突和格式修復失敗寫明降級策略。
- 規則無法被輸出行為、結構或路由證據驗收時，刪除或改寫。

對比：

```text
差：深入思考角色下一步應該做什麼。
好：檢查角色已知資訊、當前目標、能力限制和已承諾事項；只選擇四項都支援的行為。
```

```text
差：仔細分析戰鬥並計算所有結果。
好：判斷行動是否成立、命中或受阻的敘事類別，並輸出指令碼所需的源事件；數值結算交給指令碼。
```

### 4.2 判斷內容與輸出內容

在主 CoT 開頭明確：

- 步驟名、檢查表、候選行為和評分預設不輸出；
- 角色內心活動只有在敘事視角和文風允許時才作為正文輸出；
- 結構化結果只輸出目標協議要求的欄位；
- 不用“展示推理”證明協議生效；
- 格式檢查只修復格式，不趁機改寫已確定的劇情事實。

### 4.3 降級策略

至少覆蓋：

- 缺少次要事實：使用已確認事實繼續，不補寫關鍵設定。
- 缺少決定性事實：選擇可逆、低承諾的行動，或在正文中自然請求資訊。
- 模組條件不成立：跳過，不輸出“本模組未觸發”。
- 條件模組衝突：保留主 CoT 的硬約束，停止合併衝突規則並報告作者側衝突。
- 格式無法完整修復：保留最小有效正文；可選結構寧可省略也不偽造資料，具體協議另有硬性要求時按該協議安全失敗。
- CoT 關閉、缺失或拼接失敗：回到卡片穩定身份、當前事實和基本輸出約束；停用依賴該 CoT 的可選自動決策，不製造不可逆結果。

### 4.4 Token 預算與去重

先去重，再縮寫。按以下順序處理：

1. 列出預設、卡片欄位、世界書、變數規則、指令碼說明和輸出協議中的所有模型可見規則。
2. 為關鍵規則分配穩定規則 ID，並指定唯一權威來源。
3. 刪除語義相同但換了說法的重複規則。
4. 卡片只保留對通用規則的新增條件、例外或收緊，不重述主規則。
5. 條件模組只在需要時啟用。
6. 分別統計劇情模型和更新模型實際收到的 Token，不用總檔案大小代替接收方預算。
7. 用目標模型的實際 tokenizer 或執行時統計複核，不憑字元數猜測。

以下僅是開始審計時的經驗範圍，不是硬標準：

| 模板 | 建議起點 | 優先刪減物件 |
| --- | --- | --- |
| 輕量通用 CoT | 約 150～350 個目標模型 Token | 空洞動詞、重複輸出提醒 |
| 角色行為與劇情 CoT | 約 300～700 個目標模型 Token | 重複角色設定、過多候選方案 |
| 複雜群像 / 系統卡 CoT | 常駐部分約 600～1200 個目標模型 Token | 未啟用模組、重複角色掃描、指令碼公式說明 |

複雜卡應把低頻模組條件化，不應僅靠壓縮措辭把全部模組永久塞進上下文。

## 5. 可直接使用的模板

以下模板是 Prompt 文字，不宣告任何 SillyTavern 欄位或 API。標題和分隔符可以按專案預設格式調整。部署前刪除未使用的佔位符與模組。

### 5.1 輕量通用 CoT

```text
自定義 CoT：輕量通用

用途：在不依賴變數系統的情況下，穩定完成當前角色與場景的下一輪迴復。

執行規則：
- 下面的檢查只用於組織生成。不要輸出步驟名、檢查表、候選答案或分析摘要。
- 只把最終正文和當前輸出協議明確要求的結構交給使用者。

1. 輸入檢查
確定使用者本輪說了什麼、做了什麼或要求什麼。區分已發生事實、角色可見資訊和尚未確認的推測。

2. 場景檢查
確認當前地點、在場人物、時間順序和正在進行的事件。缺失的關鍵事實不要自行補成既定事實。

3. 角色檢查
根據角色已經知道的資訊、當前目標、關係、能力和限制選擇反應。角色不得使用其不可能知道的資訊。

4. 行為選擇
選擇一個由當前事實支援、符合角色動機、能夠回應使用者且不會提前鎖死後續劇情的行動。若資訊不足，優先選擇可逆行動或自然詢問。

5. 連貫性檢查
檢查是否與最近發生的事實衝突，是否重複上一輪，是否超出玩家明確允許的代演範圍。沒有代演授權時，不新增玩家臺詞、主動行動、決定、內心、感受或身體反應；已確認事實和既定玩法的客觀外部結果可以描述。

6. 輸出檢查
保持既定視角、語氣和長度，只輸出最終回覆。角色心理可按既定視角寫入正文，也可按輸出約定展示結算結果或簡短依據。無論文風如何，都不展示模型的完整內部推理。

跳過與降級：
- 沒有劇情或角色行為時，可跳過第 2～4 步，只檢查輸入和輸出。
- 某項資訊缺失時，不編造關鍵狀態；使用現有事實完成最小可靠回覆。
```

這套模板可以直接用於完全沒有 MVU 的文字卡。

### 5.2 角色行為與劇情 CoT

```text
自定義 CoT：角色行為與劇情

目標：讓角色行為有依據，讓劇情產生本輪進展，同時保留使用者的行動權和後續空間。

輸出邊界：
- 以下判斷預設不輸出。
- 角色內心活動只有在當前敘事視角允許時才寫成正文；它不是系統分析。
- 不輸出候選行為列表、評分表或“我選擇了……”之類的決策說明。

1. 讀取本輪輸入
提取使用者明確的語言、動作、目標和限制。不要把建議、假設或未傳送的選項當成已發生事實。

2. 建立當前場景
確認在場人物、空間關係、時間順序、可用物件、正在推進的事件與尚未解決的衝突。

3. 判斷角色狀態
逐項檢查角色的已知資訊、即時目標、長期動機、情緒、關係、能力限制和已作承諾。
【卡片增量插入點：character_state.after】

4. 判斷目標與衝突
確定本輪最需要回應的目標。若多個目標衝突，優先遵守明確事實、角色核心邊界和使用者已採取的行動，不用作者預設結局覆蓋當前選擇。
【卡片增量插入點：goal_conflict.after】

5. 選擇本輪行為
選擇能夠直接回應使用者、由角色狀態支援併產生可感知變化的行為。重大轉折必須有已出現的原因；資訊不足時採用試探、延遲承諾或請求確認。
【卡片增量插入點：action_selection.after】

6. 安排劇情進展
本輪只推進當前因果鏈所能支援的部分。不要為追求刺激強行引入新敵人、秘密、能力或結局。保留至少一個使用者可以繼續介入的落點。

7. 連貫性檢查
檢查角色是否越過知情範圍，空間和時間是否連續，情緒變化是否有觸發，未解決事件是否被無故遺忘，是否重複上一輪表達。

8. 組織輸出
按卡片既定視角、文風和格式寫最終正文。格式修復不得改變已經確定的劇情事實。刪除未替換的插入點標記。

降級：
- 卡片增量缺失時，繼續執行通用步驟，不偽造專屬規則。
- 場景資訊不足以支援重大行動時，選擇低承諾反應。
- 輸出格式有可選區塊但缺少可靠資料時，省略可選區塊，不編造內容。
```

插入點是作者側合併標記，不是 SillyTavern API。若專案沒有自動合併器，在交付前手工合併並刪除標記。

### 5.3 複雜群像 / 系統卡 CoT

```text
自定義 CoT：複雜群像與系統

目標：在多人、多事件或帶規則判定的場景中，選擇必要行動者，保持資訊隔離，並把確定性計算交給指令碼。

輸出邊界：
- 不輸出排程表、候選方案、分數、逐步分析或指令碼計算過程。
- 只輸出劇情正文，以及目標協議明確要求的源事件或結構。
- 獨立更新模型存在時，不在劇情正文中代寫其變數更新任務。

1. 輸入與有效狀態
提取使用者本輪動作、已確認場景事實、當前有效角色和系統狀態。忽略未啟用模組和過期狀態。

2. 場景事件佇列
列出本輪必須處理的事件，並按因果前置關係排序。只保留會改變當前回覆的事件；背景事件不搶佔正文。

3. 行動者篩選
對每個在場角色檢查：是否知情、是否有行動能力、是否有本輪必須回應的目標、行動是否與他人重複。
只有滿足至少一個明確行動理由的角色進入本輪鏡頭；其他角色保持在場但不強制發言。

4. 角色與 NPC 排程
先處理使用者直接互動物件，再處理會改變結果的 NPC，最後處理必要的環境反應。
同一資訊不讓多個 NPC 依次複述。不得讓未在場或不知情的 NPC 作出針對性反應。
【卡片增量插入點：npc_scheduling.after】

5. 目標與衝突
比較各行動者的即時目標、資源、風險和邊界。衝突結果必須來自已知能力、當前條件和使用者行動，不因預定劇情強制成功或失敗。

6. 戰鬥或系統語義判斷（僅在觸發時執行）
判斷行動意圖、物件、前置條件是否成立，以及結果屬於成功、受阻、部分達成或失敗中的哪類。
只產生指令碼所需的源事件和語義類別。傷害合計、資源扣減、冷卻、排名、派生屬性和批次聯動由指令碼計算。
【卡片增量插入點：system_judgement.after】

7. 劇情組織
把已選擇的必要行動按因果順序寫成一個連續場景。控制鏡頭切換，保證使用者能辨認誰在行動，併為下一輪保留可操作入口。

8. 連貫性與許可權檢查
檢查時間、空間、知情範圍、資源前置、角色能力、事件去重和使用者控制權。刪除無因結果和重複反應。

9. 輸出格式檢查
驗證必填區塊、順序、標籤和只允許出現一次的內容。格式錯誤只修復結構，不重新計算指令碼結果，不新增劇情事實。

跳過與降級：
- 單角色場景跳過第 3～4 步的群像掃描。
- 無戰鬥或系統事件時跳過第 6 步。
- 指令碼不可用時，不假裝完成精確計算；按專案宣告的安全回退輸出語義結果或暫停該可選系統。
- 條件模組缺失時使用通用規則繼續，不補寫未知專屬機制。
```

## 6. 預設主 CoT 與卡片增量拼接

### 6.1 主 CoT 提供穩定階段

預設主 CoT 應提供穩定階段 ID，例如：

```text
input_check
scene_state
character_state
goal_conflict
action_selection
continuity_check
output_format
```

專案可以刪減或改名，但一個已釋出的拼接契約不應隨意改動 ID。卡片只宣告它要補充哪個階段，不復制階段本身。

### 6.2 卡片宣告增量

卡片增量至少宣告：

- 增量 ID 和版本；
- 目標主 CoT 契約；
- 目標階段；
- 插入到該階段之前或之後；
- 常駐或條件啟用；
- 與其他模組的先後依賴；
- 穩定規則 ID；
- 接收模型；
- 只供判斷還是允許輸出；
- 不支援拼接時的回退來源。

作者側宣告示例：

```text
增量 ID：card.example.behavior.v1
目標主 CoT：general-cot/v1
目標階段：character_state
位置：after
啟用：always
依賴：無
規則 ID：card.example.knowledge-limit
接收模型：plot
輸出：僅供判斷
規則：該角色只能依據親歷事件和已收到的報告判斷幕後人物；傳聞不得寫成確定事實。
回退：由主 CoT v1 與本增量生成完整版本。
```

這是倉庫內的作者契約示例，不是 SillyTavern 條目格式、宏或 API。

### 6.3 去重

同時做兩種去重：

1. **ID 去重**：相同規則 ID 只裝配一次；版本衝突時停止合併，不猜測採用哪一份。
2. **語義去重**：即使 ID 不同，只要兩條規則解決同一問題且約束相同，也保留唯一權威來源。

卡片可以增加條件、例外或更窄邊界。例如主 CoT 已有“角色不得使用未知資訊”，卡片只需增加“該角色把未經第二來源確認的報告視為傳聞”，不要再次複製通用知情規則。

### 6.4 插入位置與排序

先按主 CoT 階段順序裝配。每個階段內預設按以下順序：

1. 主 CoT 的階段規則；
2. 卡片常駐增量；
3. 當前啟用的條件模組；
4. 該階段的專項格式或交接檢查。

若模組宣告依賴，先滿足依賴再應用預設順序。多個條件模組仍並列時，使用專案明確的優先順序；優先順序相同則按穩定模組 ID 排序，保證結果可復現。不要依賴世界書當前顯示順序或偶然匯入順序解決衝突。

增量通常放在目標階段之後，用於收緊或補充主判斷。只有確實提供前置輸入或前置過濾時才放在階段之前。輸出格式規則始終在內容判斷完成後執行。

### 6.5 條件世界書模組的結構保護

條件模組必須：

- 只補充宣告的階段；
- 包含獨立模組邊界、規則 ID、啟用條件和跳過條件；
- 不重新定義主 CoT 的步驟順序；
- 不復制整套主 CoT；
- 不在正文中洩漏作者側模組標題；
- 不把劇情模型規則送給更新模型，反之亦然；
- 在多個模組同時啟用時保持可排序和可去重。

世界書的具體欄位、位置、深度、順序、關鍵字、綠燈、sticky 行為和目標模型可見性取決於目標執行時。使用 `$sillytavern-api-reference` 查證，不從本契約推導 API。

### 6.6 不支援拼接時的完整回退

當目標環境沒有可靠拼接能力時：

1. 保留主 CoT、卡片增量和條件模組作為獨立維護源。
2. 在構建或人工交付階段按相同排序規則合成完整 CoT。
3. 把未能動態注入的條件模組改寫成帶明確“滿足條件才執行”的可跳過段落。
4. 標記完整版本由哪些源和版本生成。
5. 靜態檢查未替換插入點、重複規則和模型路由。
6. 不把生成後的完整版本複製回每個增量源繼續手工維護。

## 7. 與其他系統的邊界

| 系統 | 與 CoT 的關係 | 邊界 |
| --- | --- | --- |
| 角色卡正文 | 提供穩定身份、行為錨點和敘事內容 | CoT 引用這些事實，不復制正文；可見內心活動是正文，不是系統判斷 |
| 世界書 | 提供條件知識或條件 CoT 模組 | 知識條目不因被 CoT 使用就變成 CoT；條件模組不得破壞主結構 |
| 預設 | 適合承載跨卡複用的主 CoT | 卡片只寫增量；預設規則是否實際注入需按目標環境驗證 |
| MVU | 提供可選持久變數與更新協議 | CoT 可以完全脫離 MVU；MVU `<analysis>` 不等於完整 CoT |
| Zod | 定義或校驗結構化資料 | 與 CoT 沒有直接關係；schema 不能代替行為判斷，CoT 也不能代替結構校驗 |
| 指令碼計算 | 處理確定性公式、派生變數和批次更新 | 不把計算過程寫成冗長 CoT；CoT 只提供指令碼需要的語義判斷或源輸入 |
| 正則 | 轉換、隱藏或展示已有文字 | 不負責推演，不用正則掩蓋錯誤的 CoT 或變數協議 |
| UI | 展示狀態、收集選擇和觸發已定義流程 | UI 不證明 CoT 已路由，也不應偷偷成為第二套判斷源 |
| 額外更新模型 | 獨立讀取劇情結果並寫變數更新 | 只接收更新所需狀態、規則和格式；不接收劇情 CoT、文風和 NPC 排程 |

劇情模型和更新模型必須按職責隔離：

- plot model 接收劇情、角色行為、NPC 排程和正文輸出所需的 CoT；
- update model 接收當前變數、已生成劇情、更新判斷、合法操作和更新輸出格式；
- 兩者都需要的事實才進入共享上下文；
- 不為了“相容”把兩套 Prompt 全部發給兩個模型。

## 8. MVU 與指令碼計算分工

本節只討論工作量和寫入職責，不討論玩法平衡。

基本規則：

- 語義判斷交給 LLM，例如意圖、關係變化原因、事件是否成立、結果類別。
- 確定性計算交給指令碼，例如公式、累計、派生欄位、批次同步、上限和下限。
- LLM 儘量只寫源事件或源狀態。
- 指令碼根據源資料批次更新派生變數。
- 同一個變數只能有一個寫入所有者，不能由 LLM 和指令碼競爭寫入。
- 合理使用指令碼可以顯著減少 JSONPatch 數量和 LLM 輸出壓力。

示例：

| 資料 | 推薦寫入者 | 原因 |
| --- | --- | --- |
| `事件：角色 A 成功救援角色 B` | LLM | 需要理解劇情語義 |
| `關係變化原因：獲救且確認對方承擔風險` | LLM | 需要語境判斷 |
| `好感基礎增量、等級閾值、稱號聯動` | 指令碼 | 公式和派生關係確定 |
| `攻擊是否被敘事條件阻止` | LLM | 依賴場景和前置條件 |
| `傷害合計、生命值、資源扣減、冷卻` | 指令碼 | 可重複的確定性計算 |

以下經驗範圍不是硬標準，比例指“最終變數變化中，需要 LLM 顯式輸出的比例”：

| 卡片型別 | LLM 顯式更新比例 |
| --- | --- |
| 輕量敘事卡 | 70%～100% |
| 混合系統卡 | 30%～50% |
| 重計算系統卡 | 10%～30% |

比例不決定卡片質量。判斷依據是資料是否需要理解自然語言語義，以及計算是否可以由確定性程式碼可靠復現。

若使用額外更新模型：

1. plot model 只完成劇情與行為輸出。
2. update model 從已生成劇情提取源事件和源狀態。
3. 指令碼讀取這些源資料並計算派生欄位。
4. 對每個變數記錄唯一寫入者。
5. 分別驗收劇情、更新 Prompt 和指令碼，不把三者串成一段長 CoT。

## 9. 驗證與反例

### 9.1 靜態檢查

- CoT 能否在完全沒有 MVU 的文字卡中使用？
- 是否預設支援縫入預設自定義 CoT？
- 是否錯誤複製了一整套預設已有規則？
- 卡片專項 CoT 是否只包含增量？
- 每個步驟是否有明確問題、輸入和作用？
- 是否存在“深入思考”“仔細分析”一類空洞步驟？
- 是否重複正文、角色設定或世界書？
- 是否把角色內心活動當作系統判斷？
- 是否把 MVU `<analysis>` 當作完整 CoT？
- plot model 和 update model 是否收到錯誤內容？
- 是否讓 LLM 計算本應由指令碼處理的確定性結果？
- 同一個變數是否被 LLM 和指令碼同時寫入？
- 多個條件模組能否穩定排序和去重？
- 條件模組是否會改寫主 CoT 結構？
- CoT 關閉、缺失或拼接失敗時是否有安全降級？
- 是否殘留插入點、佔位符、作者註釋或完整推理輸出要求？

### 9.2 反例

| 反例 | 問題 | 修正 |
| --- | --- | --- |
| “請深入思考並給出最佳劇情。” | 沒有判斷條件，無法驗收 | 指定當前事實、角色目標、限制和可逆性檢查 |
| 每張卡都複製同一套七步 CoT | 重複、易漂移、Token 浪費 | 主 CoT 放預設，卡片只寫增量 |
| 世界書觸發條目重新定義全部步驟 | 可能破壞主結構和排序 | 只宣告目標階段、規則 ID 和跳過條件 |
| 要求輸出角色內心活動證明 CoT 生效 | 混淆敘事與系統判斷 | 按文風決定是否寫內心，協議靠行為和結構驗收 |
| 把 MVU `<analysis>` 寫成劇情、NPC、戰鬥和格式總控 | 職責過載且無法脫離 MVU | 劇情 CoT 獨立，更新判斷僅處理變數 |
| 讓 LLM 逐項計算生命、資源、冷卻和派生等級 | 輸出長且容易算錯 | LLM 寫源事件，指令碼批次計算 |
| plot model 和 update model 接收相同完整 Prompt | 洩漏職責並浪費上下文 | 建立接收方清單，只共享雙方確實需要的事實 |
| CoT 缺失時仍強制輸出依賴其判斷的結構 | 容易偽造資料或崩壞 | 宣告最小正文回退並停用可選自動決策 |

### 9.3 本地靜態驗收

至少構造以下樣例並檢查生成的最終 Prompt：

1. 完全沒有 MVU 的文字卡使用輕量通用 CoT。
2. 已有預設主 CoT 載入一個角色卡常駐增量。
3. 兩個條件模組同時啟用，排序和去重結果穩定。
4. 群像卡只讓必要 NPC 行動，不讓所有 NPC 輪流發言。
5. MVU 卡的劇情 CoT 與更新判斷分離。
6. 額外更新模型不接收劇情文風、候選劇情或 NPC 排程。
7. LLM 只產生源事件，指令碼擁有派生變數。
8. 關閉主 CoT 或移除卡片增量後仍能安全輸出最小正文。

### 9.4 真實 SillyTavern 驗收

靜態文件不能證明實際注入順序、世界書啟用、模型接收方、額外更新模型上下文或指令碼生命週期。真實驗收應：

1. 記錄目標 SillyTavern、擴充套件、預設和 MVU 版本。
2. 用 `$sillytavern-api-reference` 查證版本敏感的欄位、注入、路由和可見性。
3. 用 `$sillytavern-runtime-debug` 在目標會話中取得實際 Prompt、啟用條目、模型接收方和輸出證據。
4. 分別測試無 MVU 文字卡、預設加卡片增量、條件模組開關、群像排程、CoT 關閉回退。
5. 若有額外更新模型，分別檢查 plot 與 update 上下文，確認沒有交叉洩漏。
6. 若有指令碼，比較源事件、指令碼計算結果、重複執行和失敗回退，確認沒有雙寫。
7. 記錄 Token 變化、格式失敗、重複規則和長對話後的行為漂移。

離線 Prompt 拼接、Markdown 檢查或單次生成不能關閉真實執行時驗收門。
