# 履歷儲存中斷後的恢復

本說明只適用於 `save-mirror-record.mjs` 管理的本地追加履歷。恢復沿用本次已授權儲存的目錄和記錄；不重寫舊節點，也不補造缺失的歷史。

## 正常儲存

儲存器先取得 `.mirror-save.lock`，再讀取現有鏈。第二個程序在鎖釋放前不能儲存或恢復。

新節點寫入 `.mirror-transaction/node/`，三個檔案落盤後才生成完整的 `journal.json`。事務記錄儲存舊指標的原始位元組及下一節點的索引。隨後釋出節點，依次原子替換 `index.json` 與 `latest.json`，完整複核後刪除事務區並釋放鎖。

每個節點仍是 `record.json`、`report.html` 和 `assessment.md`；舊版不含文字評估檔案的節點按原格式校驗。未修改正式歷史的目錄結構或評分含義。

## 儲存報錯但程序正常退出

讀取報錯後，在同一目錄執行：

```bash
node <skill-root>/scripts/save-mirror-record.mjs --root <履歷根目錄> --recover
```

- 尚未形成完整事務記錄：確認原歷史仍有效後，只清理不完整暫存；隨後可重新儲存原草稿。
- 完整事務記錄已生成：檢查舊鏈、新節點的雜湊，以及實際指標是否仍為該事務的舊值或新值；通過後完成同一次追加。
- 指標被其他操作改變、舊節點損壞、出現無關遊離節點或暫存雜湊不符：拒絕恢復並保留材料，不能把異常當作空歷史。
- 事務已完成：返回 `no-pending-transaction`，不會再追加一次。

恢復中再次遇到普通 I/O 錯誤時，已完成步驟仍由事務記錄識別，可以重試同一恢復命令。

## 儲存程序異常終止並留下鎖

檢查 `.mirror-save.lock/owner.json` 中的主機名、程序 ID 和 `token`。只在同一主機確認原程序已退出後，將該鎖標識傳入：

```bash
node <skill-root>/scripts/save-mirror-record.mjs --root <履歷根目錄> --recover --stale-lock-token <owner.json中的token>
```

儲存器再次核對標識及程序是否存活，活動程序或標識不符時拒絕釋放。恢復期間另有 `.mirror-recovery.lock` 阻止併發搶佔。PID 被新程序複用時會保守拒絕，不能據此終止無關程序。

鎖元資料缺失或損壞、主機不一致，以及恢復程序自身異常終止留下恢復鎖時，不做自動清理。先確認沒有任何儲存／恢復程序，並保留鎖和事務材料供人工核對；不要遞迴刪除履歷根目錄或 `records/` 來解鎖。

## 檢查範圍

隔離臨時目錄測試覆蓋首次儲存、歷史追加、各發布檢查點的故障、併發競爭和儲存程序異常終止。舊節點逐檔案比較保持原位元組。瀏覽器報告另行驗證便攜匯出和鍵盤行為。這些結果不證明磁碟損壞或作業系統斷電時一定能夠自動恢復。
