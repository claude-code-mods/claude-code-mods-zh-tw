# v0.10 方案：壓縮和續接之後，照樣拿回之前的圖

> 狀態：使用者 2026-10-31 確認方案，讓 Claude 按自己的安排做完（第 8 節）。程式碼和單元測試已完成，spec 和 design 已改；關卡 1–4 用本機回放驗證透過，關卡 6 的大會話只有估算（係數按桌面實測校準過），小會話的實測見公開評測；關卡 5、7 的 Codex 自測 2026-11-01 跑完，10 組裡 3 組有檢查沒過，原因都查清了、不是這個版本改出來的，使用者定記為已知問題（第 8 節第 9 條）；Claude 桌面實測（壓縮、重啟、改訊息分叉）和長會話回放（關卡 8）已透過，回放發現的三處（第 2 節第 9 到 11 條）已修。公開評測（第 6 節）2026-11-01 跑完，評測裡發現並修了三處（第 2 節第 12 到 14 條），報告在 [eval/long-task/](../../eval/long-task/README_CN.md)。2026-11-01 釋出 0.10.0。起因是用 5 個真實會話評估圖片檢索（會話內容只在本機，不進倉庫）。規格以 [spec.md](../spec.md) 為準，實現見 [design.md](../design.md)。

## 1. 背景與目標

評估的結論：模型按編號選圖很準，約 55 次取圖只錯 1 次，還是錯在版本判斷上。問題出在底層，壓縮和續接讓圖和特徵行丟了或掛錯了：

- **Claude，壓縮當場。** Claude Code 2.1.304 起，壓縮時會原樣保留最後幾條訊息（壓縮記錄的 `compactMetadata.preservedSegment`，也可能是 `preservedMessages`）。它讀記錄時，把保留的訊息改接到摘要後面，再刪掉壓縮點之前的記錄；檔案裡存的卻是改接之前的樣子。外掛照檔案裡的父子關係連對話鏈：
  - 新訊息接在保留的訊息上時，對話鏈繞過了壓縮點，外掛認不出壓縮，壓縮前的圖一張都沒放回（一次真實壓縮：94 張）；
  - 新訊息接在摘要上時，外掛能認出壓縮，但把保留的訊息算在了壓縮點之前。
- **Claude，續接。** 在 Claude 桌面版裡改一條之前的訊息再發送（回退）時，桌面版從那裡分叉出一個新會話、新開一個記錄檔案（日誌裡是 `resumeSessionAt` 加 `forkSession`），Claude Code 只把壓縮點之後的記錄寫進去。只是重啟程序（歸檔再恢復、記憶體緊張時被暫停）用的還是原來的會話和記錄檔案（2026-10-31 查桌面版日誌：21 次分叉都換了會話 id，只重啟的沒換；實測也是這樣。原來寫成“每次重啟程序都續接成新會話”，不對）。外掛只讀當前檔案，於是：
  - 壓縮前的圖放不回；
  - 編號從頭重排，對話裡按舊編號寫的特徵行和評價掛到了別的圖上（一個真實程序裡，帶特徵行的佔位 30 個全部掛錯）；
  - 舊的取回副本對不上新編號，被當成新圖另編了號。
- **Claude 的勾選不沿用。** 勾選、每輪都發和自動選圖開關按會話 id 存，續接和分叉之後都失效。
- **Codex。** 編號是穩定的。但 Codex 壓縮時只留下系統和開發者訊息、全部使用者訊息和一段外掛讀不了的加密摘要，生成的圖、檢視的圖、工具返回的圖連佔位一起從請求裡消失（一個真實任務壓縮時 43 張圖只剩使用者上傳的 10 張）。模型憑編號仍能取到它們，只是看不到。

目標：

1. 兩個平臺壓縮之後（Claude 還包括續接之後），之前的每張圖都帶著編號、特徵行和評價留在請求裡，模型能照樣拿對；勾了每輪都發的（手動模式下是勾著的）照發原圖。
2. 編號在壓縮、續接、分叉前後都不變。老會話裡按重排編號寫下的記錄行換算回來，落到對的圖上（使用者 2026-10-31 要求老會話也精確找回）。
3. 代價可以接受：引擎記憶體和每條請求多出的 token 都有上限，見第 3 節。

不做（使用者 2026-10-31 定）：

- 生成時交給生圖工具哪些參考圖：不歸外掛管。
- 改檢索演算法：先修底層，修完以後小規模回放，哪裡錯了再針對那一處改。
- 截圖（瀏覽器、電腦操作）的專門規則：另議。

## 2. 規則

### Claude

1. **對話鏈照 Claude Code 的規則連。** 對最後一個帶保留資訊的壓縮點：保留的訊息接在摘要後面；原來接在摘要上的、接在被刪記錄上的訊息，都接到最後一條保留訊息後面。和 Claude Code 不同的是，壓縮前的歷史不刪：壓縮點往前接到第一條保留訊息原來的前一條，壓縮前的圖照 v0.5 的做法放回摘要後面。沒有保留資訊的舊格式不變。
2. **續接的記錄檔案往回接。** 記錄檔案從壓縮點開始、前面沒有歷史時，找到原來的記錄檔案，把壓縮點之前的歷史接上：
   - 先看摘要裡 Claude Code 寫的那句 “read the full transcript at: …”（取最後一處），只認 Claude 的 projects 目錄裡、含同一個壓縮點的檔案；
   - 不行再在同一個專案資料夾裡按壓縮點找；
   - 原來的檔案也可能是續接來的，就一層層往回接；
   - 只讀；找到的記下來，不反覆找；
   - 找不到時照現在的做法，但對不上的記錄行不認（見第 3 條），寧缺不錯。
3. **老記錄行換算回來。** 修復之前寫下的特徵行、評價，以及取回副本前面那行字，用的是寫它們的那個程序當時的編號，也就是從那個程序所在記錄檔案的起點數起的編號。外掛找出同一會話的全部記錄檔案（同一專案資料夾裡，第一條對話記錄是會話起點或某個壓縮點的那些），按建立時間判斷每條記錄行是哪個程序寫的，再經圖片本身換算到恢復後的編號。這個版本第一次執行以後寫下的不用換算：和 v0.6 的 auto-default.json 一樣，記下這個版本第一次執行的時間。
4. **勾選沿用。** 續接和分叉出來的會話還沒有自己的勾選時，沿用上一個會話的勾選、每輪都發和自動選圖開關；分叉照 Codex 的規則，只沿用分叉那一刻之前的。之後各管各的。

### Codex

5. **壓縮後放回被丟掉的圖。** 請求裡有 Codex 的壓縮項時，把壓縮之前、請求裡已經沒有的圖按編號放在壓縮項後面：沒勾每輪都發的寫成一行（見第 6 條），勾了的發原圖，帶“已提供”標籤；後面跟一條說明。手動模式同理：勾著的發原圖，沒勾的放一行。沒有被丟掉的圖時，請求不變。

### 兩邊

6. **緊湊寫法**（只用於壓縮後放回的那一段）：一張圖一行，寫編號、名稱、來源、輪次、特徵行和最近 3 條評價，例如“IMG-041｜exec-….png｜檢視｜第 28 輪｜海邊棧道｜半身中景，白襯衫，回頭｜評價：第 29 輪“光太硬了””，沒有名字的寫“-”，清單第一行說明各列；怎麼取圖在說明裡講一次，說明裡不再把圖列第二遍。
   - 原因：原來每個佔位都重複一句“需要原圖時呼叫 cam_view_image…”，說明裡又把全部圖列一遍。一個有 127 張壓縮前圖片的真實會話，照原寫法每條請求要多約 1.7–2.0 萬 token（壓縮後第一條請求的約 16%–18%）；緊湊寫法加說明約 0.7–0.9 萬（按桌面實測校準的係數估，見關卡 6）。
   - 別處的佔位（圖在原位被省略的）不變。
7. **補寫和更正特徵行**（使用者 2026-10-31 採納了方向，做法見第 8 節）：
   - 補寫：被打斷的那一輪，新圖沒寫上特徵行。被打斷那一輪裡還沒有特徵行的圖，下一輪再發一次，標籤寫“已提供，還沒有特徵行”。
   - 更正：模型發現特徵行寫錯了（比如使用者指出），寫一行 `[//]: # (cam IMG-005 更正：…)`，替換原來的特徵行。
   - 這一條改的是特徵行說明，按 AGENTS.md 跑自測。
8. **截斷按寬度算**（做的時候回放發現，Claude 定）：特徵行和評價超長時，原來按介面語言數字符截斷（中文 30、英文 100），中文介面裡模型寫的英文特徵行被截到只剩地點。第 6 條那個會話的 180 條特徵行裡 91 條是英文，全被截成“cafe storefront morning |…”這樣，51 條截完和別的行一模一樣；壓縮之後清單是模型看到這些特徵的唯一地方，它就分不清這些圖。改成按寬度算，和介面語言無關：中日韓文字一個算 1，其他字元算 0.3，特徵 30，也就是 30 個漢字或 100 個字母（評價見第 10 條）。截完相同的從 51 條降到 6 條（127 張裡能分開的特徵行從 76 條升到 105 條），放回的一段多約 0.2–0.28 萬 token（按校準後的係數）。原位的佔位用的是同一個截斷，也跟著變。

下面三條是長會話回放測試發現的（2026-10-31，使用者定三個都修；測試做法和結果只在本機，見第 3 節第 8 條）：

9. **並行讀圖亂序時照樣編號**（外掛 bug，v0.4 起就有）：模型同時讀幾張圖、結果回來的順序亂了時，對話會從前面某個呼叫的結果接著走，後面的呼叫記錄不在對話鏈上，外掛認不出它們的圖。這些圖沒有編號，每輪照發原圖，壓縮後丟失，也取不回。改成：同一次回覆的幾次呼叫帶同一個訊息 id，不在鏈上的也接回來，圖按呼叫順序編號。補上編號後，排在它後面的圖編號後移，修復之前寫下的記錄行按當時的編號換算（第 3 條的做法，舊編號跳過這些圖）；編號規則的版本記在 `stable-ids.json` 裡，規則變了，第一次執行的時間重新記。
10. **評價和特徵行一樣長**：評價原來截到 15 個漢字，長會話測試裡一條 18 個字的評價在清單裡只剩前半句，壓縮後模型看不到後半句說的問題。評價是使用者的原話，一個會話沒幾條，上限改成和特徵行一樣，30 個漢字或 100 個字母。
11. **清單裡標出同一張圖**：使用者重發同一張圖時，外掛已經認得出是同一張，但清單列成兩行、各寫各的特徵。改成後面那行寫“同 IMG-108”，不再重複特徵。
12. **等記錄檔案寫完再改寫**（公開評測試跑時發現）：Claude Code 有時在把這一輪剛讀的圖寫進記錄檔案之前就發出請求，外掛認不出這幾張圖，原樣發出、不帶編號，模型這一輪沒法給它們寫特徵行（試跑裡一輪 3 張；使用者本機日誌 8904 次請求裡有 119 次，下一次請求才認出）。改成：請求裡模型最近一次回覆之後有認不出的圖時，引擎每 100 毫秒重讀一次記錄檔案，最多 1.5 秒；認出了就照常改寫。一張一直認不出的圖只讓一次請求多等這一下。
13. **壓縮後照常看新圖**（公開評測發現）：說明裡“不要用其他工具去讀取圖片檔案”本意是被省略的圖要用 `cam_view_image` 取。評測第一次跑 0.10 時（Haiku 5.5，推理強度 low），壓縮後模型把它當成所有圖，使用者後面 5 輪讓它看的圖一張都沒讀。改成只說被省略的（Codex 的壓縮說明裡是清單裡的）圖，並寫明使用者新讓它看的圖照常去看；重跑後每輪都照常讀圖。這是發給模型的措辭，按 AGENTS.md 要跑 Codex 的 `v01-placeholder`、`v01-needs`、`v03-auto` 自測；改的也有壓縮後放回的說明，還要跑 `v10-compaction`（結果見關卡 5、7）。
14. **Claude 的提示快取接得上**（公開評測發現，使用者 2026-11-01 定先修再發 0.10）：裝外掛的 Claude 會話按 API 價格折算約是不裝的兩倍（$0.069 對 $0.036），多在寫快取上：每組 7 到 9 次請求只命中系統提示，整段對話重寫。用評測留下的請求逐個對比查到兩個原因：
    - **斷點位置**：Claude Code 只在最後兩條訊息上放斷點，外掛換掉上一輪的圖後，這兩個斷點都在改動之後；Anthropic 往回找之前的快取，評測裡往回 6 個位置的也沒找到。改成引擎自己放訊息裡的斷點（`claude-cache.ts`，design.md 的“提示快取”）：在之前請求放過斷點、又在這次第一處改動之前的最後一個位置放一個（讀），在第一張以後會換掉的原圖前面放一個（備），Claude Code 最末那個儘量留著。
    - **佔位符和清單後來又變**：使用者隔幾輪才評價一張圖時，那張圖的佔位符（或壓縮後的清單）裡多出這條評價，從它起整段快取重寫。改成佔位符只帶這張圖出現那一輪及以前記下的評價，清單用壓縮那一刻的特徵和評價；之後記下的在模型自己的回覆裡，下一次壓縮再進清單（spec 的佔位符和清單兩條）。
    - 結果（Haiku 5.5，推理強度 low，每組一次）：只改第一條的第一版 $0.047、從快取讀 86%；改成記最近 4 次請求後 $0.065、78%，那一組模型每輪都晚一輪才寫特徵行，圖在下一輪中間才換掉，之前的斷點都用不上，於是加了“備”。最後這一版第一次跑時，在 5 小時額度暫停之後上游連不上，36 步都是 502（評測指令碼已改成連著兩次出錯就停）；2026-11-01 晚換了一個賬號再跑一次（使用者為省額度定只跑這一次，第 8 節第 8 條）：58 次請求全部正常返回，新的斷點放法沒被 API 拒；$0.047、從快取讀 87%，只命中系統提示的請求 1 次（不裝外掛 $0.036、91%、1 次）。沒走快取的輸入比其他組多約 2.4 萬 token，原因還沒查。按評測留下的請求離線模擬（斷點處的快取才算讀到，往回找 20 個位置），這一版從快取讀的比例比只用 Claude Code 的斷點高十幾個百分點，讀不到幾乎任何東西的請求從 14–17 次降到 3–5 次。

## 3. 要先驗證的事（關卡）

每個關卡通過了，才做對應的部分；沒透過，就回來和使用者商量。

1. **改接覆蓋到的格式**：`preservedSegment` 和 `preservedMessages`，新訊息接在保留訊息上、接在摘要上兩種形狀。用合成記錄，再加真實記錄回放（本機，結果只放 `local/`）：壓縮前的圖都認出來，編號和原始檔案一致。
   - 原型（2026-10-31，沒改外掛，只在記憶體裡改接後交給現有的索引程式碼）：一次真實壓縮從認出 0 張變成 94 張。
   - 結果（最終程式碼，2026-10-31 回放）：透過。那次壓縮認出 94 張；兩個真實會話（6 個、3 個記錄檔案）裡，同一張圖在每個檔案裡的編號都一樣（0 處不同）。
2. **往回接**：摘要裡的路徑、按壓縮點找、往回兩層、分叉、原檔案不在。真實回放：編號和原始檔案一致，特徵行一條不掛錯。
   - 原型：續接一層和兩層都接上了，壓縮前的圖編號、特徵行和原始檔案裡一樣。
   - 結果：透過。最長的會話 210 張圖，壓縮前的 127 張都接回來了，編號和原始檔案一致；抽查原來掛錯的特徵行，都回到了對的圖；17 個取回副本都認回原圖（原型裡有 9 張被當成新圖）。
3. **換算**：真實回放裡，換算過的特徵行中“寫下的輪次等於圖出現的輪次”的比例，不低於從沒被打亂過的那段，並且抽查無誤。
   - 原型：換算的 80 條裡 73 條一致；從沒被打亂過的那段是 103 條裡 71 條，不一致的都是晚了 1–4 輪才寫（後臺任務完成算新的一輪）。約 3 條（2%）明顯不對，要查清。
   - 結果：透過。換算過的 77 條裡 73 條寫在圖出現的那一輪，4 條晚 1–4 輪；從沒被打亂過的 103 條裡 71 條、晚的 32 條；沒有掛錯的。原型裡那 3 條“明顯不對”的，是同一個檔案前後看了兩次、模型兩次寫了一樣的特徵行，統計時按文字找到了前一次，不是換算錯。
4. **記憶體和時間**：最長的真實會話（9 個記錄檔案、219 張圖），引擎的堆記憶體比現在多不超過 80 MB；第一次建索引不超過 2 秒；之後每條請求的改寫，耗時不超過現在的兩倍。
   - 原型照原樣讀：堆記憶體從 83 MB 到 268 MB，多出的幾乎都是舊檔案裡的圖片資料，所以要改成用到時再從檔案讀（發原圖、取圖、面板縮圖時）。第一次建索引 1.7 秒，之後每條請求 9–12 毫秒（現在 6 毫秒）。

## 4. 做法

- **認記錄**（`claude-index.ts`）：
  - `activeChain` 照第 2 節第 1 條改接；
  - 往回接：找原記錄檔案、逐層接、記住找到的檔案；
  - 舊檔案裡的圖片資料不常駐記憶體：記下位置，用到時再讀；
  - 換算：找出同一會話的記錄檔案、判斷每條記錄行是哪個程序寫的，換算記錄行和取回副本前面那行字。
- **勾選**（`selection.ts`）：Claude 會話沒有自己的勾選時，找到上一個會話沿用。續接的，上一個會話是同一會話裡的上一個記錄檔案；分叉的，Claude Code 在複製過來的記錄裡留著原會話的 id。
- **Claude 的請求**（`proxy.ts`、`claude-rewrite.ts`）：壓縮後放回的那一段改成緊湊寫法，說明裡不再列全部圖。
- **Codex 的請求**（`proxy.ts`、`rewrite.ts`）：認出請求裡的壓縮項，找出壓縮之前、請求裡已經沒有的圖，放回壓縮項後面。
- **措辭**（`rewrite.ts`）：新增中英文的緊湊行和兩條說明；按第 2 節第 7 條改特徵行說明。
- **面板**不用改：它讀同一個索引，續接後的會話會重新列出壓縮前的圖，編號和原來一樣。做完截圖看一下。
- **更新時的過渡**：更新外掛後，開著的 Claude 會話要重開一次，因為舊程序裡的取圖工具還按舊編號找圖。寫進 CHANGELOG。
- **文件**：釋出時一起改 spec（核心概念、選擇規則、佔位符、Claude 一節的“壓縮之後”、非目標）、design（第 3、4、12 節）、CHANGELOG，以及 AGENTS.md 的入口。

## 6. 公開評測（使用者 2026-10-31 提議）

修完以後，在 `eval/` 加一個長任務的評測。現有的關鍵幀評測只有 9 張圖、Codex 一個平臺，它的“侷限”一節裡寫著長任務沒測，這次補上。用合成的會話和圖片，誰都能復現，不用使用者的真實會話。這一輪只測 Claude Code（使用者 2026-11-01 定）；Codex 由使用者自己上手體驗，評測裡只寫測了什麼。

- **怎麼跑**：命令列版 Claude Code，指令碼驅動，一個會話一個程序，像桌面版那樣一條條發訊息。用評測自己的配置資料夾（`CLAUDE_CONFIG_DIR`），使用者的技能、設定、記錄都不混進來；外掛用 `--plugin-dir` 載入，各組各用自己的引擎埠和資料資料夾。自動壓縮關掉，指令碼在兩個固定位置發 `/compact`（和使用者手打一樣），三組都在同一處壓縮；每次壓縮後接著問題。
- **三組**：不裝外掛、0.9.1、0.10（報告裡另列快取修復之前的 0.10，見第 2 節第 14 條）。0.9.1 的 mod 在 Claude Code 2.1.309 起不載入，對照組用只換上修好的 `register.js` 的 0.9.1（兩個版本的 mod 只差這一處），比出來的才是壓縮修復本身的效果。
- **模型**：Haiku 5.5，推理強度 low，每組跑一次。原來打算再加 Sonnet，以及 300 張、600 張兩檔看全量清單從多大規模開始不準；試跑算下來要用掉測試賬號一週額度的大半，使用者定先做簡單的一版（2026-11-01），規模的問題以後需要時再測。
- **場景**：在關鍵幀評測的基礎上加長。51 張合成圖、16 輪，有使用者直接發的（簡筆畫、重發的同一張），也有工具檢視的（代替生成的，省掉生圖費用）；有同一鏡頭的幾個版本、幾乎一樣的抽幀、三檢視、一批設定頁截圖、一次並行讀的一批；中間評價幾張，有說好的、說差的、改主意的、只說區域性的。
- **題目**照真實會話裡使用者的說法設計：一批裡的哪一張、按版本、按內容、按評價（含改了主意的）、按檔名；另有隻看原圖才答得出的細節題（角落裡的數字）、不需要看圖的題。壓縮後在原會話裡接著問，最後再分叉一次問幾題。
- **記錄**：答對幾題、取了哪幾張、取錯幾次、每條請求的 token、放回的清單佔多少。指令碼看著賬號的用量，一週額度到 90% 就停。
- **真實會話**：關卡 8 的長會話回放只寫數字（圖數、壓縮次數、題數和對錯、發現並修好的問題），註明素材不公開、不能復現；題目不寫，題目本身帶著使用者專案的內容。
- 指令碼放在 `spike/src/eval-*.ts`，報告放在 `eval/`，英文和中文各一份，寫明測試日期、外掛版本、Claude Code 版本、模型和推理強度、系統；README 底部的評測一節加一句連結。
