## 2. 桌面版連不上本地代理：原因與修復

**現象**：第一次接入後，桌面版每個請求都報 `error sending request for url (http://127.0.0.1:17891/...)`，代理一條請求都沒收到。

**原因**：
- 桌面版繼承的使用者環境裡有 `HTTP_PROXY` 和 `HTTPS_PROXY`，但沒有 `NO_PROXY`。
- Codex 預設按環境變數選擇代理，所以連發往 `127.0.0.1` 的請求也交給了系統代理，而系統代理不會把請求轉回本機。
- 我們一開始的自測沒有復現，是因為測試終端恰好帶著 `NO_PROXY`。

**修復**：
- 開啟 Codex 自帶的開關 `features.respect_system_proxy`（目前處於開發階段，預設關閉；http-client 的 README 說明它會成為以後的預設做法）。開啟後，Codex 先看 Windows 的代理設定。
- 代理地址改用 `localhost`。Windows 代理設定裡的 `<local>` 只會讓不帶點的主機名直連，所以 `localhost` 能直連，`127.0.0.1` 不行。
- 代理同時監聽 `127.0.0.1` 和 `::1`。

**復現與驗證**：自測時去掉 `NO_PROXY`，模擬桌面版的環境：
- 用 `127.0.0.1`，失敗，和桌面版一樣；
- 用 `localhost` 但不開這個開關，仍然失敗；
- 用 `localhost` 並開啟開關，成功；
- 修復後，桌面版的對話和上傳圖片都能正常經過代理。

## 3. 生圖、改圖失敗：Codex 版本問題

- 桌面版裡生圖和改圖的請求同樣到不了代理。Codex 日誌裡有 11 次生圖、22 次改圖報同樣的網路錯誤，這兩個數字都包括了自動重試。
- **原因**：桌面版自帶的 `codex-cli 0.155.0-alpha.16` 裡，生圖擴充套件用的是預設的 HTTP 客戶端，不遵守 `respect_system_proxy`。上游 [#47742](https://github.com/openai/codex/pull/47742)（2026-09-24 合併）修正了這一點：生圖和歷史筆記兩個擴充套件改為使用配置裡的客戶端工廠。
- **結論**：等桌面版更新到包含 #47742 的版本後，生圖和改圖應該也能經過代理，屆時要複測。如果想在這之前就能用，只有一個辦法：使用者自己在使用者環境變數里加 `NO_PROXY=localhost,127.0.0.1,::1`。這屬於系統層面的改動，也違背“免配置”，所以不作為產品方案。

## 4. 配置安全

- 配置工具只管理帶標記的兩段設定：
  - 檔案頂部的 `openai_base_url`；
  - `[features]` 表裡的 `respect_system_proxy`（沒有這張表時，改為頂部的 `features.respect_system_proxy`）。
- 每次修改之前都會把原檔案備份到本機的 `local/config-backup/`。
- **桌面版執行時也會寫 `config.toml`**。這次測試期間它寫入了三處：使用者切換的預設模型、電腦操控用的管道名、新任務所在資料夾的信任設定。所以恢復時只能刪掉我們自己的段落，絕不能用舊備份整體覆蓋。
- 已核對兩點：
  - 寫入和恢復前後，除我們的段落外檔案完全一致；
  - 測試結束後配置已恢復，檔案裡不留任何標記。

## 5. 其他發現

- **模型列表重新整理超時**：模型列表介面的響應約 500 KB，Codex 給它的超時是 5 秒，在這臺機器的網路下經常超時。Codex 自己的日誌顯示，接入代理之前的兩天，每天就有 50–66 次，所以這不是代理造成的，Codex 會改用本地快取的模型列表。
- **生圖、改圖不帶任務 ID**：`images/generations` 和 `images/edits` 請求不帶 `x-codex-turn-metadata`。以後如果需要按任務區分這類請求，要另想辦法；不過改寫只針對 `responses`，影響不大。
- **WebSocket 連線的任務歸屬**：WebSocket 的任務 ID 來自建連時的請求頭，一條連線會被同一個任務的多輪對話複用。
