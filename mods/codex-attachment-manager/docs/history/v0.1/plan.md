# 技術方案

> 目標、約束和驗收關卡以 [spec.md](../../spec.md) 為準。本檔案說明怎麼做、為什麼這樣做。第 1–8 節是階段 0 的設計（已完成，結果見 [phase0-report.md](phase0-report.md)）；第 9、10 節是代理路線的接入（P1）和按勾選改寫（P2），都已在桌面版驗證透過；第 11 節是正在做的面板（P3）。

## 1. 已知事實（2026-09-24）

### 驗證環境（Windows）

- Codex 桌面版：`OpenAI.Codex` 26.917.6896.0（MSIX）。它自帶的 CLI 位於 `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`，版本是 `codex-cli 0.155.0-alpha.16`。`<hash>` 會隨桌面版更新而變化。
- 驗證機上沒有執行中的 app-server 後臺服務（執行 `codex app-server daemon version` 連線失敗），所以桌面版目前不經過這個服務。
- `~/.codex` 裡和本專案有關的位置：
  - 會話記錄：`sessions/**/*.jsonl`
  - 執行緒歷史庫：`thread_history_*.sqlite`；另有 `state_*.sqlite`
  - 生成的圖片：`generated_images/`
  - 附件：`attachments/`（驗證機上目前只有文字附件）
  - 執行緒寫鎖：`thread-writer-locks/`
- 樣本任務的內聯圖片在 `sessions` 的 JSONL 記錄裡，該任務沒有對應的 `generated_images/<thread-id>` 目錄。它生成的 PNG 原件散落在使用者專案資料夾的多個子目錄裡；具體位置執行者已知，不寫進倉庫。所以索引器不能只掃一個目錄。
- 樣本 fork 在“只發文字”之後呼叫了看圖工具，把 4 張圖以內聯形式寫進了歷史，單條結果約 13.3 MB。（此條和上一條由 Codex 在驗證機上核實。）

### 上游 Codex（公開原始碼和 PR）

- 歷史圖片目前以內聯 base64 的形式儲存，每一輪都整包重新發送。0.156.0 已合入 `file_id` 引用和附件儲存（[#45794](https://github.com/openai/codex/pull/45794)、[#46065](https://github.com/openai/codex/pull/46065)），但 main 分支的 app-server 仍在用內聯儲存，而且已有的圖片不會被遷移。
- [#45794](https://github.com/openai/codex/pull/45794) 會拒絕“最近圖片裡含檔案引用”的改圖請求，所以改圖這條路必須實測。
- `thread/inject_items` 向執行緒追加原始 Responses 條目：條目進入模型可見的歷史，但不產生新的使用者輪次（見 [app-server 文件](https://developers.openai.com/codex/app-server)）。
- `postToolUse` hook 只能替換 MCP 工具的輸出，改不了內建的 `view_image` 和生圖。
- `codex app-server` 的相關能力：
  - 用 `-c key=value` 覆蓋配置；
  - 用 `--enable` / `--disable` 開關功能，例如 `view_image`；
  - 用 `generate-ts` 生成和本機版本一致的 TypeScript 型別。
- 按公開原始碼，模型發起的 MCP 呼叫會附帶執行緒和會話標識（[mcp_tool_call.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/mcp_tool_call.rs)）。本地 stdio 服務實際收到什麼，還沒有實測。

## 2. 兩條路線

### 路線 A：重建（首選，待驗證）

1. 只讀讀取原任務的歷史，建立素材索引。
2. 透過 app-server 新建任務，依次呼叫：
   - `thread/start`
   - `thread/inject_items`，注入按第 3 節規則搬過來的歷史
   - `thread/name/set`
   - `turn/start`，附上選中的圖
3. 之後使用者在桌面版裡繼續這個新任務。

### 路線 B：交接包（回退方案）

生成一份文字摘要，加一個裝有選中圖片的資料夾。使用者手動開新任務，貼入摘要並附上圖片。實現成本低，但連續性差。

### 怎麼選

> 階段 0 結果：關卡 1–6 全部透過，路線 A 在技術上可行。但使用者不接受“重建後在介面上看不到原對話”，所以沒有采用，改為驗證代理路線（第 9 節）。以下是階段 0 當時的規則。

- spec 階段 0 的關卡 1–6 全部透過：路線 A 作為首版主方案。
- 關卡 2 或 3 失敗：首版改用路線 B，路線 A 留作研究。
- 關卡 4 或 5 失敗：先當實現問題排查。如果確認是結構性原因（例如 app-server 會自動帶回未選的圖片），改用路線 B。
- 關卡 6 失敗：調整佔位符的措辭。這不影響路線選擇，但首版釋出前必須透過。

## 3. 路線 A 的搬遷規則

- **搬過去的內容**
  - 使用者訊息的文字；
  - 助手的 `message` 回覆；
  - 佔位符和重複引用，格式見 spec 的“佔位符”一節。
- **不搬的內容**
  - reasoning 條目：它們是加密的，不能保證在另一個執行緒裡可用；
  - 壓縮標記；
  - 原始的工具呼叫及其輸出。每次工具呼叫改寫成一行說明，例如“（此處 image_gen 生成了 IMG-005，提示詞：……）”。
- **圖片放在哪**
  - 注入的歷史裡只放佔位符，不放圖片。選中的圖片作為下一輪 `turn/start` 的附件傳送，並在該輪文字裡寫明“附件 1 = IMG-004”。
  - 這樣“勾選”和“重新勾選”走的是同一條路：都在下一輪作為附件傳送，不需要重建。這種方式也最接近改圖工具取“最近圖片”的方式。
- **磁碟上找不到原件的圖片**（只存在於記錄裡）：解碼後快取到本地工作目錄，作為附件的來源。快取只是副本，不寫回任何原始位置。
- **原任務做過壓縮時**：記錄壓縮條目的形態（是否可讀），並在報告裡說明搬的是哪一段歷史。
- **條目格式**：以 `generate-ts` 在本機生成的協議型別為準。

## 4. 防止圖片再次堆積

在新任務裡，模型自己呼叫 `view_image` 之類的工具時，仍會把圖片以內聯形式寫回歷史，樣本 fork 就是這麼變大的。

階段 0 做一個附加實驗：用 `--disable view_image`，或在 `thread/start` 裡用配置覆蓋，關掉看圖工具，記錄這樣是否可行、對流程有什麼影響。首版方案按實驗結果再定。

## 5. 測量方法

- **請求位元組數**：調高我們自己啟動的 app-server 的日誌級別，從日誌裡讀出請求體大小。上游的日誌裡出現過 `pre_compression_bytes=... post_compression_bytes=...` 這類記錄，具體用哪個日誌開關由執行者查證。
- **歷史構成**：只讀檢查新任務的記錄，統計內聯圖片的數量和位元組數，確認裡面沒有未選的圖片。
- **原始檔案不變**：操作前後分別計算樣本記錄檔案和相關素材檔案的雜湊，然後對比。
- **估算值**：注入文字的位元組數，加上選中圖片轉成 base64 後的位元組數，與實測的請求位元組數對比。

## 6. 安全措施

- **用同一個 codex**：獨立的 app-server 用桌面版自帶的那個 `codex.exe` 啟動，避免狀態庫遷移不一致。如果版本對不上，先停下報告。
- **先備份**：第一次透過 app-server 建立任務前，用 SQLite 線上備份（只讀開啟源庫）給 `state_*.sqlite` 和 `thread_history_*.sqlite` 生成一致的副本，放進本地工作目錄 `local/`（已被 git 忽略）。
- **測試任務加字首**：測試用的新任務，名稱統一加字首 `[CAM測試]`，方便使用者識別和歸檔。
- **先釋放寫鎖**：在桌面版裡開啟新任務之前，先結束我們的 app-server 程序，釋放執行緒寫鎖。
- **不改使用者配置**：不修改使用者的 `config.toml`。需要的配置用命令列的 `-c`、`--disable`，或 `thread/start` 裡的配置覆蓋。
- **不碰認證資訊**：不輸出、不記錄認證資訊（例如 `auth.json` 的內容）。
- **沙箱許可權**：獨立的 app-server 需要聯網和寫入 `~/.codex`，可能被 Codex 沙箱攔下。遇到這種情況，請使用者批准提權，或者由使用者在普通終端裡執行。

## 7. 關鍵決策

| 決策 | 原因 |
|---|---|
| 不改原生任務，改為在新任務中繼續 | 官方沒有刪除歷史條目的介面；直接改記錄檔案不安全 |
| 路線 A 優先於只交接摘要 | 保留完整的對話文字，連續性更好 |
| 只搬文字和佔位符，不搬 reasoning 和工具記錄 | 加密條目和呼叫配對不可靠，工具記錄還可能夾帶大塊內容 |
| 選中的圖作為下一輪的附件傳送 | 一套機制同時覆蓋勾選和重新勾選，也貼近改圖工具的取圖方式 |
| 改為驗證代理路線 | 使用者要求在同一個任務裡勾選、取消檔案時對話連續可見，重建路線做不到 |
| 面板優先放進 Codex 對話（MCP Apps），做不到再做跟隨視窗的外接面板 | 使用者 2026-09-24 決定；對話內卡片在 Windows 上仍有渲染問題，需要先驗證 |
| 新圖預設勾選，包括內容相同的副本 | 使用者 2026-09-24 決定：裝了工具但不取消任何圖時，表現和沒裝一樣 |
| 每條出現記錄單獨編號、單獨勾選，內容相同的另外標出 | 使用者要能只取消副本、保留原圖；模型說“需要 IMG-007”時只對應一條 |
| 編號只由本地記錄決定，命令列（以後是面板）和代理各自計算 | 兩邊不用共享狀態，編號也不會對不上 |
| 取消了圖的任務改走 HTTP | WebSocket 只發新增條目，已發的圖留在服務端；426 是 Codex 自己的回退路徑 |
| 改寫不了就原樣傳送，並記下原因 | 寧可多發，也不讓對話中斷；面板要把這種情況顯示出來 |
| 代理跟著 Codex 一起啟動、一起退出 | 使用者 2026-09-24 確認；配置指向代理而代理不在時，Codex 連不上。做法待驗證，候選是讓 Codex 自己啟動的外掛本地服務順帶執行代理 |
| 首版只做單個任務、只做圖片 | 全量掃描很重；圖片是當前的痛點 |
| 用 TypeScript/Node | 驗證機已有 Node 24；能生成官方協議型別；面板也用同一種語言 |

路線由第 9 節的驗證結果決定，定下來之後再補首版架構和首版任務。

## 9. 代理路線（驗證中）

### 思路

在 Codex 和 OpenAI 之間放一個只在本機監聽的代理。

1. Codex 照常把完整請求發給代理；
2. 代理按這個任務當前的勾選，把沒選的圖換成佔位符，再轉發出去；
3. 回覆原路返回，由 Codex 照常記進同一個任務。

任務不換，歷史和介面都不動，勾選和取消從下一次請求起生效。

### 接入方式（已查證）

- **地址覆蓋**：`config.toml` 頂層的 `openai_base_url` 可以覆蓋內建 openai 通道的地址，ChatGPT 登入模式下同樣生效。改了地址後，任務的歸屬仍然是 openai。
- **路徑字尾**：地址必須以 `/backend-api/codex` 結尾，否則 Codex 會關掉後端專用的介面。所以代理地址用 `http://localhost:<埠>/backend-api/codex`（為什麼不用 `127.0.0.1`，見下文），代理再把同樣的路徑轉發到 `https://chatgpt.com`。
- **經過的介面**：對話走 `…/responses`，預設用 WebSocket，失敗時回退到 HTTP；生圖、改圖走同一個通道的 `…/images/generations` 和 `…/images/edits`。
- **認出任務**：每個請求的請求頭裡都有 `x-codex-turn-metadata`（其中有 thread_id、turn_id），請求體裡還有 `prompt_cache_key`，代理據此認出請求屬於哪個任務。
- **系統代理**：我們的代理往外連 chatgpt.com 時，自動沿用系統代理設定（環境變數或 Windows 設定），不需要使用者填寫。
- **Codex 連本地代理（P1 實測）**：
  - Codex 預設按環境變數選擇代理。使用者環境裡有 `HTTP(S)_PROXY`、沒有 `NO_PROXY` 時，連本地地址的請求也會被交給系統代理，然後失敗。
  - 所以要同時開啟 `features.respect_system_proxy`，讓 Codex 先看 Windows 的代理設定，並把地址寫成 `localhost`：Windows 設定裡的 `<local>` 只讓不帶點的主機名直連。
  - 生圖和改圖要等 Codex 包含 #47742 的版本才會遵守這個開關。上游從 `0.158.0-alpha.8` 起包含；桌面版 26.917（自帶 `0.155.0-alpha.16.4`）還沒有，而且檢查更新顯示已是最新。在此之前，環境變數裡有代理、又沒有 `NO_PROXY` 的使用者，開著代理時不能生圖和改圖。詳見 [p1-report.md](p1-report.md)。
- **不等更新的辦法（使用者 2026-09-24 同意；P2-6 在桌面版驗證透過）**：
  - Codex 每次啟動都會讀 `$CODEX_HOME/.env`，把裡面的變數設進自己的程序（`CODEX_` 開頭的除外，見原始碼 `arg0` 的 `load_dotenv`）。
  - 生圖模組用的預設客戶端認 `NO_PROXY`（P1-3 已實測）。所以在 `.env` 裡寫 `NO_PROXY=localhost,127.0.0.1,::1`，生圖和改圖不等 #47742 也能連到本地代理。
  - 使用者自己設過的 `NO_PROXY` 條目會合並進來，因為 `.env` 裡的值會在 Codex 程序裡替換掉原來的值。`.env` 裡已經有使用者自己的 `NO_PROXY` 時，不覆蓋，直接報告。
  - 仍然保留 `respect_system_proxy`：讀取 `.env` 這一行為沒有寫進官方文件，保留它，對話能不能連上就不依賴 `.env`。萬一以後的版本不再讀 `.env`，最壞的結果也只是生圖和改圖暫時連不上；而那些版本本來就已經包含 #47742。
  - 影響範圍只有 Codex 自己的程序和它啟動的工具，而且只涉及本機地址。留下這一段也無害：它只讓本機請求直連，不會像 `openai_base_url` 那樣在代理不在時讓 Codex 連不上。
  - 產品裡只在需要時寫入：桌面版的 Codex 還沒有 #47742，而且使用者的代理設定會攔住發往本機的請求。Codex 更新後自動刪掉。
- **元資料差異**：地址不是官方域名時，Codex 會去掉請求裡附帶的原始工具結果元資料（`executed_tool_calls` 裡的 `tool_result_metadata`）。這是隨請求上報的內部元資料，不是模型看到的內容。

### P1：只轉發、不改寫

- **轉發**：原樣轉發 HTTP 請求和 WebSocket 連線，不改動任何位元組，結果按流式返回。
- **日誌**：只記元資料，包括方法、路徑、狀態碼、位元組數、耗時、任務 ID，以及請求裡的圖片數量和位元組數。不記認證資訊，也不記對話內容。
- **配置**：
  - 工具管理兩段帶標記的設定：頂層的 `openai_base_url`，以及 `[features]` 裡的 `respect_system_proxy`（沒有這張表時，改為頂層的 `features.respect_system_proxy`）；
  - 改之前把原檔案備份到 `local/`；
  - 恢復時只刪掉帶標記的段落。桌面版執行時自己也會寫 `config.toml`，所以絕不能用舊備份整體覆蓋；
  - 使用者自己設過 `openai_base_url`，或者把 `respect_system_proxy` 設成了 false，一律不覆蓋，直接報告。
- **驗證順序**：
  1. 先用我們自己啟動的 app-server 走一遍：文字、附圖、生圖、改圖。這一步用 `-c openai_base_url=…` 指定地址，不改配置。
  2. 再改桌面版的配置。使用者重啟桌面版後，在任務裡依次發文字、上傳圖片、讓它生圖、讓它改圖。
  3. 看代理日誌，確認這些請求都經過了代理並且成功，不同任務的請求各自帶著自己的任務 ID。
- **風險**：代理沒在執行時，Codex 會連不上。驗證期間代理一直開著；驗證結束後恢復配置，或者由使用者決定是否保留。

P1 通過後，再按使用者的節奏一步步探索改寫。

## 10. 按勾選改寫（P2）

### 已查證的 Codex 行為

依據桌面版自帶的 `0.155.0-alpha.16.4` 的原始碼，以及 P2-1 的抓包：

- **WebSocket 和 HTTP**：
  - WebSocket 連線上，Codex 只發新增的條目，靠 `previous_response_id` 接上服務端儲存的歷史。代理沒法在這條連線上去掉已經發過的圖。
  - HTTP 每次都發完整歷史。
  - WebSocket 握手收到 426 時，Codex 立即改走 HTTP，並在這個會話裡一直走 HTTP，不報錯、不重試。
  - 快取的 WebSocket 連線被關掉後，下一次請求會重新握手。
- **圖片在請求裡的位置**：
  - 使用者上傳：使用者訊息裡依次是 `<image name=[Image #N] path="…">`、圖片、`</image>` 三段。
  - 工具檢視和生成：Codex 的工具都經 `exec`（程式碼模式）呼叫，圖片在 `custom_tool_call_output` 的輸出裡。檢視的檔案路徑寫在呼叫程式碼裡；生成的圖後面跟著一段說明儲存路徑的文字。
  - 託管生圖的結果（`image_generation_call.result`）是必填欄位，換不成文字。
- **條目編號**：請求裡的訊息和工具輸出，帶著和本地記錄完全相同的 `id`，以及所在輪次的 `turn_id`。所以本地記錄和請求能按條目對上，不受歷史壓縮和位置變化的影響。
- **改圖取圖**：改圖工具從 Codex 本地的歷史取最近的圖，不看代理發出的內容，所以取消勾選不影響改圖。
- **壓縮**：遠端壓縮（v2）走同一個 `/responses` 介面，同樣會被改寫。
- **請求體**：zstd 壓縮的 JSON。實測 `JSON.parse` 再 `JSON.stringify` 能逐位元組還原。

### 設計

- **編號**：從任務的本地記錄（rollout，只讀）裡按順序找出所有圖片出現記錄，依次編號 IMG-001、IMG-002……
  - 編號只由記錄內容決定，命令列（以後是面板）和代理各自讀取，結果一致。
  - 記錄只會追加，所以已有的編號不變。代理按檔案增量讀取，只解析新增的行。
  - 分叉任務的前半段歷史在父任務的記錄檔案裡，要沿 `history_base` 跨任務讀取。
  - 工具檢視的圖，如果路徑是經變數傳進去的，就取不到檔名；這時借用內容相同、有名字的那一張的名字。
- **識別鍵**：條目 `id` 加圖片在條目裡的序號；沒有 `id` 時用 `call_id`；兩者都沒有時，用型別、輪次和內容雜湊。
- **內容相同**：先比較 base64 內容的雜湊，再比較 PNG 解碼後的畫素雜湊。
- **勾選狀態**：每個任務一個檔案，只記被取消的識別鍵。驗證階段放在 `local/selection/`；產品裡放在工具自己的資料目錄，不寫進 `~/.codex`。
- **改寫**：只處理有取消項的任務的 `/responses` 請求。步驟是解壓、解析、替換、重新壓縮，然後轉發。
  - 替換規則見 spec 的“佔位符”。
  - 使用者上傳的圖，連同前後兩段路徑標籤，一起換成一段文字。
  - 沒有需要替換的圖時，原樣轉發原始位元組。
- **切換到 HTTP**：
  - 任務一有取消項，代理就對它的 WebSocket 握手回 426；
  - 它已有的 WebSocket 連線，空閒 1.5 秒後由代理關掉；
  - 從下一次請求起，這個任務在當前會話裡一直走 HTTP；
  - 沒有取消項的任務照常走 WebSocket。
- **原樣放行**：下面幾種情況原樣轉發，並記下原因：
  - 請求解不開，或者解析失敗；
  - 含有 JavaScript 表示不了的大整數；
  - 找不到本地記錄；
  - 改寫出錯。

  託管生圖的結果無法替換，所以命令列不允許取消它。
- **日誌**：只記編號、型別、佔位符種類、大小，以及圖片內容雜湊的前 16 位。不記檔名，不記對話內容。
- **除錯抓包**：`--dump-requests` 把請求存進 `local/`，圖片只留雜湊和長度。只用於合成的測試任務。

### 驗證順序

1. P2-1 抓包：用合成圖片覆蓋上傳、工具檢視、生成三種來源，確認上面的請求結構。
2. P2-2 到 P2-4：識別、編號、改寫，並接入代理，配單元測試。
3. P2-5 自測：用我們自己啟動的 app-server，環境和桌面版一致（去掉 `NO_PROXY`、開啟 `respect_system_proxy`、地址用 `localhost`）。在同一個任務裡依次上傳、取消、詢問、重新勾選、再詢問、全部勾選。
4. P2-6 桌面版驗證【需使用者】。

### 已知限制

- 取消勾選時，如果這個任務正在一輪對話中間，而且還在用 WebSocket，這一輪剩下的請求可能仍帶著原圖。從下一輪起一定生效。
- 生圖和改圖：當前版本要靠 `.env` 裡的 `NO_PROXY` 才能經過代理，見第 9 節“不等更新的辦法”。
- 桌面版會在使用者訊息裡附一段 “Files mentioned by the user”，寫著上傳檔案的完整路徑。代理不改這段使用者訊息的文字，靠佔位符裡“不要自己用工具去讀取”的要求約束模型；P2-6 裡模型遵守了。

## 11. 面板（P3）

### 已查證的事實

依據桌面版自帶的 `0.155.0-alpha.16.4` 的原始碼、上游 issue 和本機檢查：

- **對話裡的介面（MCP Apps）**：
  - 工具在自己的說明裡用 `_meta.ui.resourceUri` 指向一個 `ui://` 頁面；模型呼叫這個工具時，桌面版在對話裡顯示這個頁面。
  - `_meta["openai/ui"].preferredModelDisplayMode` 可以選 `inline`（嵌在對話裡）或 `fullscreen`（全屏）。
  - 頁面的型別是 `text/html;profile=mcp-app`，在沙箱裡執行，透過 postMessage 和桌面版握手，再經桌面版回撥同一個服務的工具。
  - 介面資訊會存進聊天記錄，重啟後不用重新查詢外掛也能顯示出來。
- **已知問題（上游未修）**：
  - [#47512](https://github.com/openai/codex/issues/47512)：Windows 上頁面偶爾整塊空白，都出現在頁面地址變化之後。所以頁面地址要保持固定。
  - [#45913](https://github.com/openai/codex/issues/45913)：頁面訪問不了 `http://localhost`，即使列進了 CSP。所以面板只經桌面版回撥外掛服務拿資料，縮圖用 data URL。
- **外掛格式**：`.codex-plugin/plugin.json` 可以帶技能（skills）、MCP 服務（`mcpServers`）和鉤子（hooks）。鉤子事件有 `SessionStart`、`UserPromptSubmit` 等，可以執行命令。
- **接入配置**：`config.toml` 的 `[mcp_servers.<名字>]` 寫啟動命令；`default_tools_approval_mode = "approve"` 讓它的工具不用逐次確認。
- **桌面版的程式**：OpenAI.Codex 安裝目錄下的 `ChatGPT.exe`，視窗標題是“ChatGPT”。截圖指令碼 `spike/scripts/capture-codex.ps1` 按安裝目錄找這個視窗，只截它。

### P3-1 實測結果（2026-09-24，桌面版 26.917）

- 面板能用：出現在 Codex 右側的側欄裡，帶標籤頁。靜態頁面、data URL 小圖、和桌面版的握手、回撥外掛服務，全都成功。
- 頁面訪問 `localhost` 被 CSP 攔截，和 #45913 一致。
- 桌面版兩套介面都提供：MCP Apps 的 `ui/*` 訊息，以及 Apps SDK 的 `window.openai`（有 `callTool`、`setWidgetState`、`requestDisplayMode` 等）。
- 工具結果會原樣送到頁面；面板回撥工具時，桌面版會在 `_meta` 裡帶上當前任務的 `threadId`，所以面板天然知道自己屬於哪個任務。
- 外掛服務是按會話啟動的：桌面版啟動時拉起了 6 個例項，其中 5 個很快被結束，當前任務那一個一直在執行，面板的回撥也由它處理。
- 外掛服務的工具不會直接列給模型，要在程式碼模式裡搜尋才能找到；gpt-6-sol 第一次沒找到，點名工具後才打開。每次開啟還要花一輪請求。所以面板不能靠模型來開啟。
- 自己加的鉤子預設是“未信任”，要使用者在 Codex 介面裡批准一次才會執行；外掛服務則由 Codex 直接啟動，不用批准。

### 設計

先把核心做完、測穩，再做介面（使用者 2026-09-24 決定）。

- **引擎**：就是代理程序，全機只執行一個（佔用埠即表示已在執行）。
  - 負責改寫請求，並把每個任務最近一次請求的統計寫進狀態檔案：大小、哪些圖發了、哪些圖被替換。
  - 定時檢查 Codex 程序，Codex 全部退出後自己退出。
- **外掛服務**：由 Codex 啟動。
  - 啟動時確保引擎在執行，之後每隔幾秒再檢查一次；引擎崩了會自動拉起。
  - 同時給面板提供資料：圖片列表、縮圖、勾選和取消、傳送預覽、模型索要的編號。
  - 它和引擎之間只通過檔案共享狀態，任何一方不在，另一方都照常工作。
- **不用鉤子**：外掛服務本來就由 Codex 啟動，不用使用者批准，比鉤子更適合做啟動器。
- **安裝和恢復**：一個命令寫好全部帶標記的配置（代理地址、`respect_system_proxy`、外掛服務，需要時加 `.env`），一個命令全部恢復。
- **介面**：見第 12 節。做成右側側邊面板裡的 MCP App，使用者從“新建標籤頁 → 外掛和 MCP”手動開啟（P4 已完成）。

### 驗證順序

1. P3-1 試驗面板（已完成，結果見上）。
2. P3-2 引擎：全機單例項、確保執行（ensure）、Codex 退出後自動退出、記錄每個任務最近一次請求的統計。
   - 實測（P3-5）：Codex 會把外掛服務和它拉起的程序一起管理，引擎隨拉起它的那個外掛服務例項一起結束；其他例項的看門狗（每 3 秒）會重新拉起，所以最多斷開 3 秒。這也讓“隨 Codex 退出”自動成立。要徹底避免斷開，可以改用 Windows 計劃任務啟動引擎，但需要使用者同意在系統裡註冊任務，暫不做。
3. P3-3 外掛服務：啟動器和看門狗，加上面板的資料工具。
4. P3-4 安裝和恢復命令。
5. P3-5 穩定性自測：多個任務同時用、歷史壓縮、引擎中途重啟、Codex 退出後引擎自動退出、分叉任務。
6. P4 介面，做到關鍵節點截圖給使用者看；P5 打包成外掛、寫說明。

## 12. 面板（P4）

### 已查證的事實

依據桌面版 26.917 的前端程式碼，以及 P4 實測：

- **不經過模型的入口**：工具可以在 `_meta["openai/ui"].entrypoints` 裡宣告入口，工具同時要用 `_meta.ui.resourceUri` 指向一個 `ui://` 頁面。入口有四種：
  - `thread`：出現在任務右側側邊面板的“新建標籤頁 → 外掛和 MCP”裡；
  - `global`：出現在左側導航欄；
  - `settings`：出現在設定裡；
  - `file`：按副檔名開啟檔案。
  - 列表裡顯示的名字是工具的 `title`，圖示取自外掛服務 `serverInfo.icons`，只收 https 或 data URL，可以分淺色和深色。
- **開啟後**：
  - 桌面版先讀頁面資源，再用當前任務的編號呼叫這個工具，把結果交給頁面。頁面之後的工具呼叫也帶著這個任務的編號（`_meta.threadId`）。
  - 這些呼叫不寫進聊天記錄，不佔模型的上下文（P4 實測：任務記錄裡沒有一條面板呼叫）。
  - 工具結果的 `_meta` 會原樣交給頁面，所以圖片資料放在 `_meta` 裡。
- **主題**：握手時，桌面版會傳來主題（light/dark）和一組樣式變數，包括顏色和字型，例如 `--color-background-primary`、`--color-text-primary`、`--font-sans`。頁面用這些變數，就和 Codex 的外觀一致。
- **標題欄**：沒有給外掛的入口。

### 設計

- **入口工具**：`cam_panel`，標題“上下文素材”，宣告 `thread` 入口，頁面固定為 `ui://codex-attachment-manager/panel.html`（地址變了可能白屏，見 #47512）。它和其他面板工具一樣只給面板用（`visibility: ["app"]`）。
- **頁面**：`spike/src/panel.html`，單檔案，不聯網。
  - 按輪次列出任務歷史裡的圖；縮圖排隊載入，看得見的優先；點開後預覽大圖。
  - 每次勾選或取消都立即呼叫 `cam_set_selection` 儲存（v0.1-22 起；之前是先暫存，點“確定”才儲存）。點選馬上顯示，儲存進行中的點選合併到下一次呼叫；讀的過程中開始了儲存，這次讀到的結果就不用，免得舊狀態蓋掉剛點的。
  - 每 3 秒重新整理一次，沒有變化就不重畫。頁面報告自己不可見時降到 15 秒一次，因為有的宿主會誤報。
- **取圖**：`cam_image`。PNG 超過要求的尺寸就縮小，其他格式原樣交給頁面，由瀏覽器縮放。
- **開發頁**：`spike/scripts/panel-dev.ts` 在瀏覽器裡扮演 Codex 的側邊面板，用合成測試圖調通頁面，不用重啟 Codex。頁面上的“切換明暗”“加一張圖”只用來模擬 Codex 的操作，不會出現在 Codex 裡。

## 13. 打包成外掛（P5）

### 已查證的事實

依據桌面版 26.917、它自帶的命令列 0.155，以及它自帶的外掛：

- **外掛**：外掛目錄裡放 `.codex-plugin/plugin.json`。
  - 欄位有 name、version、description、author、homepage、repository、keywords；`mcpServers` 指向 `.mcp.json`。
  - `interface` 裡有 displayName、shortDescription、longDescription、developerName、category、capabilities、brandColor、logo、composerIcon。
- **`.mcp.json`**：
  - 服務的 command、args、cwd（`.` 表示外掛目錄）、default_tools_approval_mode、startup_timeout_sec；
  - `env_vars` 是一張白名單，列出允許傳給服務的環境變數。
- **外掛市場**：一個目錄裡的 `.agents/plugins/marketplace.json`，列出其中的外掛和它們的相對路徑。
- **命令列**：
  - `codex plugin marketplace add <本地路徑、owner/repo 或 Git 地址>`、`codex plugin add <外掛>@<市場>`、`codex plugin remove`、`codex plugin marketplace remove`；
  - 安裝會把外掛目錄複製到 `~/.codex/plugins/cache/<市場>/<外掛>/<版本>/`，並在 config.toml 裡寫 `[marketplaces.<市場>]` 和 `[plugins."<外掛>@<市場>"]`。
- **桌面版自帶的東西**：
  - 命令列在 `%LOCALAPPDATA%\OpenAI\Codex\bin\<版本號>\codex.exe`；
  - 自帶 Node 24，能直接執行 TypeScript。自帶外掛用一個 .cmd 啟動指令碼按順序找這個 Node。
- **重啟才生效**：正在執行的桌面版不會立即載入新裝的外掛。

### 設計

- **目錄**：
  - `plugin/` 是外掛本體：清單、`.mcp.json`、`scripts/launch.cmd`、`src/`；
  - 倉庫根目錄的 `.agents/plugins/marketplace.json` 指向它；
  - `spike/` 留測試和實驗指令碼。
- **啟動**：
  - `.mcp.json` 用 `cmd.exe /d /s /c call ./scripts/launch.cmd ./src/plugin-server.ts` 啟動外掛服務，`launch.cmd` 優先用 Codex 自帶的 Node（v0.1 起改成三個平臺通用的 `./scripts/launch`，見第 14 節）；
  - 根目錄的 `cam.cmd` 用同一個指令碼執行命令列，使用者不用另裝 Node。
- **資料目錄**：`%LOCALAPPDATA%\codex-attachment-manager`（v0.1-15 起改為 `%USERPROFILE%\.codex-attachment-manager`，見第 17 節）。外掛目錄會在更新時被 Codex 替換，而且不往 `~/.codex` 裡寫。
- **安裝順序**：
  1. 檢查和使用者自己設定的衝突，然後備份 config.toml；
  2. 登記市場，裝外掛（每次都重灌，讓 Codex 的副本和倉庫一致）；
  3. 自檢裝好的副本：用它自己的啟動指令碼起服務，問工具列表和麵板頁面；
  4. 寫代理設定；
  5. 遷移舊的勾選記錄，確保引擎在執行。
- **解除安裝順序**：先去掉代理設定，恢復直連；再卸外掛、去掉市場。
- **已知風險**：只在外掛頁面關掉外掛、不執行 uninstall，Codex 會連不上，見 spec.md 第 5 節。

## 14. 釋出準備（v0.1）

### 已查證的事實

依據 Codex 的公開原始碼（codex-rs）、官方文件、桌面版 26.917 的前端程式碼，以及 CI 上 npm 版命令列 0.157.0 的實測：

- **三個平臺都有桌面版**：Linux 版 2026-08 起預覽，包名 `chatgpt`。macOS 桌面版的命令列在 `<app>/Contents/Resources/codex`；Codex 自己的安裝指令碼把命令列放在 `~/.local/bin/codex`。桌面版會把 `CODEX_CLI_PATH`、`CODEX_ELECTRON_RESOURCES_PATH` 傳給外掛服務。
- **外掛服務怎麼啟動**：
  - Windows 上用 `which` 按 PATHEXT 解析命令，所以 `./scripts/launch` 會找到 `launch.cmd`；
  - macOS、Linux 上直接執行命令，並放進新的程序組；
  - 外掛的 `cwd` 按外掛目錄解析。OpenAI 自帶外掛也是同一套：一個無副檔名的 POSIX 指令碼，加一個同名的 `.cmd`。
- **Windows 的 Job**：外掛服務在一個“關閉即結束、不許脫離”的 Job 裡，它啟動的引擎也在裡面，服務一結束引擎就跟著結束。所以外掛被移除後，Windows 上沒有我們的程序還能收尾。macOS、Linux 上引擎用 `setsid` 脫離了程序組，會留下來。
- **桌面版的外掛頁面能新增外掛市場**：來源可以是 GitHub 倉庫（`owner/repo`）、Git 地址或本地資料夾，可選 Git ref。所以使用者可以完全不開終端：新增市場、裝外掛，再在面板裡啟用。
- **Windows PowerShell 5.1**：`irm … | iex` 把 GitHub 釋出檔案按 Latin-1 解碼，腳本里的中文會亂碼，所以兩個 `.ps1` 只用 ASCII。
- **Windows 上的控制代碼繼承**：Node 在 Windows 上啟動子程序時，子程序會繼承父程序可繼承的控制代碼。所以引擎會拿著啟動它的指令碼的輸出管道；只有測試會因此多等，使用者不受影響。

### 設計

- **一份 `.mcp.json` 通用三個平臺**：命令寫 `./scripts/launch`，`scripts/launch`（POSIX，可執行位，LF）和 `scripts/launch.cmd` 按同樣的順序找 Node：
  1. Codex 傳來的路徑；
  2. 桌面版資源目錄裡的 `cua_node`；
  3. primary runtime；
  4. PATH 上 24 以上的 `node`。
- **平臺差異**：
  - 程序檢測：Windows 用 `tasklist`，其他平臺用 `ps` 按可執行檔名 `codex` 統計；
  - 系統代理：Windows 讀登錄檔，macOS 讀 `scutil --proxy`（只認 HTTP(S) 代理），Linux 只看環境變數；
  - 資料目錄：macOS 在 `~/Library/Application Support`，Linux 按 XDG。
- **升級時替換引擎**：引擎報告 build（執行目錄裡 .ts 檔案的雜湊，換行統一成 LF）和版本。外掛服務發現程式碼不同、版本不低，就請舊引擎退役：
  - 舊引擎立刻停止監聽，放掉空閒連線，把正在進行的請求和 WebSocket 這一輪做完再退出；
  - 新引擎馬上接手埠。
- **啟用、停用**（`setup.ts`，命令列、面板和引擎共用）：只增刪帶標記的塊，改之前備份 config.toml，整檔案寫好再替換。
  - 面板的 `cam_setup` 只接受面板的呼叫；
  - 啟用、停用都要重啟 Codex 才生效，面板會提示。
- **外掛被移除或關掉、沒先停用**：
  - 引擎每 15 秒檢查一次，判斷依據只用明確的跡象：外掛快取目錄不在了，或者 config.toml 寫著 `enabled = false`；
  - 連續兩次，或者引擎退出前再查一次，就恢復直連；
  - 在 Windows 上這一步通常來不及（見上面的 Job），所以面板、外掛說明和 README 都寫“先停用再移除”，解除安裝命令負責恢復。
- **安裝路徑**：
  - 外掛頁面：新增市場 `chipfighter/codex-attachment-manager` → 裝外掛 → 面板裡啟用 → 重啟；
  - 一行命令：`install.ps1` / `install.sh` 用 Codex 的命令列裝外掛，再執行裝好的副本里的 `cam.ts setup`；
  - 解除安裝：`uninstall.ps1` / `uninstall.sh` 不需要 Node 和外掛檔案，先按同樣的規則去掉帶標記的塊，再卸外掛和市場。
- **釋出**：推送 `v<版本>` 標籤後，Release 工作流先在三個平臺跑 CI，再核對標籤和外掛版本一致，然後把標籤寫進四個指令碼，建一個草稿 Release。說明取自 CHANGELOG.md。人工看過再發布。
  - 三個平臺共用同一個外掛，只有安裝指令碼分平臺；
  - `releases/latest/download/<指令碼>` 始終指向最新的釋出。
- **驗證**：
  - `spike/src/plugin-smoke.ts`：Codex 自己的命令列裝外掛，app-server 開任務，外掛服務就緒，引擎啟動；
  - `spike/src/scripts-smoke.ts`：真的跑安裝、解除安裝指令碼，config.toml 和 .env 恢復原樣；
  - CI 在 Windows、macOS、Linux 上都跑這兩項和全部單元測試。

## 15. 面板和任務的對應（v0.1-9 到 v0.1-11）

### 已查證的事實

依據桌面版 26.917 的前端程式碼、Codex 的公開原始碼（codex-rs）和使用者 2026-09-25 的實測：

- **側邊面板按任務儲存**：每個任務各記自己的面板開沒開、有哪些標籤頁、哪個在前面。切到沒開過面板的任務，面板是關的；切回來，原來的標籤頁還在。一個任務可以開好幾個標籤頁。
- **面板裡的呼叫帶著固定的任務編號**：面板每次呼叫外掛，帶的都是它被開啟時所在任務的編號，之後不會變。
- **新任務頁面**：在這裡開啟的面板，綁在 Codex 預先準備的任務上。發第一條訊息時，Codex 可能丟掉這個預備任務、另開一個，並把標籤頁帶到新任務上，但面板裡的編號不變（v0.1-8）。
- **分叉**：Codex 分叉時會把原任務的側邊面板佈局複製過去。使用者實測：在分叉裡新開的面板綁在分叉上，勾選按第 1 節的規則繼承。
- **任務名**：在 `<CODEX_HOME>/session_index.jsonl` 裡，每行 `{id, thread_name, updated_at}`。名稱只追加，同一個任務以最後一行為準；Codex 刪除某個任務的名稱時，會整個檔案重寫。
- **任務來源**：任務記錄的第一行（`session_meta`）寫明：
  - `source`：`cli`、`vscode`、`exec`、`mcp`，或者 `{subagent: …}`、`{internal: …}`；
  - `thread_source`：`user`、`subagent`，或者某個功能的名字；
  - `forked_from_id`、`parent_thread_id`。
  - 帶歷史啟動的子代理，Codex 也記成從父任務分叉（`forked_from_id` 是父任務）。
- **每個任務各有一個外掛服務程序**。所以分叉出來的任務第一次開面板時，外掛服務是新起的，記憶體裡的快取是空的。
- **任務記錄的存放**：放在 `sessions/YYYY/MM/DD`，按任務建立那天的本地日期分目錄。新任務、分叉和長任務的後續分頁，都落在當天的目錄裡。
- **記錄第一行的時間**：每行開頭的 `timestamp` 是寫入這一行的時間。新任務的記錄是發第一條訊息時才寫的，所以第一行的時間就是任務開始的時間。
- **歸檔的任務**：使用者歸檔任務後，Codex 把它的記錄挪到 `<CODEX_HOME>/archived_sessions`。從它分叉出來的任務，記錄開頭仍然指向它的某一段歷史（`history_base`）。使用者 2026-09-25 實測：原任務歸檔後，分叉出來的任務打開面板報“rollout segment not found”（v0.1-12）。
- **壓縮的舊記錄**：新版 Codex 會把一週沒動過的任務記錄壓縮成 `.jsonl.zst`。要往裡追加時，先解壓回 `.jsonl`、再刪掉壓縮檔案。以前的程式碼只認 `.jsonl`，面板開啟這種舊任務時是空的。

### 設計

- **標題**：顯示 `session_index.jsonl` 裡的名稱；沒有名稱時，顯示第一條使用者訊息的開頭；任務還沒開始時，顯示“新任務”。改名後，面板下次重新整理時跟著變。
- **新任務自動繫結**：
  - 面板頁面記下自己哪些時間段顯示在螢幕上（頁面可見、寬高不為 0），每次讀資料時帶給外掛服務：
    - 第一段從頁面開啟前 10 秒算起，因為發第一條訊息時 Codex 可能重新載入面板頁面；
    - 頁面被擋住或切走後再顯示，就開始新的一段；最多保留 20 段。
  - 面板所在的任務還沒有記錄時，外掛服務列出符合條件的任務：
    - 開始的時間落在某一段裡，或者在這一段結束後 5 秒內（使用者發完訊息馬上切走，頁面還沒來得及記下）；
    - 來源不是子代理、內部任務、`exec` 或 `mcp`，不是分叉，`thread_source` 為空或者是 `user`。
  - 正好一個就自動切過去；兩個以上就列出名稱，讓使用者選。v0.1-16 起只提供最新的一個，以及和它相差 20 秒以內開始的（見下一條）。
  - 為什麼按時間段，不按“最近 30 秒”：第一版按 30 秒算。可是使用者發完第一條訊息就切到別的視窗、過一會兒才回來，任務就超過 30 秒了，面板會一直等下去。按時間段算，回來多晚都能切過去；在別的頁面開始的任務，因為當時這個面板不在螢幕上，照樣不會被認走。
  - 已知的例外：兩個視窗並排、兩個面板都開在新任務頁上，在一個窗口裡發訊息，兩個面板都會切過去。
  - v0.1-16：使用者 2026-09-25 的機器上看到，面板所在的新任務頁大約每 5 分鐘換一個預備任務，面板收到的編號跟著變，於是每隔幾分鐘都要重新切一次，留下一條切換記錄。如果面板顯示期間先後開始過兩個任務，每次都會讓使用者選。現在只提供最新開始的任務，以及和它相差 20 秒以內開始的；寫切換記錄時刪掉一週前的舊記錄。
  - 繫結記在資料目錄的 `bindings/<面板的任務編號>.json`。之後這個標籤頁的所有呼叫都按新任務處理，面板重新載入後也一樣。
  - 只接受面板的繫結呼叫，模型呼叫會被拒絕。
- **卡頓**：
  - 實測（合成數據：12 張 1920×1080 截圖共 10.6 MB，另有 400 個其他任務）：
    - 新程序第一次讀面板資料要 1.2 秒，其中 0.9 秒花在逐張解碼 PNG、計算畫素指紋；
    - 每張縮圖要 0.14 秒；
    - 之後每次讀面板資料要 30–60 毫秒，主要花在遍歷所有任務記錄的目錄上。任務越多越慢。
  - 改法：
    - 畫素指紋存進資料目錄的 `cache/pixels/`，引擎和各個外掛服務共用。只存指紋，不存圖片內容。
    - 任務記錄的目錄只完整遍歷一次，之後每次只重新列出今天和昨天的目錄；每分鐘再完整遍歷一次，作為兜底。
  - 縮圖不寫到磁碟，免得在資料目錄裡留下圖片內容；仍然在記憶體裡快取。
  - 改後實測（同樣的資料）：
    - 分叉的任務在新程序裡第一次讀面板資料：0.07 秒（指紋已由引擎或原任務的面板存好）；
    - 之後每次讀：2–6 毫秒；
    - 每張縮圖 0.08 秒，一張張補上，不擋列表。
- **壓縮的舊記錄**：`.jsonl.zst` 用 Node 自帶的 zstd 解壓後整份讀入；同時存在 `.jsonl` 時以它為準。
- **歸檔的任務**：完整查詢時把 `archived_sessions` 也算上，同一段記錄兩邊都有時以 `sessions` 裡的為準。讀的時候找不到某一段（例如上次查詢之後才歸檔），立刻重新查詢一遍，最多每 5 秒一次。
- **找不到的歷史**（v0.1-13，使用者 2026-09-25 要求）：重新查詢之後，前面某一段歷史還是找不到（例如原任務的記錄被刪掉了，不是歸檔），就跳過這一段，照常讀剩下的：
  - 面板列出剩下的圖，並提示“前面有一段歷史找不到了，那一段裡的圖片沒法列出”；
  - 編號和輪次從剩下的部分重新算；
  - 引擎也按剩下的部分改寫。取消過的圖照樣換成佔位符，認不出的圖原樣傳送。
  - 任務自己的最後一段找不到時，仍然當作沒有記錄。

### 已查證的事實

### 設計

- **判斷語言**（`language.ts`）：以 `zh` 開頭的都算簡體中文，其他都算英文。
  - 面板：先看 host context 的 `locale`，沒有就看瀏覽器語言。
  - 面板每次呼叫都帶上語言；讀面板資料時還帶上“來自 Codex 還是系統”。外掛記在資料目錄的 `language.json` 裡，同時記下當時 Codex 的語言設定，變了才寫。
  - 引擎（發給模型的文字）和工具列表（標籤頁標題）按這個順序決定語言（v0.1-20）：
    1. 面板報告的語言，只要 Codex 的語言設定還是面板報告時那個。面板看到的是介面實際顯示的語言，可能和應用自己的語言不同。
    2. Codex 的語言設定：還沒有面板報告過，或者使用者之後改了設定。
    3. 面板最後一次報告的語言；
    4. 系統語言。
  - 結果：裝好就對，不用先打開面板；切換語言後，發給模型的說明從下一條訊息起換，標籤頁標題重啟 Codex 後換。
  - 命令列一律按系統語言：POSIX 的 `LC_ALL`、`LC_MESSAGES`、`LANG`，都沒有就看執行時報告的語言。`cam status` 顯示最終用的語言、Codex 的設定和麵板的報告。
- **文字表**：
  - 外掛服務和命令列的文字在 `messages.ts`；
  - 面板的文字在 `panel.html` 裡一段 JSON，英文可以多一條 `key_one`（數量為 1 時用）；
  - 發給模型的文字在 `rewrite.ts`，中文原樣保留，改動前後逐位元組比對過。
  - 單元測試檢查兩種語言的條目一一對應、佔位的 `{名字}` 也一致。
- **外掛服務返回的文字**：報錯和結果按面板帶來的語言給出；改寫失敗的原因改成程式碼，由面板翻譯；和使用者設定衝突的報錯帶一個文字鍵，面板和命令列各按自己的語言顯示。
- **面板認模型索要**：英文說明讓模型回覆“need IMG-004”，面板也認帶引號的寫法。
  - v0.1-24（2026-09-28）：使用者錄演示時用 GPT-6 Luna（推理強度 Light），模型回覆“Please reattach IMG-002 (v1 desktop) or IMG-003 (v1 mobile)”，提示條沒出來。
  - 說明裡改為寫清楚：這幾個字是給工具認的，要原樣寫；幾張就寫“需要 IMG-002、IMG-003”；不要讓使用者重新上傳或附上（勾選後原圖回到哪裡，v0.1-25 改了說法，見下）。
  - 面板也認 reattach、attach、send、share、upload、provide、include（中文“重新附上”“重新發送”等），編號之間認 or（“或”），編號後面可以帶括號說明。
  - 自測可以用環境變數 `CAM_TEST_MODEL`、`CAM_TEST_EFFORT` 換模型；三個 GPT-6 模型的結果見 tasks.md v0.1-24。
  - v0.1-25（2026-09-28）：使用者勾回模型要的 IMG-002 後，Luna（Light）仍然連說五次“看不到”。
    - 引擎沒錯：那幾次請求都只發了 IMG-002 的原圖，內容雜湊和原圖一致。token 用量也證明模型收到了：勾回那一輪的輸入多了約 2,900，正好是一張圖。
    - 模型的回覆都在“這條訊息裡”找圖，還複述了說明裡“下一條訊息就會帶上原圖”那句。實際上原圖回到的是它原來的位置（第 1 輪），夾在佔位符中間；Codex 自己的“[Image #2]”在每條訊息裡都從 1 開始，模型對不上編號。使用者把同一張圖重新貼進新訊息時，模型立刻能看到。
    - 在測試任務裡原樣重放使用者的分叉：問“Checked it. What color was it?”，改前改後都答對。問“what about now? Could you see IMG-002”，改前 5 次裡 4 次說看不到，其中 3 次同時說出了顏色。
    - 改法：仍傳送的圖前面加“已提供”標籤；說明裡寫清楚原圖回到原來的位置、不在新訊息裡，“被問到能不能看到就說看不到”只適用於被省略的圖，標著“已提供”的圖被問到時直接看圖回答。只加標籤、改措辭時，8 次裡還有 2 次說看不到；補上最後這條後，8 次全對。
    - 使用者分叉裡的原話，測試環境復現不出來。桌面版每輪多帶約 1 萬 token 的工具說明（電腦操作、瀏覽器等外掛）；測試裡沒開這些外掛，免得測試模型去操作使用者的電腦。
- **測試**：環境變數 `CAM_LANG=zh|en` 可以固定語言（測試、開發用）。斷言中文措辭的測試都固定成中文：第一次推到 CI 時，這些測試在英文系統上全部失敗，而且在本機也會隨記下的語言變化。
- **已知代價**：同一個任務中途切換 Codex 的語言，說明文字會變，模型那邊快取的上下文要重算一次。
- **驗證**：`v01-placeholder-selftest.ts --lang en` 用同樣的五輪對話檢查英文說明：模型不收回之前的回答，被問到沒說過的細節時回覆“need IMG-xxx”。

## 17. Windows 的資料目錄（v0.1-15）

### 已查證的事實

- Codex 桌面版和 Claude 桌面版都是微軟商店的 MSIX 應用。按 Windows 的規則，這類應用啟動的程式在 AppData 下新建的檔案，會被轉存到該應用的私有目錄 `%LOCALAPPDATA%\Packages\<應用>\LocalCache\Local\…`，只有這個應用裡的程式能在原路徑看到它們；修改 AppData 裡已有的檔案則不受影響。
- 使用者 2026-09-25 的機器上實測：外掛服務和它啟動的引擎寫的勾選記錄、請求統計、語言記錄都在 Codex 的私有目錄裡，有 6 份勾選記錄只在那裡；在 Claude 裡跑的自測寫的日誌在 Claude 的私有目錄裡。在 Codex 外面執行的 `cam status` 看不到這些檔案。
- 後果：一行命令安裝時在 Codex 外面啟動的引擎，如果在使用者重啟 Codex 後繼續被使用（重啟得快時會這樣），它看不到面板新寫的勾選，取消的圖會照樣發出去，而且沒有提示。
- 使用者目錄本身不會被轉存；Codex 自己的 `~\.codex` 就放在那裡。

### 設計

- Windows 的資料目錄改為 `%USERPROFILE%\.codex-attachment-manager`。macOS、Linux 不變。
- 遷移（`migrate-data.ts`）：外掛服務、引擎和命令列在碰資料目錄之前，先檢查一次；沒遷移過，就從舊目錄和每個應用私有目錄裡的副本，把勾選記錄、面板切換記錄、請求統計、語言記錄和 config 備份複製過來，同名檔案取最新的一份，並保留原來的修改時間。日誌和快取不搬，舊目錄原樣保留。
  - Codex 會同時啟動好幾個外掛服務：用一個鎖檔案保證只有一個在複製，其他的等它完成；鎖檔案超過一分鐘沒動，就當作複製的程序已經中斷，接手重做。
  - 設了 `CAM_DATA_DIR`（測試、開發）時不遷移。
- `uninstall.ps1` 的配置備份也改放到新目錄。

## 18. 對話裡的圖片引用（2026-09-26 調研，不做）

使用者想讓對話裡模型要的圖（“需要 IMG-017”）變成可點的引用，點了打開面板定位到那張圖，或者直接看原圖。調研後用戶決定不做，改為 v0.1-17 的“模型需要”提示條（見 spec.md 介面一節）。

### 已查證的事實

依據桌面版 26.917 的前端程式碼：

- 助手回覆裡的 Markdown 連結，目標是本機絕對路徑或 `file://` 地址時，顯示成可點的檔案連結，連結文字照常顯示；左鍵點選在右側側邊面板開啟。帶行號的連結交給 Codex 的文字編輯器；檔案不存在時改用系統的檔案管理器開啟。
- 外掛可以在工具的 `_meta["openai/ui"].entrypoints` 裡宣告 `{ type: "file", extensions: [...] }`（副檔名不分大小寫，帶不帶點都行）。開啟這類檔案時，Codex 在側邊面板裡用這個工具的頁面顯示；工具呼叫的 `_meta["openai/resource"].path` 是檔案路徑，同時帶著當前任務的編號。
- 標籤頁按檔案路徑區分。從回覆裡開啟的檔案是“預覽標籤頁”，再開啟另一個檔案會替換它。外掛沒有辦法切到某個已有的標籤頁，所以點連結進不了使用者手動開啟的面板。
- 面板頁面可以發 `openai/files/open`（引數 `path`，絕對路徑），請 Codex 在側邊面板開啟一個檔案。
- 回覆裡的 Markdown 圖片 `![說明](本機路徑)` 由 Codex 讀出檔案，顯示成縮圖（最大約 200 畫素見方），點選在原地放大；對話記錄裡的圖不能這樣引用，只能引用本機檔案。

### 為什麼不做

- 兩條路都要讓模型在回覆裡寫出連結，要改發給模型的說明並重新自測。
- 點文字連結只能在右側另開一個預覽標籤頁，和手動開啟的面板是兩個標籤頁；原地看大圖則要把被取消的圖另存成檔案，並把路徑告訴模型，模型可能自己去開啟它。
- 使用者認為收益不值得這些代價（2026-09-26）。

## 19. 面板只剩一條：整頁被滾走（v0.1-21、v0.1-23）

使用者 2026-09-27、28 報告：桌面版 26.924 裡，面板只剩一條，看得見列表最後一截和底欄，頁頭不見了，下面一片空白。兩次都是在點了整輪勾選框之後。

### 查證經過

- **第一次判斷錯了（v0.1-21）**：以為 26.924 不再給面板固定高度、框被壓成最低的 200 畫素，於是讓頁面按 Codex 給的最大高度報告自己的高度。在使用者的 Codex 裡沒有用。
- **臨時診斷版量到的（2026-09-28）**：面板讀資料時把尺寸記進資料目錄，使用者照常操作一遍。
  - Codex 給的框一直是完整的 451×727，頁面一開始也完全正常：頁頭 194、列表 490、底欄 43，正好 727。
  - 點 Turn 4、Turn 5 的勾選框之後，整個頁面被往上滾了 415、625 畫素：頁頭滾出頂部，底欄跟著上移，下面空了。
- **原因**：勾選框真正的 `<input>` 是隱藏的絕對定位元素。每一行圖片（`.row`）是定位容器，input 留在行裡；每輪標題那一行（`.turn`）不是，input 就掛在整個頁面上，位置在列表內容裡很靠下的地方（列表按未滾動時算）。頁面因此能滾動（可滾動高度 4047，視口 727），而焦點落到這個 input 時，瀏覽器把它滾進視野，滾的是整個頁面。
- **復現和修復**：開發頁裡讓 Turn 4 的勾選框獲得焦點，整頁滾走 1052 畫素，和使用者看到的一樣。給 `.turn` 加上 `position: relative` 後，頁面的可滾動高度等於視口，獲得焦點、真實點選都不再滾動。

### 保留的部分

- 26.924 的 host context 裡 `containerDimensions` 確實只有 `maxHeight`、`maxWidth`（使用者的 Codex 裡是 727）。按 MCP 應用規範，這時頁面應當用 `ui/notifications/size-changed` 報告自己的高度，所以 v0.1-21 的報告保留：頁面高度設成 `maxHeight`，發 `size-changed`；得到的框更矮時，穩定 1.5 秒後改成框的高度；沒有這個值時照舊撐滿。
- 開發頁的 `?host=924` 模擬這種宿主（報告之前只給 200 畫素，`&cap=N` 模擬截短），用來檢查頁面在這種宿主裡的表現。
