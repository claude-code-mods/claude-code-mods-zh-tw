# 代理驗證 P2 報告：按勾選改寫

> 2026-09-24，由 Claude 執行。本報告只寫統計和測試任務裡的簡短問答，不含真實對話、圖片和本機路徑。設計見 [plan.md](plan.md) 第 10 節，任務見 [tasks.md](tasks.md)。

## 1. 結論

自測（P2-5）和桌面版驗證（P2-6，第 5 節）都透過：在同一個任務裡取消圖片、重新勾選，都從下一次請求起生效，對話不中斷。桌面版的生圖和改圖也經過了代理。

自測用我們自己啟動的 app-server。它和桌面版用的是同一個 `codex.exe`，環境也一樣：去掉 `NO_PROXY`，開啟 `respect_system_proxy`，地址用 `localhost`，不改 `config.toml`。測試圖片都是合成的：

- `a.png`：白底紅方塊，右下角有一個黑色小方塊；
- `b.png`：黃底藍圓，左上角有一個綠色小方塊；
- `b-copy.png`：`b.png` 改名後的副本，位元組完全相同；
- `noise.png`：約 3 MB 的噪點圖，用來看能省下多少位元組。

| spec 第 4 節 P2 驗收項 | 結果 |
|---|---|
| 1. 取消的圖不再發送，請求變小 | 透過：a.png、b-copy.png、noise.png 的內容都沒有出現在請求裡（按內容雜湊核對）。請求從 3,205,210 位元組降到 37,382 位元組（壓縮後），解壓後是 4,312,287 → 105,242 位元組 |
| 2. 佔位符種類正確 | 透過：a.png、noise.png 是普通佔位符；b-copy.png 是指向 b.png（IMG-002）的重複佔位符 |
| 3. 模型不編造，並按約定索要 | 透過（調整措辭之後，見第 4 節）：模型回答“需要 IMG-001，才能回答。”；對 b-copy.png 則按 IMG-002 正確說出“黃色背景……藍色圓形，左上角有一個綠色小方塊” |
| 4. 重新勾選後能正確使用 | 透過：模型回答“白色背景，主要形狀是紅色正方形，右下角有一個黑色小方塊標記。” |
| 5. 同一個任務，不報錯、不重連 | 透過：4 輪都在同一個任務裡，沒有報錯和重試 |

## 2. 過程中確認的事

- **切換到 HTTP 很順暢**：第一輪走 WebSocket。取消勾選後，代理在連線空閒時把它關掉；第二輪 Codex 重新握手，收到 426，改走 HTTP，之後一直走 HTTP，沒有任何報錯或重試。
- **本地記錄和請求能按條目對上**：請求裡的每條訊息和工具輸出，都帶著和本地記錄相同的 `id`，所以代理能準確認出每張圖是哪一次出現的，改名的副本也能按內容認出來。
- **重新序列化沒有副作用**：真實請求體經 `JSON.parse` 再 `JSON.stringify` 能逐位元組還原，改寫只改變被替換的部分。
- **小圖不一定省位元組**：只取消幾 KB 的小圖時，佔位符文字可能比圖還大，壓縮後的請求甚至略大一點（第一次自測：37,037 → 37,140 位元組）。省位元組主要靠大圖，這符合預期。

## 3. 耗時（真實樣本實測）

用階段 0 的真實樣本測（只讀）。原任務一共 14 次圖片出現，其中 10 張內容不同，完整請求解壓後 43.9 MB、壓縮後 32.7 MB。

| 步驟 | 耗時 |
|---|---|
| 位元組指紋（SHA-256），每張大圖 | 1–5 毫秒；14 張合計 48 毫秒 |
| 畫素指紋（解碼 PNG），每張大圖 | 40–110 毫秒 |
| 第一次建立任務索引（含全部指紋） | 約 1.2 秒；每個任務只算一次 |
| 之後再讀索引（記錄沒變） | 約 8 毫秒 |
| 代理改寫一次完整請求（43.9 MB） | 約 0.6 秒；其中解壓 0.09、解析 0.09、找圖 0.05、替換不到 0.001、序列化 0.21、壓縮 0.12 秒 |

- 對照：Codex 自己壓縮同一個請求約 0.18 秒。
- 沒有取消項的任務，代理原樣轉發，不做這些處理。
- 這兩個樣本里，位元組指紋已經找出全部重複，畫素指紋沒有找出新的。
- 測量中發現並修好了一個問題：分叉任務的前半段歷史在父任務的記錄檔案裡，原來讀不到；現在沿 `history_base` 跨任務讀取，並加了單元測試。

## 4. 佔位符措辭的調整

- **第一次自測**：原措辭是“需要檢視時，請在回覆裡寫‘需要 IMG-001’”。問題裡帶著“看不到的就直說”這句話時，模型只回答“看不到，無法判斷”，沒有索要。
- **調整**：措辭改成“如果回答需要看這張圖，請在回覆裡寫出‘需要 IMG-001’，使用者可以在下一輪重新勾選提供”，問題裡也去掉了那句引導。
- **第二次自測**：模型按約定索要了。使用者 2026-09-24 認可現在的措辭。

## 5. 桌面版驗證（P2-6）

使用者在 Windows 桌面版（自帶 `0.155.0-alpha.16.4`）裡新建一個測試任務，上傳了 `b-copy.png`、`a.png`、`b.png`（依次編號 IMG-001、IMG-002、IMG-003），勾選由 Claude 用命令列操作。工具這次寫入了 `config.toml` 的兩段設定和 `.env` 裡的 `NO_PROXY`。

| 步驟 | 結果 |
|---|---|
| 第 1 輪：上傳三張圖 | 經過代理，走的是 WebSocket |
| 取消 IMG-001（副本）和 IMG-002 | 代理關掉了這個任務空閒的 WebSocket 連線 |
| 第 2 輪：問 a.png 和 b-copy.png | 握手收到 426，改走 HTTP；請求被改寫：IMG-001 換成指向 IMG-003 的重複佔位符（這次是靠前的副本指向後面的原圖），IMG-002 換成普通佔位符，只發出 1 張圖。模型回答：“需要 IMG-002。IMG-001 與 b.png（IMG-003）內容相同；我能看到的 b.png 是黃色背景、中央藍色圓形，左上角有綠色小方塊。” |
| 重新勾選 IMG-002，第 3 輪再問 | 模型回答：“白色背景，中央是紅色方塊；右下角有一個黑色小方塊。” |
| 第 4 輪生圖、第 5 輪改圖 | `images/generations` 和 `images/edits` 都經過代理，都返回 200。不用等上游 #47742，P1-4 剩下的問題也一併解決 |
| 全程 | 同一個任務，沒有報錯和重試 |
| 恢復配置 | 兩處標記段落都已刪除，`.env` 只剩我們那一段，所以整個檔案刪除。`config.toml` 和開啟之前相比，只多了桌面版自己寫的兩處：新的管道名、新任務資料夾的信任設定 |

兩個新發現：

- **桌面版會在使用者訊息裡附一段 “Files mentioned by the user”**，寫著上傳檔案的完整路徑。代理沒有改這一段。這次模型遵守了佔位符，沒有自己去讀檔案。
- **生成的圖沒有進入對話歷史，結果改錯了圖，介面上還多了空的圖片框**：
  - 第 4 輪，模型在程式碼模式裡按 `r.content` 讀取生圖結果，但這個結果的結構是 `{image_url, output_hint}`，本該用 `generatedImage(r)`。結果生成的圖沒有放進對話歷史，工具附帶的提示（“圖片已經顯示給使用者，回覆裡不用再貼”）模型也沒看到。
  - 於是模型在最後的回覆裡寫了一個數據為空的 Markdown 圖片 `![…](data:image/png;base64,)`，桌面版把它顯示成一個灰色的空圖片框，第 5 輪也一樣。使用者看到的真圖，是生圖工具自己顯示的。
  - 第 5 輪，改圖工具取“對話歷史裡最近的一張圖”，取到的是第 1 輪上傳的 `b.png`，把它左上角的綠色小方塊改成了紫色，而沒有去改生成的那張圖。
  - **與代理無關**：同樣錯誤的寫法，在沒經過代理的直連請求裡也出現過 4 次，都用 gpt-6-luna，這次測試用的也是它。gpt-6-sol 和 gpt-5.6-luna 大多用 `generatedImage(r)`。使用者當天直連的生圖測試裡，gpt-6-luna 第一次同樣拿回了空結果，檢查結果結構後，第三次才用對寫法，前兩次生成的圖都白白浪費了。這是 Codex 程式碼模式和模型之間的問題，屬於上游。

## 6. 待辦和限制

- **生圖和改圖**：桌面版目前帶的是 `0.155.0-alpha.16.4`，要靠 `.env` 裡的 `NO_PROXY` 才能經過代理。上游從 `0.158.0-alpha.8` 起已修復，桌面版跟進後，就不再需要寫 `.env`。
- **一輪中途取消**：如果這個任務還在用 WebSocket，這一輪剩下的請求可能仍帶著原圖，從下一輪起一定生效。
- **託管生圖的結果**（`image_generation_call`）暫時不能取消。桌面版目前生圖走 `exec` 工具，不受影響。
