# v0.11 方案：拆成接入層、核心層、面板層，接入其他 Agent 平臺

> 狀態：使用者 2026-11-02 確認方案（第 7 節）。第 1–9 步已做完：Codex 自測和 Claude 桌面版實測透過（壓縮自測裡兩張圖沒認出名字，0.10.0 一樣），2026-11-02 釋出 0.11.0。接下來改 README、定倉庫名字、簡介、標籤，做影片和圖片（第 7 節）。規格以 [spec.md](../spec.md) 為準，實現見 [design.md](../design.md)，對外的接入說明是 [ADAPTERS.md](../../ADAPTERS.md)。本機的摸底記錄和參考專案的筆記只在 `local/`，不進倉庫。

## 1. 背景與目標

2026-10-31 使用者定了新方向：從解決一個具體問題的工具，擴充套件成所有 Agent 平臺都能輕鬆接進來的多模態上下文管理工具。別人讓自己的 AI 寫一層接入，就能提 PR 接自己的平臺。

現在的程式碼做不到這一點：Codex 和 Claude 的邏輯纏在一起。

- `proxy.ts`（約 1100 行）裡，通用的轉發、Codex 的改寫、Claude 的改寫、給 Claude 面板供資料的介面混在一起，靠 `platform === "codex"` / `"claude"` 分支。
- `panel-state.ts`、`selection.ts`、`plugin-server.ts` 直接引用兩個平臺的會話索引。
- `routes.ts` 裡平臺型別寫死成兩種。
- 接一個平臺大約要寫一千多行：Claude 的會話索引、改寫、思考記錄、快取加起來約 1200 行。

目標：

1. **三層**：接入層（一個平臺一份，儘量薄）、核心層（不認識任何平臺）、面板層（只經核心介面拿資料）。以後調演算法只改核心層；維護某個平臺只看它的那一份。
2. **Codex 和 Claude 的行為不變**：這次是重組，不改使用者看得到的任何行為。
3. **對外介面文件和契約測試**：第三方照文件寫接入，跑契約測試證明能用。
4. **用新結構接其他平臺**：WorkBuddy、OpenCode、Gemini CLI、pi、DeepSeek Harness，再加 Qwen Code、Cline、Kilo Code、goose、Cherry Studio，只接核心，不帶面板，檢驗接入層是不是真的薄。

## 2. 已定的規則（使用者 2026-11-02 定）

1. 三層的分工如第 1 節。一個倉庫，不拆倉庫；拆成多個包以後看情況。
2. **面板只在 Codex 桌面版和 Claude 桌面版。** 以後接的平臺預設都不帶面板，除非使用者主動要求。面板在介面文件裡寫成可選的一節；第三方想要面板，自己看這一層接。
3. **翻譯器只抽象操作，不抽象整份請求**（第 3.4 節）：不把各家格式整個翻譯成我們自己的格式再翻回去。
4. **不受現有設計約束**：內部結構和機制可以重新設計；拆的過程中發現沒用的、冗餘的東西，直接清理。
5. **順序**：先拆和整理，抽象層在拆的過程中成形，每一步都測；再寫介面文件和契約測試；最後接新平臺來檢驗。

## 3. 設計

### 3.1 目錄

做完後的結構（檔案清單見 design.md）：

```
plugin/src/
  proxy.ts、plugin-server.ts、cam.ts、engine.ts、platforms.ts   入口、引擎生命週期、平臺登記表
  core/                     核心層：不認識任何平臺、任何請求格式（engine/transport.ts 是通往服務的路）
  panel/                    面板層：只用核心
  adapters/                 接入層
    protocols/              請求格式的翻譯器：openai-responses、anthropic-messages、openai-chat、gemini；any.ts 給只接核心的平臺用
    codex/、claude/         帶面板的兩個平臺，各自讀本地記錄、改配置、開面板
    workbuddy/、opencode/、gemini-cli/、pi/、qwen-code/、cline/、kilo-code/、goose/、cherry-studio/   只接核心的平臺，每個一個 platform.ts（pi 另有擴充套件）
    dsh/                    DeepSeek Harness 的 dsh 外掛包（index.js、offload.js、package.json、cordis.patch.yml）
```

- 宿主規定位置的檔案（`.codex-plugin/`、`.claude-plugin/`、`hooks/`、`.mcp.json`、啟動指令碼）留在原處，只改它們指向的入口。
- 原先畫的目標結構（core 下再分 session/、text/、tools/，加一個 api.ts）沒有照搬：拆到那一步時按程式碼的實際情況定，核心是平鋪的小檔案。

### 3.2 三層各管什麼

- **核心層**：轉發請求；決定每張圖發不發、換成什麼字；編號；勾選和自動選圖；特徵行；壓縮後放回哪些圖；取圖工具按編號取圖；統計和日誌。核心只認會話、輪次、圖片。
- **面板層**：頁面和麵板工具，只通過核心的公開介面拿資料、改勾選。現在有兩種宿主：MCP 應用（Codex 桌面版）和引擎提供的網頁（Claude 桌面版）。
- **接入層**：一個平臺怎麼接進來，見下面的契約。

### 3.3 接入契約

平臺分兩種：

- **帶面板的平臺**（Codex、Claude Code）：接入層讀平臺自己的本地記錄（任務記錄、會話記錄），認會話、輪次、子代理和旁聊、壓縮，改平臺的配置，打開面板，還有平臺特有的處理（Codex 的 WebSocket 降級、API key 線路；Claude 的思考簽名重試、提示快取）。這兩份接入是厚的，因為面板要用這些資訊。
- **只接核心的平臺**（其餘所有平臺）：接入層只填一個條目（`core/platform.ts` 的 `CorePlatform`）：
  1. **名字**；
  2. **原地址**：它的模型請求本來發去哪（按服務商填地址的平臺，從它的設定裡讀，或使用者在 `cam connect` 時給出）；
  3. **認會話**（可選）：哪個請求頭是會話編號；
  4. **旁路請求**（可選）：哪些請求不改（起標題、潤色提示之類）；
  5. **認平臺**：平臺給它跑的命令設的環境變數（`cam detect` 用）；
  6. **裝法**：要改哪些設定檔案、改成什麼（`cam connect --apply` 照著寫），以及給人看的步驟。

  平臺加一行進 `platforms.ts` 就接上了。請求格式、哪幾張圖、省略哪些，都由核心和翻譯器從請求本身算出來（第 3.8 節）。

### 3.4 翻譯器

每種請求格式一個翻譯器，提供三樣：

- **認路徑**：哪些請求路徑歸它管。
- **讀**：把請求讀成一份檢視，內容是有哪些輪、每張圖在哪一輪、是使用者貼的還是工具返回的、內容雜湊、能和本地記錄對上的穩定標識、哪裡能插說明、壓縮項在哪。
- **寫**：把核心的決定落回原始請求。決定只有幾種：把這張圖換成這段字、在圖前加標籤、在某一輪前插一條說明、在壓縮項後放回一些圖。沒動的部分原樣保留；一張圖都不換時原樣轉發原始位元組。

格式特有的麻煩歸翻譯器自己管，例如 Anthropic 的思考簽名和提示快取。參考專案印證了這個選擇：new-api 把整份請求互相翻譯，每多一種輸入格式，每個渠道都要多實現一個轉換方法。

### 3.5 圖片清單從哪來

- 平臺提供了會話歷史（Codex、Claude），就用它，和現在一樣。
- 只接核心的平臺：核心從經過引擎的請求裡建清單（`core/request-index.ts`，第 3.8 節）。

### 3.6 分層檢查和契約測試

- **分層檢查**（單元測試）：核心不引用 `adapters/` 和 `panel/`；面板只引用核心；平臺資料夾之間不互相引用，翻譯器只引用核心和別的翻譯器。參考專案 claude-code-router 的請求流水線直接引用了各智慧體的特殊功能，平臺的特殊處理漏進了核心；這條檢查就是防這個。
- **契約測試**：每個翻譯器、每個平臺帶一組樣例請求，跑同一套測試：不改時原樣輸出；換圖後圖不在了、字在對的位置；插說明的位置對；不認識的欄位原樣保留。

### 3.7 釋出

- 仍是一個版本、一份內容。全機只有一個引擎，所有平臺共用；各平臺裝不同版本時，引擎會互相請對方退役，Codex 和 Claude 兩份副本之間已經出現過（design 第 5 節）。所以不按平臺拆成不同的包。
- 每個平臺按它自己的方式裝：Codex、Claude 照舊走各自的外掛市場和安裝命令；只接核心的平臺把倉庫克隆到一個固定的資料夾，`cam detect` 認出平臺，`cam connect <平臺> --apply` 登記線路並改好平臺的設定，`cam disconnect` 撤回；DeepSeek Harness 用 `dsh plugin add` 裝 dsh 包。
- 使用者 2026-11-02 定：使用者把一句話發給自己的 Agent，Agent 看倉庫就能在對應的平臺上裝好，而且不會裝錯（例如 WorkBuddy 裡的 DeepSeek 模型要裝 WorkBuddy 的那一份）。所以平臺由各平臺給命令設的環境變數來認，不靠模型自己猜；改設定由命令來做，不讓模型手改：記下改了哪幾項、原來是什麼（不復制整個檔案：設定檔案和 .env 裡常有 API key），`cam disconnect` 只撤回還保持原樣的設定。帶註釋的 JSON 不改，只打出步驟。
- 面板檔案隨包一起發，只有 Codex 桌面版和 Claude 桌面版的接入開啟它。
- 拆的過程中外掛版本號不動，免得 Codex 中途從工作區自動重灌；全部做完再升到 0.11.0 釋出。

### 3.8 只接核心的平臺（使用者 2026-11-02 定：除 Codex 和 Claude 桌面版外，都不接面板）

- **導流**：平臺的服務地址改成引擎的一條線路（`/__cam/routes/<編號>`），線路記著原地址。請求原樣轉去原地址，只有圖片相關的幾處被改；引擎自己的請求頭（`x-cam-*`）不往外發，其餘請求頭照轉。
- **格式**：按路徑認：`/chat/completions`、`/responses`、`/messages`、`:generateContent` / `:streamGenerateContent`（Gemini CLI 用 Google 賬號登入時，內容包在 `request` 裡）。四種格式各有翻譯器，`adapters/protocols/any.ts` 把它們串起來。
- **輪次**：每條使用者自己寫了字的訊息開始新的一輪；工具結果、只有圖的訊息算在當前輪。
- **自動選圖一直開著**：之前各輪的圖換成佔位文字，本輪的圖照發；模型用 `cam_view_image` 取回的圖只在那一輪發，下一輪換成一句短說明。特徵行不開：模型寫的記錄行在終端裡會原樣顯示出來。
- **編號**：按內容編號，同一張圖在哪都是同一個編號；第一次見到時編號，原圖存進資料目錄（`platforms/<平臺>/`）。不讀平臺自己的記錄。
- **認會話**：平臺請求頭裡的會話編號；沒有就用我們的擴充套件加的 `x-cam-session`（pi）；再沒有就按第一條提問區分（同一平臺、同樣開頭的兩個會話會合成一個，編號仍按內容，不會拿錯圖）。
- **取圖**：平臺的 MCP 服務（`plugin-server.ts`，`CAM_HOST=<平臺>`）只有 `cam_view_image`，從最近一次發出帶工具的請求的那個會話裡取。
- **引擎保活**：MCP 服務每幾秒探一次引擎，引擎看到有平臺在探就不退出（不再只認 Codex 和 Claude 的程序）。
- **不做**：壓縮後放回、面板、手動勾選、固定傳送。

### 3.9 DeepSeek Harness（使用者 2026-11-02 定：在接入層裡頂替它官方的外掛）

DSH 的請求可能用 DeepSeek 的檔案模式發圖（請求裡是檔案引用，不是圖片資料），走引擎改不了，所以做成 dsh 外掛包（`adapters/dsh/`），用 `dsh plugin --profile <配置檔> add` 裝。包裡的補丁按 `id` 把官方底包的 `image-offload` 行停掉（兩者註冊同一個訊息投影，只能留一個），再插上我們的（使用者 2026-11-02 問能不能直接停掉官方的：能，裝包時自動停）：

- 保留官方外掛做的事：服務因圖片超預算拒絕請求時，標記最舊的幾張解除安裝，然後重試。
- 加上自動選圖：新一輪開始時（`agent/pre-step` 裡輪次變了），把之前各輪還留著的圖全部標記解除安裝。
- 官方的超預算解除安裝留在我們的外掛裡當兜底：一輪裡就可能超預算（一步一張截圖地控制瀏覽器），沒有它請求會報錯、這一輪結束。
- 解除安裝是 DSH 自己的機制：寫進會話日誌、永不撤回，模型看到的是寫著附件名和只讀路徑的文字，需要時自己讀回原圖。所以不需要我們的取圖工具，提示快取的字首也只往前走。

## 4. WorkBuddy 摸底（2026-11-02，本機 5.9.3，只看程式碼，沒跑對話）

- Electron 桌面應用，裡面打包了騰訊的 CodeBuddy Code 智慧體（`@genie/agent-cli` 2.165.0）。
- 登入後的官方模型發到 `https://www.workbuddy.cn` 加 `/v2/chat/completions`，是 **OpenAI Chat Completions** 格式，帶 Bearer 令牌。自定義模型寫在 `~/.workbuddy/models.json`，每個模型自己填 `url`，個別可選 OpenAI Responses 格式。
- 導流：環境變數 `CODEBUDDY_BASE_URL` 改官方地址；`~/.workbuddy/settings.json` 的 `env` 會被寫進智慧體程序的環境變數。設了自定義地址後不再 gzip 壓縮請求。也認 `HTTPS_PROXY`。
- 外掛：和 Claude Code 幾乎一樣的外掛市場，外掛目錄裡是 `.codebuddy-plugin/plugin.json`、`.mcp.json`，有 hooks。內建外掛裡有 `mcp-app` 類別（帶 HTML 頁面）。
- 會話：程式碼裡有 `X-Conversation-ID` 請求頭，對話記錄看起來是 jsonl。
- 11-02 抓包（只記請求的形狀，不記內容和令牌）：請求頭裡有 `x-conversation-id`（UUIDv7）和 `x-agent-type`（潤色提示這類旁路請求是 `auxiliary`）。`CODEBUDDY_BASE_URL` 要帶 `/v2`：那次沒帶，請求發到 `/chat/completions`，服務回 405，看起來像“連不上”。
- 使用者 11-02 定：不再實跑，按上面的結論寫接入，等使用者反饋。圖片是不是 `image_url` 的 data URL、登入令牌經過本機代理會不會被拒，沒有實測。

## 5. 步驟

每一步一個短分支：跑全部單元測試和冒煙測試，再合併。動到引擎啟動方式或安裝的步驟，合併後重新安裝，確認 Codex 和 Claude 都能連上（Codex 開著時不重灌，等它關了再裝）。

1. 搭目錄，加分層檢查；搬不分平臺的小檔案（路徑、語言、文字表、PNG、縮圖等），清理用不到的程式碼。行為不變。
2. 拆改寫：`rewrite.ts`、`claude-rewrite.ts` 裡決定換哪張、寫什麼字的部分進核心，在請求裡找圖、改 JSON 的部分進兩個翻譯器。驗收：各種勾選組合下改寫結果和拆之前逐位元組相同（對照測試）。
3. 拆引擎：`proxy.ts` 的通用部分進核心；Codex 的部分（任務請求頭、WebSocket 降級、API key 線路）和 Claude 的部分（會話請求頭、思考記錄重試、面板網頁）進各自的接入。
4. 拆找圖：`thread-index.ts`、`claude-index.ts` 進各自的接入，實現核心的會話歷史介面；`selection.ts` 裡認分叉和子代理的部分交給接入。
5. 拆面板：`panel-state.ts` 只讀核心介面；外掛服務裡的面板工具和取圖工具分開。
6. 拆安裝：Codex 的配置和命令列、Claude 的 Mod 進各自的接入。
7. 寫 `ADAPTERS.md`（英文，對外）和契約測試；在 Codex 和 Claude 裡跑一遍模型自測（gpt-6-sol，中英文）。
8. 接其他平臺：平臺登記表（自動選圖的規則收進核心、會話編號不限 UUID、引擎認所有平臺的探活）；openai-chat、gemini 兩個翻譯器；核心從請求建清單；WorkBuddy、OpenCode、Gemini CLI、pi 的條目，pi 的擴充套件，DSH 的外掛包；`cam detect`、`cam connect --apply`、`cam disconnect`；INSTALL.md 按平臺寫；Codex 在 cc-switch 切換後自動接回；README 底部的平臺表；再接 Qwen Code、Cline、Kilo Code、goose、Cherry Studio（goose 的設定是 YAML、Cherry Studio 的在應用裡，這兩個只打出步驟）。不帶面板，不實跑（第 7 節）。
9. Claude 桌面版實跑一輪，然後推送、發 0.11.0。

## 6. 風險

- 第 2、3 步動的是每個請求都經過的程式碼，最容易出迴歸。靠逐位元組對照測試兜底。
- 只接核心的五個平臺都沒實跑過，只有合成請求的測試。README 的平臺表寫明“新接入，歡迎反饋”，和實測過的 Codex、Claude 分開。
- cc-switch（切換 Claude Code、Codex 等的服務地址）每次切 Codex 的服務商，會刪掉頂層的 `openai_base_url`、重寫 `[model_providers.custom]`，把外掛對 Codex 的接管抹掉。使用者 2026-11-02 定：使用者要能隨便換模型，外掛也照樣起作用。所以引擎盯著 config.toml，一被改寫就重新接上，線路指向使用者剛選的服務商，切換照樣生效（`adapters/codex/setup.ts` 的 `keepRouted`）。只在使用者想用引擎（啟用過、沒停用，記在資料目錄，不看 config.toml）且外掛還在時做；十分鐘裡被改回三次就停手，免得和別的工具來回改。Codex 關著時切換的，下次啟動先直連一次，再下次才經過引擎。Claude Code 不受影響：外掛每個會話開始時重新讀地址。沒和真的 cc-switch 一起跑過。
